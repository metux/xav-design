# Compute Reference Flow

All request validation follows a deterministic stage order: framing before scalar syntax, scalar syntax before XID resolution, and XID/type/ownership checks before lifecycle status.

Target workload:

`C[i] = A[i] + B[i]`

Typical sequence:

1. Enumerate physical devices or create the default device.
2. Query memory properties and create a logical device with a compute queue.
3. Create buffers A, B, and C.
4. Query memory requirements, allocate memory, and bind the buffers.
5. Upload A and B using independent `WriteBuffer` requests.
6. Create the shader module.
7. Create the descriptor set layout, descriptor pool, and descriptor set.
8. Create the pipeline layout and compute pipeline.
9. Update the descriptor set with A, B, and C.
10. Create the command pool and command buffer.
11. Bind the pipeline.
12. Bind the descriptor sets.
13. Set push constants if needed.
14. Record `Dispatch` and finalize the command buffer.
15. Create fences/semaphores if required.
16. Execute `QueueSubmit`.
17. Wait for completion using a Fence or Semaphore.
18. Read C back using `ReadBuffer`.
19. Destroy resources according to the lifecycle rules.

The server MUST ensure that descriptors match the shader, statically used resources are present, and dispatch limits are respected.

# Conformance and tests

An implementation SHOULD test at least the following cases:

- Exact request lengths, counts, and padding
- `ReadBuffer` waits for earlier accepted writes to the requested range on the same logical Device, including writes on other queues. An earlier submission failure alone does not prevent the read, but data expected from the failed write is not guaranteed. On Device Loss, `ReadBuffer` MUST fail with `DEVICE_LOST` and MUST NOT send a successful data reply.
- `EnumeratePhysicalDevices` is an 8-byte reply request; `DestroyDevice` is a 12-byte void request.
- `EnumeratePhysicalDevices.reply.length` equals the sum of padded `PHYSICALDEVICEINFO` record lengths divided by four; it is zero when there are no records.
- `EnumeratePhysicalDevices` with a request length other than 8 bytes returns `BadLength`; an empty successful reply is permitted and MUST NOT contain incomplete records.
- `GetPhysicalDeviceQueueFamilyProperties.reply.length` equals `3 * queue_family_count`; the payload length MUST be divisible by 12.
- `GetPhysicalDeviceProperty` uses `SUCCESS = 0`, `NOT_SUPPORTED = 1`, and `NOT_AVAILABLE = 2`; on failure, `property_type`, `value_length`, and payload are zero and `reply.length = 0`.
- `GetPhysicalDeviceProperty` accepts the four canonical names from the property registry; Atom IDs are assigned by the server. Unknown Atom IDs return `BadAtom`, valid but unregistered Atom names return `NOT_SUPPORTED`, and registered but unavailable properties return `NOT_AVAILABLE`.
- `XAverius.deviceUUID` and `XAverius.driverUUID` return exactly 16 `BYTE_ARRAY` bytes on success; `XAverius.compute.maxWorkGroupInvocations` returns one `CARD32`; `XAverius.compute.maxWorkGroupSize` returns exactly three `CARD32` values in X/Y/Z order. The reply type and exact value length MUST match the registry.
- The v0.1 feature-ID and device-extension registries are empty: every feature ID returns `BadValue`; syntactically valid optional extension names return `BadMatch`; syntactically invalid extension names return `BadValue`; neither `CreateDevice` nor `CreateDefaultDevice` implicitly enables optional features or extensions.
- `CreateDevice` length must exactly match the three ordered variable record arrays; at least one queue-family request is required; queue priorities MUST be finite and within [0,1]; unknown feature IDs, `enabled != 1`, duplicate features/extensions, and syntactically invalid extension names return `BadValue`; registered but unsupported features, and unknown or unsupported syntactically valid extensions, return `BadMatch`; every error leaves the create XID unallocated; `CreateDevice` and `CreateDefaultDevice` send no reply on success.
- `GetPhysicalDeviceMemoryProperties` returns memory-type and heap indices that remain stable for the lifetime of the Physical-Device XID.
- `AllocateMemory` is exactly 32 bytes; `allocation_size` must be positive, `memory_type_index` valid, and the reserved field zero. Invalid values return `BadValue`, an invalid/occupied target XID returns `BadIDChoice`, unknown/non-live Device XIDs return `BadValue`, wrong live resource types or foreign Device ownership return `BadMatch`, an unavailable/lost Device returns `DEVICE_UNAVAILABLE` / `DEVICE_LOST`, and backend allocation failures return `ALLOCATION_FAILED`; on every error, the target XID remains unallocated.
- `CreatePipelineLayout` validates exactly `20 + 4 * set_layout_count + 12 * push_constant_range_count` bytes, registered stage bits, push-constant ranges, Device/Set-Layout ownership, and target-XID collisions. Unknown XIDs return `BadValue`, wrong live types/foreign ownership return `BadMatch`, unavailable/lost Devices return `DEVICE_UNAVAILABLE` / `DEVICE_LOST`, and backend allocation failures return `ALLOCATION_FAILED`; rejection leaves no Pipeline Layout.
- `CreateSemaphore` is exactly 28 bytes and accepts only `BINARY = 0` or `TIMELINE = 1`; for Binary, `initial_value` must be `0`. Invalid fields return `BadValue`, a target-XID collision returns `BadIDChoice`, and backend allocation failures return `ALLOCATION_FAILED`. Unknown Device XIDs return `BadValue`, wrong live types/foreign ownership return `BadMatch`, and unavailable/lost Devices return `DEVICE_UNAVAILABLE` / `DEVICE_LOST`; rejection leaves the target XID unallocated.
- `SignalSemaphore` has an exact length of 24 bytes and validates in this order: length, Device XID, Semaphore XID, type/ownership/cross-device association, Device state, then Timeline type and counter/reservation relation. In mixed-error cases, the earlier phase wins; in particular, `DEVICE_LOST` after valid resource resolution takes precedence over a Binary-semaphore type error. A synchronous rejection changes neither the counter nor signal reservations.
- Timeline host signals must exceed the observable counter and remain below every pending GPU signal value; a signal that jumps across a reserved GPU signal value is atomically rejected with `INVALID_SYNCHRONIZATION_STATE`, without changing the counter or reservations. Timeline queue waits may request a value not yet reached (wait-before-signal); acceptance registers the specific target value, waits asynchronously for it to be reached, and does not consume an exclusive Binary semaphore slot. Multiple accepted Timeline waits may share the same Semaphore XID and target value. New GPU signal reservations must remain strictly greater than the counter and every existing pending signal reservation. A signal value not greater than the observable counter results in `BadValue`, while a value that exceeds the counter but conflicts with an existing pending GPU signal reservation is rejected before acceptance with `INVALID_SYNCHRONIZATION_STATE`. Neither case may leave a partial reservation.
- A host signal to a value below a higher pending GPU-signal reservation MAY release a queue wait for that value; the GPU signal value remains reserved and can subsequently be signaled successfully.
- Timeline signal reservations are terminalized per accepted submission, not in callback order: a callback removes only the reservations belonging to its own token; afterward, `signal_slots` (if maintained internally as a compatibility mirror) equals the highest value still pending. Successful callbacks may only increase the observable counter monotonically. If callbacks arrive out of order, a later success for a lower value must not reset a higher counter already reached. After Device Loss, even delayed backend successes must not publish a reserved value; they must still release their own reservations without removing another submission's pending reservations. Each reservation has a unique internal identity tied to the exact semaphore identity; callbacks may mutate state only when their own reservation is still current. Device Loss racing callback publication is serialized, and late/duplicate callbacks cannot advance the counter or clear another reservation.
- `WaitForFence` requires exactly 24 bytes and validates length, Device then Fence XID, live type/ownership/Device association, then the atomic initial Device/Fence-state snapshot. Malformed length plus unknown XIDs yields `BadLength`; unknown XIDs yield `BadValue`; wrong live type/ownership/cross-Device use yields `BadMatch`. An already-lost Device yields normal reply status `DEVICE_LOST` even if the Fence is `FAILED`; otherwise an already-`SIGNALED`/`FAILED` Fence yields `SUCCESS`/`EXECUTION_FAILED`. With a non-terminal Fence, timeout zero yields `TIMEOUT` and installs no registration.
- `WaitSemaphores` has an exact length of `28 + 12 * semaphore_count` bytes and validates in this order: length/overflow, count/mode/duplicates, Device and Semaphore XIDs in wire order, type/ownership/cross-device association, Device state, then Timeline type. In mixed-error cases, the earlier phase wins; in particular, `DEVICE_LOST` after valid XIDs and ownership takes precedence over a Semaphore type error. All synchronous rejections occur without registering a wait or changing state. Device loss and `DestroyDevice` terminalize already-open waits with `DEVICE_LOST` and `DEVICE_DESTROYED`, respectively, without overwriting an already serialized result.
- `WaitSemaphores` MUST NOT block the X11 dispatcher: a later `SignalSemaphore` or `QueueSubmit` on the same connection may satisfy the wait; the timeout deadline continues to run from acceptance of the wait request.
- `WaitSemaphores` may wait for a Timeline value that has not yet been reserved; with a finite timeout it ends with `TIMEOUT`, while an infinite wait remains pending until the value is reached or the Device is lost. The server does not guarantee progress if no later signal is queued.
- If `WriteBuffer` waits for earlier submissions and a deferred `QueueSubmit` would satisfy a Timeline wait in an earlier non-terminal submission, but no already accepted signal operation can satisfy that wait, `WriteBuffer` ends with `DEPENDENCY_FAILED`. The deferred submission is then processed normally and is not accepted ahead of a successful upload.
- `CreateFence` is exactly 24 bytes, with `create_flags = 0` and `reserved = 0`; its initial state is `UNSIGNALED`. Invalid fields return `BadValue`, a target-XID collision returns `BadIDChoice`, and backend allocation failure returns `ALLOCATION_FAILED`. Unknown Device XIDs return `BadValue`, live resources of the wrong type or foreign ownership return `BadMatch`, and unavailable/lost Devices return `DEVICE_UNAVAILABLE` / `DEVICE_LOST`. On rejection, the target XID remains unallocated..
- `SelectEvents` is exactly 32 bytes and requires successful prior XGE 1.0 negotiation; scope, masks, and unused-field combinations are validated. Any error leaves the previous event selection unchanged atomically..
- Mixed-failure `SelectEvents`: malformed length plus any invalid field returns `BadLength`; invalid scope/unused fields plus an unknown Device returns `BadValue`; an unknown Device plus missing XGE negotiation returns `BadValue`; after valid Device XID/type/ownership checks, missing XGE negotiation plus an invalid queue tuple returns `BadMatch` from the XGE prerequisite. Every rejection preserves the previous selection.
- `ASYNC_ERROR` validates the semantic field combination: `origin = ORIGIN_QUEUE_SUBMIT` requires a nonzero token from a previously accepted submission; token 0 means there is no submission association, and a rejected `QueueSubmit` must never be the token target of an `ASYNC_ERROR`.
- For `origin = ORIGIN_QUEUE_SUBMIT`, `submission_token` MUST be nonzero and identify a previously accepted submission; token 0 means no submission association, and a rejected `QueueSubmit` MUST never be identified by an `ASYNC_ERROR` token.
- An `ASYNC_ERROR` with nonzero `submission_token` MUST be associated with an actually accepted submission. Unknown `origin` values, nonzero `reserved` fields, and invalid Device/resource references MUST NOT be serialized.
- If the affected resource was destroyed or its XID reused before the `ASYNC_ERROR` enqueue linearization point, the event MUST have `resource_xid = 0`; a later callback MUST NOT retarget the numeric XID to the new object.
- `SelectEvents` rejects unknown scope values, nonzero flags/common-header or payload reserved fields, unknown mask bits, and scope fields with incorrect zero values using `BadValue`; wrong live resource types or foreign ownership result in `BadMatch`. Every such error leaves the previous mask unchanged.
- `SelectEvents` with a valid Device but an unrequested queue combination is rejected with `BadValue`; an unknown or non-live Device XID results in `BadValue`, while a live XID of the wrong type or foreign ownership results in `BadMatch`.
- After successful `DestroyDevice`, unmaskable `DEVICE_LOST` and `ASYNC_ERROR` events MUST NOT contain the destroyed Device XID as `device_xid` or `resource_xid`; events queued before the request remain unaffected.
- When `SelectEvents`, `DestroyDevice`, and submission completion race, a shared serialized linearization point decides mask sampling and event enqueueing; a later backend callback MUST NOT enqueue a previously suppressed event.
- For each accepted submission, at most one of `SUBMISSION_COMPLETE` and `SUBMISSION_FAILED` is queued as the terminal event; `ASYNC_ERROR` is supplementary diagnostic information, not a second terminal outcome.
- After successful processing of `DestroyDevice`, no new events using its destroyed `device_xid` are generated or delivered; events already queued in the X11 output stream remain unaffected. Internal terminal processing of accepted submissions and backend references remains independent of this event suppression.
- After client disconnect, no new XAverius events are queued for the closed connection or delivered through other connections; event selections and public XID mappings are removed from the active connection state. Accepted work still reaches its actual internal terminal outcome without inventing completion or releasing backend resources prematurely; disconnect does not force indefinite waiting.
- Client disconnect cancels open server-side `WaitSemaphores`/`WaitForFence` registrations without a reply, releases only references held exclusively by those waits, and does not alter accepted GPU work or its synchronization state.
- Every accepted `WaitSemaphores` and `WaitForFence` registration captures the exact Device-generation identity and exact semaphore/fence identities resolved at acceptance. Device Loss or `DestroyDevice` terminalizes only registrations bound to that generation; a delayed success/timeout callback MUST NOT overwrite the first serialized terminal result or resolve a reused Device XID, connection/token pair, or semaphore/fence XID to a replacement object. The old callback may retire only its own registration and wait-held references.
- Competing wait termination conditions have exactly one terminal outcome: a condition already observed as satisfied remains successful; otherwise, the first serialized timeout, Device Loss, or `DestroyDevice` transition wins. Device Loss before `DestroyDevice` yields `DEVICE_LOST`; a wait still open when `DestroyDevice` is processed yields `DEVICE_DESTROYED`; later transitions do not overwrite the result.
- `CreateBuffer` rejects `usage_flags = 0` and unknown usage bits with `BadValue`.
- `CreateBuffer` distinguishes unknown/non-live Device XIDs (`BadValue`), incorrect live resource types (`BadMatch`), unavailable/lost Devices (`DEVICE_UNAVAILABLE` / `DEVICE_LOST`), and backend memory exhaustion (`ALLOCATION_FAILED`); on every failure, the target XID remains uncreated.
- `CreateDescriptorPool` distinguishes unknown Device XIDs (`BadValue`), incorrect live types/foreign ownership (`BadMatch`), unavailable/lost Devices (`DEVICE_UNAVAILABLE` / `DEVICE_LOST`), and backend allocation failures (`ALLOCATION_FAILED`); on rejection, the pool XID remains uncreated.
- `CreateDescriptorPool`, `AllocateDescriptorSets`, and `FreeDescriptorSets` reject a zero count with `BadValue`; `AllocateDescriptorSets` distinguishes unknown input XIDs (`BadValue`), incorrect live types/foreign ownership (`BadMatch`), Device states (`DEVICE_UNAVAILABLE` / `DEVICE_LOST`), and pool/backend allocation failures (`ALLOCATION_FAILED`), and leaves no partial subset live after rejection.
- All create-target XIDs are validated separately from input XIDs: invalid/occupied target XIDs return `BadIDChoice`; batch creation must not leave a partial subset after a collision.
- `ShaderModuleData` without a matching upload assembly and `CommandBufferData` without a matching `RECORDING` buffer are rejected with `INVALID_SYNCHRONIZATION_STATE`; CREATE target-XID collisions return `BadIDChoice`.
- `ShaderModuleData`: a failed continuation/FINAL discards its assembly only when the complete fixed header identifies the target XID and `CREATE=0`; a request truncated before the target XID leaves all assemblies unchanged, and a rejected `CREATE=1` attempt never destroys an existing assembly reserved under that XID. After disconnect or Device Loss, no old assembly remains addressable, and later chunks or ABORT requests must not revive it.
- `ShaderModuleData` and `CommandBufferData` chunk errors are reported synchronously as X11 errors only; they do not generate `ASYNC_ERROR`, because no submission was accepted.
- `CreateDevice` rejects zero queue-family records, a zero queue count, and duplicate queue-family records with `BadValue`; an unsupported queue count returns `BadMatch`.
- Binary semaphore: an accepted wait does not consume the signal before it is actually satisfied; the signal is consumed exactly once, and only then may a new signal cycle begin. Duplicate pending wait/signal operations are rejected atomically. Binary wait/signal values MUST be zero. Race tests must interleave Device Loss with wait-consumption, signal-success and signal-failure callbacks, including duplicate callbacks after `UNTRUSTED` is established; assert that only the matching reservation is released and no late callback changes the payload state or affects a newer reservation.
- Timeline semaphore: accepted, non-terminal signal operations reserve their values but do not increase the observable counter until successful execution; new signal values must exceed all pending reserved values. Duplicate Timeline signal entries for the same semaphore are rejected in v0.1.
- Every accepted queue wait/signal operation retains a reference to the exact internal semaphore identity until the operation reaches a terminal outcome and the backend can no longer access it; XID reuse must not redirect that reference.
- Duplicate pool-size types, duplicate descriptor updates to the same slot, duplicate wait/signal entries, and use of the same semaphore in both wait and signal arrays are atomically rejected according to the error rules.
- `CreateComputePipeline` uses the normative length `28 + ((entry_point_length + 3) & ~3)` and validates a nonempty ASCII entry point and zero padding; unknown input XIDs return `BadValue`, incorrect live types/foreign ownership return `BadMatch`, unavailable/lost Devices return `DEVICE_UNAVAILABLE` / `DEVICE_LOST`, and backend allocation failures return `ALLOCATION_FAILED`; on rejection, the pipeline XID remains uncreated.
- `DestroySemaphore` and `DestroyFence` are each 16-byte void requests; `WaitSemaphores` uses `28 + 12 * semaphore_count`.
- `DestroyFence` and `DestroySemaphore` validate the fixed request length before resolving XIDs; unknown/non-live XIDs return `BadValue`, incorrect live types or ownership return `BadMatch`, and rejections leave XIDs and state unchanged.
- `DestroyFence` is rejected while the Fence belongs to a non-terminal submission or an open `WaitForFence` registration references the same internal Fence identity. `DestroySemaphore` is rejected while a queue wait/signal, an open `WaitSemaphores` registration for the same internal Semaphore identity, or another active host operation uses it. Both rejections are atomic. Once a wait result has been terminally determined, a reply that is still pending does not block destruction.
- `GetFenceStatus` is a 16-byte reply request with the Fence status in reply byte 1, `reply.length = 0`, and zeroed reserved XAverius bytes at offsets 8–31.
- Error offsets and event/reply status values remain separate namespaces: `EXECUTION_FAILED` is error offset 3, `WaitForFence` status 2, and `SUBMISSION_FAILED.failure_class` 0; `DEVICE_LOST` is error offset 1, `WaitForFence` status 3, and `SUBMISSION_FAILED.failure_class` 1. `DEVICE_LOST.reason_code` uses its separate reason-code registry.
- `WaitSemaphores` and `WaitForFence` with timeout 0 check the state without intentionally waiting; `UINT64_MAX` waits indefinitely, and other values use a monotonic nanosecond deadline measured from acceptance.
- A finite wait deadline is not restarted for internal wait intervals or scheduler interruptions. The reply may arrive late, but a condition already satisfied wins over `TIMEOUT` during the final state check.
- A `WaitSemaphores` timeout returns status `TIMEOUT` without changing state. `WaitForFence` returns `SUCCESS`, `EXECUTION_FAILED`, or `TIMEOUT` according to the terminal Fence state and deadline, and returns `DEVICE_LOST` or `DEVICE_DESTROYED` if either terminal transition is observed first.
- `DestroyFence` is atomically rejected with `INVALID_SYNCHRONIZATION_STATE` while `PENDING` or while a `WaitForFence` registration remains open. Once a terminal wait result has been observed in serialized order, a reply that is still pending does not block destruction.
- `DestroySemaphore` is atomically rejected with `INVALID_SYNCHRONIZATION_STATE` while an open `WaitSemaphores` registration references the same internal Semaphore identity. Once a terminal wait result has been observed in serialized order, a reply that is still pending does not block destruction.
- Device Loss during a blocking wait is not masked as a timeout: `WaitSemaphores` ends with a `DEVICE_LOST` X11 error, and `WaitForFence` returns `DEVICE_LOST` in its reply.
- Processing `DestroyDevice` terminates still-open infinite waits without waiting for GPU progress: `WaitSemaphores` ends with a `DEVICE_DESTROYED` X11 error, and `WaitForFence` returns reply status `DEVICE_DESTROYED`. Conditions already observed as satisfied retain their normal result.
- `GetFenceStatus` precedence is exact length (`BadLength`), Device then Fence XID resolution (`BadValue`), live type/ownership/Device association (`BadMatch`), then an atomic state snapshot. Device Loss is not an error for this state-only query.
- After Device Loss, `GetFenceStatus` returns the stored state. Fences belonging to non-terminal submissions that failed because of Device Loss become `FAILED`; Fences that were never submitted are not changed artificially. After Device Loss is detected, `WaitForFence` always returns `DEVICE_LOST` instead of waiting indefinitely.
- `GetSemaphoreCounterValue` precedence is exact length (`BadLength`), Device then Semaphore XID resolution (`BadValue`), live type/ownership/Device association (`BadMatch`), Device state (`DEVICE_LOST`), then Timeline-semaphore validation (`BadMatch`). The Device-loss check is serialized with the counter snapshot.
- After Device Loss, `GetSemaphoreCounterValue` fails with the X11 error `DEVICE_LOST` (not a normal reply status and never a success counter reply). Verify that the error packet carries the request sequence/opcode fields and that no counter reply is emitted. Pair Device Loss with a Binary semaphore and require `DEVICE_LOST` to win over the later Timeline-type check; with a live Device, the Binary semaphore yields `BadMatch`. `SignalSemaphore`, `QueueSubmit`, and `WaitSemaphores` must not treat semaphore operations as able to continue successfully.
- Device-loss teardown invalidates public Fence/Semaphore XIDs, but internal synchronization objects may be freed only after backend accesses and server-side operations have safely ended, or when the objects remain isolated under the quarantine rules.
- `CommandBufferData` ABORT requests are exactly 16 bytes; all other chunks contain only complete entries.
- `CommandBufferData` akzeptiert exakt die Flag-Kombinationen `000` (Append), `010` (FINAL), `100` (CREATE), `110` (CREATE|FINAL) und `001` (ABORT); jede andere Kombination sowie reservierte Flag-Bits ergeben `BadValue`.
- `CommandBufferData` validates the target XID before the pool XID: CREATE with an invalid or occupied target XID returns `BadIDChoice`; without CREATE, an unknown Buffer XID returns `BadValue`. An unknown pool XID returns `BadValue`; an incorrect live resource type, foreign ownership, or a pool XID that is not the Buffer's parent pool returns `BadMatch`.
- `CommandBufferData` error precedence: malformed request/entry structure (`BadLength`) takes precedence over invalid flags, reserved bits, padding, and command-ID/scalar values (`BadValue`); these field errors take precedence over XID errors. Resolve the target XID, pool XID, then every embedded command-entry XID in entry order and field order; unknown/non-live XIDs return `BadValue`. Resolve all required XIDs before checking live resource types, client/device ownership, and parent-pool association (`BadMatch`); these checks precede Device state, which precedes command-buffer state and resource-dependent entry compatibility.
- Mixed-failure vectors for embedded command-entry XIDs: combine a CREATE target-XID collision with an unknown entry XID and require `BadIDChoice`; with a valid target, combine an unknown Pool XID and unknown entry XID and require the Pool XID's earlier `BadValue`; combine an unknown later entry XID with a live earlier entry XID of the wrong type and require `BadValue` because all required XIDs resolve before type checks; combine a live wrong-type/foreign entry resource with Device Loss and require `BadMatch`; with all XIDs/types/ownership valid, Device Loss wins over resource-dependent entry compatibility. Verify the entire chunk and all reference edges remain unchanged on every rejection.
- For `CommandBufferData`, an invalid flag combination combined with an invalid target XID returns `BadValue`; a structurally truncated entry combined with an invalid target XID returns `BadLength`; with valid CREATE flags and an invalid or occupied target XID, `BadIDChoice` takes precedence over an invalid pool XID.
- For CREATE/Append/FINAL on a lost Device, `DEVICE_LOST` takes precedence after valid XID/type/ownership checks, even if an existing buffer is not `RECORDING`. ABORT is the exception: after Device loss, pool/buffer association and the `RECORDING` state are still checked; an invalid state results in `INVALID_SYNCHRONIZATION_STATE`.
- Even for `ABORT`, `command_pool_xid` MUST exactly match the Buffer's parent pool. A mismatched pool is rejected without changing recording state, entries, or references.
- An entry with an incomplete header or a declared length extending beyond the request boundary returns `BadLength`; a zero length, a length smaller than the entry header, or an unknown command ID returns `BadValue`. In all cases, no part of the current chunk is appended.
- `ResetCommandBuffer` validates request length, XIDs, type, ownership, and cross-Device association before changing state. After successful XID validation, an unavailable/lost Device returns `DEVICE_UNAVAILABLE` / `DEVICE_LOST`; missing reset permission and `PENDING` return `INVALID_SYNCHRONIZATION_STATE`, leaving state, entries, and references unchanged.
- `QueueSubmit` length MUST equal `40 + 4*C + 16*W + 12*S` exactly. Zero or reused submission tokens return `BadValue`; count/length overflow returns `BadLength`; foreign ownership or queue mismatch returns `BadMatch`; invalid states return `INVALID_SYNCHRONIZATION_STATE`; synchronously rejected requests emit no submission event.
- `QueueSubmit` error precedence: invalid total length/counts (`BadLength`) take precedence over token/mask/reserved-field errors (`BadValue`); syntax errors take precedence over XID resolution; XID/type/ownership/queue errors take precedence over Device and state errors.
- For `QueueSubmit`, unknown Device/resource XIDs return `BadValue`; a queue-family/queue-index pair not belonging to the Device configuration, an incorrect live type, or foreign ownership returns `BadMatch`. All XID references are resolved before queue/type/ownership and Device checks; queue/type/ownership errors take precedence over `DEVICE_LOST`.
- If `QueueSubmit` uses token `0` or a previously used token while also containing an unknown Device/Buffer XID, token validation returns `BadValue`; an incorrect request length takes precedence over both errors.
- With valid syntax and XIDs, an incorrect live resource type or foreign ownership returns `BadMatch`, even if the Device is lost. After valid XID/type/ownership/queue checks, Device Loss returns `DEVICE_LOST` before errors for a non-`EXECUTABLE` command buffer, a non-submittable Fence, or an invalid mutable Semaphore state.
- A wait-stage mask containing reserved bits returns `BadValue` before XID/state validation. A syntactically valid stage unsupported by the queue family returns `INVALID_SYNCHRONIZATION_STATE` only after XID/ownership and Device checks.
- Nonzero binary wait/signal values and timeline signal values not greater than the observable counter are rejected with `BadValue` only after XID/type/ownership and Device checks. A timeline signal value greater than the counter but conflicting with an already reserved pending GPU signal value returns `INVALID_SYNCHRONIZATION_STATE`. Every rejection leaves previously validated command buffers, Fences, and Semaphores unchanged.
- If multiple state errors are present, after checking Device state `QueueSubmit` validates the optional Fence first, then command buffers in array order, then wait entries, and finally signal entries in array order. Within each wait entry, type-dependent values are checked before stage support and mutable Semaphore state; within each signal entry, type-dependent values are checked before signal state and reservation conflicts. A specific error from a wait or signal entry takes precedence over the generic dependency fallback: `DEPENDENCY_FAILED` from unspecified dependency analysis is returned only after all entries pass validation without a specific error. A `DEPENDENCY_FAILED` arising from a specific `UNTRUSTED` entry remains that entry's specific result.
- A failed FINAL chunk of `CommandBufferData` leaves the buffer `RECORDING`, preserves all previously accepted entries and references, and appends neither entries nor references from the failed chunk.
- `QueueSubmit` validates all command buffers and synchronization objects before commit. If a later entry is rejected, previously validated objects also remain unchanged.
- On rejected `QueueSubmit`, every command buffer remains `EXECUTABLE`; no Fence is assigned or toggled, semaphore counters, signal availability, pending slots, and Timeline reservations remain unchanged, and no internal submission references are created. The rejected request reserves neither `submission_token` nor semaphore wait/signal slots.
- The `submission_token` is consumed only at acceptance: after a synchronously rejected request, the same token may be used in a corrected request; an accepted request reserves it exactly once.
- A rejected `QueueSubmit` emits neither `SUBMISSION_COMPLETE`/`SUBMISSION_FAILED` nor `ASYNC_ERROR`; a later backend failure of an accepted submission follows the terminal-submission rules.
- Before acceptance, `QueueSubmit` atomically rejects duplicate command-buffer XIDs, duplicate Semaphore XIDs within either the wait array or the signal array, and the same Semaphore appearing in both arrays. The error is `BadValue`, and command-buffer, Fence, Semaphore, and submission states remain unchanged.
- `QueueSubmit` validates Semaphore types and values before acceptance: Binary wait/signal values MUST be zero; timeline signal values MUST exceed the counter and every previously reserved pending GPU signal value; duplicate timeline signal entries for the same Semaphore are invalid.
- A rejected `QueueSubmit` reserves neither `submission_token` nor Semaphore wait/signal slots, and creates neither submission events nor internal submission references.
- An accepted timeline signal reservation remains binding until its submission's terminal callback. On successful completion, the counter advances monotonically to at least the reserved value; a failed completion removes only that submission's reservations and does not publish a signal value. After each terminal callback, the summary pending slot represents the highest still-open signal value, or is empty if none remain.
- Callback order does not change these rules: a later-arriving successful callback with a lower value MUST NOT decrease the counter. After Device Loss has been observed, a late backend success MUST NOT advance a timeline counter; its reservations are still released when the submission terminates. A submission token that is already terminal MUST NOT trigger a second state transition.
- `QueueSubmit.wait_stage_mask` is interpreted as an XAverius bitmask, not as a raw Vulkan mask: `DRAW_INDIRECT=0x1`, `COMPUTE_SHADER=0x2`, `TRANSFER=0x4`, and `ALL_COMMANDS=0x8`. The backend translation uses the corresponding Vulkan stage bits.
- Wait-stage masks with value 0 or reserved bits return `BadValue`; rejection is atomic and leaves Fence/Semaphore state unchanged.
- All four individually defined stage bits are valid on a compute queue; only `TRANSFER` and `ALL_COMMANDS` are valid on a transfer-only queue. `COMPUTE_SHADER` on a non-compute queue, or `DRAW_INDIRECT` without graphics or compute support, returns `INVALID_SYNCHRONIZATION_STATE`.

## Presentation lifecycle race and atomicity vectors

The presentation-capable conformance suite MUST exercise the following serialized race pairs. A test controls the serialization order explicitly; wall-clock timing alone is not a valid oracle.

- **Acquire timeout versus lifecycle:** if timeout/zero-timeout poll terminalizes first, the reply remains TIMEOUT/NOT_READY and a later resize, Surface loss, Device loss, or DestroyDevice cannot rewrite it. If a lifecycle transition terminalizes first, the reply is respectively DEVICE_LOST, SURFACE_LOST, OUT_OF_DATE, or DEVICE_DESTROYED according to the AcquireNextImage precedence; no image is acquired and neither optional semaphore nor fence is signaled.
- **Overlapping presentation lifecycle conditions and terminal first-wins:** for a new AcquireNextImage and a pre-acceptance QueuePresent, arrange both resize/zero extent and underlying Window destruction to be visible at the same serialized lifecycle check; require SURFACE_LOST rather than OUT_OF_DATE. Add Device loss to that snapshot and require DEVICE_LOST. For QueuePresent, repeat with an invalid queue-family/index: on a usable Device require BadValue before Surface status, but with Device loss require DEVICE_LOST before that queue/index error. With no lifecycle failure, verify unsupported presentation queue support remains BadMatch before token/image/wait checks. Repeat with the lower-priority transition arriving first and second; the effective status for a single snapshot must be identical. For a pending AcquireNextImage and an accepted QueuePresent, serialize one lifecycle transition and its terminal commit, then serialize a higher-priority transition afterward: the already committed terminal status MUST remain unchanged. Also serialize multiple lifecycle conditions before terminalization and require DEVICE_LOST > SURFACE_LOST > OUT_OF_DATE. For QueuePresent, assert that terminal status selection never releases the image by itself; IMAGE_RELEASED still requires backend access to have ended and a reusable image in a live Swapchain.
- **Acquire initial-check versus registration:** arrange an image to become available exactly between the initial availability check and pending-registration installation. Require either immediate SUCCESS from the check or exactly one wake of the installed registration; the image must never be lost, acquired twice, or left ACQUIRED without a successful reply. Repeat with both optional synchronization objects supplied and assert the image transition plus both signals commit atomically.
- **Competing pending acquires for one released image:** install at least two open acquire registrations for the same Swapchain, with distinct optional signal objects, then serialize exactly one image-release transition. Require exactly one registration to receive SUCCESS and that image to become ACQUIRED with only that registration's supplied objects signaled; the other registration remains open and receives no image or signal from that release. The server may choose either waiter, because FIFO order and fairness are not guaranteed. A later release may satisfy another waiter; a timeout or lifecycle terminalization of the losing waiter must remain independent. Assert that no request can observe the image as AVAILABLE between release and assignment while an eligible waiter exists.
- **Acquire completion versus timeout:** for finite and infinite waits, serialize image availability immediately before and immediately after timeout terminalization. If success commits first, require one SUCCESS reply, one ACQUIRED image, and exactly one signal for each supplied object; later timeout/lifecycle callbacks do nothing. If timeout commits first, require one TIMEOUT reply, no acquired image, no signal, and no later callback may acquire or signal. For timeout zero, require an immediate poll result (SUCCESS if an image is available at the poll linearization point, otherwise NOT_READY) and prove no registration or retained wait reference is installed.
- **Acquire lifecycle precedence mixed failures:** combine valid Device/Swapchain with Device loss plus Surface loss and OUT_OF_DATE; require DEVICE_LOST. With a live Device, combine Surface loss and OUT_OF_DATE; require SURFACE_LOST. With usable lifecycle state, combine OUT_OF_DATE with an ineligible Semaphore/Fence or conflicting acquire; require OUT_OF_DATE. Once lifecycle checks pass, combine ineligible synchronization state with no available image and zero/finite timeout; require INVALID_SYNCHRONIZATION_STATE before NOT_READY/TIMEOUT. Malformed length plus unknown XIDs is BadLength; unknown Device/Swapchain/optional synchronization XID is BadValue; wrong live type/ownership/cross-Device association is BadMatch before lifecycle/status checks.
- **Acquire signal reservation and rollback:** while an acquire is pending, race QueueSubmit/SignalSemaphore/ResetFence or another acquire against each supplied signal object. Require the pending acquire's reservation to prevent conflicting use. On TIMEOUT, NOT_READY, OUT_OF_DATE, SURFACE_LOST, DEVICE_LOST, or DEVICE_DESTROYED, release reservations exactly once without signaling either object or changing their prior confirmed state. On SUCCESS with both objects supplied, signal both exactly once with the image transition; no interleaving may expose only one signal or an acquired image without both signals.
- **Acquire duplicate callbacks and disconnect:** deliver duplicate image-available, timeout, Device-loss, Surface-loss, Swapchain-out-of-date, and DestroyDevice callbacks in every ordering after one terminal outcome. Require exactly one reply (or no delivery after disconnect), no duplicate image acquisition/signaling, and exactly-once release of the Swapchain, Surface, Device, Semaphore, and Fence registration references.
- **Acquire synchronization eligibility versus timeout:** combine an unavailable image and `timeout_ns = 0` with an ineligible supplied semaphore, an ineligible fence, and a conflicting pending acquire in separate vectors. Each must return `INVALID_SYNCHRONIZATION_STATE` before `NOT_READY`/`TIMEOUT`, with no registration, image transition, or signal; repeat with an available image to prove eligibility is validated before the success commit as well.
- **DestroyDevice versus pending acquire:** DestroyDevice terminalizes each still-open registration with DEVICE_DESTROYED and invalidates the owned Swapchain. It must not overwrite an already-terminal acquire reply. Registration-only references are released exactly once; disconnect suppresses delivery but not cleanup.
- **DestroySurface versus CreateSwapchain:** if CreateSwapchain commits first, the new live Swapchain reference causes DestroySurface to fail atomically with INVALID_SYNCHRONIZATION_STATE. If DestroySurface commits first, the later CreateSwapchain fails at Surface-XID resolution and publishes no target XID or backing resource.

- **DestroySurface versus underlying Window destruction:** serialize both orders for an otherwise destroyable Surface. If DestroySurface commits first, require immediate public-XID invalidation; a later Window-destruction notification for the retained Window identity must not mutate a replacement resource, queue a Surface event, or resolve a reused Surface XID. If Window destruction commits first, require the Surface to remain publicly addressable in SURFACE_LOST; DestroySurface may then succeed only if no live Swapchain references it. With a live Swapchain, require INVALID_SYNCHRONIZATION_STATE and preserve the lost Surface identity; AcquireNextImage and QueuePresent follow their existing SURFACE_LOST precedence and accepted work terminalizes without an invented release. Destroy the Swapchain after its blockers drain, then require DestroySurface success. Repeat with Window XID reuse and assert that the old Surface never binds to the replacement Window.
- **DestroySurface versus AcquireNextImage:** with a live Swapchain, attempt DestroySurface before, during, and after immediate acquire success; with a pending acquire, attempt it before and after registration terminalization. Every attempt while the Swapchain remains live must fail atomically with INVALID_SYNCHRONIZATION_STATE, preserving Surface XID, Window identity, acquire reply/registration, image state, and signal state. After DestroySwapchain succeeds, serialize DestroySurface before an acquire using the retired Swapchain XID; require BadValue, not SURFACE_LOST, with no registration or signal side effects. Repeat with the Swapchain XID reused for a distinct generation and verify the request cannot follow the old identity.
- **DestroySurface versus QueuePresent:** attempt DestroySurface while the live Swapchain has an ACQUIRED image, a pre-acceptance rejected QueuePresent, an accepted presentation before terminalization, between terminalization and backend release, and after both milestones. All attempts while the Swapchain exists must fail with INVALID_SYNCHRONIZATION_STATE and leave token/wait reservations, image state, terminal result, event decisions, and Surface/Window identity unchanged. Then destroy the Swapchain and race successful DestroySurface against QueuePresent using the retired Swapchain XID; QueuePresent must fail BadValue without acceptance side effects. Verify that explicit Surface destruction never produces SURFACE_LOST; separately race underlying Window destruction to exercise the asynchronous SURFACE_LOST path and existing status precedence.
- **DestroyDevice versus CreateSwapchain:** if DestroyDevice serializes before XID resolution, the request reports BadValue for the now non-live Device XID. If Device loss (without destruction) serializes first, it returns the DEVICE_LOST status. If creation commits first, the Device destruction cascade invalidates the newly published Swapchain. No interleaving may publish a partially initialized Swapchain.
- **Resize/window destruction versus CreateSwapchain preparation:** lifecycle changes that serialize before the atomic commit point must be observed during commit-time revalidation; return OUT_OF_DATE or SURFACE_LOST (DEVICE_LOST has higher precedence), with target XID unallocated and all provisional references/resources released exactly once. If creation commits first, its success reply is not retroactively changed; the later lifecycle transition updates the published state.
- **QueuePresent rejection versus accepted state:** a rejected QueuePresent leaves the image ACQUIRED, reserves neither presentation_token nor wait slots, consumes no semaphore payload, and creates no presentation operation. Retry with the same token is permitted unless an earlier attempt was accepted. Acceptance atomically reserves token and waits and changes ACQUIRED to PRESENT_PENDING.
- **Acquire success versus QueuePresent on the same image:** start with one AVAILABLE image and serialize an immediate AcquireNextImage success before QueuePresent for that image. Require the acquire commit to establish ACQUIRED and signal its supplied objects exactly once; the later QueuePresent may then be accepted and atomically establish PRESENT_PENDING with its token/wait reservations. Reverse the order using an image that has not yet been assigned to the pending acquire: QueuePresent MUST return INVALID_SYNCHRONIZATION_STATE, reserve no token or waits, and leave the image/registration unchanged; a later acquire assignment may then succeed. No execution may expose two owners or accept a present based on a future acquire.
- **QueuePresent acceptance versus a pending acquire:** hold an acquire registration open because no image is available, then present a different ACQUIRED image. Acceptance MUST only transition that image to PRESENT_PENDING and reserve its own token/waits; it MUST NOT complete, cancel, or preassign the pending acquire. On release, the common serialization order assigns the image to exactly one still-open acquire, unless timeout or lifecycle terminalization committed first. Repeat with the same supplied signal Semaphore/Fence reserved by the acquire and verify QueuePresent cannot consume or reserve either object incompatibly before acquire success.
- **Image release versus acquire timeout/lifecycle while QueuePresent is pending:** accept QueuePresent, then race its backend-release milestone against the pending acquire's timeout, Surface loss, Swapchain OUT_OF_DATE, and Device loss. If release/assignment commits first, require one acquire SUCCESS and one ACQUIRED image; later timeout/lifecycle callbacks cannot revoke it. If timeout/lifecycle commits first, require the acquire's corresponding terminal status, no acquire signal, and no assignment to that registration; the release follows the no-eligible-waiter path (or invalidates the image if lifecycle state forbids reuse). In all orders, QueuePresent's already-committed terminal status remains governed by its own terminalization gate.
- **Acquire-to-present semaphore handoff:** acquire an image with a binary Semaphore, then issue QueuePresent using that Semaphore as a wait. If acquire success commits first, QueuePresent may reserve the now-signaled payload according to the common semaphore rules. If QueuePresent serializes while the acquire still owns the signal reservation, it MUST be rejected with INVALID_SYNCHRONIZATION_STATE (or the earlier image-state error, according to the specified validation order), with no token/wait reservation or payload consumption. A rejected attempt may retry the same token after acquire success. Verify the acquire signal and present wait are each committed/consumed at most once.

- **Accepted presentation versus resize/Surface loss/Device loss:** exactly one terminal status wins by serialization order. A terminalized operation cannot emit a second PRESENTATION_COMPLETE or later change status. IMAGE_RELEASED is permitted only when backend access has ended and the image remains reusable in a usable Swapchain; otherwise the image is invalidated and no release event is emitted.
- **DestroySwapchain versus pending references:** recording command buffers, pending acquire registrations, accepted presentation operations, queue submissions, and backend access block destruction. An acquired-but-idle image alone does not. Rejection preserves the public XID and all references; success invalidates the public XID and all image indices atomically, while internal release may be deferred.

- **DestroySwapchain versus AcquireNextImage:** run both serialization orders for an immediate acquire and for an open pending acquire. If destroy commits before acquire XID resolution, require synchronous BadValue, no reply-status registration, no signals, and no retained references. If a pending acquire is already open, require destroy to return INVALID_SYNCHRONIZATION_STATE with the XID, image set, registration, and reservations unchanged. If immediate acquire SUCCESS commits first, preserve its reply/signals, then allow destroy of the acquired-but-idle Swapchain and require all image indices to become invalid; a later QueuePresent must return BadValue. Also serialize timeout/NOT_READY terminalization before destroy and verify the terminal reply is not rewritten.
- **DestroySwapchain versus QueuePresent:** if destroy commits first, require QueuePresent to fail XID resolution with BadValue and reserve no token/waits. If QueuePresent acceptance commits first, require destroy to fail with INVALID_SYNCHRONIZATION_STATE until both the terminal and backend-release milestones have committed; test terminal-first and release-first order separately. After both milestones, destroy may invalidate the public XID and all image indices. A duplicate or late callback must not change the retired generation or a replacement Swapchain reusing the XID.
- **DestroyDevice versus AcquireNextImage:** if the cascade commits before acquire XID resolution, require BadValue and no registration. If an acquire is pending first, require exactly one DEVICE_DESTROYED result, no Semaphore/Fence signal, immediate public invalidation of the Device/Swapchain/images, and exactly-once release of registration references. If immediate SUCCESS or timeout/NOT_READY commits first, preserve that reply; the cascade may invalidate an acquired image but cannot rewrite the terminal result.
- **DestroyDevice versus QueuePresent:** if the cascade commits before QueuePresent XID resolution, require BadValue and no token/wait reservation. If acceptance commits first, retain the accepted operation and its captured Device/Swapchain generations until backend quiescence; invalidate public identities immediately and suppress all newly queued events. Verify that destruction alone does not rewrite its terminal status to DEVICE_LOST; if the backend operation is abandoned solely because of destruction, its internal terminal result is PRESENTATION_FAILED. No IMAGE_RELEASED is emitted for the invalidated image. Test destroy before terminal, between terminal and release, and after both milestones; late callbacks must be mutation-free.
- **Semaphore uncertainty after accepted presentation failure:** resolve each reserved wait independently. Proven non-consumption releases its reservation without losing a valid signal; proven consumption records consumption; uncertainty marks that binary semaphore UNTRUSTED. Never silently reset it to UNSIGNALED. These internal transitions occur even if events are masked or the client disconnected.

Every vector must assert both externally observable result (X11 error versus normal reply/status versus optional XGE event) and internal invariants (public XID visibility, image state, token reservation, semaphore state, pending-reference count). Include at least one case per vector with presentation event masks disabled to verify that event selection does not suppress terminalization or cleanup. Run the vectors in both request byte orders wherever wire parsing is involved. These are required conformance cases; they do not claim runtime implementation coverage until an implementation test harness executes them.

## Queue-Reihenfolge und Fortschritt

- Submissions derselben Queue werden in der Annahmereihenfolge eingereiht; unabhängige Arbeit darf sich überlappen.
- Zwischen verschiedenen Queues besteht ohne explizite Synchronisation keine zugesicherte Reihenfolge oder Memory-Visibility.
- Queueübergreifende Abhängigkeiten werden mit Semaphore-Signal und -Wait hergestellt. Erforderliche Memory-Dependencies werden separat nach Vulkan-Regeln geprüft.
- Fence-Waits und Host-Semaphore-Waits beobachten Zustände, erzeugen aber selbst keine Queue-seitige Abhängigkeit.
- Ein Host-Signal kann einen Queue-Wait auf denselben Semaphore-Wert freigeben, ordnet aber keine unverbundene GPU-Arbeit.
- Submission-Tokens und Event-Sequence-Nummern sind keine Ordnungswerte.
- Für unabhängige Queues sind weder Fairness noch eine feste maximale Scheduling-Latenz zugesichert.

## XGE- und Reply-ABI

- Jeder XAverius-XGE-Event-Header ist genau 32 Bytes groß: `response_type = 35`, `extension` ist der ausgehandelte XAverius-Major-Opcode, `sequence` liegt bei Offset 2, `length` bei Offset 4 und `evtype` bei Offset 8; Header-Padding bei Offset 10–31 ist null.
- XGE-Längen werden als `32 + 4 * length` geprüft: `ASYNC_ERROR` 60 Bytes/length 7; `DEVICE_LOST`, `DEVICE_STATUS_CHANGED`, `DEVICE_MEMORY_PRESSURE` und `DEVICE_IDLE` je 48 Bytes/length 4; `SUBMISSION_COMPLETE` und `SUBMISSION_FAILED` je 56 Bytes/length 6.
- Event-`evtype`-Werte stimmen exakt mit der Event-Registry überein (0–6); der dynamische Extension-Major-Opcode wird nicht als Event-Type-ID verwendet.
- Die event-spezifischen Felder beginnen bei Offset 32. Alle als reserviert definierten Felder sind null; `SUBMISSION_COMPLETE` und `SUBMISSION_FAILED` unterscheiden sich bei Offset 44 (reserviert null bzw. `failure_class`) und dürfen für dieselbe angenommene Submission nicht beide als terminales Event auftreten.
- `SelectEvents` hat exakt 32 Bytes, ist als Void-Request unter Subopcode 40 registriert und besitzt null Flags (Offset 5) sowie ein null-reserviertes Common-Header-Feld (Offset 6). Die Scope-spezifischen Felder liegen bei Offset 8–31; der Prüfer kontrolliert Layout und Registrierung gemeinsam. Der Event-Maskenwert wird anhand des Scopes validiert; Fehler ändern die vorherige Auswahl nicht.
- Feste Replies sind 32 Bytes mit `reply.length = 0`, sofern keine Payload über Offset 32 hinausgeht. Bei variabler Payload bezeichnet `reply.length` ausschließlich die gepaddeten Vierbyteeinheiten nach Offset 32; Payload-Bytes und Null-Padding werden getrennt geprüft.
- `GetFenceStatus` legt den Fence-Status in Reply-Byte 1 ab; Offset 0 bleibt `response_type`, Offsets 2–3 Sequenznummer und Offsets 4–7 `reply.length = 0`. Die restlichen XAverius-reservierten Bytes sind null.

## Automatisierter Wire-Layout-Check

Im Repository-Root ausführen:

```sh
python3 -m py_compile tools/check-wire-layout.py
python3 tools/check-wire-layout.py
```

Der Checker verwendet nur die Python-Standardbibliothek. Er prüft die sieben Compute-Baseline-XGE-Event-IDs und -Längen sowie die zwei zusätzlichen, profilgebundenen Präsentations-Events, extrahiert die Event-Felder aus den Layoutbeschreibungen und meldet Überlappungen, Lücken, unzulässige Offsets/Ausrichtung, Felder außerhalb der Eventlänge sowie nicht explizit auf null gesetzte reservierte Felder. Für Replies vergleicht er das 47-Request-Inventar (40 Compute-Baseline-Requests plus sieben Präsentations-Requests) und die Längenmatrix mit dem Subopcode-Register und prüft zentrale feste Reply-Felder sowie variable `reply.length`-Formeln in den normativen Kapiteln. GitHub Actions führt den Check bei Änderungen auf dem Arbeitsbranch und bei Pull Requests aus.

Der Check ist eine statische Dokumentations-Konsistenzprüfung. Er ersetzt weder Tests gegen einen laufenden X11/XGE-Server noch Backend-/Vulkan-Konformitätstests.

### Reply-ABI-Abdeckung des statischen Prüfers

Der Wire-Layout-Check muss alle 15 als `Reply` registrierten Requests abdecken: `EnumeratePhysicalDevices`, `GetPhysicalDeviceProperty`, `GetPhysicalDeviceQueueFamilyProperties`, `GetPhysicalDeviceMemoryProperties`, `GetBufferMemoryRequirements`, `WriteBuffer`, `ReadBuffer`, `GetSemaphoreCounterValue`, `WaitSemaphores`, `GetFenceStatus`, `WaitForFence`, `GetSurfaceCapabilities`, `CreateSwapchain`, `AcquireNextImage` und `QueuePresent`. Die Prüfliste wird mit den `Reply`-Einträgen im zentralen Subopcode-Register verglichen; fehlt ein registrierter Reply oder ein erwarteter Vertrag, schlägt der Check fehl.

Die XGE-Prüfungen validieren außerdem die gemeinsamen 32-Byte-Headerfelder und deren Offsets, den dynamischen Extension-Major-Opcode gegenüber den statischen Event-Type-IDs, die exakten Payload-Feldtypen/-Offsets und Längen aller sieben Compute-Baseline-Events sowie – sofern das presentation-capable Profil aktiviert ist – beider zusätzlicher Presentation-Events, die event-lokalen Werte-Registries und die 32-Byte-`SelectEvents`-Struktur einschließlich Scope-abhängiger Masken und XGE-Aushandlungsregeln. Synthetische Frames für Little- und Big-Endian prüfen die Längenformel und weisen inkonsistente Längen, falsche `response_type`-Werte und nicht-nullige reservierte Headerbytes zurück. `IMAGE_RELEASED` und `PRESENTATION_COMPLETE` müssen jeweils exakt 64 Bytes lang sein (`length = 8`), die korrekten Feldoffsets einschließlich des 64-Bit-Presentation-Tokens verwenden und die presentation-lokalen Statuswerte beziehungsweise `reserved = 0` prüfen. Der Compute-only Prüflauf darf diese beiden Events nicht als aktiv registrieren oder deren Queue-Maskenbits zulassen. Diese Tests sind statische ABI-/Referenzprüfungen und ersetzen keinen Test gegen einen laufenden X11/XGE-Server.

Zusätzlich zu festen Reply-Feldern prüft er jetzt die variablen Record- und Payload-Verträge: `PHYSICALDEVICEINFO`-Records einschließlich Namenslänge und Padding, `QUEUEFAMILYINFO`-Records, `MEMORYTYPEINFO`/`MEMORYHEAPINFO`-Größen und -Counts, Property-Werte, `ReadBuffer`-Payloads sowie den variablen Request-/Reply-Vertrag von `WriteBuffer` und `WaitSemaphores`. Der Check ist absichtlich eine normative Text-Konsistenzprüfung; er führt keine Server- oder Vulkan-Operation aus.

Die Formeltests enthalten zusätzlich Grenzwertvektoren für Byte-Padding und Reply-Wörter bei Payload-Längen 0, 1, 3, 4 und 5; für `PHYSICALDEVICEINFO`-Namenslängen 0, 1, 4 und 5; für leere und nichtleere Queue-Family-Arrays; sowie für Memory-Type-/Heap-Counts einschließlich der v0.1-Maxima 32/16. Für `WriteBuffer` und `WaitSemaphores` werden variable Request-Längen ebenfalls anhand konkreter Count-/Payload-Vektoren geprüft.

## Golden-Wire-Testvektoren

`tests/wire-vectors.json` enthält konkrete Request-Bytes für `CreateBuffer`, `WriteBuffer` und `ReadBuffer`, jeweils in Little- und Big-Endian-Byteordnung. Die `WriteBuffer`-Vektoren decken Payload-Längen 1, 3, 4 und 5 Bytes ab und prüfen damit Padding von 3, 1, 0 und 3 Bytes. Die Fixtures prüfen den 8-Byte-Request-Header, das Null-`data`-Feld, den Subopcode am Offset 4, die vierbytebasierte Request-Länge und die festen Feldlayouts. Zusätzliche Raw-Frame-Tests weisen abgeschnittene Header, falsche deklarierte Längen und nicht-nullige reservierte Headerbytes zurück. Der Major-Opcode `0x90` ist nur ein Fixture-Wert; im Betrieb wird er vom X-Server zugewiesen.

Mit `python3 -m unittest discover -s tests -p 'test_*.py' -v` werden die Golden-Bytes gegen einen kleinen Referenz-Encoder geprüft. Der Referenz-Encoder ist kein XAverius-Client und keine Serverimplementierung: Die Tests belegen die Konsistenz der Vektoren und der abgedeckten Wire-Regeln, nicht die Interoperabilität. Sobald ein Client- oder Server-Encoder existiert, muss derselbe Vektorsatz direkt gegen dessen erzeugte beziehungsweise geparste Bytes laufen. Die Negativtests weisen außerdem abweichende deklarierte Paketlängen, nicht-nulliges WriteBuffer-Padding, inkonsistente Payload-Längen und nicht-nullige reservierte CreateBuffer-Felder zurück. Diese Tests prüfen die Ablehnungslogik des Referenz-Encoders; sie sind ausdrücklich noch kein Nachweis, dass ein Server dieselben fehlerhaften Pakete korrekt zurückweist.


# Presentation-profile conformance cases (future profile)

The following cases apply only when the server implements the presentation-capable profile; they do not expand the compute-only baseline by implication.

- Surface creation binds the exact internal identity of an existing X11 Window. Unknown/non-Window IDs fail synchronously, a failed create leaves the target XID unallocated, and destroying/reusing the numeric Window XID never retargets an existing Surface.
- Surface is connection-owned and can be queried against more than one logical Device. A Surface destroy with a live Swapchain reference is rejected atomically. Device destruction invalidates device-owned Swapchains but does not implicitly destroy the connection-owned Surface.
- A Swapchain image is identified only by (Swapchain XID, image_index), has no independent XID, and cannot be acquired twice concurrently. Invalid indices and invalid image-state transitions leave state unchanged.
- Capability query returns a self-consistent variable-length reply: exact total size is 64 + 8 * format_pair_count + 4 * present_mode_count + 8 * queue_family_count; reply.length is 8 + 2 * format_pair_count + present_mode_count + 2 * queue_family_count. Count arithmetic must be overflow-checked. Queue-family support records contain exactly one ascending-index record per physical queue family. A zero-sized window reports TEMPORARILY_NOT_PRESENTABLE without blocking.
- CreateSwapchain either creates exactly the requested image_count and returns that count, or leaves the target XID unallocated. Unreported format/color-space pairs, modes, and usage bits are rejected atomically.
- `CMD_COPY_BUFFER_TO_SWAPCHAIN_IMAGE` accepts only a 36-byte entry with command ID 5, `entry_length = 9`, and zero reserved field; it requires a `TRANSFER_SRC` Buffer, `TRANSFER_DST` Swapchain image usage, an in-range image index, and an image in `ACQUIRED` state at submission validation. Reject bad alignment, too-small row/image dimensions, out-of-bounds source span, arithmetic overflow, and incompatible usage atomically; the last-byte calculation must use overflow-safe wide arithmetic. Verify RGBA8/BGRA8 channel order is preserved without implicit format or color-space conversion, and a rejected entry appends no partial command.

- Mixed-failure tests for `CMD_COPY_BUFFER_TO_SWAPCHAIN_IMAGE` must verify the specified stage order: malformed entry length/reserved field beats every later failure; bad `buffer_offset` alignment or invalid row/image dimension syntax beats an invalid Buffer-XID; invalid Buffer-XID beats an invalid Swapchain-XID; unknown Swapchain-XID beats resource-dependent image-index and bounds checks; wrong live resource type/ownership beats usage incompatibility; an out-of-range image index or out-of-bounds source span beats usage incompatibility; and all these synchronous validation failures beat the submission-time image-state check. Every rejection must leave the complete CommandBufferData chunk unattached and preserve image, Swapchain, semaphore, and reference state. Test checked-arithmetic overflow separately from ordinary bounds failure.
- `AcquireNextImage` with `timeout_ns = 0` returns `NOT_READY` when no image is immediately available; expiration of a finite positive timeout returns `TIMEOUT`. Every non-success reply has `image_index = 0`; no failure signals the optional semaphore/fence or changes image state. Semaphore and fence are independently optional and may both be supplied; on SUCCESS each supplied eligible same-device object is signaled exactly once. A successful acquire returns a valid image index; timeline semaphore acquisition signals are rejected.
- QueuePresent rejection leaves the image ACQUIRED and does not consume wait semaphores. An accepted present moves the image to PRESENT_PENDING; request success does not imply GPU completion, image release, or presentation completion.
- QueuePresent reserves each binary wait atomically with acceptance and uses the same one-pending-wait rule as QueueSubmit. Acceptance does not consume the signal; a confirmed backend wait does. If an accepted present fails before wait completion, each semaphore preserves confirmed unconsumed state, records confirmed consumption, or becomes UNTRUSTED if payload outcome is uncertain. UNTRUSTED waits fail with DEPENDENCY_FAILED; incompatible pending waits fail atomically with INVALID_SYNCHRONIZATION_STATE.
- IMAGE_RELEASED and PRESENTATION_COMPLETE are distinct milestones and may arrive in either order. Each accepted present has one internal terminal presentation transition and one internal image-release-or-invalidation transition. PRESENTATION_COMPLETE is enqueued only if Queue mask bit 3 is set at its terminal point and connection/device lifecycle permit delivery. IMAGE_RELEASED is enqueued only if the image is reusable, Queue mask bit 2 is set at its release point, and connection/device lifecycle permit delivery. Masking or suppressed delivery never skips internal cleanup. If the image is invalidated, no IMAGE_RELEASED is enqueued. No new events are enqueued after DestroyDevice for that Device; previously enqueued events remain unaffected. Disconnect suppresses delivery without skipping internal terminal cleanup. An image is reacquirable only after internal release; the event is visible only under its delivery conditions.
- Presentation event race vectors MUST exercise both milestone orders: image release before presentation completion and presentation completion before image release. Change the Queue event mask between the two milestones and verify each event independently samples the mask at its own milestone; no later mask change retroactively adds or removes an already decided event. For every accepted present, assert exactly one internal presentation terminal transition and exactly one image-release-or-invalidation transition, regardless of event masking or delivery suppression.
- Race resize, Window destruction, Device loss, `DestroyDevice`, and client disconnect against each accepted-present terminal milestone. The first serialized terminal outcome wins; later lifecycle signals cannot rewrite it or emit a duplicate event. A terminal failure that invalidates the image MUST NOT emit `IMAGE_RELEASED`; a reusable image may emit it only after backend quiescence. `DestroyDevice` and disconnect suppress new event delivery according to the lifecycle rules but MUST still complete semaphore resolution, terminal state changes, and backend/reference cleanup. Verify delayed backend callbacks carry the original internal identities and cannot enqueue events for a reused Swapchain XID or a different connection.
- Each presentation event's Queue mask is sampled independently at its own terminal milestone (image-release eligibility versus presentation completion); later `SelectEvents` changes cannot retroactively change that event's delivery decision.
- Resize marks the old Swapchain OUT_OF_DATE, prevents new acquire/present acceptance, and allows replacement creation while old work drains. Window destruction marks the Surface SURFACE_LOST; no XID reuse can revive it.
- Destroy the underlying X11 Window while its Surface exists, then reuse the numeric Window XID for a new Window on the same connection. The original Surface remains live but `SURFACE_LOST`; `GetSurfaceCapabilities` must report `SURFACE_LOST`, and `CreateSwapchain`, `AcquireNextImage`, and `QueuePresent` must not resolve the old Surface through the reused Window XID. `CreateSwapchain` must leave its target XID unallocated on this status. The new Window must not inherit the old Surface. `DestroySurface` remains available once no live Swapchain references the Surface; its internal Window identity is retained until all remaining Surface/backend references are quiescent.
- Destroy a `SURFACE_LOST` Surface after its final live Swapchain has been destroyed, while a delayed Window notification or internal backend/tombstone reference is still being retired. `DestroySurface` must succeed because internal retained references are not request-level blockers; it invalidates the public Surface XID atomically, while internal identity references remain until quiescent. Deliver the delayed notification after reusing the Surface XID and verify it cannot affect the new resource or enqueue an event for it. Conversely, if any live Swapchain still references the Surface, `DestroySurface` must fail atomically with `INVALID_SYNCHRONIZATION_STATE` and preserve the public XID and all references.
- Unmap and remap a Window without changing its pixel extent. These transitions alone must not mark its Swapchain `OUT_OF_DATE`, mark the Surface `SURFACE_LOST`, change resource identity, or imply GPU/presentation completion. Separately test resize and destruction so the implementation cannot conflate all X11 lifecycle notifications.
- Accepted-present terminalization is serialized exactly once: resize permits `SUCCESS` only if the accepted operation still reaches its completion point, otherwise `OUT_OF_DATE`; a destroyed Window yields `SURFACE_LOST` for still-pending operations that cannot complete, and Device Loss yields `DEVICE_LOST`. These lifecycle failures invalidate the affected image/Swapchain and do not emit `IMAGE_RELEASED`; a later lifecycle notification cannot overwrite an already serialized terminal result.
- `PRESENTATION_FAILED` emits `IMAGE_RELEASED` only after backend quiescence is established and the image remains reusable in a usable Swapchain; otherwise the image/Swapchain is invalidated. Internal cleanup completes exactly once even when event delivery is suppressed.
- Conformance validation must check presentation event IDs 7 and 8 with total lengths 64 and 64 bytes respectively, and queue event-mask bits 2 and 3 are rejected by compute-only implementations.


## Presentation-profile conformance cases (provisional)

The following cases apply only when the presentation-capable profile is advertised; they do not expand the compute-only baseline:

- `CreateSurface` rejects a bad target XID with `BadIDChoice`, an invalid/non-Window core X11 Window XID with `BadWindow`, and a live Window owned by another X11 client with `BadMatch`; failure allocates no Surface and retains no window reference.
- Mixed-failure `CreateSurface`: after exact-length and scalar validation, an invalid/already occupied `surface_xid` combined with an unknown/destroyed/non-Window `window_xid` returns `BadIDChoice` because the target XID is checked first; an invalid request length combined with either invalid XID returns `BadLength`. Neither rejection allocates a Surface or retains a Window reference.
- Mixed-failure `CreateSwapchain` requests validate scalar fields first, then `device_xid`, target `swapchain_xid`, and `surface_xid` in wire-field order; capability/status checks occur only after XID, type, ownership, and Device-state validation.
- `DestroySurface` is atomically rejected with `INVALID_SYNCHRONIZATION_STATE` while any live Swapchain references it.
- Race `CreateSurface` against destruction of its target Window in both serialized orders. If `CreateSurface` binds before destruction, the resulting Surface becomes `SURFACE_LOST`; if destruction occurs first and the XID remains unbound, it returns `BadWindow`. Separately destroy a Window, create a new Window using the same numeric XID, then issue `CreateSurface`: it may bind to the new Window identity. Verify that no existing Surface bound to the old identity is redirected to the replacement. Preserve same-connection X11 request order in every case.
- Race `DestroySurface` against Window destruction in both serialized orders. Successful Surface destruction invalidates the public Surface XID immediately and a later Window notification must not affect a reused Surface XID; Window destruction first leaves the Surface `SURFACE_LOST` and explicitly destroyable if no live Swapchain references it.
- Attempt `DestroySurface` while a live Swapchain references it and verify `INVALID_SYNCHRONIZATION_STATE` leaves the Surface XID, Surface state, Swapchain, and reference graph unchanged. Repeat after Swapchain destruction and verify Surface destruction can succeed once all other blocking references are gone.
- Disconnect while Surface-associated backend work is pending; invalidate public XIDs and suppress delivery immediately, but retain internal Window/backend identities until quiescent. Delayed notifications/completions must not resolve reused XIDs or enqueue events to another connection.
- `DestroySwapchain` is atomically rejected with `INVALID_SYNCHRONIZATION_STATE` while a recording command buffer, pending acquire, accepted queue work, accepted presentation, or possible backend access still references its images; acquired-but-idle images alone do not block destruction. The resource-lifetime matrix must state the same rule.
- `DestroySwapchain` lifetime boundary vectors MUST distinguish public invalidation from internal release. If any listed blocker exists at the destroy request's serialized validation point, reject atomically and preserve the live XID, image-index validity, command-buffer states, and all reference counts. If no blocker exists, invalidate the Swapchain XID and all image indices atomically; backing storage may be released immediately only if backend quiescence is proven, otherwise retain the exact internal image/Swapchain identity until every backend access is terminal. An acquired-but-idle image alone is not a blocker and must not require a synthetic present/release operation.
- Race `DestroySwapchain` against the final submission completion, presentation terminalization, acquire terminalization, and backend-access retirement. The first serialized state transition determines whether destroy is rejected or succeeds; a completion arriving after successful destroy may release only the old internal identity and MUST NOT resolve the numeric Swapchain XID again. Reuse the Swapchain XID for a new resource before delivering a delayed completion and verify the new resource, its image indices, and its references are unchanged. Check both event orders (completion before destroy validation and destroy validation before completion) and require exactly-once release of every retained image/backend reference.
- `GetSurfaceCapabilities` uses exactly the defined 64-byte fixed reply prefix plus 8 bytes per format/color-space pair, 4 bytes per present mode, and 8 bytes per queue-family support record; `reply.length = 8 + 2 * format_pair_count + present_mode_count + 2 * queue_family_count`. Every physical queue family has exactly one ordered support record. Temporary-not-presentable, surface-lost, and device-lost statuses return zeroed capability fields as specified.
- `CreateSwapchain` validates image count and extent bounds, a reported format/color-space pair, a reported mode, and advertised usage bits against current capabilities. A zero-sized Surface or requested extent outside current supported bounds returns `OUT_OF_DATE`; however, a requested width or height of zero is rejected earlier as `BadValue` during scalar validation. A valid but unsupported configuration returns `UNSUPPORTED_CONFIGURATION`. Success provides the exact requested image count; every non-success reply sets `actual_image_count = 0` and leaves the target Swapchain XID unallocated.
- `AcquireNextImage` timeout, not-ready, out-of-date, surface-lost, device-lost, and device-destroyed results neither signal the supplied semaphore/fence nor change image state. `DestroyDevice` terminates an open acquire with `DEVICE_DESTROYED` without waiting for image availability; an already serialized terminal result wins. Disconnect suppresses the reply but removes the registration and releases registration-only references safely. Destroying the referenced Swapchain or Surface while the acquire is pending remains rejected.
- Keep an acquire pending with an infinite timeout and independently trigger Swapchain resize/zero extent, Window destruction, Device loss, and `DestroyDevice`. Verify each still-open registration terminates promptly with `OUT_OF_DATE`, `SURFACE_LOST`, `DEVICE_LOST`, or `DEVICE_DESTROYED` respectively, without signaling its semaphore/fence or transitioning an image to `ACQUIRED`. Race each lifecycle trigger against timeout expiry and successful acquisition; the first serialized terminal result wins, later notifications cannot rewrite it, and registration-only references are released exactly once. Repeat with disconnect, where reply delivery is suppressed but cleanup still completes.
- `QueuePresent` has total request size `40 + 4 * wait_semaphore_count` and a 36-byte reply with status values 0 `SUCCESS`, 1 `OUT_OF_DATE`, 2 `SURFACE_LOST`, and 3 `DEVICE_LOST` (local to the reply field). Duplicate waits, token zero/reuse, wrong resource types, invalid image state, and non-existent queues follow the specific error mapping; rejection does not consume waits or transition the image.
- A successful `QueuePresent` reply means accepted, not displayed. Image release and presentation completion are separate terminal events and may be observed in either order; each accepted presentation gets at most one of each event.

- Presentation error precedence is tested with mixed-failure requests: malformed length/overflow beats all field checks; invalid scalar syntax (including zero token or duplicate waits, but not reuse of an accepted token) beats XID resolution; XIDs are resolved in wire-field order; live type/ownership errors beat Device and lifecycle outcomes; Device loss beats Surface loss and accepted-token reuse; Surface loss and OUT_OF_DATE beat accepted-token reuse; unsupported queue presentation capability is `BadMatch` before token reuse; accepted-token reuse returns `BadValue` before image-state and semaphore-eligibility checks. The expected winner is the first failing stage. A rejected request causes no partial state mutation attributable to that request; independent lifecycle transitions that race with it are not rolled back.
- `CreateSurface` validates the target create-XID before the Window XID; `CreateSwapchain` validates `device_xid`, target `swapchain_xid`, then `surface_xid` after scalar syntax. Failed creates leave target XIDs unallocated and retain no references.
- `GetSurfaceCapabilities` returns `DEVICE_LOST` rather than `SURFACE_LOST` when both apply; each non-success status has zero capability fields and arrays and a fixed 64-byte reply (`reply.length = 8`).
- `GetSurfaceCapabilities` MUST be queried with the exact requested Device/Surface pair. The same live Surface may be queried with two different owned Devices; each query independently reports that pair's presentation support. A valid Device/Surface pair that cannot present returns `SUCCESS` with `present_supported = 0`, not `BadMatch` merely because the Surface is not Device-owned.
- `GetSurfaceCapabilities` precedence vectors MUST separately combine (a) Device loss with Surface loss, expecting `DEVICE_LOST`; (b) a live zero-extent Surface with a usable Device, expecting `TEMPORARILY_NOT_PRESENTABLE`; and (c) Surface loss with a stale zero-extent snapshot, expecting `SURFACE_LOST`, never `TEMPORARILY_NOT_PRESENTABLE`. The zero-extent status applies only while the Surface is live.
- `GetSurfaceCapabilities` wire-vector tests MUST cover a successful presentable result with nonempty format, mode, and queue-family arrays; a successful but non-presentable Device/Surface pair with `present_supported = 0`; and each status result with every capability field other than `status` zero, all three counts zero, and no trailing payload. For successful replies, `present_supported` MUST equal the logical OR of all queue-family `present_supported` values; every record's support value is exactly 0 or 1, queue-family indices are unique and strictly ascending, and the queue-family record count equals the number of physical queue families. Check that format/color-space pairs and presentation modes are serialized in the same order as their advertised count and that no padding or uncounted bytes appear between or after arrays. For each vector, decode the reply using the connection byte order and verify both `reply.length * 4 + 32` and the actual packet size equal `64 + 8 * format_pair_count + 4 * present_mode_count + 8 * queue_family_count`. Include boundary cases where `format_pair_count` and `present_mode_count` are individually zero where semantically permitted, mixed zero/nonzero format/mode counts, and the largest representable count tuple whose total fits the protocol's reply-length field. Do not use a successful reply with `queue_family_count = 0` as a boundary vector: successful capability replies require at least one queue-family record, while non-success replies require all three counts to be zero; a tuple whose checked wide-arithmetic total exceeds the CARD32 X11 reply-length-field capacity MUST be rejected before allocation/serialization and MUST NOT wrap, truncate, or emit a partial reply. Verify the same checked arithmetic is used before allocation and before writing any record.
- `CreateSwapchain` returns `DEVICE_LOST` before `SURFACE_LOST`, `SURFACE_LOST` before `OUT_OF_DATE`, and `OUT_OF_DATE` before `UNSUPPORTED_CONFIGURATION`. Every non-success reply has `actual_image_count = 0` and leaves the target XID unallocated.
- `CreateSwapchain` extent vectors MUST distinguish a zero-sized current Window extent (`OUT_OF_DATE`) from a requested width or height of zero (`BadValue` during scalar validation). If the Device is lost or the Surface is lost at the serialized status check, those lifecycle statuses win before extent/configuration outcomes as specified. A requested nonzero extent outside current supported bounds returns `OUT_OF_DATE`; a valid in-bounds extent with an unsupported format/mode/usage returns `UNSUPPORTED_CONFIGURATION`.
- `CreateSwapchain` status-vector tests MUST exercise all six defined numeric values (`SUCCESS=0`, `OUT_OF_DATE=1`, `SURFACE_LOST=2`, `DEVICE_LOST=3`, `UNSUPPORTED_CONFIGURATION=4`, `ALLOCATION_FAILED=5`) and confirm that the status namespace is local to this reply. `ALLOCATION_FAILED` is reachable only after XID/ownership, lifecycle, extent, and requested-configuration validation all succeed; it MUST NOT mask `DEVICE_LOST`, `SURFACE_LOST`, `OUT_OF_DATE`, or `UNSUPPORTED_CONFIGURATION`. For each of the five non-success statuses, `actual_image_count` is zero and the target Swapchain XID remains unallocated; for `SUCCESS`, it equals the exact requested count. Inject allocation failure at each allocation point and verify atomic cleanup of partial image/backing allocations and references.
- Mixed-failure `CreateSwapchain` cases verify that a zero requested width/height (`BadValue`) and an invalid target create-XID (`BadIDChoice`) are reported before Device-loss or Surface-lifecycle statuses; after scalar and XID/type/ownership validation succeeds, `DEVICE_LOST` wins over `SURFACE_LOST`, which wins over `OUT_OF_DATE`, which wins over `UNSUPPORTED_CONFIGURATION`. Each failure leaves `swapchain_xid` unallocated and returns `actual_image_count = 0`.
- `CreateSwapchain` stage-boundary vectors MUST distinguish Device-state validation from immutable-identifier validation: after scalar syntax, XID resolution, type, ownership, and cross-device checks, a lost Device returns `DEVICE_LOST` even when the request also contains an unknown format, color-space, or present-mode identifier or unassigned usage bits. With a usable Device, those syntactically invalid identifiers/bits return `BadValue` before Surface lifecycle outcomes; with valid identifiers, `SURFACE_LOST` wins over zero-current-extent or out-of-bounds `OUT_OF_DATE`, which wins over a syntactically valid but unsupported configuration. Keep requested zero width/height in the earlier scalar-validation stage, so it remains `BadValue` even when the Device is lost. Each mixed vector MUST assert the exact winner and that the target XID remains unallocated with `actual_image_count = 0` and no retained Surface, Device, image, or backend references attributable to the rejected request.
- `CreateSwapchain` atomic-publication fault injection MUST cover each resource-acquisition boundary independently: Swapchain host allocation, per-image record allocation, backing-image allocation, backend/window-system resource creation, and acquisition of retained Device/Surface references. For each injected failure, require `ALLOCATION_FAILED`, `actual_image_count = 0`, no visible target XID, no partially enumerable images, no leaked backing/backend objects, and balanced reference counts. Retry the identical request after removing the fault and require success with exactly `image_count` images, proving failed attempts leave no stale reservation. Race each publication boundary against `DestroySurface`, `DestroyDevice`, Window resize, and Window destruction; the serialization/commit point MUST produce either a fully published Swapchain that then observes the independent lifecycle transition, or a wholly rejected create with no request-owned partial state—never a partially visible resource set.
- `AcquireNextImage` lifecycle outcomes precede timeout polling: `DEVICE_LOST`, then `SURFACE_LOST`, then `OUT_OF_DATE`; `NOT_READY` is only the zero-timeout result for a usable Swapchain with no immediately available image, and `TIMEOUT` is only returned when a finite timeout expires. `DEVICE_DESTROYED` applies only to a pending acquire terminalized by `DestroyDevice`, with the first serialized terminal result winning. Every non-success result has zero `image_index` and signals neither optional synchronization object.
- `AcquireNextImage` mixed-failure tests MUST distinguish synchronization-object resolution from synchronization eligibility: an unknown/non-live optional semaphore or fence XID (`BadValue`), or a live wrong-type/foreign/cross-Device object (`BadMatch`), is reported before lifecycle status; after all XIDs, types, and ownership validate, `DEVICE_LOST` beats `SURFACE_LOST`, which beats `OUT_OF_DATE`, and these lifecycle outcomes beat an otherwise valid but ineligible semaphore/fence state and timeout polling. Exercise both optional objects separately and together, with zero, finite, and infinite timeouts. Every rejected vector must leave both synchronization objects unchanged and unsignaled and must not acquire an image; do not let a stale/ineligible sync state mask a higher-priority lifecycle status.
- `AcquireNextImage` reply-vector tests MUST exercise all seven defined numeric status values (`SUCCESS=0`, `TIMEOUT=1`, `NOT_READY=2`, `OUT_OF_DATE=3`, `SURFACE_LOST=4`, `DEVICE_LOST=5`, `DEVICE_DESTROYED=6`) and verify that this status namespace is independent of `CreateSwapchain`, `QueuePresent`, and event statuses. Every reply is exactly 44 bytes with `reply.length = 3` and `reserved = 0`; `image_index` is nonzero only when the actual acquired index is nonzero on `SUCCESS`, and is exactly zero for every non-success result. For each non-success vector, verify neither optional synchronization object is signaled and no image transitions to `ACQUIRED`. Include index zero as a valid successful acquisition so tests do not incorrectly infer success from a nonzero index.
- `QueuePresent` returns `DEVICE_LOST` after valid XIDs/types/ownership but before queue/index validity; once the Device is usable, nonexistent queue-family/index or out-of-range image index is `BadValue`, then `SURFACE_LOST` precedes `OUT_OF_DATE`, and both lifecycle statuses precede image/semaphore state checks.
- `QueuePresent` mixed-failure boundary vectors MUST pin down the exact stage transitions: (a) malformed length or scalar syntax (`BadLength`/`BadValue`) beats every XID or lifecycle failure; (b) valid scalar syntax with an unknown Device/Swapchain/wait-semaphore XID reports `BadValue` before Device status; (c) a live wrong-type, foreign, or cross-Device resource reports `BadMatch` before Device status; (d) for a usable Device, nonexistent queue-family/index or out-of-range `image_index` reports `BadValue` even if the Surface is lost or out of date; (e) after valid queue/index values, `SURFACE_LOST` beats `OUT_OF_DATE`, and both beat accepted-token reuse, non-ACQUIRED image state, and all wait-semaphore state failures; (f) with lifecycle valid, an accepted-token reuse reports `BadValue` before image-state or wait-semaphore eligibility, while a new token plus non-ACQUIRED image reports `INVALID_SYNCHRONIZATION_STATE` before examining wait semaphores. Every vector MUST assert the winning result and verify no request-attributable token reservation, wait reservation/consumption, or image transition on rejection. Keep independent lifecycle invalidation intact.
- After `QueuePresent` lifecycle status checks, image state is validated before wait semaphores; if the image is `ACQUIRED`, wait semaphores are checked in array order. An `UNTRUSTED` wait yields `DEPENDENCY_FAILED`; another incompatible semaphore state or pending wait yields `INVALID_SYNCHRONIZATION_STATE`. Zero token, duplicate wait XIDs, and accepted-token reuse are `BadValue`; tokens from rejected attempts remain reusable. Acceptance atomically reserves the token and all wait slots and changes `ACQUIRED` to `PRESENT_PENDING`; any rejection leaves pre-request image/semaphore states unchanged and does not restore an image invalidated by an independent lifecycle transition.
- A buffer-to-swapchain-image command requires an acquired image at submission acceptance, retains the exact Swapchain/image identity while pending, and prevents backing storage from being freed until the submission and backend accesses are terminal.
- If `QueueSubmit` is accepted before `QueuePresent`, the submission keeps its exact image/Swapchain references and presentation requires the specified GPU semaphore dependency where the submission may access the image; a copy submission processed after the image has transitioned to `PRESENT_PENDING` is atomically rejected with `INVALID_SYNCHRONIZATION_STATE`. Request order alone is not a GPU dependency.
- Destroying a Buffer referenced by a `RECORDING` command buffer is atomically rejected with `INVALID_SYNCHRONIZATION_STATE`; successful Buffer destruction invalidates all non-pending executable command buffers that still reference it.
- The provisional copy entry rejects unknown Buffer/Swapchain XIDs with `BadValue`, wrong live types/ownership/device or incompatible transfer usage with `BadMatch`, malformed dimensions/alignment/out-of-range source spans and invalid image indices with `BadValue`, and a non-`ACQUIRED` image at submission acceptance with `INVALID_SYNCHRONIZATION_STATE`; every rejection is atomic.
- Resize/out-of-date, Window destruction/surface-lost, and device loss prevent new acquire/present operations while preserving safe terminal cleanup of previously accepted work. Accepted present operations reach a terminal status; a non-reusable image is invalidated rather than left PRESENT_PENDING.


## Request framing, maximum length, and BIG-REQUESTS

- XAverius v0.1 rejects BIG-REQUESTS framing: an XAverius request whose original X11 16-bit `length` field is zero is rejected as `BadLength` before offset 4 is interpreted as the XAverius common header.
- A normal request of exactly 262140 bytes is the maximum permitted size; a request that would exceed 262140 bytes is rejected with `BadLength`, even if its variable-length formula and counts are otherwise internally consistent.
- Variable-length request formulas are evaluated with checked arithmetic. Counts that overflow the formula, a computed size above 262140 bytes, a declared-length mismatch, or trailing/truncated payload bytes all produce `BadLength` before payload allocation, XID lookup, or state mutation.
- Chunked `WriteBuffer`, `ShaderModuleData`, and `CommandBufferData` requests enforce the limit per wire request. The aggregate logical upload/recording may exceed the limit only by using multiple valid chunks; a single oversized chunk is rejected. For `CommandBufferData`, verify the exact maximum framing boundary: `entry_length = 65531` words plus the 16-byte fixed request header yields exactly 262140 bytes and passes the request-length phase; subsequent entry-specific semantic checks still apply. `entry_length = 65532` cannot fit and is rejected with `BadLength` before entry semantics or XID lookup. Also verify that multiple individually valid entries whose aggregate exceeds 65531 words are rejected atomically with `BadLength`.
- For each rejection above, no partial resource creation, upload commit, command-buffer append/finalization, queue-submission acceptance, or event-mask change occurs.

- Fehlerpräzedenz für mehrteilige Requests: Bei `BindBufferMemory` schlägt ein unbekanntes XID (`BadValue`) einen Device-Loss-Fehler; falscher live Typ/fremde Ownership (`BadMatch`) schlägt Device Loss; nach gültigen XIDs und Ownership schlägt `DEVICE_LOST` einen bereits gebundenen Buffer oder inkompatiblen Memory-Type. For `UpdateDescriptorSets`, length/field syntax and unknown XIDs take precedence over Device/state errors; after XID/type/ownership validation, `DEVICE_LOST` takes precedence over layout/binding incompatibility and a pending-set conflict. All rejected requests remain atomic and change no binding, descriptor slots, or internal references.

- Fehlerpräzedenz für Create-/Batch-Requests: `AllocateDescriptorSets` prüft zuerst Länge und Feldsyntax, dann Ziel-Set-XIDs in Array-Reihenfolge (`BadIDChoice`), dann Device-/Pool-/Layout-Eingabe-XIDs in Wire-Reihenfolge (`BadValue`), danach Typ/Ownership (`BadMatch`) und Device-Zustand (`DEVICE_LOST`/`DEVICE_UNAVAILABLE`) vor Pool-Kapazität und Backend-Allokation. `CreatePipelineLayout` und `CreateComputePipeline` prüfen Feldsyntax vor Ziel-XID, Ziel-XID vor Eingabe-XIDs, dann Typ/Ownership und Device-Zustand vor geräteabhängigen Kompatibilitäts- bzw. Backend-Prüfungen. Jeder Fehler lässt alle Ziel-XIDs unangelegt.

- `ResetFence`-Fehlerpräzedenz: falsche Länge schlägt alle weiteren Prüfungen; unbekannte Device-/Fence-XIDs ergeben `BadValue`, falscher live Typ/Ownership/Cross-Device `BadMatch`; nach gültigen XIDs und Ownership gewinnt `DEVICE_LOST` vor `INVALID_SYNCHRONIZATION_STATE` für einen nicht zurücksetzbaren Fence-Zustand. Jede Ablehnung erhält den gespeicherten Fence-Zustand.


## Presentation request wire-layout audit (assigned, profile-gated ABI)

The request/reply framing matrix is cross-checked against [the presentation chapter](presentation.md#cross-request-wire-length-audit). Request sizes include the 8-byte X11/XAverius header; reply sizes include the 32-byte X11 reply header.

| Request | Request bytes | Normal reply bytes | Reply length field |
|---|---:|---:|---:|
| CreateSurface | 16 | none | — |
| DestroySurface | 12 | none | — |
| GetSurfaceCapabilities | 16 | 64 + variable records | 8 + 2×format_pair_count + present_mode_count + 2×queue_family_count |
| CreateSwapchain | 48 | 40 | 2 |
| DestroySwapchain | 12 | none | — |
| AcquireNextImage | 32 | 44 | 3 |
| QueuePresent | 40 + 4×wait_semaphore_count | 36 | 1 |

Conformance tests MUST verify every fixed request at exact length and at one four-byte unit shorter/longer, plus QueuePresent count/length mismatch and arithmetic overflow. Reply tests verify the X11 reply length field against the actual serialized byte count, zero reserved fields, and status-dependent fields. In particular, GetSurfaceCapabilities has a 64-byte minimum reply; each variable record contributes exactly the bytes specified in presentation.md. CreateSwapchain has a 48-byte request but a 40-byte reply; these lengths must not be conflated. AcquireNextImage's request is 32 bytes and its reply is 44 bytes. QueuePresent's request length varies with the semaphore count, but its reply is always 36 bytes.

For each request, mixed-failure tests verify framing before scalar syntax, scalar syntax before XID resolution, XID/type/ownership checks before lifecycle and mutable-state checks, and atomic rejection. CreateSurface and CreateSwapchain tests verify target-XID validation order and that failed creation leaves the target XID unallocated. QueuePresent tests verify that rejection neither consumes waits nor reserves the token nor transitions the image, while an accepted request commits token, wait reservations, references, and image transition together. Accepted asynchronous failure must produce one terminal presentation outcome and no delayed X11 request error. The mixed-failure matrix MUST specifically combine (a) Device loss with an invalid queue tuple or image index, (b) a nonexistent queue/index with Surface loss or OUT_OF_DATE, (c) Surface loss with OUT_OF_DATE, (d) a valid queue tuple without presentation support with a reused accepted token, and (e) a reused accepted token with an invalid image state or ineligible wait semaphore. Expected precedence is respectively DEVICE_LOST; BadValue for queue/index; SURFACE_LOST; BadMatch for missing presentation support; and BadValue for token reuse. In each case, also verify that no request-attributable token reservation, wait reservation/consumption, or image transition occurs. Repeat cases with malformed length, zero token, duplicate wait XIDs, and unresolved wait XIDs to confirm the earlier framing/scalar/XID stages take precedence.

Presentation lifecycle race tests MUST also cover the following serialized outcomes, not merely the request/reply bytes:

- Race `QueuePresent` acceptance against Surface loss, Swapchain resize/out-of-date, and Device loss. If the lifecycle transition is serialized before acceptance, return the specified normal status without reserving the token or wait slots; if acceptance is serialized first, preserve the accepted operation and terminalize it exactly once according to the first serialized terminal outcome.
- Race image release and presentation completion in both orders. Each accepted token may produce at most one `IMAGE_RELEASED` and at most one `PRESENTATION_COMPLETE`; masking either event must not skip its underlying state transition or resource cleanup. When `PRESENTATION_COMPLETE` is masked or delivery is suppressed, verify that terminal state and the corresponding safe-release or invalidation transition are still applied: success may leave a reusable image, while a failure that prevents reuse must invalidate the image and Swapchain. Do not require a later request to reproduce the exact terminal cause.
- Model both callback orders explicitly: (a) image release before terminal completion makes the image reusable once, and the later terminal callback must not release it again; (b) terminal SUCCESS before image release leaves the image `PRESENT_PENDING` until backend access ends. Insert resize/zero extent, Surface loss, and Device loss between those milestones: preserve an already committed terminal SUCCESS, invalidate the image/Swapchain, and omit `IMAGE_RELEASED`. A duplicate release callback is mutation-free. For `PRESENTATION_FAILED`, test both proven-safe release and uncertain/unsafe release; only the former may return the image to `AVAILABLE`.
- Fail a backend wait before it consumes a signal, after confirmed consumption, and with an uncertain consumption result. Verify semaphore state is respectively preserved, updated, or marked `UNTRUSTED` as specified, and ensure the image is released only if reuse is safe; otherwise invalidate the image/Swapchain rather than leaving `PRESENT_PENDING` indefinitely.
- Reuse a token after a rejected status reply and after a synchronous validation error (both permitted), then reuse it after an accepted presentation (must fail with `BadValue`). Verify that a status reply does not hide higher-priority malformed-wire, scalar, XID, Device, queue/index, or lifecycle errors.
- Destroy the Swapchain after an acquired-but-idle image, after accepted presentation work, and while backend access is possible. The first case may succeed once GPU references are drained; the latter cases must reject atomically until all relevant references and accesses are terminal.

- Disconnect after QueuePresent acceptance but before either callback: detach event delivery and connection-owned semaphore-owner links immediately, but retain the accepted presentation record, wait reservations, image backing, and backend-access hold until their owning callbacks retire them. A late terminal or release callback may perform internal cleanup but MUST NOT enqueue an event to the disconnected connection.
- Race disconnect with terminal SUCCESS, terminal DEVICE_LOST, and image release in both callback orders. The first terminal result remains immutable; Device Loss invalidates the image even if SUCCESS was already terminal, and release after loss only drains backend access without making the image reusable. A duplicate or stale callback is mutation-free.
- Race DestroySwapchain against an accepted QueuePresent and each callback milestone. Destruction MUST reject atomically while terminalization or backend image release remains outstanding. It may succeed only after both milestones have drained; successful destruction invalidates the image. Delayed duplicate callbacks after destruction MUST NOT resolve a reused XID or alter a new Swapchain generation.
- **Swapchain XID and presentation-token reuse:** accept token T in generation G, complete both terminal and image-release milestones, destroy the Swapchain, then create a new Swapchain using the same XID and accept the same token T in generation G+1. Deliver delayed terminal and image-release callbacks carrying G. Each MUST be rejected without mutation of the G+1 image, token, terminal/release records, or events. Then deliver the valid G+1 callbacks and verify normal completion.
- **Old-generation Device Loss:** after reusing a Swapchain XID, deliver a delayed DEVICE_LOST terminal callback from the retired generation while a presentation is pending in the new generation. It MUST NOT mark the new Device lost, invalidate its image, quarantine its semaphores, or replace its terminal result. A Device Loss genuinely serialized for the live generation still follows the normal device-wide propagation rules.
- **Stale wait callback after XID reuse:** accept a presentation with a binary wait in generation G, drain its terminal/release/wait holds, destroy and recreate the Swapchain with the same XID, and reuse the presentation token and semaphore where legal. A delayed wait callback from G MUST NOT release the new generation's reservation, consume its payload, or rewrite its local/canonical semaphore state.
- **Callback-generation mismatch atomicity:** for terminal, image-release, and wait callbacks, snapshot all new-generation state and inject callbacks with an older, newer, zero, and otherwise unknown generation. Every mismatch MUST be mutation-free, including no event enqueue and no backend-reference decrement. Exact-generation callbacks remain one-shot; duplicate callbacks are also mutation-free.

- Repeat the disconnect/device-loss/resource-destroy permutations with shared binary wait semaphores. Disconnect MUST NOT steal a callback-owned wait reservation; Device Loss may quarantine the canonical semaphore state, and the late wait callback may retire only its exact reservation without restoring a trusted payload or releasing it twice.

These are state-machine conformance tests; golden-wire tests alone cannot establish them.


- Keep QueuePresent reply status values separate from presentation-event terminal status values: the 36-byte QueuePresent reply uses only SUCCESS=0, OUT_OF_DATE=1, SURFACE_LOST=2, DEVICE_LOST=3; the 64-byte PRESENTATION_COMPLETE event additionally permits PRESENTATION_FAILED=4. A synchronously rejected QueuePresent must not emit either presentation event or reserve its token. Once accepted, later backend failure is reported only through the single terminal event/state transition, never as a delayed X11 error or by rewriting the original SUCCESS reply.
- Change the Queue mask between image-release eligibility and presentation completion, testing both orders: IMAGE_RELEASED delivery uses the mask sampled at the release milestone, and PRESENTATION_COMPLETE delivery uses the mask sampled at its terminal milestone. Changing a mask after one milestone must not retroactively suppress or create that milestone's event; suppressing delivery must still apply the corresponding internal state transition.
- At each terminal status (SUCCESS, OUT_OF_DATE, SURFACE_LOST, DEVICE_LOST, PRESENTATION_FAILED), verify the image's internal state and Swapchain usability agree with the status contract. In particular, an invalidated image never emits IMAGE_RELEASED; a safely reusable image is released at most once; late backend callbacks and later lifecycle notifications cannot emit a second terminal event or overwrite the first serialized terminal status.

- Exercise lifecycle transitions at each boundary around both presentation milestones: (a) resize/zero extent before QueuePresent acceptance, (b) resize after acceptance but before terminal completion, (c) resize after successful terminal completion but before backend image release, (d) Window destruction at each of those points, and (e) Device loss at each point. Before acceptance, require the defined status reply and no token/wait reservation. After acceptance, require exactly one terminal status based on the first serialized terminal outcome; a later lifecycle change must not rewrite it. If resize or loss makes the image non-reusable before the release milestone, invalidate it and omit IMAGE_RELEASED even when PRESENTATION_COMPLETE(SUCCESS) was already emitted.
- For each lifecycle case above, repeat with Queue mask bits 2 and 3 independently enabled, disabled, and changed between the two milestones. Event suppression must affect only wire delivery: it must not defer OUT_OF_DATE/SURFACE_LOST/DEVICE_LOST state changes, backend-reference release, or terminalization. No event may be created after successful DestroyDevice processing; events already queued before that point remain in the X11 output stream.
- Verify the old Swapchain replacement path after resize and zero extent: new AcquireNextImage/QueuePresent requests against the old Swapchain return OUT_OF_DATE without consuming waits or reserving tokens; a replacement Swapchain may be created only from current successful capabilities; DestroySwapchain remains blocked while accepted work or backend access holds references, but becomes legal once those references drain, even if an image remains acquired-but-idle or has been invalidated by lifecycle loss.
- Verify replacement creation does not implicitly destroy or transfer ownership from the old Swapchain: while the old Swapchain is `OUT_OF_DATE`, create a second Swapchain against the same live Surface using current capabilities, then retire the old one only when its explicit destroy blockers have drained. An acquired-but-idle image is invalidated by successful `DestroySwapchain` and does not require a present/release operation; image backing storage must nevertheless remain retained for any independent backend access.
- Race `CreateSwapchain` against `DestroySurface` and `DestroyDevice` at the commit boundary: if creation commits first, verify the live Surface reference makes `DestroySurface` fail atomically or that the subsequent Device cascade invalidates the child; if destruction commits first, verify creation cannot publish a Swapchain referencing the invalidated Surface/Device. In every ordering, public XIDs and internal references change exactly once. Specifically distinguish successful `DestroyDevice` before XID resolution (`BadValue` for the now non-live Device XID) from Device loss without destruction before state validation (`DEVICE_LOST`); both leave the target Swapchain XID unallocated.
- Race `CreateSwapchain` against Window resize, zero extent, Window destruction, and Device loss at the creation commit boundary. If the lifecycle transition serializes first, require the corresponding status (`DEVICE_LOST` before `SURFACE_LOST` before `OUT_OF_DATE`), an unallocated target XID, and no retained image/backend references. If creation commits first, require `SUCCESS` and then immediate lifecycle invalidation of the published Swapchain when the later transition is serialized; the create status must not be rewritten even if its reply is still queued. Inject allocation failure before commit and verify `ALLOCATION_FAILED` leaves no public XID, partial Swapchain, image, or retained request-owned reference. Repeat with stale capabilities from before the resize and require validation against the extent current at the commit point.

## `CreateDevice` mixed-failure and atomicity tests

The `CreateDevice` validation order in [the error mapping](errors.md) is normative. Conformance tests MUST exercise at least these mixed-failure pairs and assert that the earlier stage wins:

- Malformed total length plus an invalid or occupied `device_xid` → `BadLength`.
- A scalar/reserved-field or duplicate-record error plus an invalid or occupied `device_xid` → `BadValue`.
- Invalid or occupied `device_xid` plus unknown `physical_device_xid` → `BadIDChoice`.
- Unknown `physical_device_xid` plus missing XGE 1.0 negotiation → `BadValue`.
- Valid XIDs but missing XGE 1.0 negotiation plus an unsupported queue request or unsupported feature → `BadMatch` from the missing handshake.
- An unavailable Physical Device plus a well-formed but unsupported queue/feature/extension request → `DEVICE_UNAVAILABLE`.
- An unknown feature ID plus a registered-but-unsupported feature on the same request → `BadValue` for the unknown ID, because feature IDs are checked in wire-array order after earlier validation stages.
- A syntactically invalid extension name plus a syntactically valid but unsupported extension → `BadValue` for the invalid name, with extension records checked in wire-array order.

For every rejection, verify that `device_xid` remains unallocated, no logical Device or Queue is published, and no requested feature or extension is partially enabled. A corrected retry using the same target XID must succeed when all conditions are subsequently valid. The v0.1 feature and device-extension registries are empty: every feature ID is therefore currently unknown (`BadValue`), while every syntactically valid extension name is currently unknown (`BadMatch`); tests for registered-but-unsupported entries are forward-compatibility tests against a test registry fixture, not ordinary v0.1 registry data.



- A server without the presentation-capable profile rejects requests 41–47 with core X11 `BadRequest` before parsing presentation payloads or resolving their XIDs; no normal reply or state change follows. A server advertising the profile handles each request according to its assigned request-specific contract.



### Descriptor-set release mixed-failure vectors

The following combinations MUST be issued as individual requests and checked against the ordered phases in [Errors](errors.md#normative-descriptor-set-release-validation-precedence):

- `DestroyDescriptorPool`: a truncated or oversized request combined with an unknown Device/Pool XID and a child lifetime blocker returns `BadLength`.
- `DestroyDescriptorPool`: an unknown Device or Pool XID combined with a live wrong-type/foreign-owned resource or a child blocker returns `BadValue`; a live wrong type or foreign ownership combined with a child blocker returns `BadMatch`.
- `DestroyDescriptorPool`: a child Set pending or referenced by a `RECORDING` command buffer returns `INVALID_SYNCHRONIZATION_STATE`; verify the Pool, every child Set, capacity accounting, command-buffer states, and all references remain unchanged. Device Loss alone does not reject destruction; after terminalization, destruction succeeds if no recording reference remains.
- `FreeDescriptorSets`: malformed count-derived length combined with zero count, duplicate Set XIDs, unknown XIDs, and a pending Set returns `BadLength`.
- `FreeDescriptorSets`: zero count, nonzero reserved/scalar fields, or duplicate Set XIDs combined with unknown Device/Pool/Set XIDs and a lifetime blocker returns `BadValue`.
- `FreeDescriptorSets`: an unknown Device/Pool/Set XID combined with wrong ownership or a pending/recording blocker returns `BadValue`; a live wrong type, foreign ownership, or Set-to-Pool/Device association mismatch combined with a lifetime blocker returns `BadMatch`.
- `FreeDescriptorSets`: place the only unknown Set, wrong-Pool Set, pending Set, and recording-referenced Set in the final array position in separate vectors. Require the corresponding earlier-phase error and verify no earlier Set is freed.
- `FreeDescriptorSets`: Device Loss after valid XID/type/ownership resolution does not block logical freeing. Verify no Vulkan operation is attempted and internal references survive until backend quiescence.
- For both requests, verify successful cleanup invalidates all intended public XIDs exactly once, and a repeated destroy/free using the old XID returns `BadValue` without changing any newer resource that reuses the numeric XID.


### `UpdateDescriptorSets` mixed-failure and rollback vectors

Each vector is one request. Assert the exact winning error and compare every affected Set slot, Buffer reference edge, and reference count before and after rejection.

- Malformed/truncated/oversized total length or `write_count` mismatch combined with zero count, nonzero reserved fields, duplicate slots, unknown XIDs, and pending use returns `BadLength`.
- Valid framing with zero `write_count`, either nonzero reserved field, unassigned/zero descriptor type, invalid typeless values, or duplicate (Set, binding, array-element) slots combined with unknown XIDs and Device Loss returns `BadValue`.
- Valid framing/scalars with an unknown Device XID and later unknown Set/Buffer XIDs returns `BadValue` for the Device first; with a valid Device, place unknown Set and Buffer XIDs in later writes and verify first invalid XID in wire order wins.
- With all XIDs known, a live wrong resource type, foreign client ownership, cross-Device Set/Buffer, or Set not belonging to the Device returns `BadMatch` before Device Loss or later compatibility/pending failures.
- With valid XIDs/types/ownership, Device Loss combined with an invalid binding, array element, descriptor-type/layout mismatch, unbound Buffer, missing usage, bad alignment/range, or a pending Set returns `DEVICE_LOST`.
- With a live Device, test each compatibility failure independently: nonexistent binding, out-of-range array element, descriptor type incompatible with the binding, unbound Buffer, missing required usage, zero/overflowing/out-of-bounds range, invalid alignment, and exceeded device limit. Each returns `BadMatch` before pending-state inspection.
- With all writes compatible, a Set used by already accepted work returns `INVALID_SYNCHRONIZATION_STATE`. Put the pending Set in the final write after earlier valid writes and verify no earlier slot changes.
- Include multiple distinct slots in one Set and across multiple Sets (valid); duplicate the same slot with identical data and with conflicting Buffer/range data (both `BadValue`).
- Inject failure while preparing/retaining a replacement Buffer reference after at least one earlier replacement has been prepared. Require all newly prepared references to be released, all old slots and references to remain unchanged, and no transient zero-reference interval for an old Buffer.
- On success, assert all slot contents and new Buffer reference edges become visible together; old Buffer references are released only after the atomic swap. Non-pending `EXECUTABLE` command buffers remain executable and observe the new contents on subsequent submission.
- After each rejected request, retry with a corrected final write and verify it succeeds, proving that rollback did not poison slots, reference counts, or Set state.

## Remaining request error-path negative tests

The following negative cases are mandatory in addition to the wire-vector checks. They target lifecycle and cross-resource paths where a syntactically valid request can still be rejected. For each rejected operation, verify the stated error and that public XIDs, bindings, pool membership, descriptor contents, semaphore/fence state, and retained references are unchanged unless the contract explicitly says otherwise.

- **`FreeMemory` after Buffer-XID invalidation:** keep a Buffer internally alive because a recording or accepted operation retains it, invalidate its public XID through the applicable lifecycle path, then attempt to free its bound allocation. Require `BadMatch` while any internally live Buffer remains bound; after the final Buffer reference drains and the Buffer is actually destroyed, retrying `FreeMemory` may succeed. Separately, if accepted GPU work still accesses the allocation, require `INVALID_SYNCHRONIZATION_STATE` and no partial free.
- **`BindBufferMemory` mixed failures:** combine a malformed request with invalid XIDs (`BadLength` wins); combine a bad reserved/value field with invalid XIDs (`BadValue` wins); then combine a live wrong-type Buffer/Memory resource with an unavailable Device and require `BadMatch` from type/ownership validation before Device state. With valid resources but a lost Device, require `DEVICE_LOST` before already-bound, alignment, memory-type, or allocation-range checks. Every rejection leaves the Buffer unbound.
- **`DestroyResource` lifetime failures:** separately test an unknown XID (`BadValue`), a live Fence/Semaphore passed to the generic destroy (`BadMatch`), and an otherwise eligible resource referenced by a `RECORDING` command buffer or forbidden pending work (`INVALID_SYNCHRONIZATION_STATE`). Confirm the failed destroy leaves the XID live and recording references intact; a corrected destroy after the blocker is removed succeeds exactly once.
- **`FreeDescriptorSets` atomicity and precedence:** use a multi-set request where a later Set belongs to another Pool, then where a selected Set is pending or referenced by a recording command buffer. Require `BadMatch` for the wrong Pool and `INVALID_SYNCHRONIZATION_STATE` for the lifetime blocker, with no earlier Set freed. Also test malformed length before all XID errors and unknown/non-live XIDs before ownership checks.
- **`DestroyDescriptorPool` child blockers:** create a Pool with multiple Sets and arrange for one child Set to be pending or referenced while others are idle. Require `INVALID_SYNCHRONIZATION_STATE` and verify the Pool, all child Sets, and all Pool capacity accounting remain unchanged. After the blocker is removed, successful destruction invalidates the Pool and its children atomically.
- **`ResetFence`/`DestroyFence` synchronization states:** reset an unsignaled Fence and destroy a Fence tied to non-terminal work or an open host wait. Require `INVALID_SYNCHRONIZATION_STATE`; neither operation may change the Fence state or detach the pending identity. Repeat after the wait's terminal result has been serialized to verify the documented boundary: an unsent reply alone does not keep destruction blocked.

These are contract-level negative tests for a future implementation, not claims that a live XAverius server currently executes them. Static CI should at least ensure every case remains documented alongside the central error mapping.


## Discovery, allocation, and transfer rejection matrix

The request register and the request-specific error map define the expected result for each case below. These tests cover remaining non-presentation error paths not represented by the reply golden vectors alone. Run each mixed-failure pair with valid framing in both byte orders where the request has a multi-byte wire payload. For every rejected create/allocation/bind/update, verify that the target XID and all affected object state remain unchanged.

- **`EnumeratePhysicalDevices`:** exercise zero, one, and multiple Physical Device records; reject a truncated fixed record, a name length that runs past the reply, nonzero reserved bytes, invalid UTF-8, embedded NUL, and nonzero name padding. Zero devices is a successful empty reply, not an error.
- **`GetPhysicalDeviceProperty`:** apply the normative order: exact request length (`BadLength`), Physical-Device XID resolution (`BadValue` if unknown/non-live), live resource type (`BadMatch` if not a Physical Device), Atom validation (`BadAtom`), then registry lookup (`NOT_SUPPORTED`) and per-device availability (`NOT_AVAILABLE`). Exercise mixed failures explicitly: malformed length + invalid Atom → `BadLength`; unknown Device + invalid Atom → `BadValue`; live non-Physical-Device XID + invalid Atom → `BadMatch`; valid Physical Device + invalid Atom → `BadAtom`. A valid but unregistered Atom name returns `NOT_SUPPORTED`; a registered property unavailable on that device returns `NOT_AVAILABLE`. For both non-success statuses require zero `property_type`, `value_length`, and payload.
- **`GetPhysicalDeviceQueueFamilyProperties` / `GetPhysicalDeviceMemoryProperties`:** both use exact 12-byte framing (`BadLength`), then Physical-Device XID resolution (`BadValue`), then live resource-type validation (`BadMatch`); they return immutable server-stored metadata and do not check logical-Device availability or call the backend. Exercise these mixed failures independently for both requests: malformed length + unknown XID + wrong-type live XID → `BadLength`; valid length + unknown XID + wrong-type condition → `BadValue`; valid length + live non-Physical-Device XID → `BadMatch`. Also test a still-live Physical-Device XID marked removed/failed: both queries must return the same stored metadata snapshot, while a subsequent `CreateDevice`/`AllocateMemory` must apply its own current-availability rules.
- On `GetPhysicalDeviceQueueFamilyProperties` replies, reject non-multiple 12-byte record payload lengths, nonzero reserved fields, and invalid/reserved queue-flag bits; on `GetPhysicalDeviceMemoryProperties` replies, reject nonzero reserved fields, invalid flag bits, out-of-range heap indices, counts above 32 memory types/16 heaps, and records inconsistent with declared counts. Verify exact reply lengths and checked count arithmetic.
- **`CreateDefaultDevice`:** malformed length wins over all other errors; zero queue count, invalid priority, and nonzero reserved field yield `BadValue` before target-XID checks; invalid/occupied target XID yields `BadIDChoice`; no suitable device yields `DEVICE_UNAVAILABLE`. Every failure leaves the target XID unallocated and publishes no Queue; success is a Void request and emits no normal reply.
- **`CreateBuffer` / `AllocateMemory`:** combine malformed length with invalid target XID (`BadLength` wins), invalid scalar/reserved values with invalid target XID (`BadValue` wins), and invalid target XID with unknown Device XID (`BadIDChoice` wins). Then test unknown Device (`BadValue`), live wrong type/foreign ownership (`BadMatch`), unavailable/lost Device (`DEVICE_UNAVAILABLE` / `DEVICE_LOST`), and injected backend allocation failure (`ALLOCATION_FAILED`). All failures leave the target XID unallocated.
- **`GetBufferMemoryRequirements`:** malformed length wins over XID errors; unknown Device or Buffer yields `BadValue`; live wrong type, foreign ownership, or cross-device Buffer yields `BadMatch`. Successful requirements must have positive size/alignment and at least one compatible memory-type bit; no successful reply may contain zero size/alignment. Because the query returns immutable metadata and performs no backend work, a still-live Device/Buffer pair remains queryable after Device Loss and returns the same requirements snapshot; this must not be confused with `AllocateMemory`, which must reject an unavailable/lost Device.
- **`ReadBuffer`:** malformed length wins first, then zero data length/reserved-field errors (`BadValue`), then XID/type/ownership and range/usage validation (`BadValue` for unknown XIDs, `BadMatch` for incompatible live resources). Device Loss must prevent a successful data reply. Inject transfer and staging-allocation failures and require `TRANSFER_FAILED` / `ALLOCATION_FAILED`; an identified dependency cycle before snapshot capture yields `DEPENDENCY_FAILED`. No failed read may return a success payload.
- **`BindBufferMemory` / `UpdateDescriptorSets`:** mix Device Loss with a later bind-compatibility or descriptor-layout/pending-state failure and require `DEVICE_LOST` after XID/type/ownership checks. With a live Device, a write touching a Set used by accepted work must yield `INVALID_SYNCHRONIZATION_STATE`. For multi-write descriptor updates, make a later write invalid after an earlier write would be valid; reject the entire request and preserve every old slot and indirect resource reference.

These checks distinguish reply-format validation from server-side request rejection: reply golden vectors do not prove that the server chooses the correct X11 error/status or preserves state on rejection.


### `WriteBuffer` mixed-failure precedence

The normative validation order in [Memory and Buffers](memory-buffers.md#57-writebuffer) MUST be tested with mixed failures, not only one invalid field at a time:

- A truncated or oversized request combined with zero `data_length`, nonzero payload padding, and unknown XIDs returns `BadLength`.
- A correctly framed request with zero `data_length` or nonzero padding combined with unknown Device/Buffer XIDs returns `BadValue` before any XID lookup.
- A syntactically valid request with unknown Device XID and a Buffer XID that is unknown or has the wrong live type returns `BadValue` for the Device XID first.
- A valid Device XID followed by an unknown Buffer XID returns `BadValue`; a live wrong-type or cross-Device Buffer returns `BadMatch` before Device-state checks.
- With valid XIDs and ownership, `DEVICE_LOST` takes precedence over an unbound Buffer, missing `TRANSFER_DST`, or out-of-range destination.
- Binding/usage/range errors return `BadMatch` before any dependency wait, staging allocation, or transfer attempt. Injected dependency, staging-allocation, and transfer failures must not produce a successful reply or claim that the destination was updated.
- Every synchronous rejection leaves destination bytes and transfer/wait reservations unchanged by the rejected request; earlier independent GPU work may still complete normally.



### Query and reply error/status boundary vectors

These vectors distinguish X11 request errors from normal reply statuses and ensure that state-only queries retain their specified behavior after Device Loss:

- `GetSemaphoreCounterValue`: after valid XID/type/ownership resolution, established Device Loss emits exactly one X11 `DEVICE_LOST` error and no normal reply; a Binary semaphore combined with Device Loss still yields that error, while a Binary semaphore on an available Device yields `BadMatch`. This matches the request chapter's lack of a reply status field.
- `GetBufferMemoryRequirements`: with valid live Device and Buffer XIDs, Device Loss does not block the metadata-only query; the exact stored `size`, `alignment`, and `memory_type_bits` are returned unchanged. Unknown XIDs and wrong live types retain their earlier `BadValue`/`BadMatch` outcomes even after Device Loss. No backend call is made.
- `GetFenceStatus`: after Device Loss, return the atomically stored Fence state in reply byte 1; do not substitute a `DEVICE_LOST` error or alter a Fence that was never submitted.
- `GetPhysicalDeviceQueueFamilyProperties` and `GetPhysicalDeviceMemoryProperties`: a still-live Physical-Device XID marked removed/failed continues to return its stored metadata; an unknown XID remains `BadValue`, and a live wrong type remains `BadMatch`.
- `EnumeratePhysicalDevices`: serialize only complete records; checked arithmetic must reject any record-size or aggregate-reply overflow before emission. A zero-device result is a valid empty reply, but a truncated record is never reinterpreted as zero devices.

## Synchronization request rejection matrix

The following negative cases are required in addition to the positive wait/signal vectors above. Each case is repeated with both connection byte orders where its wire fields differ by byte order; an X11 error replaces the reply, while normal wait outcomes remain reply statuses.

- **`CreateSemaphore` / `CreateFence`:** combine malformed length with a colliding target XID and require `BadLength`; with valid length, a target collision yields `BadIDChoice` before Device lookup. Invalid enum/flags/reserved values yield `BadValue`; backend allocation failure yields `ALLOCATION_FAILED`. Every rejection leaves the target XID unallocated.
- **`SignalSemaphore`:** combine a Binary semaphore with Device Loss and require `DEVICE_LOST` to win after valid XID/type/ownership resolution; with a live Device, an invalid Binary signal yields `BadMatch`. A Timeline signal that crosses a pending GPU-signal reservation yields `INVALID_SYNCHRONIZATION_STATE`. In every rejected case, the observed counter and all reservations remain unchanged.
- **`WaitSemaphores` status races:** race an already-satisfied WAIT_ANY/WAIT_ALL condition against timeout expiry, Device Loss, and `DestroyDevice`; serialize each terminal transition and require exactly one result. A condition committed first remains `SUCCESS`; timeout committed first remains `TIMEOUT`; Device Loss committed first is exactly one X11 `DEVICE_LOST` error (no normal reply); `DestroyDevice` committed while still open is exactly one X11 `DEVICE_DESTROYED` error unless Device Loss already won. Late signal/wake callbacks after timeout, loss, destroy, or disconnect must not emit another reply/error or release the wait reference twice.
- **`WaitForFence` status races:** with a nonzero timeout, race initial Fence-state snapshot against completion/failure callbacks and prove completion is either observed before registration or terminalizes the installed registration. Race `SIGNALED` and `FAILED` transitions independently against timeout; whichever terminal transition is committed first determines exactly one normal reply (`SUCCESS`, `EXECUTION_FAILED`, or `TIMEOUT`), and late callbacks cannot rewrite it. Race Device Loss and `DestroyDevice` against each other and against Fence completion/timeout: already-established Device Loss at initial check returns `DEVICE_LOST` even for `FAILED`; for an open wait the first committed terminal transition wins, with `DEVICE_DESTROYED` only if processed while still open and Device Loss has not already won. Repeat with zero, finite, and infinite timeout; zero timeout installs no registration. Assert no X11 error for any `WaitForFence` outcome, no state mutation by timeout, and exactly-once cancellation/reference release after disconnect.
- **`WaitSemaphores`:** test count zero and duplicate Semaphore XIDs (`BadValue`), count/length mismatch (`BadLength`), unknown later array XID (`BadValue`), wrong live type/ownership (`BadMatch`), and Device Loss combined with a Binary semaphore (`DEVICE_LOST` after valid ownership). No synchronous rejection may install a wait registration or retain a wait-only resource reference. Race the initial condition check against a host `SignalSemaphore` and a completed `QueueSubmit` signal: the signal must either be seen by the initial check or cause reevaluation after registration, never be lost between check and registration. For `timeout_ns = 0`, assert one serialized check and no registration. Race cancellation/disconnect and terminalization against late wake callbacks; exactly one terminal result is allowed, and a callback after cancellation or terminalization must not send a second reply or retain/release a wait reference twice.
- **`WaitForFence`:** combine malformed length with unknown XIDs and require `BadLength`; test unknown XIDs (`BadValue`) and wrong live type/ownership (`BadMatch`). Assert the precedence order: exact length, Device then Fence XID resolution, type/ownership/device association, then wait outcome. A zero timeout returns the already-terminal Fence result or `TIMEOUT` without changing Fence state. Device Loss returns normal reply status `DEVICE_LOST` even when the stored Fence state is `FAILED`; if `DestroyDevice` races an open wait, the first committed terminal transition wins: `DEVICE_LOST` only if already committed, otherwise `DEVICE_DESTROYED`. Neither is an X11 error, and synchronous X11-error rejection must not leave a wait registration or wait-only reference.
- **`GetFenceStatus` / `GetSemaphoreCounterValue`:** malformed length precedes XID validation; unknown XIDs yield `BadValue`, wrong live type/ownership `BadMatch`. After Device Loss, Fence status reports the stored terminal state, whereas the semaphore-counter request returns `DEVICE_LOST` rather than a success counter.
- **`ResetFence`:** after valid XIDs/type/ownership, Device Loss takes precedence over an invalid Fence state. With a live Device, resetting `UNSIGNALED` or `PENDING` yields `INVALID_SYNCHRONIZATION_STATE`; all rejections preserve the stored state.
- **`DestroyFence` / `DestroySemaphore`:** malformed length precedes XID checks; resolve Device XID before object XID, then validate live type/ownership/device association before lifetime blockers. Wrong live type/ownership yields `BadMatch`. Reject atomically with `INVALID_SYNCHRONIZATION_STATE` while the object is referenced by pending accepted work or an open host wait. After the wait's terminal result is serialized, an unsent reply alone must not block destruction. Device Loss alone does not invalidate the public XID or make `DestroyFence` fail; it does not override earlier validation errors or an active lifetime blocker.



## Command recording and submission rejection matrix

These cases target request-error paths that can be hidden by otherwise valid command-buffer and queue-submit vectors. The tests must assert both the winning error and the absence of partial state changes.

- **`ShaderModuleData`:** test malformed fixed/chunk length and nonzero padding before resolving the Shader Module XID; test an unknown XID (`BadValue`), wrong live type or foreign Device ownership (`BadMatch`), and a valid Shader Module without an active assembly (`INVALID_SYNCHRONIZATION_STATE`). With an active assembly, verify that a malformed continuation with the complete fixed header discards that assembly, while a request truncated before `shader_module_xid` leaves it unchanged. A malformed or duplicate `CREATE=1` attempt must not discard the already reserved assembly. Inject a failure in a non-final chunk and verify the entire identified assembly is discarded; a later FINAL chunk must not revive it. Repeat with ABORT after Device Loss and after XID destruction/reuse.
- **`CommandBufferData`:** pair a truncated entry with an invalid Buffer XID and require `BadLength`; pair invalid flags/reserved bits or an invalid entry-local scalar field with an invalid target/resource XID and require `BadValue` before XID lookup; for CREATE with valid syntax, require target-XID collision (`BadIDChoice`) before Pool-XID resolution. Test unknown Buffer/Pool/embedded resource XIDs (`BadValue`), live wrong types/foreign ownership (`BadMatch`), and a valid but non-RECORDING Buffer (`INVALID_SYNCHRONIZATION_STATE`). Separately combine a resource-dependent entry incompatibility with Device Loss and require `DEVICE_LOST` after valid XID/type/ownership checks. Any failed append or FINAL leaves the pre-request recording unchanged; any failed CREATE leaves the target XID unallocated.
- **`QueueSubmit`:** malformed count/length/overflow must win before any XID lookup; invalid scalar fields, duplicate waits/signals, and a token already accepted for another submission must be rejected before resource-state mutation. Resolve Device and command/synchronization XIDs in wire order, then enforce type, ownership, and cross-Device constraints before Device-state and executable/pending-state checks. Mix Device Loss with a non-EXECUTABLE command buffer and require `DEVICE_LOST` only after all XIDs and ownership are valid. Verify rejected submissions reserve neither token nor semaphore values, do not attach a Fence, do not change command-buffer state, and emit no submission-terminal or `ASYNC_ERROR` event.
- **`QueueSubmit` mixed failures across validation phases:** (a) combine a truncated request or count/length overflow with every other invalid field class and require `BadLength`; (b) combine token zero/reuse, nonzero reserved bits, an empty/reserved-bit wait-stage mask, duplicate command-buffer XIDs, or duplicate/cross-array semaphore XIDs with an unknown Device or later resource XID and require the scalar `BadValue` first; (c) with scalar syntax valid, make multiple XIDs invalid and require the first unknown/non-live XID in the defined wire order (Device, optional Fence, command buffers in array order, waits in array order, signals in array order); (d) combine an earlier live wrong-type/foreign-owned/cross-Device resource or invalid queue association with a later unknown XID and require the later XID-resolution `BadValue`, because all XIDs resolve before type/ownership/queue checks; (e) combine any resolved type/ownership/queue mismatch with Device Unavailable/Loss and require `BadMatch`; (f) with all identities and associations valid, combine Device Unavailable/Loss with each mutable failure class (unsignaled/pending Fence, non-EXECUTABLE Command Buffer, invalid Binary state, invalid Timeline counter value, pending Timeline reservation conflict, unsupported wait stage, or dependency cycle) and require the Device error first. Every rejected case leaves the token unused and all public and internal submission/synchronization state unchanged.
- **`QueueSubmit` mutable-state ordering:** with an operational Device, combine an invalid Fence with invalid command-buffer/wait/signal entries and require the Fence result first; combine an invalid earlier Command Buffer with a later invalid Command Buffer or any semaphore error and require the first Command Buffer in array order; combine an invalid wait entry with a later wait or signal failure and require the first wait in array order; combine a wait failure with any signal failure and require the wait result. Within a wait entry, combine a nonzero Binary wait value with unsupported stage support or an unusable semaphore and require `BadValue` before the state result; within a signal entry, combine a nonzero Binary value or Timeline value not greater than the observable counter with a pending-reservation conflict or unusable state and require `BadValue`. A Timeline value greater than the observable counter but not greater than every pending GPU signal reservation returns `INVALID_SYNCHRONIZATION_STATE`. An `UNTRUSTED` Binary semaphore's specific `DEPENDENCY_FAILED` result must not be replaced by the generic dependency fallback. A generic dependency failure is considered only after all Fence, Command Buffer, wait, and signal entries pass their specific checks.
- **`QueueSubmit` queue-stage and acceptance rollback:** combine a syntactically invalid wait-stage mask with an unknown XID and require `BadValue` from scalar validation; combine a syntactically valid but queue-unsupported stage with Device Loss and require `DEVICE_LOST`, then repeat with an operational Device and require `INVALID_SYNCHRONIZATION_STATE`. Put a valid wait/signal entry before an invalid later entry and verify that no earlier wait slot, binary signal state, Timeline reservation, Fence association, command-buffer `PENDING` transition, token consumption, or internal reference is committed. Retry the corrected request with the same token and require it to be accepted exactly once.
- **`QueueSubmit` timeline reservations:** use two submissions whose signal values are increasing, then try a third submission with a duplicate or lower pending signal value; reject it atomically. Mix an invalid later signal entry with a valid earlier entry and verify no partial reservation. If a dependency cycle is detected before acceptance, return `DEPENDENCY_FAILED`; do not report the rejected token in any later event.
- **`QueueSubmit` command/resource validation:** test a command buffer containing a destroyed/reused resource XID, an incompatible descriptor slot, a missing statically used descriptor, and an invalid dispatch limit. Each failure must follow the documented validation stage, leave the command buffer and all resources unchanged, and not create a pending submission. A Buffer referenced by a RECORDING command buffer cannot be destroyed; after successful Buffer destruction, affected non-pending executable command buffers become INVALID and cannot be submitted.
- **`QueueSubmit` versus `CommandBufferData`:** submit a command buffer, then race/sequence a second append or FINAL against that accepted submission. Once pending, mutation must be rejected with `INVALID_SYNCHRONIZATION_STATE`; if mutation is serialized before submission acceptance, the submit sees the resulting finalized or invalid recording state. Request order does not create a GPU dependency between different queues.
- **`DestroyResource` / `FreeMemory`:** malformed length precedes XID resolution; unknown/non-live XIDs yield `BadValue`, live wrong type or foreign ownership yields `BadMatch`. Reject destruction of a Buffer while a recording command buffer or pending GPU access references it, and reject freeing bound Memory or Memory with pending access using `INVALID_SYNCHRONIZATION_STATE` / `BadMatch` as specified. Verify public XIDs and all binding/reference edges remain unchanged after rejection; successful destruction invalidates the public XID immediately without allowing stale callbacks to resolve a reused XID.
- **Atomicity across batch requests:** for `AllocateDescriptorSets`, `UpdateDescriptorSets`, and any multi-entry binding/update request, place the only invalid entry last after at least one valid entry. The request must fail as a whole: no target XID is published, no descriptor slot or binding changes, and no internal reference is leaked or released early. Repeat with the first entry invalid to ensure the same externally visible atomicity.



### `CreatePipelineLayout` and `CreateComputePipeline` mixed-failure vectors

The following combinations MUST be tested as single requests, and the reported error MUST be the first failing phase in each request's normative validation order:

- `CreatePipelineLayout`: malformed count-derived length combined with an occupied target XID and an unknown Device or Set-Layout XID returns `BadLength`.
- `CreatePipelineLayout`: valid length but nonzero reserved fields or invalid stage/range syntax combined with an occupied target XID returns `BadValue`.
- `CreatePipelineLayout`: valid framing and scalar fields with an invalid or occupied target XID plus an unknown Device or Set-Layout XID returns `BadIDChoice`; no input XID is resolved first.

### Descriptor creation mixed-failure vectors

The following combinations MUST be issued as individual requests. Each test checks the exact winning error, that no public target XID is created, and that no pool capacity or internal reference is retained after rejection.

- `CreateDescriptorSetLayout`: truncated or count-mismatched payload combined with invalid binding fields and an occupied target returns `BadLength`.
- `CreateDescriptorSetLayout`: valid framing with duplicate binding numbers, zero descriptor count, unsupported descriptor type/stage bits, or nonzero reserved fields combined with an occupied target returns `BadValue`.
- `CreateDescriptorSetLayout`: valid framing/scalars with an invalid or occupied target XID plus an unknown Device XID returns `BadIDChoice`; the Device XID is not resolved first.
- `CreateDescriptorSetLayout`: valid target plus unknown Device returns `BadValue`; live wrong-type or foreign-owned Device returns `BadMatch`; after valid Device resolution/ownership, Device Loss returns `DEVICE_LOST` before backend allocation. Injected backend failure returns `ALLOCATION_FAILED`.
- `CreateDescriptorPool`: malformed count-derived length combined with zero/duplicate pool-size entries and an occupied target returns `BadLength`.
- `CreateDescriptorPool`: valid framing with zero descriptor count, duplicate pool-size types, unsupported descriptor type, or nonzero reserved field combined with an occupied target returns `BadValue`.
- `CreateDescriptorPool`: valid framing/scalars with an occupied pool target plus an unknown Device XID returns `BadIDChoice`; valid target plus unknown Device returns `BadValue`; live wrong type/foreign ownership returns `BadMatch`; Device Loss precedes pool backend allocation and returns `DEVICE_LOST`.
- `AllocateDescriptorSets`: malformed count-derived length combined with zero count, duplicate/occupied target Set XIDs, and unknown Device/Pool/Layout XIDs returns `BadLength`.
- `AllocateDescriptorSets`: valid framing with zero count or nonzero reserved fields combined with any target collision or unknown input XID returns `BadValue`.
- `AllocateDescriptorSets`: valid framing/scalars with an occupied or duplicate target Set XID anywhere in the target array plus an unknown Device, Pool, or Layout XID returns `BadIDChoice`. Include a collision in the final target entry and assert that no earlier Set becomes live.
- `AllocateDescriptorSets`: all target Set XIDs valid, then an unknown Device/Pool/Layout XID returns `BadValue`; live wrong type, foreign ownership, or cross-Device resource returns `BadMatch`; Device Loss after valid XID/type/ownership resolution returns `DEVICE_LOST` before Pool/Layout compatibility or capacity checks.
- `AllocateDescriptorSets`: with valid Device/Pool/Layout resources, incompatible Pool/Layout returns `BadMatch`; insufficient pool capacity or injected backend allocation failure returns `ALLOCATION_FAILED`. Both failures leave every target Set unallocated and restore Pool capacity and reference counts exactly.
- For all three requests, rejected creates leave target XIDs available for a subsequent valid create. For `AllocateDescriptorSets`, assert the entire target batch is absent after every failure, including a late collision, a later invalid Layout, Device Loss, insufficient capacity, and backend failure.

## Remaining resource, descriptor, and device rejection matrix

This matrix closes cross-request gaps not covered by isolated golden replies. Each test must assert the precise X11 error or protocol status, unchanged state on rejection, and absence of delayed events for work that was never accepted.

- **Device lifecycle and queue lookup:** for every Device-scoped request, combine unknown Device XID, live wrong resource type, foreign ownership, Device unavailable, and Device lost with one later invalid field/state. Require the precedence specified by that request: framing/scalar checks first, then XID resolution in wire order, then type/ownership, then Device lifecycle, then mutable state/backend checks. In particular, no unknown XID may be reclassified as Device Loss, and a live wrong-type/foreign-owned XID must not leak lifecycle state. After `DestroyDevice`, test each still-live child XID with its documented destroy/query behavior; no child may become usable through a reused Device XID.
- **`CreateCommandPool` / `ResetCommandBuffer` / `DestroyCommandPool`:** exercise exact length and reserved/flag validation before XID resolution; unknown Device/Pool/Buffer yields `BadValue`, wrong live type or ownership yields `BadMatch`, and the create target collision yields `BadIDChoice`. For `CreateCommandPool`, combine Device Loss with an invalid queue-family index and require `DEVICE_LOST`; with an available Device, the invalid family returns `BadValue`. Inject backend allocation failure only after all earlier phases pass and verify no Pool XID is published. `ResetCommandBuffer` applies to one Buffer: Device Loss wins over a missing pool reset flag or pending Buffer; on an available Device those state failures return `INVALID_SYNCHRONIZATION_STATE`. `DestroyCommandPool` rejects atomically while any child Buffer is pending; after blockers clear, it invalidates the Pool and all child Buffer XIDs together.
- **`CreateDescriptorSetLayout`:** test count/length overflow, invalid descriptor type/count/stage bits, nonzero reserved fields, duplicate binding numbers, and invalid target XID. Framing errors win first, then scalar syntax, target-XID validation, input-XID checks where applicable, Device/type/ownership and Device state. Every rejected create leaves its target XID unallocated; injected backend failure returns the documented allocation status without publishing a partial layout.
- **`CreateDescriptorPool` / `AllocateDescriptorSets` / `FreeDescriptorSets`:** mix zero counts, duplicate target Set XIDs, occupied targets, unknown Pool/Layout XIDs, wrong types, cross-Device ownership, Device Loss and insufficient pool capacity. Validate the full target-XID array before publishing any Set; a collision in the final entry must not leave earlier Sets allocated. Allocation failure must roll back all capacity and references. Freeing a Set referenced by a recording/pending command buffer must follow the specified invalidation or rejection rule and never leave a half-freed batch.
- **`UpdateDescriptorSets`:** test out-of-range binding/array element, descriptor-type mismatch, destroyed/reused Buffer or Sampler XID, invalid Buffer range/usage, and a Set already referenced by accepted work. Put the invalid write last after a valid write and verify all slots and indirect references retain their pre-request values. Mix Device Loss with a later layout or pending-state error; after valid XID/type/ownership resolution, Device Loss wins where specified. Duplicate writes to the same slot and conflicting duplicate entries must follow the explicit duplicate-entry rule, not silently apply in order.
- **`CreatePipelineLayout` / `CreateComputePipeline`:** combine malformed variable strings/counts and padding with invalid target and input XIDs; require framing and scalar validation to precede lookup. Test cross-Device Set Layout/Shader Module, invalid push-constant ranges, invalid/non-ASCII or empty entry point, bad padding, and backend allocation failure. Each rejection leaves the target XID unallocated. For pipeline creation, an otherwise valid pipeline whose shader has no matching entry point must fail without retaining a partially created Pipeline or leaking Shader Module references.
- **`BindBufferMemory`:** test zero/misaligned/out-of-range offsets, incompatible memory type, already-bound Buffer, and a Memory allocation too small for the required Buffer span. Mix each with unknown and wrong-type XIDs and Device Loss to verify the declared precedence. Rejection must leave the binding and both objects' reference counts unchanged; a successful bind must be visible atomically to subsequent requests on the same X11 connection.
- **`CreateBuffer` / `AllocateMemory` / `GetBufferMemoryRequirements`:** include integer overflow at size/alignment calculations, unsupported usage combinations, invalid memory-type masks, zero allocation size, and backend allocation failure. A successful requirements reply must not advertise an index absent from the Physical Device memory properties. Failed allocation/creation leaves no XID or capacity reservation; repeat with an occupied target XID to verify target validation wins over backend-only failures.
- **`ReadBuffer` / `WriteBuffer`:** test offset-plus-size overflow, ranges exactly ending at allocation size, one byte beyond the bound, zero-length payloads, malformed chunk/final flags, and Device Loss during transfer. A failed final `WriteBuffer` must not report commit success; a non-final deferred failure must not corrupt later independent writes. `ReadBuffer` must never return partially initialized payload as success. Where a read waits for earlier writes, test overlapping and disjoint ranges across queues and verify the documented visibility guarantee without treating X11 request order as a GPU dependency.
- **`GetPhysicalDeviceProperty` and enumeration replies:** for every registered property type, inject wrong value length, wrong wire type, nonzero reserved fields and malformed string padding into reply decoder tests. Ensure invalid reply records are rejected as malformed protocol data rather than coerced into a different property type. For enumeration count/capacity combinations, verify returned record count never exceeds the supplied capacity and that a truncated record cannot be mistaken for an empty successful result.
- **Error-channel separation:** for every request with both core X11 errors and XAverius result/status fields, force one synchronous validation failure and one asynchronous backend failure in separate runs. A rejected request produces exactly its specified X11 error and no terminal completion event; an accepted request whose execution later fails produces its specified asynchronous/normal-reply outcome and never a delayed X11 request error. Confirm status numeric values are interpreted only in their defined reply/event namespace.

## Executable QueuePresent reference-state tests

`tests/xa_state_model.py` is a small, dependency-free executable oracle for the normative `QueuePresent` validation order. `tests/test_state_model.py` supplies mixed-failure cases and checks the actual result selected by the model, not just the presence of explanatory prose. It covers wire/scalar errors, XID and ownership failures, Device loss, queue/index validation, Surface lifecycle, presentation capability, accepted-token reuse, image state, wait eligibility, retry after rejection, and the atomic acceptance commit.

For every modeled rejection, the test compares the complete state before and after the request, including accepted tokens, image state, and all wait states. The success case checks that token reservation, wait reservation, and the `ACQUIRED` to `PRESENT_PENDING` transition all occur together. Lifecycle changes are injected before validation and are retained; the rejected request itself adds no mutation.

This is intentionally a **reference state model**, not a production server or proof that an implementation conforms. Its boolean fixture fields abstract away X11 resource lookup and backend behavior. The model and tests are useful as an executable semantic oracle while a server is not available; once a protocol implementation exists, the same precedence vectors should be replayed against it through a test harness and compare wire errors/replies plus externally observable state.


## Executable compute state-model tests

The dependency-free oracle in `tests/xa_state_model.py` now models three additional contracts:

- `ShaderModuleData`: single-request CREATE|FINAL and multi-chunk assembly; malformed or failed chunks discard the entire in-progress shader assembly, FINAL publishes the module only on success, and ABORT releases assembly storage without starting GPU work.
- `CommandBufferData`: CREATE, per-chunk append validation, FINAL, and ABORT. A failed chunk appends no entries and preserves previously accepted recording chunks; failed FINAL leaves the buffer RECORDING; ABORT clears a non-pending recording buffer back to INITIAL and is allowed after Device Loss.
- `QueueSubmit`: framing/scalar/XID/type/device/state checks precede acceptance; all command buffers, waits, and signal reservations are validated before one acceptance commit. A rejected submission must not reserve its token or waits/signals, attach its Fence, transition command buffers to PENDING, or enqueue a pending submission.

These are deliberately small reference models with injected validation outcomes, not a Vulkan backend and not proof of server conformance. When a server exists, replay the same vectors against its wire interface.

## Reconciliation of the executable state model

The reference tests in `tests/test_state_model.py` reflect the precedence rules specified in this document and `spec/errors.md`:

- `ShaderModuleData`: request/payload length, padding, flag combinations, and empty data chunks are checked before XID or Device state. ABORT requires an existing assembly; Device Loss terminates the assembly, and a later ABORT MUST NOT revive it. CREATE reserves the target XID, so a second CREATE fails with `BadIDChoice`.
- `CommandBufferData`: wire structure and entry boundaries are checked first (`BadLength`); common flags, reserved fields, padding, command IDs, and entry-local scalar/field syntax are checked next (`BadValue`), before any XID lookup. The target XID, Pool XID, and embedded resource XIDs are then resolved in the normative wire order, followed by live type/ownership/Device/parent-Pool association checks. For CREATE, append, and FINAL, Device state is checked before command-buffer state and resource-dependent command compatibility. This distinguishes entry-local syntax (before XIDs) from resource-dependent semantics (after XID, ownership, and Device checks). ABORT also validates the exact parent Pool and remains permitted after Device Loss only for a live `RECORDING` Buffer.
- `QueueSubmit`: length/count and scalar errors precede XID resolution; token reuse is checked before XIDs; all resource XIDs and queue/ownership errors precede Device Loss. After Device Loss is checked, Fence, Command Buffer, waits, and signals are validated in the normative order. The oracle distinguishes Binary and Timeline Semaphores, checks Binary values for zero, validates Timeline signal values against the counter and pending reservations, and checks wait-stage syntax and queue support. Only then does the acceptance commit reserve the token, waits, signal values, Fence, and `PENDING` states.

The Python oracle still does not model complete wire decoding, every Semaphore state variant, or a real Vulkan backend call. Those areas remain covered by the normative request/error rules and wire-layout tests; the oracle specifically checks the state transitions and error-precedence cases listed above.

### QueuePresent terminal-order and precedence vectors

The following vectors are mandatory for the presentation-capable profile. Each vector is a separate request/callback sequence; compare the exact status and the complete observable reference-model state after every step.

- **Device loss versus accepted-token reuse:** submit QueuePresent with a token already used by an accepted presentation while the referenced live Device is lost. The result is DEVICE_LOST, not BadValue; no new token, wait reservation, or image transition is attributable to the rejected request. The pre-existing accepted operation retains its already-recorded terminal status.
- **Release callback before terminal callback:** accept token T for an ACQUIRED image, then deliver the backend image-release callback before presentation terminalization. If the backend confirms the image reusable and Device/Surface/Swapchain remain usable, the image becomes AVAILABLE and the release milestone is recorded once. A later terminal SUCCESS must not repeat release or enqueue a second IMAGE_RELEASED.
- **Release followed by terminal Device Loss:** accept token T, record a reusable image-release milestone, then serialize DEVICE_LOST as the operation's first terminal outcome before any replacement operation acquires the image. The terminal status is recorded as DEVICE_LOST, the image/Swapchain becomes invalid, and no IMAGE_RELEASED is emitted for an invalidated image. A late duplicate terminal callback (including SUCCESS) is rejected without changing the terminal status or image state.
- **Terminal success before release, then lifecycle invalidation:** accept token T, terminalize it as SUCCESS, then serialize resize/Surface loss/Device loss before image release. The terminal status remains SUCCESS, but the image becomes INVALID; the later release callback must not make it AVAILABLE or emit IMAGE_RELEASED.
- **Retry after rejection:** use a token in a request rejected for image state, unsupported presentation, or lifecycle status; after correcting that independent condition, retry the same token. The first request must not reserve the token; the retry is accepted if all remaining validation succeeds.
- **Mixed precedence:** combine malformed length with every later failure class and require BadLength; combine token zero or duplicate wait XIDs with invalid XIDs and require BadValue; combine unknown/wrong-type/foreign-owned resources with Device loss and require the documented XID/type error; combine Device loss with queue/index, lifecycle, and accepted-token reuse and require DEVICE_LOST; combine Surface loss or OUT_OF_DATE with accepted-token reuse and require the lifecycle status; combine unsupported presentation with accepted-token reuse and require BadMatch; combine accepted-token reuse with invalid image/wait state and require BadValue.

For all rejection vectors, snapshot token sets, pending-token sets, image state, wait states, canonical semaphore reservations/payload state, and terminal/release records before the request. Assert they are unchanged by that request (separately serialized lifecycle transitions remain in effect). For callback vectors, assert duplicate or stale callbacks are mutation-free and cannot replace the first serialized terminal result. These reference tests do not replace replay against a real server once one exists.


## Seven-request presentation error-precedence matrix

These vectors are normative for the presentation-capable profile and MUST be run as separate requests with a controlled initial state. For each row, combine the named failures in one request and assert the exact winning X11 error or normal reply status. Also assert that a rejected request creates no request-attributable object/reference/image/synchronization/token mutation. Run wire-parsing vectors in both client byte orders. Independent lifecycle transitions remain in effect and are never rolled back.

- **CreateSurface:** combine a wrong request length, nonzero reserved/scalar syntax, an occupied/invalid target Surface XID, and an unknown/non-Window window_xid. Require BadLength, then BadValue for scalar syntax, then BadIDChoice for the target create-XID, then BadWindow for the Window lookup. With valid XIDs, a live Window owned by another connection returns BadMatch. Verify every failure leaves the target XID unallocated and retains no Window identity/reference. Also test a valid Window destroyed immediately after the successful create commit: the create remains successful and the Surface subsequently becomes SURFACE_LOST.

- **DestroySurface:** combine malformed length with an unknown Surface XID and require BadLength; with valid framing, an unknown/non-live Surface returns BadValue, while a live wrong-type or foreign-owned resource returns BadMatch. With a valid owned Surface still referenced by a live Swapchain, require INVALID_SYNCHRONIZATION_STATE and preserve the Surface XID, state, Window identity, and reference graph. Repeat for a SURFACE_LOST Surface: the lost state does not change the error or remove the live-Swapchain blocker. Once the Swapchain is retired, destruction succeeds; explicit destruction MUST NOT be reported as SURFACE_LOST.

- **GetSurfaceCapabilities:** combine malformed request length with unknown XIDs (BadLength); then test unknown Device/Surface XIDs (BadValue) and live wrong-type/foreign-owned resources (BadMatch) before status evaluation. With valid resources, Device loss plus Surface loss returns DEVICE_LOST; Surface loss plus a stale zero-extent snapshot returns SURFACE_LOST; a live zero-extent Surface returns TEMPORARILY_NOT_PRESENTABLE; a usable nonzero Surface returns SUCCESS, including when that Device/Surface pair simply has no present-capable queue family. For every non-success result, require the exact 64-byte fixed reply, reply.length = 8, zero capability fields and zero variable counts/payload.

- **CreateSwapchain:** combine malformed count/length arithmetic with all later failures and require BadLength; combine zero image count or zero requested width/height with an occupied target and lost Device and require BadValue; with valid scalar syntax, check XID order (device_xid, target swapchain_xid, surface_xid) so an invalid target wins as BadIDChoice before later input-XID lookup. Unknown input XIDs return BadValue; live wrong-type, foreign-owned, or cross-Device resources return BadMatch. After those checks, Device loss wins over invalid immutable format/color-space/mode/usage identifiers and all Surface statuses. With a usable Device, invalid identifiers/unassigned usage bits return BadValue; then Surface loss wins over zero-current-extent or out-of-bounds OUT_OF_DATE; OUT_OF_DATE wins over a valid but unsupported configuration (UNSUPPORTED_CONFIGURATION); injected allocation failure is reached only after every preceding check and returns ALLOCATION_FAILED. Every non-success reply has actual_image_count = 0, leaves the target XID unallocated, and releases all provisional references/resources.

- **DestroySwapchain:** combine malformed length with an unknown Swapchain XID and require BadLength; with valid framing, unknown/non-live XID returns BadValue, while a live wrong-type or foreign-owned resource returns BadMatch. With a valid owned Swapchain, independently combine each blocker (recording command buffer, pending acquire, accepted queue work, accepted presentation, backend image access) and require INVALID_SYNCHRONIZATION_STATE with the public XID, image indices, and references unchanged. An acquired-but-idle image alone is not a blocker. Once all blockers are absent, destruction succeeds and immediately invalidates the public XID/image indices; delayed internal cleanup must remain attached to the old identity.

- **AcquireNextImage:** combine malformed length with unknown Device/Swapchain/optional synchronization XIDs and require BadLength; then combine invalid scalar/reserved syntax with those XIDs and require BadValue. Resolve nonzero XIDs in wire order; unknown XIDs return BadValue, live wrong-type/foreign/cross-Device objects return BadMatch, all before Device status. With valid XIDs/types/ownership, Device loss wins over Surface loss, which wins over OUT_OF_DATE; these lifecycle statuses win over ineligible Semaphore/Fence state and timeout polling. Once lifecycle checks pass, ineligible signal state or a conflicting pending acquire returns INVALID_SYNCHRONIZATION_STATE even with an available image or zero timeout; only eligible synchronization reaches SUCCESS, NOT_READY, or TIMEOUT. DEVICE_DESTROYED is tested separately as terminalization of an already-open registration, and cannot overwrite an earlier terminal result. Every non-success reply is 44 bytes, has image_index = 0 and reserved = 0, and signals neither optional object.

- **QueuePresent:** combine malformed variable length/overflow with every later failure and require BadLength; combine zero token, duplicate wait XIDs, or invalid reserved/scalar values with unknown XIDs and require BadValue. With valid scalars, unknown Device/Swapchain/wait XIDs return BadValue; live wrong-type, foreign-owned, or cross-Device resources return BadMatch, all before Device status. With valid resources, Device loss wins before queue/index validation. On a usable Device, nonexistent queue-family/index or out-of-range image index returns BadValue before Surface/extent status. With valid queue/index, SURFACE_LOST wins over OUT_OF_DATE; both win over unsupported queue presentation (BadMatch), accepted-token reuse (BadValue), image-state failure, and wait-semaphore eligibility. With lifecycle valid and a supported queue, accepted-token reuse wins before image/wait state; a new token with a non-ACQUIRED image returns INVALID_SYNCHRONIZATION_STATE before wait checks; for an ACQUIRED image, UNTRUSTED wait state returns DEPENDENCY_FAILED and other incompatible wait state returns INVALID_SYNCHRONIZATION_STATE. For every rejected request, assert no token reservation, wait reservation/consumption, image transition, or accepted operation. A token from a rejected attempt remains reusable.

This matrix complements, and MUST remain consistent with, the request-specific mapping in errors.md, the shared stage order in errors.md#normative-validation-precedence-for-the-seven-presentation-requests, and the status/atomic-acceptance rules in presentation.md#53-request-validation-status-precedence-and-atomic-acceptance. In particular, Device loss is checked after XID/type/ownership validation but before immutable queue/index checks; on a usable Device, invalid queue/index values precede Surface status. Immutable format/mode/usage identifiers for CreateSwapchain are checked after Device availability, not as early scalar syntax.


## Non-presentation request error-precedence conformance matrix

This matrix covers the compute-baseline requests (subopcodes 1–40). The common envelope/header/profile-dispatch checks in wire-protocol.md apply to every row and MUST be tested independently: envelope/length errors precede common-header errors; common-header errors precede request dispatch; for supported requests, request-specific exact length precedes the declared scalar/XID/state order. For every synchronous rejection, assert the exact winning X11 error or reply status and verify no request-attributable partial allocation, mutation, reservation, wait registration, or event. Run request vectors in both byte orders. Reply-decoder vectors are separate from request-error vectors.

- **Physical-device discovery:** `EnumeratePhysicalDevices` rejects malformed request length with `BadLength`; it has no XID or scalar phase. For `GetPhysicalDeviceQueueFamilyProperties` and `GetPhysicalDeviceMemoryProperties`, assert `BadLength` > Physical-Device XID (`BadValue`) > live type (`BadMatch`); Device/Physical-Device removal does not add a later availability error to these stored-metadata queries.
- **Device creation and destruction:** `CreateDevice` tests MUST preserve the ten ordered phases in devices.md/errors.md, including target-XID validation before Physical-Device lookup, XGE negotiation before availability, and availability before queue/feature support checks. `CreateDefaultDevice` tests MUST preserve length > scalar fields > target XID > XGE prerequisite > suitable-device selection. `DestroyDevice` combines malformed length with unknown/wrong-type Device XID (`BadLength` wins); unknown/non-live Device XID combined with a live wrong-type/foreign-owned resource returns `BadValue`; a live wrong-type or foreign-owned resource returns `BadMatch` after successful XID resolution. Device Loss is not an additional blocker for logical teardown. Verify that no availability/backend check runs and no state changes occur on rejection. - **Buffer and memory creation:** `CreateBuffer` and `AllocateMemory` combine malformed length, invalid scalar/reserved values, occupied target XID, unknown Device XID, wrong live type/ownership, Device Loss, and injected allocation failure.
