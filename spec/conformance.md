# Compute Reference Flow

All request validation follows a deterministic stage order: framing before scalar syntax, scalar syntax before XID resolution, and XID/type/ownership checks before lifecycle status.

Ziel-Workload:

`C[i] = A[i] + B[i]`

Typischer Ablauf:

1. Enumerate physical devices or create the default device.
2. Query memory properties and create a logical device with a compute queue.
3. Create buffers A, B, and C.
4. Query memory requirements, allocate memory, and bind the buffers.
5. Upload A and B using independent `WriteBuffer` requests.
6. Create the shader module.
7. Create the descriptor set layout, descriptor pool, and descriptor set.
8. Create the pipeline layout and compute pipeline.
9. Update the descriptor set with A, B, and C.
10. Create the command pool and command buffer.
11. Bind the pipeline.
12. Bind the descriptor sets.
13. Set push constants if needed.
14. Record `Dispatch` and finalize the command buffer.
15. Create fences/semaphores if required.
16. Execute `QueueSubmit`.
17. Wait for completion using a Fence or Semaphore.
18. Read C back through ReadBuffer.
19. Destroy resources according to the lifetime rules.

The server MUST ensure that descriptors match the shader, statically used resources are present, and dispatch limits are respected.

# Conformance and Tests

An implementation SHOULD test at least the following cases:

- Exact request lengths, counts, and padding
- ReadBuffer waits for earlier accepted writes to the requested range on the same logical Device, including writes from other queues. An earlier submission failure alone does not prevent the read, but the data is not guaranteed to match the failed write's expected output. On Device loss, ReadBuffer MUST fail with DEVICE_LOST and MUST NOT send a successful data reply.
- EnumeratePhysicalDevices is an 8-byte Reply request; DestroyDevice is a 12-byte Void request.
- EnumeratePhysicalDevices.reply.length equals the sum of padded PHYSICALDEVICEINFO record lengths divided by four; it is zero when there are no records.
- EnumeratePhysicalDevices with a request length other than 8 bytes returns BadLength; an empty successful reply is permitted and MUST NOT contain incomplete records.
- GetPhysicalDeviceQueueFamilyProperties.reply.length equals 3 * queue_family_count; the payload length MUST be divisible by 12.
- GetPhysicalDeviceProperty uses SUCCESS = 0, NOT_SUPPORTED = 1, and NOT_AVAILABLE = 2. On failure, property_type, value_length, and payload are zero and reply.length = 0.
- GetPhysicalDeviceProperty accepts the four canonical names in the Property Registry; Atom IDs are assigned by the server. Unknown Atom IDs result in BadAtom; valid but unregistered Atom names return NOT_SUPPORTED; registered but unavailable properties return NOT_AVAILABLE.
- XAverius.deviceUUID and XAverius.driverUUID return exactly 16 BYTE_ARRAY bytes on success; XAverius.compute.maxWorkGroupInvocations returns one CARD32; XAverius.compute.maxWorkGroupSize returns exactly three CARD32 values in X/Y/Z order. Reply type and exact value length MUST match the registry.
- The v0.1 Feature-ID and Device-Extension registries are empty: every feature ID returns BadValue; syntactically valid optional extension names return BadMatch; syntactically invalid extension names return BadValue. Neither CreateDevice nor CreateDefaultDevice implicitly enables optional features or extensions.
- CreateDevice length exactly matches the three ordered variable record arrays; at least one queue-family request is required; queue priorities MUST be finite and within [0,1]. Unknown feature IDs, enabled != 1, duplicate features/extensions, and syntactically invalid extension names return BadValue. Registered but unsupported features and unknown or unsupported syntactically valid extensions return BadMatch. Any error leaves the target XID unallocated. CreateDevice and CreateDefaultDevice send no reply on success.
- GetPhysicalDeviceMemoryProperties returns Memory-Type and Heap indices that remain stable for the lifetime of the Physical-Device XID.
- AllocateMemory is exactly 32 bytes; allocation_size MUST be positive, memory_type_index MUST be valid, and the reserved field MUST be zero. Invalid values return BadValue; an invalid or occupied target XID returns BadIDChoice; unknown/non-live Device XIDs return BadValue; live resources of the wrong type or foreign Device ownership return BadMatch; an unavailable/lost Device returns DEVICE_UNAVAILABLE / DEVICE_LOST; backend allocation failures return ALLOCATION_FAILED. On every error, the target XID remains unallocated.
- CreatePipelineLayout validates exactly 20 + 4 * set_layout_count + 12 * push_constant_range_count bytes, registered stage bits, push-constant ranges, Device/Set-Layout ownership, and target-XID collisions. Unknown XIDs return BadValue; live resources of the wrong type or foreign ownership return BadMatch; unavailable/lost Devices return DEVICE_UNAVAILABLE / DEVICE_LOST; backend allocation failures return ALLOCATION_FAILED. Rejection leaves no Pipeline Layout.
- CreateSemaphore is exactly 28 bytes and accepts only BINARY = 0 or TIMELINE = 1; for Binary semaphores, initial_value MUST be 0. Invalid fields return BadValue; a target-XID collision returns BadIDChoice; backend allocation failure returns ALLOCATION_FAILED. Unknown Device XIDs return BadValue; live resources of the wrong type or foreign ownership return BadMatch; unavailable/lost Devices return DEVICE_UNAVAILABLE / DEVICE_LOST. On rejection, the target XID remains unallocated.
- `SignalSemaphore` has an exact length of 24 bytes and validates in this order: length, Device XID, Semaphore XID, type/ownership/cross-device association, Device state, then Timeline type and counter/reservation relation. In mixed-error cases, the earlier phase wins; in particular, `DEVICE_LOST` after valid resource resolution takes precedence over a Binary-semaphore type error. A synchronous rejection changes neither the counter nor signal reservations.
- Timeline host signals must exceed the observable counter and remain below every pending GPU signal value; a signal that jumps across a reserved GPU signal value is atomically rejected with `INVALID_SYNCHRONIZATION_STATE`, without changing the counter or reservations. Timeline queue waits may request a value not yet reached (wait-before-signal); acceptance registers the specific target value, waits asynchronously for it to be reached, and does not consume an exclusive Binary semaphore slot. Multiple accepted Timeline waits may share the same Semaphore XID and target value. New GPU signal reservations must remain strictly greater than the counter and every existing pending signal reservation. A signal value not greater than the observable counter results in `BadValue`, while a value that exceeds the counter but conflicts with an existing pending GPU signal reservation is rejected before acceptance with `INVALID_SYNCHRONIZATION_STATE`. Neither case may leave a partial reservation.
- A host signal to a value below a higher pending GPU-signal reservation MAY release a queue wait waiting for that value; the GPU signal value remains reserved and can be signaled successfully afterward.
- Timeline signal reservations are terminalized per accepted submission, not in callback order: a callback removes only reservations belonging to its own token; afterward, signal_slots (if maintained internally as a compatibility mirror) equals the highest value that remains pending. Successful callbacks may only increase the observable counter monotonically. If callbacks arrive out of order, a later success for a lower value MUST NOT decrease a higher counter already reached. After Device loss, late backend successes MUST NOT publish any reserved value; they must still release their own reservations without removing other pending reservations.
- WaitForFence validates exactly 24 bytes and resolves Device/Fence XIDs before registering the wait. Unknown XIDs return BadValue; live resources of the wrong type, foreign ownership, or cross-Device use return BadMatch. Timeout, execution failure, Device loss, and DestroyDevice are returned through the defined normal reply status values.
- `WaitSemaphores` has an exact length of `28 + 12 * semaphore_count` bytes and validates in this order: length/overflow, count/mode/duplicates, Device and Semaphore XIDs in wire order, type/ownership/cross-device association, Device state, then Timeline type. In mixed-error cases, the earlier phase wins; in particular, `DEVICE_LOST` after valid XIDs and ownership takes precedence over a Semaphore type error. All synchronous rejections occur without registering a wait or changing state. Device loss and `DestroyDevice` terminalize already-open waits with `DEVICE_LOST` and `DEVICE_DESTROYED`, respectively, without overwriting an already serialized result.
- WaitSemaphores MUST NOT block the X11 dispatcher: a later SignalSemaphore or QueueSubmit on the same connection may satisfy the wait. The timeout deadline continues from when the wait request is accepted for execution.
- WaitSemaphores may wait for a Timeline value that has not yet been reserved. With a finite timeout it ends with TIMEOUT; with an infinite timeout it remains open until the value is reached or the Device is lost. The server does not guarantee progress if no later signal is queued.
- If WriteBuffer waits for earlier submissions and a deferred QueueSubmit would satisfy a Timeline wait of an earlier nonterminal submission, but no already-accepted signal operation can satisfy that wait, WriteBuffer ends with DEPENDENCY_FAILED. The deferred submission is then processed normally and is not accepted before a successful upload.
- CreateFence is exactly 24 bytes, with create_flags = 0 and reserved = 0; its initial state is UNSIGNALED. Invalid fields return BadValue; a target-XID collision returns BadIDChoice; backend allocation failure returns ALLOCATION_FAILED. Unknown Device XIDs return BadValue; live resources of the wrong type or foreign ownership return BadMatch; unavailable/lost Devices return DEVICE_UNAVAILABLE / DEVICE_LOST. On rejection, the target XID remains unallocated.
- SelectEvents is exactly 32 bytes and requires prior successful XGE 1.0 negotiation. Scope/mask combinations and unused fields are validated. Every error leaves the previous event selection atomically unchanged.
- ASYNC_ERROR validates the semantic field combination: origin = ORIGIN_QUEUE_SUBMIT requires a nonzero token for a previously accepted submission; token 0 means no submission association, and a rejected QueueSubmit MUST never be identified by an ASYNC_ERROR token.
- For `origin = ORIGIN_QUEUE_SUBMIT`, `submission_token` MUST be nonzero and identify a previously accepted submission; token 0 means no submission association, and a rejected `QueueSubmit` MUST never be identified by an `ASYNC_ERROR` token.
- An `ASYNC_ERROR` with nonzero `submission_token` MUST be associated with an actually accepted submission. Unknown `origin` values, nonzero `reserved` fields, and invalid Device/resource references MUST NOT be serialized.
- If the affected resource was destroyed or its XID reused before the `ASYNC_ERROR` enqueue linearization point, the event MUST have `resource_xid = 0`; a later callback MUST NOT retarget the numeric XID to the new object.
- `SelectEvents` rejects unknown scope values, nonzero flags/common-header or payload reserved fields, unknown mask bits, and scope fields with incorrect zero values using `BadValue`; wrong live resource types or foreign ownership result in `BadMatch`. Every such error leaves the previous mask unchanged.
- `SelectEvents` with a valid Device but an unrequested queue combination is rejected with `BadValue`; an unknown or non-live Device XID results in `BadValue`, while a live XID of the wrong type or foreign ownership results in `BadMatch`.
- After successful `DestroyDevice`, unmaskable `DEVICE_LOST` and `ASYNC_ERROR` events MUST NOT contain the destroyed Device XID as `device_xid` or `resource_xid`; events queued before the request remain unaffected.
- When `SelectEvents`, `DestroyDevice`, and submission completion race, a shared serialized linearization point decides mask sampling and event enqueueing; a later backend callback MUST NOT enqueue a previously suppressed event.
- For each accepted submission, at most one of `SUBMISSION_COMPLETE` and `SUBMISSION_FAILED` is queued as the terminal event; `ASYNC_ERROR` is supplementary diagnostic information, not a second terminal outcome.
- After successful processing of `DestroyDevice`, no new events using its destroyed `device_xid` are generated or delivered; events already queued in the X11 output stream remain unaffected. Internal terminal processing of accepted submissions and backend references remains independent of this event suppression.
- After client disconnect, no new XAverius events are queued for the closed connection or delivered through other connections; event selections and public XID mappings are removed from the active connection state. Accepted work still reaches its actual internal terminal outcome without inventing completion or releasing backend resources prematurely; disconnect does not force indefinite waiting.
- Client disconnect aborts open server-side WaitSemaphores/WaitForFence registrations without a reply, releases only references held exclusively by those waits, and does not change already-accepted GPU work or its synchronization state.
- Competing wait terminal conditions have exactly one outcome: an already-established satisfaction remains successful; otherwise, the first serialized timeout, Device-loss, or DestroyDevice transition wins. Device loss before DestroyDevice yields DEVICE_LOST; an open wait when DestroyDevice is processed yields DEVICE_DESTROYED; later transitions MUST NOT overwrite the result.
- CreateBuffer rejects usage_flags = 0 and unknown usage bits with BadValue.
- CreateBuffer distinguishes unknown/non-live Device XIDs (BadValue), live resources of the wrong type (BadMatch), unavailable/lost Devices (DEVICE_UNAVAILABLE / DEVICE_LOST), and backend memory exhaustion (ALLOCATION_FAILED). On every error, the target XID remains unallocated.
- CreateDescriptorPool distinguishes unknown Device XIDs (BadValue), live resources of the wrong type or foreign ownership (BadMatch), unavailable/lost Devices (DEVICE_UNAVAILABLE / DEVICE_LOST), and backend allocation failures (ALLOCATION_FAILED). On rejection, the pool XID remains unallocated.
- CreateDescriptorPool, AllocateDescriptorSets, and FreeDescriptorSets reject a zero count with BadValue. AllocateDescriptorSets distinguishes unknown input XIDs (BadValue), live resources of the wrong type or foreign ownership (BadMatch), Device states (DEVICE_UNAVAILABLE / DEVICE_LOST), and pool/backend allocation failures (ALLOCATION_FAILED); on rejection, no subset remains live.
- Create target XIDs are validated separately from input XIDs: invalid/occupied target XIDs return BadIDChoice; batch creation leaves no partial subset on collision.
- ShaderModuleData without a matching upload assembly and CommandBufferData without a matching RECORDING buffer are rejected with INVALID_SYNCHRONIZATION_STATE; CREATE target-XID collisions return BadIDChoice.
- ShaderModuleData: any malformed chunk discards the entire assembly. After disconnect or Device loss, no old assembly remains addressable, and later chunks/ABORT requests MUST NOT resurrect it.
- `ShaderModuleData` and `CommandBufferData` chunk errors are reported synchronously as X11 errors only; they do not generate `ASYNC_ERROR`, because no submission was accepted.
- CreateDevice rejects zero queue-family records, a zero queue count, and duplicate queue-family records with BadValue; an unsupported queue count returns BadMatch.
- Binary semaphore: an accepted wait does not consume the signal before it is actually satisfied; the signal is consumed exactly once, and only then may a new signal cycle begin. Duplicate pending wait/signal operations are rejected atomically. Binary wait/signal values MUST be zero.
- Timeline semaphore: accepted, non-terminal signal operations reserve their values but do not increase the observable counter until successful execution; new signal values must exceed all pending reserved values. Duplicate Timeline signal entries for the same semaphore are rejected in v0.1.
- Every accepted queue wait/signal operation retains a reference to the exact internal Semaphore identity until the operation reaches a terminal outcome and the backend can no longer access it; XID reuse MUST NOT redirect that reference.
- Duplicate pool-size types, duplicate descriptor updates to the same slot, duplicate wait/signal entries, and a semaphore appearing in both wait and signal lists are atomically rejected according to the error rules.
- CreateComputePipeline uses the normative length 28 + ((entry_point_length + 3) & ~3) and validates a nonempty ASCII entry point and zero padding. Unknown input XIDs return BadValue; live resources of the wrong type or foreign ownership return BadMatch; unavailable/lost Devices return DEVICE_UNAVAILABLE / DEVICE_LOST; backend allocation failures return ALLOCATION_FAILED. On rejection, the Pipeline XID remains unallocated.
- DestroySemaphore and DestroyFence are each 16-byte Void requests; WaitSemaphores uses 28 + 12 * semaphore_count.
- DestroyFence and DestroySemaphore validate the fixed request length before resolving XIDs. Unknown/non-live XIDs return BadValue; live resources of the wrong type or ownership return BadMatch; rejection leaves XIDs and states unchanged.
- DestroyFence is rejected while the Fence is associated with a nonterminal submission or an open WaitForFence registration references the same internal Fence identity. DestroySemaphore is rejected while a queue wait/signal, an open WaitSemaphores registration for the same internal Semaphore identity, or another active host operation uses it. Both rejections are atomic. Once a wait result is terminally established, an outstanding reply alone does not block destruction.
- `GetFenceStatus` ist ein 16-Byte-Reply-Request mit Fence-Status in Reply-Byte 1, `reply.length = 0` und null reservierten XAverius-Bytes in Offsets 8–31
- Error-Offsets und Event-/Reply-Statuswerte bleiben getrennte Namespaces: `EXECUTION_FAILED` ist Error-Offset 3, `WaitForFence`-Status 2 und `SUBMISSION_FAILED.failure_class` 0; `DEVICE_LOST` ist Error-Offset 1, `WaitForFence`-Status 3 und `SUBMISSION_FAILED.failure_class` 1. `DEVICE_LOST.reason_code` verwendet wiederum die eigene Reason-Code-Registry.
- WaitSemaphores and WaitForFence with timeout 0 check the state without intentional waiting; UINT64_MAX waits indefinitely, and other values use a monotonic nanosecond deadline measured from execution acceptance.
- A finite wait deadline MUST NOT restart after internal wait phases or scheduler interruptions. The reply may arrive late, but a condition already satisfied MUST win over TIMEOUT in the final state check.
- WaitSemaphores timeout returns TIMEOUT without changing state. WaitForFence returns SUCCESS, EXECUTION_FAILED, or TIMEOUT according to the terminal Fence state and deadline, and returns DEVICE_LOST or DEVICE_DESTROYED if either terminal transition is established first.
- DestroyFence is atomically rejected with INVALID_SYNCHRONIZATION_STATE while the Fence is PENDING or an open WaitForFence registration exists. Once the wait result is terminally established, an outstanding reply alone does not block destruction.
- DestroySemaphore is atomically rejected with INVALID_SYNCHRONIZATION_STATE while an open WaitSemaphores registration references the same internal Semaphore identity. Once the wait result is terminally established, an outstanding reply alone does not block destruction.
- Device loss during a blocking wait MUST NOT be masked as a timeout: WaitSemaphores ends with a DEVICE_LOST X11 error; WaitForFence returns DEVICE_LOST in its reply.
- Processing DestroyDevice ends still-open infinite waits without waiting for GPU progress: WaitSemaphores ends with a DEVICE_DESTROYED X11 error; WaitForFence returns DEVICE_DESTROYED in its reply. Conditions established as satisfied earlier retain their normal result.
- GetFenceStatus validates exactly 16 bytes and resolves Device/Fence XIDs before the reply. Unknown XIDs return BadValue; live resources of the wrong type, foreign ownership, or cross-Device use return BadMatch. After Device loss, the query returns the stored state.
- After Device loss, GetFenceStatus returns the stored state; Fences belonging to nonterminal submissions failed by that loss are FAILED, not SIGNALED. Fences that were never submitted are not changed artificially. After Device loss is detected, WaitForFence always returns DEVICE_LOST and does not wait indefinitely.
- GetSemaphoreCounterValue validates exactly 16 bytes and resolves Device/Semaphore XIDs before the reply. Unknown XIDs return BadValue; live resources of the wrong type, foreign ownership, or cross-Device use return BadMatch. The request is valid only for Timeline semaphores.
- After Device loss, GetSemaphoreCounterValue MUST NOT return a seemingly successful counter reply; it returns DEVICE_LOST. SignalSemaphore, QueueSubmit, and WaitSemaphores MUST NOT treat semaphore operations as successfully continuing.
- Device-loss teardown invalidates public Fence/Semaphore XIDs, but internal synchronization objects MUST NOT be released until backend accesses and server-side operations have safely ended or the objects remain isolated under the quarantine rules.
- CommandBufferData ABORT is exactly 16 bytes; other chunks contain only complete entries.
- CommandBufferData accepts exactly the flag combinations 000 (append), 010 (FINAL), 100 (CREATE), 110 (CREATE|FINAL), and 001 (ABORT). Every other combination and any reserved flag bit returns BadValue.
- CommandBufferData validates the target XID before the pool XID: CREATE with an invalid/occupied target XID returns BadIDChoice; without CREATE, unknown Buffer XIDs return BadValue. Unknown pool XIDs return BadValue; live resources of the wrong type, foreign ownership, or a pool XID that does not belong to the Buffer return BadMatch.
- `CommandBufferData` error precedence: malformed request/entry structure (`BadLength`) takes precedence over invalid flags, reserved bits, padding, and command-ID/values (`BadValue`); these field errors take precedence over XID errors. The target XID is then checked before the pool XID, and type/ownership before Device/Buffer state.
- For `CommandBufferData`, an invalid flag combination combined with an invalid target XID returns `BadValue`; a structurally truncated entry combined with an invalid target XID returns `BadLength`; with valid CREATE flags and an invalid or occupied target XID, `BadIDChoice` takes precedence over an invalid pool XID.
- For CREATE/Append/FINAL on a lost Device, `DEVICE_LOST` takes precedence after valid XID/type/ownership checks, even if an existing buffer is not `RECORDING`. ABORT is the exception: after Device loss, pool/buffer association and the `RECORDING` state are still checked; an invalid state results in `INVALID_SYNCHRONIZATION_STATE`.
- For ABORT as well, command_pool_xid MUST exactly match the Buffer's parent pool. A mismatched pool is rejected without changing recording state, entries, or references.
- An entry with an incomplete header or a declared length extending past the request end returns BadLength; zero length, a length smaller than the entry header, or an unknown command ID returns BadValue. In every case, no part of the current chunk is appended.
- ResetCommandBuffer validates request length, XIDs, type, ownership, and cross-Device association before state changes. After successful XID validation, an unavailable/lost Device returns DEVICE_UNAVAILABLE / DEVICE_LOST; missing reset permission and PENDING return INVALID_SYNCHRONIZATION_STATE, leaving state, entries, and references unchanged.
- QueueSubmit length exactly matches 40 + 4*C + 16*W + 12*S. Zero or reused submission tokens return BadValue; count/length overflow returns BadLength; foreign ownership or queue association returns BadMatch; invalid states return INVALID_SYNCHRONIZATION_STATE. Synchronously rejected requests produce no submission event.
- QueueSubmit error precedence: an invalid total length/count (BadLength) takes precedence over token/mask/reserved-field errors (BadValue); syntax errors take precedence over XID resolution; XID/type/ownership/queue errors take precedence over Device and state errors.
- For QueueSubmit, unknown Device/resource XIDs return BadValue; a queue-family/queue-index pair not configured for the Device, a live resource of the wrong type, or foreign ownership returns BadMatch. All XID references are resolved before queue/type/ownership and Device checks; queue/type/ownership errors take precedence over DEVICE_LOST.
- QueueSubmit with token 0 or an already-used token and an unknown Device/Buffer XID at the same time returns BadValue from token validation; an invalid request length takes precedence over both.
- With valid syntax and XIDs, a live resource of the wrong type or foreign ownership returns BadMatch even if the Device is lost. After valid XID/type/ownership/queue validation, Device loss returns DEVICE_LOST before checking for a non-EXECUTABLE Command Buffer, an ineligible Fence, or an invalid mutable Semaphore state.
- A wait-stage mask with reserved bits returns BadValue before XID/state validation; a syntactically valid stage unsupported by the queue family returns INVALID_SYNCHRONIZATION_STATE only after XID/ownership and Device checks.
- Nonzero Binary wait/signal values and Timeline signal values not greater than the observable counter are rejected with BadValue only after XID/type/ownership and Device checks. A Timeline signal value greater than the counter but conflicting with an existing pending GPU-signal reservation returns INVALID_SYNCHRONIZATION_STATE. Every rejection leaves previously checked Command Buffers, Fences, and Semaphores completely unchanged.
- If multiple state errors are present, QueueSubmit checks the optional Fence first after Device state, then Command Buffers in array order, then wait entries, and finally signal entries in array order. Within a wait entry, type-dependent values are checked before stage support and mutable Semaphore state; within a signal entry, type-dependent values are checked before signal state and reservation conflicts. A specific wait/signal-entry error takes precedence over the general dependency fallback: DEPENDENCY_FAILED for unspecified dependency analysis is returned only if all entries validate without a specific error. DEPENDENCY_FAILED caused by a concrete UNTRUSTED entry remains that entry's specific result.
- A failed FINAL chunk of `CommandBufferData` leaves the buffer `RECORDING`, preserves all previously accepted entries and references, and appends neither entries nor references from the failed chunk.
- QueueSubmit validates all Command Buffers and synchronization objects before commit. If a later entry is rejected, objects that passed individual validation earlier remain unchanged as well.
- On rejected `QueueSubmit`, every command buffer remains `EXECUTABLE`; no Fence is assigned or toggled, semaphore counters, signal availability, pending slots, and Timeline reservations remain unchanged, and no internal submission references are created. The rejected request reserves neither `submission_token` nor semaphore wait/signal slots.
- The `submission_token` is consumed only at acceptance: after a synchronously rejected request, the same token may be used in a corrected request; an accepted request reserves it exactly once.
- A rejected `QueueSubmit` emits neither `SUBMISSION_COMPLETE`/`SUBMISSION_FAILED` nor `ASYNC_ERROR`; a later backend failure of an accepted submission follows the terminal-submission rules.
- QueueSubmit atomically rejects duplicate Command Buffer XIDs, duplicate Semaphore XIDs within the wait array or signal array, and a Semaphore appearing in both arrays before acceptance. The error is BadValue, and Command Buffer, Fence, Semaphore, and submission states remain unchanged.
- QueueSubmit validates Semaphore types and values before acceptance: Binary wait/signal values MUST be zero; Timeline signal values MUST exceed both the counter and all earlier reserved pending GPU-signal values; duplicate Timeline signal entries for the same Semaphore are not permitted.
- A rejected QueueSubmit reserves neither submission_token nor Semaphore wait/signal slots and creates neither submission events nor internal submission references.
- An accepted Timeline signal reservation remains bound until the terminal callback for its submission. On success, the counter advances monotonically to at least the reserved value; on failure, only that submission's reservations are removed and no signal value is published. After each terminal callback, the aggregate pending slot equals the highest signal value still pending, or is empty if none remains.
- Callback order does not change these rules: a later-arriving successful callback for a lower value MUST NOT decrease the counter. After Device loss is observed, a late backend success MUST NOT advance a Timeline counter; its reservations are still resolved when it becomes terminal. A submission token that is already terminal MUST NOT trigger a second state transition.
- QueueSubmit.wait_stage_mask is interpreted as an XAverius bit mask, not a raw Vulkan mask: DRAW_INDIRECT=0x1, COMPUTE_SHADER=0x2, TRANSFER=0x4, ALL_COMMANDS=0x8. The backend translation uses the corresponding Vulkan stage bits.
- Wait-stage masks with value 0 or reserved bits return BadValue; rejection is atomic and leaves Fence/Semaphore states unchanged.
- On a Compute queue, all four individually defined stage bits are valid. On a transfer-only queue, only TRANSFER and ALL_COMMANDS are valid. COMPUTE_SHADER on a non-Compute queue, and DRAW_INDIRECT without Graphics or Compute support, return INVALID_SYNCHRONIZATION_STATE.
- Combined masks containing multiple supported stages (for example, COMPUTE_SHADER | TRANSFER) are accepted; ALL_COMMANDS | COMPUTE_SHADER is also accepted and translated correctly as the OR of the Vulkan stage bits. A mask containing an unsupported stage is atomically rejected with INVALID_SYNCHRONIZATION_STATE.
- ShaderModuleData: single-request CREATE|FINAL, multi-part upload, exact concatenation without padding bytes, valid flag combinations, and zero padding.
- An error in any Shader chunk discards the entire assembly; a FINAL error leaves no live Shader Module; ABORT releases assembly memory.
- Upload limits and aggregate assembly-memory limits are checked before allocation.
- CreateDescriptorSetLayout validates the exact length 24 + 16 * binding_count, flags = 0, unique bindings, positive descriptor counts, and supported descriptor/stage values. Unknown Device XIDs return BadValue; live resources of the wrong type or foreign ownership return BadMatch; unavailable/lost Devices return DEVICE_UNAVAILABLE / DEVICE_LOST; backend allocation failure returns ALLOCATION_FAILED. On rejection, the target XID remains unallocated.
- An empty Descriptor Set Layout with binding_count = 0 is valid; invalid binding records or nonzero layout flags leave no public object.
- A payload inconsistent with the count returns BadLength; unsupported flags, types, or stage bits are rejected.
- CreateCommandPool validates the queue-family index and reserved pool flags. Unknown Device XIDs and invalid queue-family indices return BadValue; live resources of the wrong type or foreign ownership return BadMatch; unavailable/lost Devices return DEVICE_UNAVAILABLE / DEVICE_LOST; backend allocation failure returns ALLOCATION_FAILED. On rejection, the pool XID remains unallocated; DestroyCommandPool invalidates all children atomically.
- CreateCommandPool accepts only TRANSIENT and RESET_COMMAND_BUFFER. Unknown pool flags are rejected with BadValue and are not silently added.
- TRANSIENT does not change observable semantics; RESET_COMMAND_BUFFER and TRANSIENT may be combined independently.
- ResetCommandBuffer without RESET_COMMAND_BUFFER is rejected. With the flag, it resets INITIAL, RECORDING, EXECUTABLE, or INVALID to INITIAL and discards entries and recorded references.
- ResetCommandBuffer while PENDING is atomically rejected; state and references remain unchanged.
- CommandBufferData ABORT may reset a non-pending RECORDING buffer to INITIAL regardless of the pool reset flag, but is invalid for other states. It remains permitted as logical cleanup after Device loss if the Buffer and Pool are still live and correctly associated.
- After Device loss, CREATE/append/FINAL chunks of CommandBufferData are rejected with DEVICE_LOST and do not change previously accepted entries or references; ABORT starts no Vulkan work.
- CommandBufferData validates all entries in a chunk before appending; if any entry in the chunk is invalid, none of that chunk is appended.
- After a failed CommandBufferData chunk, previously accepted chunks remain; a corrected chunk may follow, or ABORT may reset the Buffer to INITIAL.
- Failed CREATE leaves no Command Buffer; failed FINAL leaves the existing Buffer in RECORDING.
- ABORT is invalid in INITIAL, EXECUTABLE, INVALID, or PENDING and changes no state.
- The central request registry contains 47 unique, explicitly assigned subopcodes (1–47): 1–40 for the compute-baseline profile and 41–47 exclusively for the presentation-capable profile. Subopcode 0 is reserved, no value is duplicated, and future requests MUST NOT shift or reuse existing values.
- The Command Entry Registry assigns IDs 1–4 uniquely to CMD_BIND_PIPELINE, CMD_BIND_DESCRIPTOR_SETS, CMD_DISPATCH, and CMD_PUSH_CONSTANTS. ID 5 identifies CMD_COPY_BUFFER_TO_SWAPCHAIN_IMAGE only in the presentation-capable profile; a compute-only server rejects this entry as an unknown command ID with BadValue. ID 0 and all other unassigned IDs return BadValue.
- The Descriptor Type Registry defines only STORAGE_BUFFER = 1 in v0.1; 0 and all unassigned values are rejected and MUST NOT be silently reinterpreted.
- The Shader Stage Registry defines only the COMPUTE bit 0x00000001; all other bits are reserved and MUST be rejected.
- Queue flags are translated and returned according to the central registry; bits 5–31 are zero/reserved.
- PHYSICALDEVICEINFO.device_type contains only registered values 0–4; unknown native categories are mapped to OTHER = 0.

## Presentation lifecycle race and atomicity vectors

The presentation-capable conformance suite MUST exercise the following serialized race pairs. A test controls the serialization order explicitly; wall-clock timing alone is not a valid oracle.

- **Acquire timeout versus lifecycle:** if timeout/zero-timeout poll terminalizes first, the reply remains TIMEOUT/NOT_READY and a later resize, Surface loss, Device loss, or DestroyDevice cannot rewrite it. If a lifecycle transition terminalizes first, the reply is respectively DEVICE_LOST, SURFACE_LOST, OUT_OF_DATE, or DEVICE_DESTROYED according to the AcquireNextImage precedence; no image is acquired and neither optional semaphore nor fence is signaled.
- **Acquire synchronization eligibility versus timeout:** combine an unavailable image and `timeout_ns = 0` with an ineligible supplied semaphore, an ineligible fence, and a conflicting pending acquire in separate vectors. Each must return `INVALID_SYNCHRONIZATION_STATE` before `NOT_READY`/`TIMEOUT`, with no registration, image transition, or signal; repeat with an available image to prove eligibility is validated before the success commit as well.
- **DestroyDevice versus pending acquire:** DestroyDevice terminalizes each still-open registration with DEVICE_DESTROYED and invalidates the owned Swapchain. It must not overwrite an already-terminal acquire reply. Registration-only references are released exactly once; disconnect suppresses delivery but not cleanup.
- **DestroySurface versus CreateSwapchain:** if CreateSwapchain commits first, the new live Swapchain reference causes DestroySurface to fail atomically with INVALID_SYNCHRONIZATION_STATE. If DestroySurface commits first, the later CreateSwapchain fails at Surface-XID resolution and publishes no target XID or backing resource.
- **DestroyDevice versus CreateSwapchain:** if DestroyDevice serializes before XID resolution, the request reports BadValue for the now non-live Device XID. If Device loss (without destruction) serializes first, it returns the DEVICE_LOST status. If creation commits first, the Device destruction cascade invalidates the newly published Swapchain. No interleaving may publish a partially initialized Swapchain.
- **Resize/window destruction versus CreateSwapchain preparation:** lifecycle changes that serialize before the atomic commit point must be observed during commit-time revalidation; return OUT_OF_DATE or SURFACE_LOST (DEVICE_LOST has higher precedence), with target XID unallocated and all provisional references/resources released exactly once. If creation commits first, its success reply is not retroactively changed; the later lifecycle transition updates the published state.
- **QueuePresent rejection versus accepted state:** a rejected QueuePresent leaves the image ACQUIRED, reserves neither presentation_token nor wait slots, consumes no semaphore payload, and creates no presentation operation. Retry with the same token is permitted unless an earlier attempt was accepted. Acceptance atomically reserves token and waits and changes ACQUIRED to PRESENT_PENDING.
- **Accepted presentation versus resize/Surface loss/Device loss:** exactly one terminal status wins by serialization order. A terminalized operation cannot emit a second PRESENTATION_COMPLETE or later change status. IMAGE_RELEASED is permitted only when backend access has ended and the image remains reusable in a usable Swapchain; otherwise the image is invalidated and no release event is emitted.
- **DestroySwapchain versus pending references:** recording command buffers, pending acquire registrations, accepted presentation operations, queue submissions, and backend access block destruction. An acquired-but-idle image alone does not. Rejection preserves the public XID and all references; success invalidates the public XID and all image indices atomically, while internal release may be deferred.
- **Semaphore uncertainty after accepted presentation failure:** resolve each reserved wait independently. Proven non-consumption releases its reservation without losing a valid signal; proven consumption records consumption; uncertainty marks that binary semaphore UNTRUSTED. Never silently reset it to UNSIGNALED. These internal transitions occur even if events are masked or the client disconnected.

Every vector must assert both externally observable result (X11 error versus normal reply/status versus optional XGE event) and internal invariants (public XID visibility, image state, token reservation, semaphore state, pending-reference count). Include at least one case per vector with presentation event masks disabled to verify that event selection does not suppress terminalization or cleanup. Run the vectors in both request byte orders wherever wire parsing is involved. These are required conformance cases; they do not claim runtime implementation coverage until an implementation test harness executes them.

## Queue-Reihenfolge und Fortschritt

- Submissions derselben Queue werden in der Annahmereihenfolge eingereiht; unabhängige Arbeit darf sich überlappen.
- Zwischen verschiedenen Queues besteht ohne explizite Synchronisation keine zugesicherte Reihenfolge oder Memory-Visibility.
- Queueübergreifende Abhängigkeiten werden mit Semaphore-Signal und -Wait hergestellt. Erforderliche Memory-Dependencies werden separat nach Vulkan-Regeln geprüft.
- Fence-Waits und Host-Semaphore-Waits beobachten Zustände, erzeugen aber selbst keine Queue-seitige Abhängigkeit.
- Ein Host-Signal kann einen Queue-Wait auf denselben Semaphore-Wert freigeben, ordnet aber keine unverbundene GPU-Arbeit.
- Submission-Tokens und Event-Sequence-Nummern sind keine Ordnungswerte.
- Für unabhängige Queues sind weder Fairness noch eine feste maximale Scheduling-Latenz zugesichert.

## XGE- und Reply-ABI

- Jeder XAverius-XGE-Event-Header ist genau 32 Bytes groß: `response_type = 35`, `extension` ist der ausgehandelte XAverius-Major-Opcode, `sequence` liegt bei Offset 2, `length` bei Offset 4 und `evtype` bei Offset 8; Header-Padding bei Offset 10–31 ist null.
- XGE-Längen werden als `32 + 4 * length` geprüft: `ASYNC_ERROR` 60 Bytes/length 7; `DEVICE_LOST`, `DEVICE_STATUS_CHANGED`, `DEVICE_MEMORY_PRESSURE` und `DEVICE_IDLE` je 48 Bytes/length 4; `SUBMISSION_COMPLETE` und `SUBMISSION_FAILED` je 56 Bytes/length 6.
- Event-`evtype`-Werte stimmen exakt mit der Event-Registry überein (0–6); der dynamische Extension-Major-Opcode wird nicht als Event-Type-ID verwendet.
- Die event-spezifischen Felder beginnen bei Offset 32. Alle als reserviert definierten Felder sind null; `SUBMISSION_COMPLETE` und `SUBMISSION_FAILED` unterscheiden sich bei Offset 44 (reserviert null bzw. `failure_class`) und dürfen für dieselbe angenommene Submission nicht beide als terminales Event auftreten.
- `SelectEvents` hat exakt 32 Bytes, ist als Void-Request unter Subopcode 40 registriert und besitzt null Flags (Offset 5) sowie ein null-reserviertes Common-Header-Feld (Offset 6). Die Scope-spezifischen Felder liegen bei Offset 8–31; der Prüfer kontrolliert Layout und Registrierung gemeinsam. Der Event-Maskenwert wird anhand des Scopes validiert; Fehler ändern die vorherige Auswahl nicht.
- Feste Replies sind 32 Bytes mit `reply.length = 0`, sofern keine Payload über Offset 32 hinausgeht. Bei variabler Payload bezeichnet `reply.length` ausschließlich die gepaddeten Vierbyteeinheiten nach Offset 32; Payload-Bytes und Null-Padding werden getrennt geprüft.
- `GetFenceStatus` legt den Fence-Status in Reply-Byte 1 ab; Offset 0 bleibt `response_type`, Offsets 2–3 Sequenznummer und Offsets 4–7 `reply.length = 0`. Die restlichen XAverius-reservierten Bytes sind null.

# Presentation-profile conformance cases (future profile)

The following cases apply only when the server implements the presentation-capable profile; they do not expand the compute-only baseline by implication.

- Surface creation binds the exact internal identity of an existing X11 Window. Unknown/non-Window IDs fail synchronously, a failed create leaves the target XID unallocated, and destroying/reusing the numeric Window XID never retargets an existing Surface.
- Surface is connection-owned and can be queried against more than one logical Device. A Surface destroy with a live Swapchain reference is rejected atomically. Device destruction invalidates device-owned Swapchains but does not implicitly destroy the connection-owned Surface.
- A Swapchain image is identified only by (Swapchain XID, image_index), has no independent XID, and cannot be acquired twice concurrently. Invalid indices and invalid image-state transitions leave state unchanged.
- Capability query returns a self-consistent variable-length reply: exact total size is 64 + 8 * format_pair_count + 4 * present_mode_count + 8 * queue_family_count; reply.length is 8 + 2 * format_pair_count + present_mode_count + 2 * queue_family_count. Count arithmetic must be overflow-checked. Queue-family support records contain exactly one ascending-index record per physical queue family. A zero-sized window reports TEMPORARILY_NOT_PRESENTABLE without blocking.
- CreateSwapchain either creates exactly the requested image_count and returns that count, or leaves the target XID unallocated. Unreported format/color-space pairs, modes, and usage bits are rejected atomically.
- `CMD_COPY_BUFFER_TO_SWAPCHAIN_IMAGE` accepts only a 36-byte entry with command ID 5, `entry_length = 9`, and zero reserved field; it requires a `TRANSFER_SRC` Buffer, `TRANSFER_DST` Swapchain image usage, an in-range image index, and an image in `ACQUIRED` state at submission validation. Reject bad alignment, too-small row/image dimensions, out-of-bounds source span, arithmetic overflow, and incompatible usage atomically; the last-byte calculation must use overflow-safe wide arithmetic. Verify RGBA8/BGRA8 channel order is preserved without implicit format or color-space conversion, and a rejected entry appends no partial command.

- Mixed-failure tests for `CMD_COPY_BUFFER_TO_SWAPCHAIN_IMAGE` must verify the specified stage order: malformed entry length/reserved field beats every later failure; bad `buffer_offset` alignment or invalid row/image dimension syntax beats an invalid Buffer-XID; invalid Buffer-XID beats an invalid Swapchain-XID; unknown Swapchain-XID beats resource-dependent image-index and bounds checks; wrong live resource type/ownership beats usage incompatibility; an out-of-range image index or out-of-bounds source span beats usage incompatibility; and all these synchronous validation failures beat the submission-time image-state check. Every rejection must leave the complete CommandBufferData chunk unattached and preserve image, Swapchain, semaphore, and reference state. Test checked-arithmetic overflow separately from ordinary bounds failure.
- `AcquireNextImage` with `timeout_ns = 0` returns `NOT_READY` when no image is immediately available; expiration of a finite positive timeout returns `TIMEOUT`. Every non-success reply has `image_index = 0`; no failure signals the optional semaphore/fence or changes image state. Semaphore and fence are independently optional and may both be supplied; on SUCCESS each supplied eligible same-device object is signaled exactly once. A successful acquire returns a valid image index; timeline semaphore acquisition signals are rejected.
- QueuePresent rejection leaves the image ACQUIRED and does not consume wait semaphores. An accepted present moves the image to PRESENT_PENDING; request success does not imply GPU completion, image release, or presentation completion.
- QueuePresent reserves each binary wait atomically with acceptance and uses the same one-pending-wait rule as QueueSubmit. Acceptance does not consume the signal; a confirmed backend wait does. If an accepted present fails before wait completion, each semaphore preserves confirmed unconsumed state, records confirmed consumption, or becomes UNTRUSTED if payload outcome is uncertain. UNTRUSTED waits fail with DEPENDENCY_FAILED; incompatible pending waits fail atomically with INVALID_SYNCHRONIZATION_STATE.
- IMAGE_RELEASED and PRESENTATION_COMPLETE are distinct milestones and may arrive in either order. Each accepted present has one internal terminal presentation transition and one internal image-release-or-invalidation transition. PRESENTATION_COMPLETE is enqueued only if Queue mask bit 3 is set at its terminal point and connection/device lifecycle permit delivery. IMAGE_RELEASED is enqueued only if the image is reusable, Queue mask bit 2 is set at its release point, and connection/device lifecycle permit delivery. Masking or suppressed delivery never skips internal cleanup. If the image is invalidated, no IMAGE_RELEASED is enqueued. No new events are enqueued after DestroyDevice for that Device; previously enqueued events remain unaffected. Disconnect suppresses delivery without skipping internal terminal cleanup. An image is reacquirable only after internal release; the event is visible only under its delivery conditions.
- Presentation event race vectors MUST exercise both milestone orders: image release before presentation completion and presentation completion before image release. Change the Queue event mask between the two milestones and verify each event independently samples the mask at its own milestone; no later mask change retroactively adds or removes an already decided event. For every accepted present, assert exactly one internal presentation terminal transition and exactly one image-release-or-invalidation transition, regardless of event masking or delivery suppression.
- Race resize, Window destruction, Device loss, `DestroyDevice`, and client disconnect against each accepted-present terminal milestone. The first serialized terminal outcome wins; later lifecycle signals cannot rewrite it or emit a duplicate event. A terminal failure that invalidates the image MUST NOT emit `IMAGE_RELEASED`; a reusable image may emit it only after backend quiescence. `DestroyDevice` and disconnect suppress new event delivery according to the lifecycle rules but MUST still complete semaphore resolution, terminal state changes, and backend/reference cleanup. Verify delayed backend callbacks carry the original internal identities and cannot enqueue events for a reused Swapchain XID or a different connection.
- Each presentation event's Queue mask is sampled independently at its own terminal milestone (image-release eligibility versus presentation completion); later `SelectEvents` changes cannot retroactively change that event's delivery decision.
- Resize marks the old Swapchain OUT_OF_DATE, prevents new acquire/present acceptance, and allows replacement creation while old work drains. Window destruction marks the Surface SURFACE_LOST; no XID reuse can revive it.
- Destroy the underlying X11 Window while its Surface exists, then reuse the numeric Window XID for a new Window on the same connection. The original Surface remains live but `SURFACE_LOST`; `GetSurfaceCapabilities` must report `SURFACE_LOST`, and `CreateSwapchain`, `AcquireNextImage`, and `QueuePresent` must not resolve the old Surface through the reused Window XID. `CreateSwapchain` must leave its target XID unallocated on this status. The new Window must not inherit the old Surface. `DestroySurface` remains available once no live Swapchain references the Surface; its internal Window identity is retained until all remaining Surface/backend references are quiescent.
- Destroy a `SURFACE_LOST` Surface after its final live Swapchain has been destroyed, while a delayed Window notification or internal backend/tombstone reference is still being retired. `DestroySurface` must succeed because internal retained references are not request-level blockers; it invalidates the public Surface XID atomically, while internal identity references remain until quiescent. Deliver the delayed notification after reusing the Surface XID and verify it cannot affect the new resource or enqueue an event for it. Conversely, if any live Swapchain still references the Surface, `DestroySurface` must fail atomically with `INVALID_SYNCHRONIZATION_STATE` and preserve the public XID and all references.
- Unmap and remap a Window without changing its pixel extent. These transitions alone must not mark its Swapchain `OUT_OF_DATE`, mark the Surface `SURFACE_LOST`, change resource identity, or imply GPU/presentation completion. Separately test resize and destruction so the implementation cannot conflate all X11 lifecycle notifications.
- Accepted-present terminalization is serialized exactly once: resize permits `SUCCESS` only if the accepted operation still reaches its completion point, otherwise `OUT_OF_DATE`; a destroyed Window yields `SURFACE_LOST` for still-pending operations that cannot complete, and Device Loss yields `DEVICE_LOST`. These lifecycle failures invalidate the affected image/Swapchain and do not emit `IMAGE_RELEASED`; a later lifecycle notification cannot overwrite an already serialized terminal result.
- `PRESENTATION_FAILED` emits `IMAGE_RELEASED` only after backend quiescence is established and the image remains reusable in a usable Swapchain; otherwise the image/Swapchain is invalidated. Internal cleanup completes exactly once even when event delivery is suppressed.
- Conformance validation must check presentation event IDs 7 and 8 with total lengths 64 and 64 bytes respectively, and queue event-mask bits 2 and 3 are rejected by compute-only implementations.

If `CreateSurface` binds before destruction, the resulting Surface becomes `SURFACE_LOST`; if destruction occurs first and the XID remains unbound, it returns `BadWindow`. Separately destroy a Window, create a new Window using the same numeric XID, then issue `CreateSurface`: it may bind to the new Window identity. Verify that no existing Surface bound to the old identity is redirected to the replacement. Preserve same-connection X11 request order in every case.

The resource-lifetime matrix must state the same rule.
- `DestroySwapchain` lifetime boundary vectors MUST distinguish public invalidation from internal release. If no blocker exists, invalidate the Swapchain XID and all image indices atomically; backing storage may be released immediately only if backend quiescence is proven, otherwise retain the exact internal image/Swapchain identity until every backend access is terminal. An acquired-but-idle image alone is not a blocker and must not require a synthetic present/release operation.
- Race `DestroySwapchain` against the final submission completion, presentation terminalization, acquire terminalization, and backend-access retirement. The first serialized state transition determines whether destroy is rejected or succeeds; a completion arriving after successful destroy may release only the old internal identity and MUST NOT resolve the numeric Swapchain XID again. Reuse the Swapchain XID for a new resource before delivering a delayed completion and verify the new resource, its image indices, and its references are unchanged. Check both event orders (completion before destroy validation and destroy validation before completion) and require exactly-once release of every retained image/backend reference.

Every physical queue family has exactly one ordered support record. Temporary-not-presentable, surface-lost, and device-lost statuses return zeroed capability fields as specified.
- `CreateSwapchain` validates image count and extent bounds, a reported format/color-space pair, a reported mode, and advertised usage bits against current capabilities. A zero-sized Surface or requested extent outside current supported bounds returns `OUT_OF_DATE`; however, a requested width or height of zero is rejected earlier as `BadValue` during scalar validation. A valid but unsupported configuration returns `UNSUPPORTED_CONFIGURATION`. Success provides the exact requested image count; every non-success reply sets `actual_image_count = 0` and leaves the target Swapchain XID unallocated.
- `AcquireNextImage` timeout, not-ready, out-of-date, surface-lost, device-lost, and device-destroyed results neither signal the supplied semaphore/fence nor change image state. `DestroyDevice` terminates an open acquire with `DEVICE_DESTROYED` without waiting for image availability; an already serialized terminal result wins. Disconnect suppresses the reply but removes the registration and releases registration-only references safely. Destroying the referenced Swapchain or Surface while the acquire is pending remains rejected.
- Keep an acquire pending with an infinite timeout and independently trigger Swapchain resize/zero extent, Window destruction, Device loss, and `DestroyDevice`. Verify each still-open registration terminates promptly with `OUT_OF_DATE`, `SURFACE_LOST`, `DEVICE_LOST`, or `DEVICE_DESTROYED` respectively, without signaling its semaphore/fence or transitioning an image to `ACQUIRED`. Race each lifecycle trigger against timeout expiry and successful acquisition; the first serialized terminal result wins, later notifications cannot rewrite it, and registration-only references are released exactly once. Repeat with disconnect, where reply delivery is suppressed but cleanup still completes.
- `QueuePresent` has total request size `40 + 4 * wait_semaphore_count` and a 36-byte reply with status values 0 `SUCCESS`, 1 `OUT_OF_DATE`, 2 `SURFACE_LOST`, and 3 `DEVICE_LOST` (local to the reply field). Duplicate waits, token zero/reuse, wrong resource types, invalid image state, and non-existent queues follow the specific error mapping; rejection does not consume waits or transition the image.
- A successful `QueuePresent` reply means accepted, not displayed. Image release and presentation completion are separate terminal events and may be observed in either order; each accepted presentation gets at most one of each event.

- Presentation error precedence is tested with mixed-failure requests: malformed length/overflow beats all field checks; invalid scalar syntax (including zero token or duplicate waits, but not reuse of an accepted token) beats XID resolution; XIDs are resolved in wire-field order; live type/ownership errors beat Device and lifecycle outcomes; Device loss beats Surface loss and accepted-token reuse; Surface loss and OUT_OF_DATE beat accepted-token reuse; unsupported queue presentation capability is `BadMatch` before token reuse; accepted-token reuse returns `BadValue` before image-state and semaphore-eligibility checks. The expected winner is the first failing stage. A rejected request causes no partial state mutation attributable to that request; independent lifecycle transitions that race with it are not rolled back.
- `CreateSurface` validates the target create-XID before the Window XID; `CreateSwapchain` validates `device_xid`, target `swapchain_xid`, then `surface_xid` after scalar syntax. Failed creates leave target XIDs unallocated and retain no references.

- `GetSurfaceCapabilities` MUST be queried with the exact requested Device/Surface pair. The same live Surface may be queried with two different owned Devices; each query independently reports that pair's presentation support. A valid Device/Surface pair that cannot present returns `SUCCESS` with `present_supported = 0`, not `BadMatch` merely because the Surface is not Device-owned.
- `GetSurfaceCapabilities` precedence vectors MUST separately combine (a) Device loss with Surface loss, expecting `DEVICE_LOST`; (b) a live zero-extent Surface with a usable Device, expecting `TEMPORARILY_NOT_PRESENTABLE`; and (c) Surface loss with a stale zero-extent snapshot, expecting `SURFACE_LOST`, never `TEMPORARILY_NOT_PRESENTABLE`. The zero-extent status applies only while the Surface is live.
- `GetSurfaceCapabilities` wire-vector tests MUST cover a successful presentable result with nonempty format, mode, and queue-family arrays; a successful but non-presentable Device/Surface pair with `present_supported = 0`; and each status result with every capability field other than `status` zero, all three counts zero, and no trailing payload. For successful replies, `present_supported` MUST equal the logical OR of all queue-family `present_supported` values; every record's support value is exactly 0 or 1, queue-family indices are unique and strictly ascending, and the queue-family record count equals the number of physical queue families. Check that format/color-space pairs and presentation modes are serialized in the same order as their advertised count and that no padding or uncounted bytes appear between or after arrays. For each vector, decode the reply using the connection byte order and verify both `reply.length * 4 + 32` and the actual packet size equal `64 + 8 * format_pair_count + 4 * present_mode_count + 8 * queue_family_count`. Include boundary cases where `format_pair_count` and `present_mode_count` are individually zero where semantically permitted, mixed zero/nonzero format/mode counts, and the largest representable count tuple whose total fits the protocol's reply-length field. Do not use a successful reply with `queue_family_count = 0` as a boundary vector: successful capability replies require at least one queue-family record, while non-success replies require all three counts to be zero; a tuple whose checked wide-arithmetic total exceeds the CARD32 X11 reply-length-field capacity MUST be rejected before allocation/serialization and MUST NOT wrap, truncate, or emit a partial reply. Verify the same checked arithmetic is used before allocation and before writing any record.
- `CreateSwapchain` returns `DEVICE_LOST` before `SURFACE_LOST`, `SURFACE_LOST` before `OUT_OF_DATE`, and `OUT_OF_DATE` before `UNSUPPORTED_CONFIGURATION`. Every non-success reply has `actual_image_count = 0` and leaves the target XID unallocated.
- `CreateSwapchain` extent vectors MUST distinguish a zero-sized current Window extent (`OUT_OF_DATE`) from a requested width or height of zero (`BadValue` during scalar validation). If the Device is lost or the Surface is lost at the serialized status check, those lifecycle statuses win before extent/configuration outcomes as specified. A requested nonzero extent outside current supported bounds returns `OUT_OF_DATE`; a valid in-bounds extent with an unsupported format/mode/usage returns `UNSUPPORTED_CONFIGURATION`.
- `CreateSwapchain` status-vector tests MUST exercise all six defined numeric values (`SUCCESS=0`, `OUT_OF_DATE=1`, `SURFACE_LOST=2`, `DEVICE_LOST=3`, `UNSUPPORTED_CONFIGURATION=4`, `ALLOCATION_FAILED=5`) and confirm that the status namespace is local to this reply. `ALLOCATION_FAILED` is reachable only after XID/ownership, lifecycle, extent, and requested-configuration validation all succeed; it MUST NOT mask `DEVICE_LOST`, `SURFACE_LOST`, `OUT_OF_DATE`, or `UNSUPPORTED_CONFIGURATION`. For each of the five non-success statuses, `actual_image_count` is zero and the target Swapchain XID remains unallocated; for `SUCCESS`, it equals the exact requested count. Inject allocation failure at each allocation point and verify atomic cleanup of partial image/backing allocations and references.
- Mixed-failure `CreateSwapchain` cases verify that a zero requested width/height (`BadValue`) and an invalid target create-XID (`BadIDChoice`) are reported before Device-loss or Surface-lifecycle statuses; after scalar and XID/type/ownership validation succeeds, `DEVICE_LOST` wins over `SURFACE_LOST`, which wins over `OUT_OF_DATE`, which wins over `UNSUPPORTED_CONFIGURATION`. Each failure leaves `swapchain_xid` unallocated and returns `actual_image_count = 0`.
- `CreateSwapchain` stage-boundary vectors MUST distinguish Device-state validation from immutable-identifier validation: after scalar syntax, XID resolution, type, ownership, and cross-device checks, a lost Device returns `DEVICE_LOST` even when the request also contains an unknown format, color-space, or present-mode identifier or unassigned usage bits. With a usable Device, those syntactically invalid identifiers/bits return `BadValue` before Surface lifecycle outcomes; with valid identifiers, `SURFACE_LOST` wins over zero-current-extent or out-of-bounds `OUT_OF_DATE`, which wins over a syntactically valid but unsupported configuration. Keep requested zero width/height in the earlier scalar-validation stage, so it remains `BadValue` even when the Device is lost. Each mixed vector MUST assert the exact winner and that the target XID remains unallocated with `actual_image_count = 0` and no retained Surface, Device, image, or backend references attributable to the rejected request.

For each injected failure, require `ALLOCATION_FAILED`, `actual_image_count = 0`, no visible target XID, no partially enumerable images, no leaked backing/backend objects, and balanced reference counts. Retry the identical request after removing the fault and require success with exactly `image_count` images, proving failed attempts leave no stale reservation. Race each publication boundary against `DestroySurface`, `DestroyDevice`, Window resize, and Window destruction; the serialization/commit point MUST produce either a fully published Swapchain that then observes the independent lifecycle transition, or a wholly rejected create with no request-owned partial state—never a partially visible resource set.
- `AcquireNextImage` lifecycle outcomes precede timeout polling: `DEVICE_LOST`, then `SURFACE_LOST`, then `OUT_OF_DATE`; `NOT_READY` is only the zero-timeout result for a usable Swapchain with no immediately available image, and `TIMEOUT` is only returned when a finite timeout expires. `DEVICE_DESTROYED` applies only to a pending acquire terminalized by `DestroyDevice`, with the first serialized terminal result winning. Every non-success result has zero `image_index` and signals neither optional synchronization object.
- `AcquireNextImage` mixed-failure tests MUST distinguish synchronization-object resolution from synchronization eligibility: an unknown/non-live optional semaphore or fence XID (`BadValue`), or a live wrong-type/foreign/cross-Device object (`BadMatch`), is reported before lifecycle status; after all XIDs, types, and ownership validate, `DEVICE_LOST` beats `SURFACE_LOST`, which beats `OUT_OF_DATE`, and these lifecycle outcomes beat an otherwise valid but ineligible semaphore/fence state and timeout polling. Exercise both optional objects separately and together, with zero, finite, and infinite timeouts. Every rejected vector must leave both synchronization objects unchanged and unsignaled and must not acquire an image; do not let a stale/ineligible sync state mask a higher-priority lifecycle status.
- `AcquireNextImage` reply-vector tests MUST exercise all seven defined numeric status values (`SUCCESS=0`, `TIMEOUT=1`, `NOT_READY=2`, `OUT_OF_DATE=3`, `SURFACE_LOST=4`, `DEVICE_LOST=5`, `DEVICE_DESTROYED=6`) and verify that this status namespace is independent of `CreateSwapchain`, `QueuePresent`, and event statuses. Every reply is exactly 44 bytes with `reply.length = 3` and `reserved = 0`; `image_index` is nonzero only when the actual acquired index is nonzero on `SUCCESS`, and is exactly zero for every non-success result. For each non-success vector, verify neither optional synchronization object is signaled and no image transitions to `ACQUIRED`. Include index zero as a valid successful acquisition so tests do not incorrectly infer success from a nonzero index.

Every vector MUST assert the winning result and verify no request-attributable token reservation, wait reservation/consumption, or image transition on rejection. Keep independent lifecycle invalidation intact.
- After `QueuePresent` lifecycle status checks, image state is validated before wait semaphores; if the image is `ACQUIRED`, wait semaphores are checked in array order. An `UNTRUSTED` wait yields `DEPENDENCY_FAILED`; another incompatible semaphore state or pending wait yields `INVALID_SYNCHRONIZATION_STATE`. Zero token, duplicate wait XIDs, and accepted-token reuse are `BadValue`; tokens from rejected attempts remain reusable. Acceptance atomically reserves the token and all wait slots and changes `ACQUIRED` to `PRESENT_PENDING`; any rejection leaves pre-request image/semaphore states unchanged and does not restore an image invalidated by an independent lifecycle transition.
- A buffer-to-swapchain-image command requires an acquired image at submission acceptance, retains the exact Swapchain/image identity while pending, and prevents backing storage from being freed until the submission and backend accesses are terminal.
- If `QueueSubmit` is accepted before `QueuePresent`, the submission keeps its exact image/Swapchain references and presentation requires the specified GPU semaphore dependency where the submission may access the image; a copy submission processed after the image has transitioned to `PRESENT_PENDING` is atomically rejected with `INVALID_SYNCHRONIZATION_STATE`. Request order alone is not a GPU dependency.
- Destroying a Buffer referenced by a `RECORDING` command buffer is atomically rejected with `INVALID_SYNCHRONIZATION_STATE`; successful Buffer destruction invalidates all non-pending executable command buffers that still reference it.
- The provisional copy entry rejects unknown Buffer/Swapchain XIDs with `BadValue`, wrong live types/ownership/device or incompatible transfer usage with `BadMatch`, malformed dimensions/alignment/out-of-range source spans and invalid image indices with `BadValue`, and a non-`ACQUIRED` image at submission acceptance with `INVALID_SYNCHRONIZATION_STATE`; every rejection is atomic.
- Resize/out-of-date, Window destruction/surface-lost, and device loss prevent new acquire/present operations while preserving safe terminal cleanup of previously accepted work. Accepted present operations reach a terminal status; a non-reusable image is invalidated rather than left PRESENT_PENDING.


## Request framing, maximum length, and BIG-REQUESTS

- XAverius v0.1 rejects BIG-REQUESTS framing: an XAverius request whose original X11 16-bit `length` field is zero is rejected as `BadLength` before offset 4 is interpreted as the XAverius common header.
- A normal request of exactly 262140 bytes is the maximum permitted size; a request that would exceed 262140 bytes is rejected with `BadLength`, even if its variable-length formula and counts are otherwise internally consistent.
- Variable-length request formulas are evaluated with checked arithmetic. Counts that overflow the formula, a computed size above 262140 bytes, a declared-length mismatch, or trailing/truncated payload bytes all produce `BadLength` before payload allocation, XID lookup, or state mutation.
- Chunked `WriteBuffer`, `ShaderModuleData`, and `CommandBufferData` requests enforce the limit per wire request. The aggregate logical upload/recording may exceed the limit only by using multiple valid chunks; a single oversized chunk is rejected.
- For each rejection above, no partial resource creation, upload commit, command-buffer append/finalization, queue-submission acceptance, or event-mask change occurs.

- Fehlerpräzedenz für mehrteilige Requests: Bei `BindBufferMemory` schlägt ein unbekanntes XID (`BadValue`) einen Device-Loss-Fehler; falscher live Typ/fremde Ownership (`BadMatch`) schlägt Device Loss; nach gültigen XIDs und Ownership schlägt `DEVICE_LOST` einen bereits gebundenen Buffer oder inkompatiblen Memory-Type. For `UpdateDescriptorSets`, length/field syntax and unknown XIDs take precedence over Device/state errors; after XID/type/ownership validation, `DEVICE_LOST` takes precedence over layout/binding incompatibility and a pending-set conflict. All rejected requests remain atomic and change no binding, descriptor slots, or internal references.

- Fehlerpräzedenz für Create-/Batch-Requests: `AllocateDescriptorSets` prüft zuerst Länge und Feldsyntax, dann Ziel-Set-XIDs in Array-Reihenfolge (`BadIDChoice`), dann Device-/Pool-/Layout-Eingabe-XIDs in Wire-Reihenfolge (`BadValue`), danach Typ/Ownership (`BadMatch`) und Device-Zustand (`DEVICE_LOST`/`DEVICE_UNAVAILABLE`) vor Pool-Kapazität und Backend-Allokation. `CreatePipelineLayout` und `CreateComputePipeline` prüfen Feldsyntax vor Ziel-XID, Ziel-XID vor Eingabe-XIDs, dann Typ/Ownership und Device-Zustand vor geräteabhängigen Kompatibilitäts- bzw. Backend-Prüfungen. Jeder Fehler lässt alle Ziel-XIDs unangelegt.

- `ResetFence`-Fehlerpräzedenz: falsche Länge schlägt alle weiteren Prüfungen; unbekannte Device-/Fence-XIDs ergeben `BadValue`, falscher live Typ/Ownership/Cross-Device `BadMatch`; nach gültigen XIDs und Ownership gewinnt `DEVICE_LOST` vor `INVALID_SYNCHRONIZATION_STATE` für einen nicht zurücksetzbaren Fence-Zustand. Jede Ablehnung erhält den gespeicherten Fence-Zustand.


## Presentation request wire-layout audit (assigned, profile-gated ABI)

The request/reply framing matrix is cross-checked against [the presentation chapter](presentation.md#cross-request-wire-length-audit). Request sizes include the 8-byte X11/XAverius header; reply sizes include the 32-byte X11 reply header.

| Request | Request bytes | Normal reply bytes | Reply length field |
|---|---:|---:|---:|
| CreateSurface | 16 | none | — |
| DestroySurface | 12 | none | — |
| GetSurfaceCapabilities | 16 | 64 + variable records | 8 + 2×format_pair_count + present_mode_count + 2×queue_family_count |
| CreateSwapchain | 48 | 40 | 2 |
| DestroySwapchain | 12 | none | — |
| AcquireNextImage | 32 | 44 | 3 |
| QueuePresent | 40 + 4×wait_semaphore_count | 36 | 1 |

Conformance tests MUST verify every fixed request at exact length and at one four-byte unit shorter/longer, plus QueuePresent count/length mismatch and arithmetic overflow. Reply tests verify the X11 reply length field against the actual serialized byte count, zero reserved fields, and status-dependent fields. In particular, GetSurfaceCapabilities has a 64-byte minimum reply; each variable record contributes exactly the bytes specified in presentation.md. CreateSwapchain has a 48-byte request but a 40-byte reply; these lengths must not be conflated. AcquireNextImage's request is 32 bytes and its reply is 44 bytes. QueuePresent's request length varies with the semaphore count, but its reply is always 36 bytes.

For each request, mixed-failure tests verify framing before scalar syntax, scalar syntax before XID resolution, XID/type/ownership checks before lifecycle and mutable-state checks, and atomic rejection. CreateSurface and CreateSwapchain tests verify target-XID validation order and that failed creation leaves the target XID unallocated. QueuePresent tests verify that rejection neither consumes waits nor reserves the token nor transitions the image, while an accepted request commits token, wait reservations, references, and image transition together. Accepted asynchronous failure must produce one terminal presentation outcome and no delayed X11 request error. The mixed-failure matrix MUST specifically combine (a) Device loss with an invalid queue tuple or image index, (b) a nonexistent queue/index with Surface loss or OUT_OF_DATE, (c) Surface loss with OUT_OF_DATE, (d) a valid queue tuple without presentation support with a reused accepted token, and (e) a reused accepted token with an invalid image state or ineligible wait semaphore. Expected precedence is respectively DEVICE_LOST; BadValue for queue/index; SURFACE_LOST; BadMatch for missing presentation support; and BadValue for token reuse. In each case, also verify that no request-attributable token reservation, wait reservation/consumption, or image transition occurs. Repeat cases with malformed length, zero token, duplicate wait XIDs, and unresolved wait XIDs to confirm the earlier framing/scalar/XID stages take precedence.

Presentation lifecycle race tests MUST also cover the following serialized outcomes, not merely the request/reply bytes:

- Race `QueuePresent` acceptance against Surface loss, Swapchain resize/out-of-date, and Device loss. If the lifecycle transition is serialized before acceptance, return the specified normal status without reserving the token or wait slots; if acceptance is serialized first, preserve the accepted operation and terminalize it exactly once according to the first serialized terminal outcome.
- Race image release and presentation completion in both orders. Each accepted token may produce at most one `IMAGE_RELEASED` and at most one `PRESENTATION_COMPLETE`; masking either event must not skip its underlying state transition or resource cleanup. When `PRESENTATION_COMPLETE` is masked or delivery is suppressed, verify that terminal state and the corresponding safe-release or invalidation transition are still applied: success may leave a reusable image, while a failure that prevents reuse must invalidate the image and Swapchain. Do not require a later request to reproduce the exact terminal cause.
- Fail a backend wait before it consumes a signal, after confirmed consumption, and with an uncertain consumption result. Verify semaphore state is respectively preserved, updated, or marked `UNTRUSTED` as specified, and ensure the image is released only if reuse is safe; otherwise invalidate the image/Swapchain rather than leaving `PRESENT_PENDING` indefinitely.
- Reuse a token after a rejected status reply and after a synchronous validation error (both permitted), then reuse it after an accepted presentation (must fail with `BadValue`). Verify that a status reply does not hide higher-priority malformed-wire, scalar, XID, Device, queue/index, or lifecycle errors.
- Destroy the Swapchain after an acquired-but-idle image, after accepted presentation work, and while backend access is possible. The first case may succeed once GPU references are drained; the latter cases must reject atomically until all relevant references and accesses are terminal.

These are state-machine conformance tests; golden-wire tests alone cannot establish them.


- Keep QueuePresent reply status values separate from presentation-event terminal status values: the 36-byte QueuePresent reply uses only SUCCESS=0, OUT_OF_DATE=1, SURFACE_LOST=2, DEVICE_LOST=3; the 64-byte PRESENTATION_COMPLETE event additionally permits PRESENTATION_FAILED=4. A synchronously rejected QueuePresent must not emit either presentation event or reserve its token. Once accepted, later backend failure is reported only through the single terminal event/state transition, never as a delayed X11 error or by rewriting the original SUCCESS reply.
- Change the Queue mask between image-release eligibility and presentation completion, testing both orders: IMAGE_RELEASED delivery uses the mask sampled at the release milestone, and PRESENTATION_COMPLETE delivery uses the mask sampled at its terminal milestone. Changing a mask after one milestone must not retroactively suppress or create that milestone's event; suppressing delivery must still apply the corresponding internal state transition.
- At each terminal status (SUCCESS, OUT_OF_DATE, SURFACE_LOST, DEVICE_LOST, PRESENTATION_FAILED), verify the image's internal state and Swapchain usability agree with the status contract. In particular, an invalidated image never emits IMAGE_RELEASED; a safely reusable image is released at most once; late backend callbacks and later lifecycle notifications cannot emit a second terminal event or overwrite the first serialized terminal status.

- Exercise lifecycle transitions at each boundary around both presentation milestones: (a) resize/zero extent before QueuePresent acceptance, (b) resize after acceptance but before terminal completion, (c) resize after successful terminal completion but before backend image release, (d) Window destruction at each of those points, and (e) Device loss at each point. Before acceptance, require the defined status reply and no token/wait reservation. After acceptance, require exactly one terminal status based on the first serialized terminal outcome; a later lifecycle change must not rewrite it. If resize or loss makes the image non-reusable before the release milestone, invalidate it and omit IMAGE_RELEASED even when PRESENTATION_COMPLETE(SUCCESS) was already emitted.
- For each lifecycle case above, repeat with Queue mask bits 2 and 3 independently enabled, disabled, and changed between the two milestones. Event suppression must affect only wire delivery: it must not defer OUT_OF_DATE/SURFACE_LOST/DEVICE_LOST state changes, backend-reference release, or terminalization. No event may be created after successful DestroyDevice processing; events already queued before that point remain in the X11 output stream.
- Verify the old Swapchain replacement path after resize and zero extent: new AcquireNextImage/QueuePresent requests against the old Swapchain return OUT_OF_DATE without consuming waits or reserving tokens; a replacement Swapchain may be created only from current successful capabilities; DestroySwapchain remains blocked while accepted work or backend access holds references, but becomes legal once those references drain, even if an image remains acquired-but-idle or has been invalidated by lifecycle loss.
- Verify replacement creation does not implicitly destroy or transfer ownership from the old Swapchain: while the old Swapchain is `OUT_OF_DATE`, create a second Swapchain against the same live Surface using current capabilities, then retire the old one only when its explicit destroy blockers have drained. An acquired-but-idle image is invalidated by successful `DestroySwapchain` and does not require a present/release operation; image backing storage must nevertheless remain retained for any independent backend access.
- Race `CreateSwapchain` against `DestroySurface` and `DestroyDevice` at the commit boundary: if creation commits first, verify the live Surface reference makes `DestroySurface` fail atomically or that the subsequent Device cascade invalidates the child; if destruction commits first, verify creation cannot publish a Swapchain referencing the invalidated Surface/Device. In every ordering, public XIDs and internal references change exactly once. Specifically distinguish successful `DestroyDevice` before XID resolution (`BadValue` for the now non-live Device XID) from Device loss without destruction before state validation (`DEVICE_LOST`); both leave the target Swapchain XID unallocated.
- Race `CreateSwapchain` against Window resize, zero extent, Window destruction, and Device loss at the creation commit boundary. If the lifecycle transition serializes first, require the corresponding status (`DEVICE_LOST` before `SURFACE_LOST` before `OUT_OF_DATE`), an unallocated target XID, and no retained image/backend references. If creation commits first, require `SUCCESS` and then immediate lifecycle invalidation of the published Swapchain when the later transition is serialized; the create status must not be rewritten even if its reply is still queued. Inject allocation failure before commit and verify `ALLOCATION_FAILED` leaves no public XID, partial Swapchain, image, or retained request-owned reference. Repeat with stale capabilities from before the resize and require validation against the extent current at the commit point.

## `CreateDevice` mixed-failure and atomicity tests

The `CreateDevice` validation order in [the error mapping](errors.md) is normative. Conformance tests MUST exercise at least these mixed-failure pairs and assert that the earlier stage wins:

- Malformed total length plus an invalid or occupied `device_xid` → `BadLength`.
- A scalar/reserved-field or duplicate-record error plus an invalid or occupied `device_xid` → `BadValue`.
- Invalid or occupied `device_xid` plus unknown `physical_device_xid` → `BadIDChoice`.
- Unknown `physical_device_xid` plus missing XGE 1.0 negotiation → `BadValue`.
- Valid XIDs but missing XGE 1.0 negotiation plus an unsupported queue request or unsupported feature → `BadMatch` from the missing handshake.
- An unavailable Physical Device plus a well-formed but unsupported queue/feature/extension request → `DEVICE_UNAVAILABLE`.
- An unknown feature ID plus a registered-but-unsupported feature on the same request → `BadValue` for the unknown ID, because feature IDs are checked in wire-array order after earlier validation stages.
- A syntactically invalid extension name plus a syntactically valid but unsupported extension → `BadValue` for the invalid name, with extension records checked in wire-array order.

For every rejection, verify that `device_xid` remains unallocated, no logical Device or Queue is published, and no requested feature or extension is partially enabled. A corrected retry using the same target XID must succeed when all conditions are subsequently valid. The v0.1 feature and device-extension registries are empty: every feature ID is therefore currently unknown (`BadValue`), while every syntactically valid extension name is currently unknown (`BadMatch`); tests for registered-but-unsupported entries are forward-compatibility tests against a test registry fixture, not ordinary v0.1 registry data.



- A server without the presentation-capable profile rejects requests 41–47 with core X11 `BadRequest` before parsing presentation payloads or resolving their XIDs; no normal reply or state change follows. A server advertising the profile handles each request according to its assigned request-specific contract.


## Remaining request error-path negative tests

The following negative cases are mandatory in addition to the wire-vector checks. They target lifecycle and cross-resource paths where a syntactically valid request can still be rejected. For each rejected operation, verify the stated error and that public XIDs, bindings, pool membership, descriptor contents, semaphore/fence state, and retained references are unchanged unless the contract explicitly says otherwise.

- **`FreeMemory` after Buffer-XID invalidation:** keep a Buffer internally alive because a recording or accepted operation retains it, invalidate its public XID through the applicable lifecycle path, then attempt to free its bound allocation. Require `BadMatch` while any internally live Buffer remains bound; after the final Buffer reference drains and the Buffer is actually destroyed, retrying `FreeMemory` may succeed. Separately, if accepted GPU work still accesses the allocation, require `INVALID_SYNCHRONIZATION_STATE` and no partial free.
- **`BindBufferMemory` mixed failures:** combine a malformed request with invalid XIDs (`BadLength` wins); combine a bad reserved/value field with invalid XIDs (`BadValue` wins); then combine a live wrong-type Buffer/Memory resource with an unavailable Device and require `BadMatch` from type/ownership validation before Device state. With valid resources but a lost Device, require `DEVICE_LOST` before already-bound, alignment, memory-type, or allocation-range checks. Every rejection leaves the Buffer unbound.
- **`DestroyResource` lifetime failures:** separately test an unknown XID (`BadValue`), a live Fence/Semaphore passed to the generic destroy (`BadMatch`), and an otherwise eligible resource referenced by a `RECORDING` command buffer or forbidden pending work (`INVALID_SYNCHRONIZATION_STATE`). Confirm the failed destroy leaves the XID live and recording references intact; a corrected destroy after the blocker is removed succeeds exactly once.
- **`FreeDescriptorSets` atomicity and precedence:** use a multi-set request where a later Set belongs to another Pool, then where a selected Set is pending or referenced by a recording command buffer. Require `BadMatch` for the wrong Pool and `INVALID_SYNCHRONIZATION_STATE` for the lifetime blocker, with no earlier Set freed. Also test malformed length before all XID errors and unknown/non-live XIDs before ownership checks.
- **`DestroyDescriptorPool` child blockers:** create a Pool with multiple Sets and arrange for one child Set to be pending or referenced while others are idle. Require `INVALID_SYNCHRONIZATION_STATE` and verify the Pool, all child Sets, and all Pool capacity accounting remain unchanged. After the blocker is removed, successful destruction invalidates the Pool and its children atomically.
- **`ResetFence`/`DestroyFence` synchronization states:** reset an unsignaled Fence and destroy a Fence tied to non-terminal work or an open host wait. Require `INVALID_SYNCHRONIZATION_STATE`; neither operation may change the Fence state or detach the pending identity. Repeat after the wait's terminal result has been serialized to verify the documented boundary: an unsent reply alone does not keep destruction blocked.

These are contract-level negative tests for a future implementation, not claims that a live XAverius server currently executes them. Static CI should at least ensure every case remains documented alongside the central error mapping.


## Discovery, allocation, and transfer rejection matrix

The request register and the request-specific error map define the expected result for each case below. These tests cover remaining non-presentation error paths not represented by the reply golden vectors alone. Run each mixed-failure pair with valid framing in both byte orders where the request has a multi-byte wire payload. For every rejected create/allocation/bind/update, verify that the target XID and all affected object state remain unchanged.

- **`EnumeratePhysicalDevices`:** exercise zero, one, and multiple Physical Device records; reject a truncated fixed record, a name length that runs past the reply, nonzero reserved bytes, invalid UTF-8, embedded NUL, and nonzero name padding. Zero devices is a successful empty reply, not an error.
- **`GetPhysicalDeviceProperty`:** unknown Atom XID must produce core `BadAtom`; a valid but unregistered Atom name returns `NOT_SUPPORTED`; a registered property unavailable on that device returns `NOT_AVAILABLE`. For both non-success statuses require zero `property_type`, `value_length`, and payload. Combine invalid Atom with unknown Physical Device XID and require `BadValue` for the earlier XID stage as defined by the request contract.
- **`GetPhysicalDeviceQueueFamilyProperties` / `GetPhysicalDeviceMemoryProperties`:** malformed request length yields `BadLength` before XID resolution; unknown/non-live Physical Device XID yields `BadValue`; live XID of the wrong resource type yields `BadMatch`. On replies, reject non-multiple queue-record payload lengths, nonzero reserved fields, invalid queue-flag bits, out-of-range heap indices, counts above registry limits, and memory type/heap records inconsistent with declared counts.
- **`CreateDefaultDevice`:** malformed length wins over all other errors; zero queue count, invalid priority, and nonzero reserved field yield `BadValue` before target-XID checks; invalid/occupied target XID yields `BadIDChoice`; no suitable device yields `DEVICE_UNAVAILABLE`. Every failure leaves the target XID unallocated and publishes no Queue; success is a Void request and emits no normal reply.
- **`CreateBuffer` / `AllocateMemory`:** combine malformed length with invalid target XID (`BadLength` wins), invalid scalar/reserved values with invalid target XID (`BadValue` wins), and invalid target XID with unknown Device XID (`BadIDChoice` wins). Then test unknown Device (`BadValue`), live wrong type/foreign ownership (`BadMatch`), unavailable/lost Device (`DEVICE_UNAVAILABLE` / `DEVICE_LOST`), and injected backend allocation failure (`ALLOCATION_FAILED`). All failures leave the target XID unallocated.
- **`GetBufferMemoryRequirements`:** malformed length wins over XID errors; unknown Device or Buffer yields `BadValue`; live wrong type or cross-device Buffer yields `BadMatch`. Successful requirements must have positive size/alignment and at least one compatible memory-type bit; no successful reply may contain zero size/alignment.
- **`ReadBuffer`:** malformed length wins first, then zero data length/reserved-field errors (`BadValue`), then XID/type/ownership and range/usage validation (`BadValue` for unknown XIDs, `BadMatch` for incompatible live resources). Device Loss must prevent a successful data reply. Inject transfer and staging-allocation failures and require `TRANSFER_FAILED` / `ALLOCATION_FAILED`; an identified dependency cycle before snapshot capture yields `DEPENDENCY_FAILED`. No failed read may return a success payload.
- **`BindBufferMemory` / `UpdateDescriptorSets`:** mix Device Loss with a later bind-compatibility or descriptor-layout/pending-state failure and require `DEVICE_LOST` after XID/type/ownership checks. With a live Device, a write touching a Set used by accepted work must yield `INVALID_SYNCHRONIZATION_STATE`. For multi-write descriptor updates, make a later write invalid after an earlier write would be valid; reject the entire request and preserve every old slot and indirect resource reference.

These checks distinguish reply-format validation from server-side request rejection: reply golden vectors do not prove that the server chooses the correct X11 error/status or preserves state on rejection.

## Synchronization request rejection matrix

The following negative cases are required in addition to the positive wait/signal vectors above. Each case is repeated with both connection byte orders where its wire fields differ by byte order; an X11 error replaces the reply, while normal wait outcomes remain reply statuses.

- **`CreateSemaphore` / `CreateFence`:** combine malformed length with a colliding target XID and require `BadLength`; with valid length, a target collision yields `BadIDChoice` before Device lookup. Invalid enum/flags/reserved values yield `BadValue`; backend allocation failure yields `ALLOCATION_FAILED`. Every rejection leaves the target XID unallocated.
- **`SignalSemaphore`:** combine a Binary semaphore with Device Loss and require `DEVICE_LOST` to win after valid XID/type/ownership resolution; with a live Device, an invalid Binary signal yields `BadMatch`. A Timeline signal that crosses a pending GPU-signal reservation yields `INVALID_SYNCHRONIZATION_STATE`. In every rejected case, the observed counter and all reservations remain unchanged.
- **`WaitSemaphores`:** test count zero and duplicate Semaphore XIDs (`BadValue`), count/length mismatch (`BadLength`), unknown later array XID (`BadValue`), wrong live type/ownership (`BadMatch`), and Device Loss combined with a Binary semaphore (`DEVICE_LOST` after valid ownership). No synchronous rejection may install a wait registration or retain a wait-only resource reference.
- **`WaitForFence`:** combine malformed length with unknown XIDs and require `BadLength`; test unknown XIDs (`BadValue`) and wrong live type/ownership (`BadMatch`). A zero timeout returns the already-terminal Fence result or `TIMEOUT` without changing Fence state. Device Loss returns normal reply status `DEVICE_LOST`, and `DestroyDevice` while the wait remains open returns normal reply status `DEVICE_DESTROYED`; neither is an X11 error.
- **`GetFenceStatus` / `GetSemaphoreCounterValue`:** malformed length precedes XID validation; unknown XIDs yield `BadValue`, wrong live type/ownership `BadMatch`. After Device Loss, Fence status reports the stored terminal state, whereas the semaphore-counter request returns `DEVICE_LOST` rather than a success counter.
- **`ResetFence`:** after valid XIDs/type/ownership, Device Loss takes precedence over an invalid Fence state. With a live Device, resetting `UNSIGNALED` or `PENDING` yields `INVALID_SYNCHRONIZATION_STATE`; all rejections preserve the stored state.
- **`DestroyFence` / `DestroySemaphore`:** malformed length precedes XID checks; wrong live type/ownership yields `BadMatch`. Reject atomically with `INVALID_SYNCHRONIZATION_STATE` while the object is referenced by pending accepted work or an open host wait. After the wait's terminal result is serialized, an unsent reply alone must not block destruction. Device Loss alone does not invalidate the public XID.



## Command recording and submission rejection matrix

These cases target request-error paths that can be hidden by otherwise valid command-buffer and queue-submit vectors. The tests must assert both the winning error and the absence of partial state changes.

- **`ShaderModuleData`:** test malformed fixed/chunk length and nonzero padding before resolving the Shader Module XID; test an unknown XID (`BadValue`), wrong live type or foreign Device ownership (`BadMatch`), and a valid Shader Module without an active assembly (`INVALID_SYNCHRONIZATION_STATE`). Inject a failure in a non-final chunk and verify the entire assembly is discarded; a later FINAL chunk must not revive it. Repeat with ABORT after Device Loss and after XID destruction/reuse.
- **`CommandBufferData`:** pair a truncated entry with an invalid Buffer XID and require `BadLength`; pair invalid flags/reserved bits with an invalid target XID and require `BadValue`; for CREATE with valid syntax, require target-XID collision (`BadIDChoice`) before Pool-XID resolution. Test unknown Buffer/Pool XIDs (`BadValue`), live wrong types/foreign ownership (`BadMatch`), and a valid but non-RECORDING Buffer (`INVALID_SYNCHRONIZATION_STATE`). Any failed append or FINAL leaves the pre-request recording unchanged; any failed CREATE leaves the target XID unallocated.
- **`QueueSubmit`:** malformed count/length/overflow must win before any XID lookup; invalid scalar fields, duplicate waits/signals, and a token already accepted for another submission must be rejected before resource-state mutation. Resolve Device and command/synchronization XIDs in wire order, then enforce type, ownership, and cross-Device constraints before Device-state and executable/pending-state checks. Mix Device Loss with a non-EXECUTABLE command buffer and require `DEVICE_LOST` only after all XIDs and ownership are valid. Verify rejected submissions reserve neither token nor semaphore values, do not attach a Fence, do not change command-buffer state, and emit no submission-terminal or `ASYNC_ERROR` event.
- **`QueueSubmit` timeline reservations:** use two submissions whose signal values are increasing, then try a third submission with a duplicate or lower pending signal value; reject it atomically. Mix an invalid later signal entry with a valid earlier entry and verify no partial reservation. If a dependency cycle is detected before acceptance, return `DEPENDENCY_FAILED`; do not report the rejected token in any later event.
- **`QueueSubmit` command/resource validation:** test a command buffer containing a destroyed/reused resource XID, an incompatible descriptor slot, a missing statically used descriptor, and an invalid dispatch limit. Each failure must follow the documented validation stage, leave the command buffer and all resources unchanged, and not create a pending submission. A Buffer referenced by a RECORDING command buffer cannot be destroyed; after successful Buffer destruction, affected non-pending executable command buffers become INVALID and cannot be submitted.
- **`QueueSubmit` versus `CommandBufferData`:** submit a command buffer, then race/sequence a second append or FINAL against that accepted submission. Once pending, mutation must be rejected with `INVALID_SYNCHRONIZATION_STATE`; if mutation is serialized before submission acceptance, the submit sees the resulting finalized or invalid recording state. Request order does not create a GPU dependency between different queues.
- **`DestroyResource` / `FreeMemory`:** malformed length precedes XID resolution; unknown/non-live XIDs yield `BadValue`, live wrong type or foreign ownership yields `BadMatch`. Reject destruction of a Buffer while a recording command buffer or pending GPU access references it, and reject freeing bound Memory or Memory with pending access using `INVALID_SYNCHRONIZATION_STATE` / `BadMatch` as specified. Verify public XIDs and all binding/reference edges remain unchanged after rejection; successful destruction invalidates the public XID immediately without allowing stale callbacks to resolve a reused XID.
- **Atomicity across batch requests:** for `AllocateDescriptorSets`, `UpdateDescriptorSets`, and any multi-entry binding/update request, place the only invalid entry last after at least one valid entry. The request must fail as a whole: no target XID is published, no descriptor slot or binding changes, and no internal reference is leaked or released early. Repeat with the first entry invalid to ensure the same externally visible atomicity.

This matrix closes cross-request gaps not covered by isolated golden replies. Each test must assert the precise X11 error or protocol status, unchanged state on rejection, and absence of delayed events for work that was never accepted.

- **Device lifecycle and queue lookup:** for every Device-scoped request, combine unknown Device XID, live wrong resource type, foreign ownership, Device unavailable, and Device lost with one later invalid field/state. Require the precedence specified by that request: framing/scalar checks first, then XID resolution in wire order, then type/ownership, then Device lifecycle, then mutable state/backend checks. In particular, no unknown XID may be reclassified as Device Loss, and a live wrong-type/foreign-owned XID must not leak lifecycle state. After `DestroyDevice`, test each still-live child XID with its documented destroy/query behavior; no child may become usable through a reused Device XID.
- **`CreateCommandPool` / `ResetCommandPool` / `DestroyCommandPool`:** exercise exact length and reserved/flag validation before XID resolution; unknown Device/Pool yields `BadValue`, wrong live type or ownership yields `BadMatch`, and target collisions yield `BadIDChoice` for create. - **`CreateDescriptorSetLayout`:** test count/length overflow, invalid descriptor type/count/stage bits, nonzero reserved fields, duplicate binding numbers, and invalid target XID. - **`CreateDescriptorPool` / `AllocateDescriptorSets` / `FreeDescriptorSets`:** mix zero counts, duplicate target Set XIDs, occupied targets, unknown Pool/Layout XIDs, wrong types, cross-Device ownership, Device Loss and insufficient pool capacity. - **`CreatePipelineLayout` / `CreateComputePipeline`:** combine malformed variable strings/counts and padding with invalid target and input XIDs; require framing and scalar validation to precede lookup. - **`BindBufferMemory`:** test zero/misaligned/out-of-range offsets, incompatible memory type, already-bound Buffer, and a Memory allocation too small for the required Buffer span. - **`CreateBuffer` / `AllocateMemory` / `GetBufferMemoryRequirements`:** include integer overflow at size/alignment calculations, unsupported usage combinations, invalid memory-type masks, zero allocation size, and backend allocation failure. A failed final `WriteBuffer` must not report commit success; a non-final deferred failure must not corrupt later independent writes. `ReadBuffer` must never return partially initialized payload as success. Where a read waits for earlier writes, test overlapping and disjoint ranges across queues and verify the documented visibility guarantee without treating X11 request order as a GPU dependency.
- **`GetPhysicalDeviceProperty` and enumeration replies:** for every registered property type, inject wrong value length, wrong wire type, nonzero reserved fields and malformed string padding into reply decoder tests. Ensure invalid reply records are rejected as malformed protocol data rather than coerced into a different property type. For enumeration count/capacity combinations, verify returned record count never exceeds the supplied capacity and that a truncated record cannot be mistaken for an empty successful result.
- **Error-channel separation:** for every request with both core X11 errors and XAverius result/status fields, force one synchronous validation failure and one asynchronous backend failure in separate runs. A rejected request produces exactly its specified X11 error and no terminal completion event; an accepted request whose execution later fails produces its specified asynchronous/normal-reply outcome and never a delayed X11 request error. Confirm status numeric values are interpreted only in their defined reply/event namespace.

## Executable QueuePresent reference-state tests

`tests/xa_state_model.py` is a small, dependency-free executable oracle for the normative `QueuePresent` validation order. `tests/test_state_model.py` supplies mixed-failure cases and checks the actual result selected by the model, not just the presence of explanatory prose. It covers wire/scalar errors, XID and ownership failures, Device loss, queue/index validation, Surface lifecycle, presentation capability, accepted-token reuse, image state, wait eligibility, retry after rejection, and the atomic acceptance commit.

For every modeled rejection, the test compares the complete state before and after the request, including accepted tokens, image state, and all wait states. The success case checks that token reservation, wait reservation, and the `ACQUIRED` to `PRESENT_PENDING` transition all occur together. Lifecycle changes are injected before validation and are retained; the rejected request itself adds no mutation.

This is intentionally a **reference state model**, not a production server or proof that an implementation conforms. Its boolean fixture fields abstract away X11 resource lookup and backend behavior. The model and tests are useful as an executable semantic oracle while a server is not available; once a protocol implementation exists, the same precedence vectors should be replayed against it through a test harness and compare wire errors/replies plus externally observable state.


## Executable compute state-model tests

The dependency-free oracle in `tests/xa_state_model.py` now models three additional contracts:

- `ShaderModuleData`: single-request CREATE|FINAL and multi-chunk assembly; malformed or failed chunks discard the entire in-progress shader assembly, FINAL publishes the module only on success, and ABORT releases assembly storage without starting GPU work.
- `CommandBufferData`: CREATE, per-chunk append validation, FINAL, and ABORT. A failed chunk appends no entries and preserves previously accepted recording chunks; failed FINAL leaves the buffer RECORDING; ABORT clears a non-pending recording buffer back to INITIAL and is allowed after Device Loss.
- `QueueSubmit`: framing/scalar/XID/type/device/state checks precede acceptance; all command buffers, waits, and signal reservations are validated before one acceptance commit. A rejected submission must not reserve its token or waits/signals, attach its Fence, transition command buffers to PENDING, or enqueue a pending submission.

These are deliberately small reference models with injected validation outcomes, not a Vulkan backend and not proof of server conformance. When a server exists, replay the same vectors against its wire interface.

## Abgleich des ausführbaren Zustandsmodells

Die Referenztests in `tests/test_state_model.py` spiegeln die in diesem Dokument und in `spec/errors.md` normierten Präzedenzregeln wider:

- `ShaderModuleData`: Request-/Payload-Länge, Padding, Flag-Kombinationen und leere Datenchunks werden vor XID-/Device-Zustand geprüft. ABORT erfordert ein existierendes Assembly; Device Loss beendet das Assembly und ein späterer ABORT darf es nicht wiederbeleben. CREATE reserviert die Ziel-XID, sodass ein zweites CREATE mit `BadIDChoice` scheitert.
- `CommandBufferData`: Wire-Struktur und Entry-Längen werden vor XID-Auflösung geprüft; danach folgen Ziel-XID und Pool-XID in Feldreihenfolge, Typ/Ownership, semantische Entry-Werte sowie Device-/Buffer-Zustand. Das entspricht der normativen Regel, dass strukturelle Längenfehler vor XID-Prüfung stehen, semantische Entry-Fehler aber nicht die Ziel-XID-Prüfung verdecken. ABORT prüft ebenfalls den exakten Eltern-Pool und bleibt nach Device Loss nur für einen live `RECORDING`-Buffer zulässig.
- `QueueSubmit`: Länge/Counts und skalare Fehler stehen vor XID-Auflösung; Token-Wiederverwendung wird vor XIDs geprüft; alle Ressourcen-XIDs sowie Queue-/Ownership-Fehler stehen vor Device Loss. Nach Device Loss werden Fence, Command Buffer, Waits und Signals in normativer Reihenfolge validiert. Der Oracle unterscheidet Binary- und Timeline-Semaphoren, prüft Binary-Werte auf null, Timeline-Signalwerte gegen Counter und pending Reservierungen sowie Wait-Stage-Syntax und Queue-Unterstützung. Der Commit reserviert erst dann Token, Waits, Signalwerte, Fence und PENDING-Zustände.

Der Python-Oracle modelliert weiterhin keine vollständige Wire-Decodierung, sämtliche Semaphore-Zustandsvarianten oder einen echten Vulkan-Backend-Aufruf. Diese Bereiche bleiben durch die normativen Request-/Fehlerregeln und Wire-Layout-Tests abgedeckt; der Oracle prüft hier gezielt die oben aufgeführten Zustandsübergänge und Fehlerpräzedenzfälle.
