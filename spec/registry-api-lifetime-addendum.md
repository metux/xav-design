# Registry API lifetime addendum

This normative addendum supplements [device-registry-architecture.md](device-registry-architecture.md) §§2.4, 3, 3.1, and 7. It states the ownership and lifetime requirements for the current direct per-PhysicalDevice DDX binding and shared `GpuModuleRole` control record. The DDX binding is the direct dispatch target; the module role provides only shared code/module lifetime and quiescence control.

## Direct DDX binding

The DDX enumerates every PhysicalDevice it serves and calls `GpuRegistryRegisterDdxDevice` once per device. The registration supplies structured identity evidence, the exact native PhysicalDevice handle, per-device backend context, immutable typed operation vectors, and the owning DDX module-role generation. The registry canonicalizes the identity, validates the complete operation table, queries one immutable snapshot through that binding, and atomically installs the complete binding and snapshot. This registration does not itself publish the PhysicalDevice or allocate its XID; publication is a separate operation after identity resolution, eligible-binding selection, and opening of the startup publication gate. The registration descriptor carries a pointer to a `const GpuDeviceBackendOps` descriptor. That descriptor begins with `struct_size` and `abi_version`; v0.1 requires `struct_size == sizeof(GpuDeviceBackendOps)` and `abi_version == GPU_DEVICE_BACKEND_OPS_ABI_VERSION`. The ABI version governs the top-level descriptor, all four nested typed operation-table layouts, and every DDX-facing callback signature and parameter/result structure they reference, including token/completion types. The registry validates this header before reading callback fields, then validates and copies the operation-table descriptors by value into immutable server-owned storage before publication. A size mismatch is `INVALID_ARGUMENT`; an unknown ABI version is `UNSUPPORTED`; neither failure invokes a callback or retains registration-owned resources. The native handle and per-device context remain borrowed DDX-owned opaque values: the DDX MUST keep them alive until exact binding removal and all dependent calls, objects, tokens, and callbacks have retired; the registry never frees them. The PhysicalDevice owns its snapshot as a member/value rather than through a separate DeviceCaps registry object. The server-private XID/resource wrapper is not exposed in the DDX ABI. On `SUCCESS`, `GpuRegistryRegisterDdxDevice` returns one caller-owned opaque PhysicalDevice reference and the exact PhysicalDevice/binding generations; this does not imply that the PhysicalDevice has already been published or assigned an XID. An exact idempotent replay of the same live registration returns `SUCCESS`, the same live binding generation, and one additional caller-owned PhysicalDevice reference. Conflicting or invalid registration returns a classified failure with no caller-owned PhysicalDevice reference or installed binding. The DDX MUST release the immediate reference through `GpuPhysicalDeviceRelease` and MUST NOT retain or later dereference the bare pointer. Later references are generation-checked and server-owned.

There is no independent Vulkan-ICD candidate inventory, no candidate-list callback API, no DDX backend-local numeric binding ID, and no per-request lookup of a DDX backend object. A selected PhysicalDevice binding is the direct dispatch target.

## Module-role control record

A `GpuModuleRole` exists only to pin unloadable DDX code and shared module resources, coordinate callback admission, and establish module-wide quiescence. It is not an execution backend. There is no generic module-role context accessor. Per-device context and native handles are passed directly through the exact DeviceBackendBinding; module-role APIs expose only lifetime and quiescence operations.

The role generation and binding generation are separate, non-reusable identities. A binding retains its role. Operation tokens carry both identities as needed to reject stale callbacks. Module-role shutdown closes admission and drains every binding owned by that role; binding removal affects only one PhysicalDevice. ScreenAttachment teardown remains independent. The DDX-supplied `GpuModuleRoleDescriptor` and `GpuDeviceBackendRegistration` are also size/versioned v1 descriptors; each API validates its descriptor header before reading later fields, retaining the supplied module-lease reference, invoking callbacks, or retaining registration resources. Their exact size/version constants and rejection results are defined in `device-registry-architecture.md`.

## Lifetime requirements

- The DDX binding retains its native handle and device context until all logical Devices, backend objects, synchronous calls, accepted operation tokens, and callbacks that can access them have retired.
- The module role retains its loader lease until all bindings, callbacks, shared contexts, and module-owned workers have quiesced.
- A completion callback identifies a server-owned operation token by token ID and generation, plus the exact binding/module-role generations. It never resolves a raw module-role or binding pointer or client XID.
- A terminal callback does not prove backend quiescence. If later backend access cannot be excluded, retain or quarantine the binding and module lease.
- A Screen close detaches only that Screen generation. It does not unregister a shared DDX device binding.

The C declarations are an implementation-facing API sketch, not the XAverius wire ABI. An implementation may adapt internal symbol names only if every caller and declaration is updated consistently; the versioned descriptor layouts, callback signatures for the selected ABI version, ownership, and lifetime semantics remain mandatory.
