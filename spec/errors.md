# Errors and error mapping

Error codes are offsets relative to the X11 extension's `first_error` value. The absolute X11 error code is `first_error + offset`; implementations must use the central values in [the error registry](../registries/errors.md), not allocate values ad hoc.

The error registry's offsets and event-local status values are separate numeric namespaces. In particular, `EXECUTION_FAILED` is error offset 3, while `SUBMISSION_FAILED.failure_class = EXECUTION_FAILED` is the event-local value 0; `WaitForFence` also has its own reply-status value for execution failure. Likewise, `DEVICE_LOST` has error offset 1, while the `WaitForFence` reply status is 3 and the `DEVICE_LOST` event's `reason_code` is a separate enum (for example, `VULKAN_DEVICE_LOST = 3`). Implementations MUST use the value from the field's defining registry, never a same-named value from another namespace.

For an accepted `QueueSubmit`, an execution failure is reported through the submission terminal event and synchronization state, with `ASYNC_ERROR` available for diagnostics. It MUST NOT be reported as a delayed X11 request error. The `EXECUTION_FAILED` error offset is not a substitute for the event-local `failure_class` or `WaitForFence` status.

XAverius errors use the standard 32-byte X11 error packet and add no XAverius-specific payload bytes. The packet carries the extension major opcode and the sequence number of the request that caused the error. The resource field identifies the affected resource when meaningful; otherwise it is zero. For v0.1, the X11 request-header `data` byte MUST be zero; XAverius `subopcode` is carried at offset 4, and the error packet's `minorCode` is the zero-extended `subopcode`. The error packet's `majorCode` is the extension major opcode.

## General Error Classes

| Situation | Result |
|---|---|
| Inconsistent request length or count | `BadLength` |
| Invalid field value, reserved bits, or flags | `BadValue` |
| Invalid or already occupied create XID | `BadIDChoice` |
| Wrong resource type or cross-device combination | normally `BadMatch` |
| XID does not identify a live XAverius resource or is unknown in this resource context | `BadValue` |
| Invalid Atom XID | `BadAtom` |
| Live XID has a resource type other than the expected type | `BadMatch` |
| Live resource belongs to another client and no sharing path is defined | `BadMatch` |
| Device unavailable | `DEVICE_UNAVAILABLE` |
| Device lost | `DEVICE_LOST` |
| Execution failure as an X11 error | `EXECUTION_FAILED` is assigned in the error registry but is not emitted by any v0.1 request; `WaitForFence` reports execution failure as a normal reply status, and accepted `QueueSubmit` reports it through terminal events and synchronization state |
| Logical device normally destroyed while a host wait is open (`WaitSemaphores`) | `DEVICE_DESTROYED` as an X11 error; `WaitForFence` instead uses the normal reply status `DEVICE_DESTROYED = 4` |
| Logical device destroyed while an earlier `WriteBuffer` operation remains open | `DEVICE_DESTROYED` as an X11 error, unless the write's success or another failure was committed first |
| Invalid synchronization state | `INVALID_SYNCHRONIZATION_STATE` |
| Synchronous transfer failure | `TRANSFER_FAILED` |
| Synchronous allocation failure | `ALLOCATION_FAILED` |
| Invalid dependency prevents acceptance | `DEPENDENCY_FAILED` |
| Unexpected server error | `INTERNAL_SERVER_ERROR` |

## Normative XID Error Rule

The following baseline mapping applies to all XAverius requests unless a request defines an explicitly narrower rule:

- A required XAverius XID that does not identify a live resource in the XAverius resource space results in `BadValue`. This includes unknown, destroyed, and no-longer-public XIDs. XAverius resources use extension-specific resource types, so there is no corresponding core error such as `BadWindow` or `BadPixmap`.
- An XID that identifies a live resource but not the expected resource type results in `BadMatch`.
- A live resource owned by another client, with no explicit sharing path defined, results in `BadMatch`. The same applies to cross-device use.
- An invalid `ATOM` value results in `BadAtom`, not `BadValue`.
- An invalid or already-occupied create XID results in `BadIDChoice`; this differs from an invalid input XID.
- For server-assigned physical-device XIDs, an unknown or no-longer-valid XID also results in `BadValue`; a live resource of the wrong type results in `BadMatch`.

This mapping also applies when a request contains multiple XIDs: the server validates wire structure first, then field values, then XIDs in the field order specified by the request chapter. The first invalid XID determines the reported resource error. The request remains atomic.

### Create XIDs and Chunk-Based Creation

The target XID of a create request is not an input XID to be resolved as an existing resource. An invalid or occupied target XID therefore results in `BadIDChoice`; it MUST NOT be treated as an ordinary unknown input XID producing `BadValue`. For atomic batch creation, the entire request is rejected if any target XID is invalid, already occupied, or duplicated within the same request; no subset remains live.

This rule applies in particular to target XIDs for `CreatePipelineLayout`, `CreateComputePipeline`, and descriptor sets requested by `AllocateDescriptorSets`. It also applies to `ShaderModuleData` and `CommandBufferData` when the `CREATE` flag is set. For `ShaderModuleData`, a successful CREATE chunk reserves the target XID for the upload assembly; a second CREATE or an already-live target XID results in `BadIDChoice`.

For `ShaderModuleData` without `CREATE`, a matching upload assembly MUST exist. If the XID identifies a live resource of another type, the result is `BadMatch`; otherwise, a missing assembly results in `INVALID_SYNCHRONIZATION_STATE`, even if no public shader-module object exists yet. For `CommandBufferData` without `CREATE`, the target XID MUST identify a live command buffer: unknown or non-live XIDs result in `BadValue`, a live resource of the wrong type results in `BadMatch`, and a command buffer outside `RECORDING` results in `INVALID_SYNCHRONIZATION_STATE`. All checks occur before any state change.


## `CreateDevice`: Feature and Extension Requirements

Error mapping distinguishes invalid input from valid but unsupported requirements:

- The mandatory v0.1 `timelineSemaphore` baseline capability is unsupported by the selected Physical Device (`XAverius.timelineSemaphore = 0`): `BadMatch`.
- `feature_id` is not defined in the XAverius feature registry: `BadValue`.
- `feature_id` is registered but is not supported by the selected physical device: `BadMatch`.
- A feature record with `enabled != 1` or a duplicate feature ID: `BadValue`.
- An extension name that is empty, longer than 255 bytes, or syntactically invalid: `BadValue`.
- An extension name that is syntactically valid but unknown to the XAverius extension registry or unsupported by the physical device: `BadMatch`.
- Duplicate extension names: `BadValue`.
- All requirements MUST be checked before device creation. On any failure, the requested `device_xid` remains unallocated; the server MUST NOT silently omit features or extensions.

The following error precedence applies to `CreateDevice` and refines the general XID rule for this request. It MUST match the ordered phases in [Device Discovery and Logical Devices](devices.md):

1. Validate complete request framing using checked arithmetic and the exact variable-length formula. Truncation, trailing bytes, or arithmetic overflow returns `BadLength`.
2. Validate wire-level and scalar fields: reserved fields and padding are zero; queue counts are positive; queue-family entries, feature IDs, and extension names are unique; priorities are finite and in [0,1]; `enabled = 1`; and extension names have valid ASCII Vulkan-name syntax and length 1–255. Violations return `BadValue`. Because no optional feature IDs are assigned in v0.1, every feature ID is unknown and returns `BadValue` here. A syntactically valid extension name is not rejected merely because it is unregistered.
3. Validate create-XID `device_xid`; an invalid or occupied target returns `BadIDChoice`.
4. Resolve `physical_device_xid`; an unknown or non-live XID returns `BadValue`.
5. Validate that the resolved XID is a Physical-Device resource and that its ownership/association is valid for this connection; wrong type or invalid ownership/association returns `BadMatch`.
6. Require successful XGE 1.0-or-later negotiation through `GEQueryVersion`; otherwise return `BadMatch`.
7. Check Physical-Device availability; an unavailable device returns `DEVICE_UNAVAILABLE`.
8. Validate queue-family indices and requested queue counts; an out-of-range family index returns `BadValue`, while a valid family unable to supply the requested count returns `BadMatch`.
9. Validate the mandatory v0.1 `timelineSemaphore` baseline capability (`XAverius.timelineSemaphore = 1` required; otherwise `BadMatch`) and registered optional feature/extension support. The server MUST enable the mandatory feature for the created logical Device. This phase is reached only after earlier validation; if future versions register a feature, an unsupported registered feature returns `BadMatch`. A syntactically valid but unregistered or unsupported client extension returns `BadMatch`.
10. Only after all validation succeeds may backend creation begin. Backend failures use the defined allocation/device error, and no logical Device or child resources may be published.

A later phase MUST NOT override an error from an earlier phase. In particular, malformed framing takes precedence over scalar errors; scalar errors (including unknown feature IDs) take precedence over XID errors; target-XID validation precedes physical-device lookup; resource type/ownership checks precede XGE negotiation; and XGE negotiation precedes device availability. All feature and extension records must be validated before creation, and every failure leaves `device_xid` unallocated with no partial Device or Queue objects.

## Request-specific error mapping

### `WriteBuffer`

Normative precedence: (1) total length with checked count/overflow arithmetic and the X11 request limit (`BadLength`); (2) positive `data_length` and zero padding (`BadValue`); (3) `device_xid`, then `buffer_xid` in wire order (`BadValue` for unknown/non-live XIDs); (4) live resource type, client ownership, and Device association (`BadMatch`); (5) Device state (`DEVICE_UNAVAILABLE` / `DEVICE_LOST`); (6) Buffer binding, `TRANSFER_DST`, and range (`BadMatch`); (7) transfer/synchronization work.

- Request-Gesamtlänge mit Überlauf oder oberhalb des für die Verbindung geltenden X11-Limits: `BadLength`
- Incorrect request length: `BadLength`
- Zero length, nonzero padding, or invalid reserved fields: `BadValue`
- Unknown/non-live XAverius XID: `BadValue`
- Wrong type, wrong Device, unbound Buffer, missing `TRANSFER_DST`, or range outside the Buffer: `BadMatch`
- Unavailable/lost Device: `DEVICE_UNAVAILABLE` / `DEVICE_LOST`
- If Device Loss or `DestroyDevice` terminalizes an already-open `WriteBuffer`, the request reports `DEVICE_LOST` or `DEVICE_DESTROYED`, respectively, unless another terminal outcome was committed first.
- Synchronous transfer failure: `TRANSFER_FAILED`
- Staging allocation failure: `ALLOCATION_FAILED`
- Detected dependency cycle while waiting for earlier GPU work, including a deferred GPU signal that is the only candidate to satisfy an earlier wait: `DEPENDENCY_FAILED`. Only an already-accepted signal operation eligible under the Timeline wait-ordering rules counts as a possible release; a later signal on the same queue cannot satisfy an earlier wait.

### `ReadBuffer`

Normative precedence: (1) exact 28-byte length (`BadLength`); (2) positive `data_length` (`BadValue`); (3) `device_xid`, then `buffer_xid` in wire order (`BadValue` for unknown/non-live XIDs); (4) live resource type, client ownership, and Device association (`BadMatch`); (5) Device state (`DEVICE_UNAVAILABLE` / `DEVICE_LOST`); (6) Buffer binding, `TRANSFER_SRC`, and range (`BadMatch`); (7) snapshot/transfer work.

- Incorrect request length: `BadLength`
- Zero length or invalid reserved fields: `BadValue`
- Unknown/non-live XAverius XID: `BadValue`
- Wrong type, wrong Device, unbound Buffer, missing `TRANSFER_SRC`, or range outside the Buffer: `BadMatch`
- Unavailable/lost Device: `DEVICE_UNAVAILABLE` / `DEVICE_LOST`
- Synchronous transfer failure: `TRANSFER_FAILED`
- Staging allocation failure: `ALLOCATION_FAILED`
- Detected dependency cycle before capturing the data snapshot: `DEPENDENCY_FAILED`
- If Device Loss or `DestroyDevice` terminalizes an open read before snapshot commit: X11 error `DEVICE_LOST` or `DEVICE_DESTROYED`, respectively; a previously committed snapshot remains successful.
- Client disconnect before snapshot commit cancels the read without a reply.

### `ShaderModuleData`

- Incorrect request length or mismatched payload size: `BadLength`
- Zero `data_length` for a data chunk, nonzero `data_length` for ABORT, nonzero padding, or an invalid flag combination: `BadValue`
- Invalid/non-live `device_xid`: `BadValue`; a live resource of the wrong Device type: `BadMatch`. With `CREATE`, an invalid/occupied `shader_module_xid` results in `BadIDChoice`. Without `CREATE`, the request requires a matching upload assembly; if none exists, the result is `INVALID_SYNCHRONIZATION_STATE`.
- `ABORT` without a matching active upload assembly: `INVALID_SYNCHRONIZATION_STATE`
- Invalid SPIR-V or a SPIR-V module that does not satisfy the v0.1 validation rules: `BadValue`; no Shader Module remains live, and the assembly is discarded
- Vulkan creation failure: the specific backend error, such as `DEVICE_LOST`, `ALLOCATION_FAILED`, or `INTERNAL_SERVER_ERROR`; no Shader Module remains live, and the assembly is discarded
- A failed continuation or `FINAL` chunk discards the matching assembly only when the complete fixed header identifies its `shader_module_xid` and `CREATE=0`. A request truncated before that XID is available cannot identify or mutate an assembly. A rejected `CREATE=1` attempt never discards an existing assembly reserved under the same XID. The X11 error for the failed chunk is synchronous and leaves no partial Shader Module. Errors during `ShaderModuleData` upload MUST NOT generate `ASYNC_ERROR`; Device loss is reported only through the general Device-loss path, not through an additional upload-specific event.

### Device discovery and Device creation

- `EnumeratePhysicalDevices`: an incorrect request length (`!= 8` bytes) results in `BadLength`; the reply payload consists only of complete `PHYSICALDEVICEINFO` records. An incomplete record MUST NOT be emitted. If no Physical Devices are available, an empty successful reply with `reply.length = 0` is permitted.
- `GetPhysicalDeviceProperty` precedence is: exact 16-byte length (`BadLength`); Physical-Device XID resolution (`BadValue` for unknown/non-live XIDs); live resource type (`BadMatch` if not a Physical Device); Atom validation (`BadAtom`); registered-property lookup and availability (`NOT_SUPPORTED` / `NOT_AVAILABLE`). Thus an invalid Device XID or wrong live resource type takes precedence over an invalid Atom. When status is not `SUCCESS`, `property_type`, `value_length`, and the reply payload MUST be zero.
- `GetPhysicalDeviceQueueFamilyProperties` and `GetPhysicalDeviceMemoryProperties` each use the same complete precedence: exact 12-byte length (`BadLength`); Physical-Device XID resolution (`BadValue`); live resource type (`BadMatch` if not a Physical Device); then return the server-stored metadata snapshot. A still-live Physical-Device XID remains queryable after physical-device removal/failure; these metadata-only queries do not perform a Device-availability check or backend operation. `CreateDevice` and `AllocateMemory` independently check current availability when they need an operational Device.
- `CreateDevice`: an incorrect request length returns `BadLength`; `queue_family_request_count = 0`, `queue_count = 0`, duplicate queue-family records, nonzero reserved fields, invalid priorities, `enabled != 1`, duplicate feature/extension entries, unknown feature IDs, and syntactically invalid extension names return `BadValue`. An invalid/occupied `device_xid` returns `BadIDChoice`; an unknown/non-live Physical-Device XID returns `BadValue`; a live resource of the wrong type, missing mandatory `timelineSemaphore` baseline support (`XAverius.timelineSemaphore = 0`), an unsupported registered feature, an unknown or unsupported syntactically valid extension, or cross-device use returns `BadMatch`. An out-of-range queue-family index returns `BadValue`; a valid family unable to supply the requested queue count returns `BadMatch`. An unavailable Physical Device returns `DEVICE_UNAVAILABLE`. The normative phase ordering is authoritative: Physical-Device availability is checked before queue-family index/count validation, so `DEVICE_UNAVAILABLE` takes precedence when both apply. Creation is atomic and publishes no logical Device on failure.
- `CreateDefaultDevice`: incorrect length returns `BadLength`; a zero count, nonzero reserved field, or invalid priority returns `BadValue`; an invalid/occupied `device_xid` returns `BadIDChoice`; missing XGE negotiation returns `BadMatch`; no compute-capable device with `XAverius.timelineSemaphore = 1` and sufficient queue count returns `DEVICE_UNAVAILABLE`.

  Normative precedence for `CreateDefaultDevice`: (1) exact/formula-based request length using checked arithmetic (`BadLength`); (2) `queue_count`, reserved field, and all priorities (`BadValue`); (3) target XID `device_xid` (`BadIDChoice`); (4) successful XGE 1.0 negotiation (`BadMatch`); (5) selection of a suitable Physical Device and compute queue (`DEVICE_UNAVAILABLE`). All checks occur before publishing a logical Device; on any error, the target XID remains unallocated.
- Both requests are void requests; success produces no normal reply.
- `DestroyDevice`: normative precedence is exact 12-byte length (`BadLength`) > Device-XID resolution (`BadValue` for unknown/non-live) > live resource type and client ownership (`BadMatch` for wrong type or foreign ownership) > atomic logical teardown. There is no Device-availability phase; Device Loss does not block cleanup. A later phase MUST NOT override an earlier error.

### `SelectEvents`

Normative validation precedence, matching [Event Selection](events.md#event-selection-selectevents): (1) exact 32-byte request length (`BadLength`); (2) scope, unused fields, reserved fields, and profile-legal mask bits (`BadValue`); (3) for `DEVICE` and `QUEUE` scope, resolve `device_xid` (`BadValue` if unknown/non-live); (4) validate live type and client ownership (`BadMatch`); (5) require successful XGE 1.0-or-later negotiation through `GEQueryVersion` (`BadMatch` otherwise); (6) for `QUEUE` scope, validate the queue-family/index tuple (`BadValue` if it does not identify an existing queue); (7) atomically replace the selected mask.

A later phase MUST NOT override an earlier error. In particular, malformed framing and scalar errors take precedence over XID errors, and XID/type/ownership errors take precedence over the XGE prerequisite and queue existence check. For `CONNECTION` scope, the device XID and queue tuple are not resolved because their required values are zero. Every error leaves the previous event selection unchanged.

The following individual mappings are retained as explicit error summaries and MUST be interpreted according to the ordered phases above:
- An incorrect request length results in `BadLength`.
- If the client has not successfully negotiated at least XGE 1.0 with `GEQueryVersion`, the request results in `BadMatch`.
- An unknown scope, nonzero flags/reserved fields, invalid mask bits, or nonzero fields outside the selected scope results in `BadValue`.
- An unknown or non-live Device XID, or an invalid queue-family/queue index, results in `BadValue`; a live resource of the wrong type or foreign client ownership results in `BadMatch`.
- An error leaves the previous event selection unchanged; a successful request atomically replaces only the selection for the specified scope.

### `CreateDescriptorSetLayout`

- An incorrect request length or a payload inconsistent with `binding_count` returns `BadLength`.
- Nonzero `flags`, reserved/invalid field values, unknown or unsupported stage bits, an unsupported descriptor type, or invalid binding records return `BadValue`.
- An invalid or already allocated create XID returns `BadIDChoice`.
- An unknown/non-live Device XID returns `BadValue`; a live resource of the wrong type, foreign Device ownership, or a cross-Device resource returns `BadMatch`.
- An unavailable/lost Device returns `DEVICE_UNAVAILABLE` / `DEVICE_LOST`; a synchronous backend allocation failure returns `ALLOCATION_FAILED`.
- A syntactically valid binding count that exceeds the selected Device's descriptor limits returns `BadMatch`, after the Device-state phase and before backend allocation.
- Every error leaves the Descriptor Set Layout uncreated; partial results are not permitted.

### `CreateDescriptorPool`, `AllocateDescriptorSets`, and descriptor capacity

- `CreateDescriptorPool` retains its ordered length, scalar, target-XID, Device-XID, ownership, Device-state, and backend-allocation phases. Pool Size entries with zero counts, duplicate or unsupported descriptor types, or nonzero reserved fields return `BadValue`.
- `AllocateDescriptorSets` returns `BadMatch` for a Pool/Layout Device or resource compatibility mismatch. Exhausted `max_sets`, a missing pool-size type, or insufficient remaining descriptor capacity for the complete requested batch returns `ALLOCATION_FAILED`. Capacity is computed by summing each allocated Set Layout's descriptor counts by type; every Set in the batch contributes independently. No capacity or Set is committed unless the entire batch succeeds.
- Successful `FreeDescriptorSets` returns the selected Sets' logical set and per-type capacity to the Pool in the same serialized commit that invalidates their XIDs. A rejected free changes neither capacity nor membership. `DestroyDescriptorPool` invalidates all child Sets and ends the Pool's capacity accounting atomically.

### `CreateCommandPool`

- An incorrect request length results in `BadLength`.
- Unknown pool flags or nonzero reserved bits result in `BadValue`; an invalid or already allocated pool XID results in `BadIDChoice`.
- An unknown or non-live Device XID results in `BadValue`; a live resource of the wrong type or foreign Device ownership results in `BadMatch`.
- A `queue_family_index` that does not identify a family for which this Device requested at least one queue (`queue_count > 0`) results in `BadValue`. This is the sole queue-family eligibility test for pool creation: all Vulkan queue families support command-buffer submission, and v0.1 defines no separate command-buffer-support capability or flag. `CMD_DISPATCH` recorded into a pool whose family lacks the `COMPUTE` queue flag is incompatible and returns `BadMatch` during resource-dependent `CommandBufferData` validation.
- An unavailable or lost Device results in `DEVICE_UNAVAILABLE` or `DEVICE_LOST`, respectively; backend allocation failure results in `ALLOCATION_FAILED`.
- On rejection, the pool XID remains unallocated.

### `CommandPool` and `CommandBufferData`

- An incorrect request length, an entry whose declared length exceeds the request boundary, or an incomplete entry header results in `BadLength`.
- Reserved bits/fields, invalid flag combinations, malformed padding, unknown command IDs, or invalid entry lengths (especially zero or less than the entry header) result in `BadValue`.
- After successful wire-structure and entry-syntax validation, `CommandBufferData` resolves XIDs in wire order: target command-buffer XID, pool XID, then embedded command-entry XIDs in entry order and field order. With `CREATE`, an invalid or already allocated target XID results in `BadIDChoice`; without `CREATE`, an unknown or non-live Buffer XID results in `BadValue`. Unknown/non-live pool or embedded entry XIDs also result in `BadValue`.
- Only after every required XID has been resolved does the server validate resource type, client/device ownership, cross-device association, and exact parent-pool association. A live resource of the wrong type, foreign ownership, cross-device association, or incorrect pool association results in `BadMatch`. The specified pool MUST match the Buffer's parent pool even for `ABORT`.
- For CREATE, append, and FINAL, Device state is checked after all XID/type/ownership validation and before Buffer state or resource-dependent command-entry compatibility; an unavailable or lost Device returns `DEVICE_UNAVAILABLE` or `DEVICE_LOST`. Without CREATE, the Buffer must then be in `RECORDING`, otherwise `INVALID_SYNCHRONIZATION_STATE` is returned. `ABORT` is the explicit logical exception: after structure, field, XID, type, and ownership validation, the `RECORDING` state is checked even if the Device is unavailable or lost; for a valid live Buffer/pool pair with matching parent pool, ABORT remains permitted after Device loss and starts no Vulkan work.
- `ResetCommandBuffer` with an incorrect request length results in `BadLength`; unknown or non-live Device/Buffer XIDs result in `BadValue`; a live resource of the wrong type, foreign ownership, or cross-device use results in `BadMatch`.
- After successful XID/ownership validation, an unavailable or lost logical Device returns `DEVICE_UNAVAILABLE` or `DEVICE_LOST` before the pool reset flag or Buffer state is checked.
- `ResetCommandBuffer` without the `RESET_COMMAND_BUFFER` pool flag or with a pending Buffer is rejected with `INVALID_SYNCHRONIZATION_STATE`.
- `CMD_DISPATCH` recorded into a Command Buffer whose parent Command Pool queue family lacks the `COMPUTE` flag returns `BadMatch` during resource-dependent `CommandBufferData` validation, after XID/type/ownership and Device-state phases; the current chunk is not appended.

### `CMD_PUSH_CONSTANTS`

Within `CommandBufferData`, malformed entry framing or padding, `stage_flags` other than exactly `COMPUTE`, zero `data_length`, unaligned `offset`/`data_length`, or arithmetic overflow of `offset + data_length` returns `BadValue`. An unknown/non-live PipelineLayout XID returns `BadValue`; a live wrong resource type, foreign ownership, or cross-Device PipelineLayout returns `BadMatch`. A well-formed range whose end exceeds `maxPushConstantsSize`, or whose complete interval is not contained in one declared COMPUTE range of that PipelineLayout, returns `BadMatch`. Rejection appends none of the current CommandBufferData chunk.

### Presentation-only `CMD_COPY_BUFFER_TO_SWAPCHAIN_IMAGE`

These rules apply only to the presentation-capable profile; `CMD_COPY_BUFFER_TO_SWAPCHAIN_IMAGE` is assigned command-entry ID 5 in the central registry. Error precedence follows the enclosing `CommandBufferData` phases: (1) command-entry structure, exact entry length, `entry_length`, and reserved fields; (2) entry-local syntax, including four-byte alignment of `buffer_offset` and the rule that `row_length`/`image_height` are zero or positive; (3) resolve Buffer XID and then Swapchain XID (`BadValue` for unknown/non-live XIDs); (4) validate type, client/Device ownership, and cross-Device association (`BadMatch`); (5) for CREATE, append, and FINAL, check Device state (`DEVICE_UNAVAILABLE` / `DEVICE_LOST`) before command-buffer state and resource-dependent entry compatibility; (6) check resource-dependent static values: an `image_index` outside the Swapchain, effective row length/height smaller than the Swapchain extent, or a source range outside the Buffer returns `BadValue`; missing `TRANSFER_SRC` on the Buffer, missing `TRANSFER_DST` on the Swapchain, or a parent Command Pool queue family lacking all of `GRAPHICS`, `COMPUTE`, and `TRANSFER` returns `BadMatch`; (7) check the image's mutable state atomically at `QueueSubmit` acceptance, returning `INVALID_SYNCHRONIZATION_STATE` unless the image is still `ACQUIRED`. Diese Reihenfolge verhindert, dass XID-abhängige Prüfungen ohne aufgelöste Ressource ausgeführt werden, während entry-lokale Syntaxfehler nicht durch einen ungültigen XID verdeckt werden. Die Image-State-Prüfung erfolgt atomar bei Submission-Annahme: ist das Image dann nicht `ACQUIRED` oder konkurriert der Submit mit einer Present-Transition, ergibt sich `INVALID_SYNCHRONIZATION_STATE`. Die Prüfung berücksichtigt alle zuvor in X11-Request-Reihenfolge angenommenen Zustandsübergänge: ein Copy-Submit nach einer bereits angenommenen `QueuePresent`-Transition auf `PRESENT_PENDING` wird abgewiesen; ein zuvor angenommener Submit bleibt dagegen gültig und behält seine internen Referenzen. Die Request-Reihenfolge ersetzt keine GPU-Synchronisation. Die Ablehnung darf weder den Command-Buffer teilweise annehmen noch Image-, Referenz- oder Semaphore-Zustände verändern. Ein Swapchain-Destroy bleibt abgewiesen, solange ein Recording-Command-Buffer darauf referenziert; nach erfolgreichem Destroy wird ein nicht-pending ausführbarer Command-Buffer mit dieser Referenz invalidiert.

### Einheitliche XID- und Zustandszuordnung für ausgewählte Requests

Die Prüfung erfolgt in dieser Reihenfolge: Wire-Länge und strukturelle Integrität; Feldwerte und reservierte Felder; Auflösung jeder erforderlichen XID; Ressourcentyp und Ownership; request-spezifische Zustands- und Backend-Prüfungen. Ein Fehler beendet den Request ohne Teiländerungen. Ein als `0` definierter optionaler XID-Wert wird nicht aufgelöst.

| Request / Condition | Error |
|---|---|
| `DestroyResource`: falsche Länge | `BadLength` |
| `DestroyResource`: XID löst keine live Ressource auf | `BadValue` für unbekannte/nicht-live XIDs; `BadMatch` für einen falschen live Ressourcentyp |
| `DestroyResource`: Ressourcentyp ist nicht für den generischen Request zugelassen oder Ressource gehört einem anderen Client | `BadMatch` |
| `DestroyResource`: Ressource wird von einem `RECORDING`-Command-Buffer referenziert oder ihre typabhängige Pending-Regel verbietet die Zerstörung | `INVALID_SYNCHRONIZATION_STATE` |
| `BindBufferMemory`: falsche Länge | `BadLength` |
| `BindBufferMemory`: ungültige Feldwerte oder nicht-null reservierte Felder, sofern vorhanden | `BadValue` |
| `BindBufferMemory`: Device-, Buffer- oder Memory-XID ist ungültig/nicht live | `BadValue` für unbekannte/nicht-live XIDs; `BadMatch` für einen falschen live Ressourcentyp |
| `BindBufferMemory`: falscher Ressourcentyp oder Client-/Device-Ownership passt nicht | `BadMatch` |
| `BindBufferMemory`: Device ist nicht verfügbar/verloren, nach XID-/Typ-/Ownership-Prüfung und vor bindungsabhängigen Zustands-/Backend-Prüfungen | `DEVICE_UNAVAILABLE` / `DEVICE_LOST` |
| `BindBufferMemory`: Buffer bereits gebunden, Memory-Type nicht erlaubt, Alignment falsch oder Allocation zu klein | `BadMatch` |
| `UpdateDescriptorSets`: falsche Gesamtlänge oder Payload passt nicht zu `write_count` | `BadLength` |
| `UpdateDescriptorSets`: `write_count = 0`, reservierte Felder ungleich null, doppelte Writes desselben Slots, ungültige Werte/Flags oder nicht zugewiesener `descriptor_type` | `BadValue` |
| `UpdateDescriptorSets`: ungültige/nicht-live Device-, Set- oder Buffer-XID | `BadValue` für unbekannte/nicht-live XIDs; `BadMatch` für einen falschen live Ressourcentyp |
| `UpdateDescriptorSets`: falscher live Typ, fremde Client-/Device-Ownership, Layout/Binding/Array-Slot oder registrierter Descriptor-Typ inkompatibel, Buffer ungebunden oder Bereich/Alignment ungültig | `BadMatch` |
| `UpdateDescriptorSets`: Device ist nicht verfügbar/verloren, nach XID-/Typ-/Ownership-Prüfung und vor Layout-/Binding-/Pending-Zustandsprüfungen | `DEVICE_UNAVAILABLE` / `DEVICE_LOST` |
| `UpdateDescriptorSets`: Layout-/Binding-/Slot-Inkompatibilität oder betroffenes Set wird von angenommener Arbeit verwendet | `BadMatch` / `INVALID_SYNCHRONIZATION_STATE` gemäß Bedingung |
| `QueueSubmit`: falsche Länge, inkonsistente Counts oder Längenberechnung läuft über | `BadLength` |
| `QueueSubmit`: Token ist null oder auf derselben Verbindung bereits verwendet; reservierte Felder, syntaktisch ungültige Wait-Stage-Maske (0 oder reservierte Bits), ungültige typunabhängige Feldwerte, doppelte rohe Wait-/Signal-Semaphore-XIDs oder dieselbe Semaphore in beiden Arrays | `BadValue` |
| `QueueSubmit`: Device-, Command-Buffer-, Semaphore- oder nicht-null Fence-XID ungültig/nicht live | `BadValue` für unbekannte/nicht-live XIDs; `BadMatch` für einen falschen live Ressourcentyp |
| `QueueSubmit`: falscher Ressourcentyp, fremde Client-/Device-Ownership, angegebene Queue wurde nicht für dieses Device erstellt oder ein Command Buffer stammt aus einem Command Pool einer anderen Queue-Family | `BadMatch` |
| `QueueSubmit`: Device unavailable/lost after successful XID/type/ownership/queue-family validation and before mutable submission-state checks | `DEVICE_UNAVAILABLE` / `DEVICE_LOST` |
| `QueueSubmit`: type-dependent Binary value is nonzero or Timeline signal value is not greater than the observable counter, after XID, type, and Device-state checks | `BadValue` |
| `QueueSubmit`: Timeline signal value exceeds the observable counter but conflicts with an already reserved pending GPU signal value | `INVALID_SYNCHRONIZATION_STATE` |
| `QueueSubmit`: a Command Buffer is not `EXECUTABLE`, a Fence is not submit-eligible, a Semaphore state is invalid, or a syntactically valid wait-stage mask contains a stage unsupported by the addressed queue family | `INVALID_SYNCHRONIZATION_STATE` |
| `QueueSubmit`: Abhängigkeit verhindert die Annahme, ohne dass eine speziellere Zustandsregel greift | `DEPENDENCY_FAILED` |
| `QueueSubmit`: synchronous error before acceptance | no state changes; the token remains unused, command buffers remain `EXECUTABLE`, Fence/Semaphore states and internal references remain unchanged; no submission event or `ASYNC_ERROR` is emitted |
| `ResetFence`: falsche Länge | `BadLength` |
| `ResetFence`: Device- oder Fence-XID ungültig/nicht live | `BadValue` für unbekannte/nicht-live XIDs; `BadMatch` für einen falschen live Ressourcentyp |
| `ResetFence`: falscher Ressourcentyp oder Fence gehört zu einem anderen Client/Device | `BadMatch` |
| `ResetFence`: Fence ist weder `SIGNALED` noch `FAILED` | `INVALID_SYNCHRONIZATION_STATE` |
| `ResetFence`: Device verloren | `DEVICE_LOST` |

`ResetFence` serializes its state check and reset atomically against submission completion and new `QueueSubmit` acceptance. A reset of `PENDING` is rejected without mutation; a terminal state committed first may be reset. Each accepted submission captures the Fence's internal identity and use generation. Completion/failure callbacks may mutate Fence state only when their terminal transition wins and the captured identity, generation, and current submission association still match. Reset and reuse invalidate stale callback authority; delayed/duplicate callbacks from older submissions cannot overwrite a newer `PENDING`, `SIGNALED`, `FAILED`, or reset state.

Für alle fünf Requests gilt: Fehler vor Annahme werden synchron als X11-Fehler gemeldet; der Request darf keine Teiländerungen hinterlassen. Nach angenommener `QueueSubmit` werden Ausführungsfehler ausschließlich über die Submission-Terminalereignisse und zugehörige Zustände gemeldet, nicht als nachträglicher X11-Fehler. Ein nicht verfügbarer Zustand wird nur dann gemeldet, wenn der Request tatsächlich weitere Backend-Arbeit benötigt; rein logische Bereinigung nach Device Loss folgt den jeweiligen Lebensdauerregeln.

### Synchronization Requests

- `CreateSemaphore`: normative precedence: exact 28-byte length (`BadLength`); semaphore type and type-dependent initial value (`BadValue`); target XID (`BadIDChoice`); Device XID (`BadValue`); wrong live resource type or foreign Device ownership `BadMatch`; unavailable or lost Device `DEVICE_UNAVAILABLE` / `DEVICE_LOST`; backend allocation failure `ALLOCATION_FAILED`. For Binary, `initial_value` MUST be zero. On rejection, the target XID remains unallocated.
- `CreateFence`: normative precedence: exact 24-byte length (`BadLength`); create flags and reserved fields (`BadValue`, all must be zero); target XID (`BadIDChoice`); Device XID (`BadValue`); wrong live resource type or foreign Device ownership `BadMatch`; unavailable or lost Device `DEVICE_UNAVAILABLE` / `DEVICE_LOST`; backend allocation failure `ALLOCATION_FAILED`. On rejection, the target XID remains unallocated.
- `GetSemaphoreCounterValue`: normative precedence: exact 16-byte length (`BadLength`); resolve Device then Semaphore XID (`BadValue`); validate live type, ownership, and Device association (`BadMatch`); check Device state (`DEVICE_LOST` X11 error); require Timeline semaphore (`BadMatch`). Earlier phases win. The Device-state check is serialized with the counter snapshot: established Device Loss emits the X11 error `DEVICE_LOST` and no normal reply; otherwise the counter is returned as of the query's linearization point.
- `SignalSemaphore`: normative precedence: incorrect length `BadLength`; resolve Device XID, then Semaphore XID (`BadValue` for unknown or non-live XIDs); validate resource type, ownership, and cross-device use (`BadMatch`); check Device state (`DEVICE_UNAVAILABLE` / `DEVICE_LOST`); finally validate semaphore type and signal-value/reservation rules. A Binary semaphore returns `BadMatch`; a timeline `signal_value` not greater than the observable counter returns `BadValue`; a value that exceeds the counter but crosses or violates an already reserved GPU signal value returns `INVALID_SYNCHRONIZATION_STATE`. A synchronous rejection performs no partial host signal and leaves counters and reservations unchanged. The numeric reservation check does not establish signal-operation order: the client MUST ensure that any pending GPU signal operation executes after this host signal, and all Timeline signal operations execute in strictly increasing value order.
- `WaitSemaphores`: normative precedence: length and overflow `BadLength`; then zero count, invalid wait mode, or duplicate Semaphore XIDs `BadValue`; then resolve Device and Semaphore XIDs in array order (`BadValue` for unknown or non-live XIDs); validate type, ownership, and cross-device use (`BadMatch`); check Device state (`DEVICE_LOST`); finally require every Semaphore to be `TIMELINE` (`BadMatch`). These errors occur before wait registration and leave state unchanged. The final Device-state check, Timeline-type check, initial coherent counter snapshot, and immediate-success/registration decision are serialized against Device Loss and counter publication; a Device Loss committed first returns `DEVICE_LOST` even if the predicate is already satisfied. Entry *i* is satisfied when its observable Timeline counter reaches `wait_value[i]`; `WAIT_ANY` succeeds when at least one entry is satisfied, while `WAIT_ALL` requires every entry. The predicate uses one coherent counter snapshot; partial `WAIT_ALL` progress remains open and does not consume or reserve counters. No winning semaphore index is returned. Device loss of an already registered wait is terminal and reported as X11 error `DEVICE_LOST`; `DestroyDevice` terminates an open wait with `DEVICE_DESTROYED` unless Device loss was already terminally established. `TIMEOUT` is only a normal reply status. For nonzero timeouts, the initial condition check and registration are atomic with counter publication; a racing signal is either observed by the check or triggers reevaluation of the installed registration. Timeout zero performs a single coherent check without registering. The first committed complete predicate, timeout, or lifecycle outcome wins; this prevents lost wakeups and partial-ALL success.
- `GetFenceStatus`: normative precedence: exact 16-byte length (`BadLength`); resolve Device then Fence XID (`BadValue`); validate live types, ownership, and Device association (`BadMatch`); atomically snapshot the stored Fence state. Device Loss is not an error for this state-only query; the result reflects the state at its linearization point.
- `ResetFence`: incorrect length `BadLength`; unknown or non-live Device or Fence XIDs `BadValue`; wrong live resource type, foreign ownership, or cross-device use `BadMatch`. After valid XID, type, and ownership checks, `DEVICE_LOST` takes precedence over the Fence state. Only when the Device is available may `SIGNALED` and `FAILED` be reset; other states return `INVALID_SYNCHRONIZATION_STATE`.
- `WaitForFence`: normative precedence: exact 24-byte length (`BadLength`); resolve Device XID, then Fence XID in wire order (`BadValue`); validate live resource types, client ownership, and Device association (`BadMatch`); then inspect Device state and the Fence/wait outcome in an atomic initial Device/Fence-state snapshot. Device loss returns normal reply status `DEVICE_LOST`, even if the stored Fence state is `FAILED`; Device Loss has already been detected and established as terminal if it wins the open wait; otherwise an already-lost Device yields normal reply status `DEVICE_LOST` even for a `FAILED` Fence; otherwise an already-terminal Fence yields `SUCCESS` or `EXECUTION_FAILED`, and timeout zero on a non-terminal Fence yields `TIMEOUT` without registration. For nonzero timeout, initial snapshot and wait registration are atomic with Fence terminalization, timeout, Device Loss, and `DestroyDevice`. An open wait has exactly one first-committed terminal outcome; late callbacks cannot overwrite it or reply/release twice. Timeout, execution failure, Device Loss, and `DestroyDevice` use normal reply statuses, never X11 errors. Device Loss beats `DestroyDevice` only if it was already committed; otherwise `DestroyDevice` wins while the wait is open. Synchronous X11-error rejection leaves no wait registration or wait-only reference.
- `DestroyFence`: normative precedence: exact 16-byte length (`BadLength`); resolve Device XID, then Fence XID (`BadValue`); validate live types, client ownership, and Device association (`BadMatch`); finally check lifetime blockers (`INVALID_SYNCHRONIZATION_STATE` while the Fence is `PENDING`—including a pending `AcquireNextImage` signal reservation—or an open `WaitForFence` registration references that exact internal Fence identity). Device Loss alone is not an error for this logical cleanup request. A terminally established wait no longer blocks destruction, even if its reply has not yet been sent. Rejection leaves the XID and Fence state unchanged.
- `DestroySemaphore`: normative precedence is exact 16-byte length (`BadLength`); resolve Device XID, then Semaphore XID in wire order (`BadValue` for unknown/non-live XIDs); validate live resource type, client ownership, and Device association (`BadMatch`); then check exact-identity lifetime blockers (`INVALID_SYNCHRONIZATION_STATE`) while an accepted queue wait, queue signal, an open `WaitSemaphores` registration for that exact internal Semaphore identity, or another active host operation references it. A terminally established wait no longer blocks destruction, even if its reply has not yet been sent. Rejection leaves the XID and synchronization state unchanged. Device Loss alone does not invalidate public XIDs or bypass an active lifetime blocker; subsequent `DestroyDevice` cascade invalidation may bypass these ordinary rejection rules.

### `DestroyResource`

- Falsche Request-Länge: `BadLength`
- Ungültige oder nicht mehr live XID: `BadValue` für eine unbekannte/nicht-live XAverius-XID
- Ressourcentyp, der nicht für den generischen Request zugelassen ist (insbesondere Fence und Semaphore), oder falsche Ownership: `BadMatch`
- Verstoß gegen die typabhängigen Recording-/Pending-Lebensdauerregeln: `INVALID_SYNCHRONIZATION_STATE`
- Ablehnung lässt XID, interne Lebensdauerzustände und abhängige Command-Buffer-Zustände unverändert.
- Verbindliche Präzedenz: (1) exakte Request-Länge (`BadLength`); (2) Auflösung der `resource_xid` (`BadValue` bei unbekannt/nicht live); (3) erlaubter Ressourcentyp und Client-Ownership (`BadMatch`); (4) typabhängige Recording-/Pending-Lebensdauerregeln (`INVALID_SYNCHRONIZATION_STATE`). Die Prüfungen und die öffentliche Invalidierung bilden einen atomaren Übergang. Device Loss allein ist kein zusätzlicher Ablehnungsgrund und darf nicht pauschal `DEVICE_LOST` für `DestroyResource` erzeugen. Bereits terminalisierte GPU-Arbeit blockiert nicht mehr allein wegen ihres früheren Pending-Zustands; tatsächliche Recording-Referenzen und typabhängige noch aktive Verwendungen bleiben maßgeblich. Interne Objekte und Backend-Referenzen werden bis zur sicheren Quieszenz erhalten oder quarantänisiert. `DestroyDevice` darf anschließend die definierte Kaskadeninvalidierung durchführen.

### Ressourcenzerstörung und Memory-Freigabe

- Destroy einer Ressource, die von einem `RECORDING`-Command-Buffer referenziert wird: `INVALID_SYNCHRONIZATION_STATE`.
- Destroy eines pending Command Buffers, Descriptor Sets, Buffers oder einer Pipeline: `INVALID_SYNCHRONIZATION_STATE`. Für ein Pipeline Layout gilt dies bei direkter Pending-Verwendung; eine Pipeline-interne Layout-Abhängigkeit blockiert die öffentliche XID-Invalidierung nicht, hält aber die interne Backend-Ressource bis zur Zerstörung der Pipeline am Leben.
- `DestroyCommandPool`: `INVALID_SYNCHRONIZATION_STATE`, wenn mindestens ein Kind-Command-Buffer pending ist.
- `DestroyDescriptorPool` oder `FreeDescriptorSets`: `INVALID_SYNCHRONIZATION_STATE`, wenn ein betroffenes Set pending verwendet oder von einem `RECORDING`-Command-Buffer referenziert wird.
- `DestroyFence`: `INVALID_SYNCHRONIZATION_STATE`, solange die Fence einer nicht-terminalen Submission zugeordnet ist oder eine offene `WaitForFence`-Registrierung genau diese interne Fence-Identität referenziert.
- `DestroySemaphore`: `INVALID_SYNCHRONIZATION_STATE`, solange ein angenommener Queue-Wait/-Signal, eine offene `WaitSemaphores`-Registrierung für genau diese interne Semaphore-Identität oder eine andere laufende Host-Operation die Semaphore verwendet.
- Bei beiden Requests blockiert ein Host-Wait die Zerstörung nicht mehr, sobald sein terminales Ergebnis serverseitig serialisiert festgestellt wurde; ein noch nicht versendeter Reply ist kein Hindernis. Device loss alone does not invalidate public XIDs. If `DestroyDevice` is subsequently processed, its device-wide cascading invalidation may bypass these ordinary rejections.
- `FreeMemory`: `BadMatch`, solange irgendein intern noch lebender Buffer an die Allokation gebunden ist, auch wenn dessen öffentliche XID bereits invalidiert wurde; `INVALID_SYNCHRONIZATION_STATE`, solange angenommene Arbeit auf die Allokation zugreift.
- A destroy request rejected by lifetime rules leaves all public XIDs and command-buffer states unchanged.
- Die Device-weite Kaskadeninvalidierung durch `DestroyDevice` ist von diesen normalen Pending-Use-Ablehnungen ausgenommen; Device Loss allein invalidiert keine öffentlichen XIDs. Interne Referenzen müssen in jedem Fall sicher erhalten bleiben.

### Buffer- und Memory-Requests

- `CreateBuffer`: falsche feste Länge `BadLength`; nicht-positive Größe, unbekannte Usage-Bits oder nicht-null reservierte Felder `BadValue`; ungültige oder bereits belegte Create-XID `BadIDChoice`; unbekannte/nicht-live Device-XID `BadValue`; falscher live Ressourcentyp oder fremdes Device `BadMatch`; nicht verfügbares/verlorenes Device `DEVICE_UNAVAILABLE` / `DEVICE_LOST`; fehlgeschlagene Backend-Erstellung wegen Speicherknappheit `ALLOCATION_FAILED`; kein Buffer bleibt bei Ablehnung live. Präzedenz: Länge, skalare Felder, Ziel-XID, Device-XID, Typ/Ownership, Device-Zustand, Backend-Erstellung.
- `GetBufferMemoryRequirements`: falsche Länge `BadLength`; unbekannte/nicht-live Buffer-/Device-XID `BadValue`; falscher Ressourcentyp oder Cross-Device-Zugriff `BadMatch`. Präzedenz: (1) exakte 16-Byte-Länge; (2) Device-XID, dann Buffer-XID in Wire-Reihenfolge; (3) Ressourcentyp, Ownership und Device-Zuordnung; (4) gespeicherte Requirements zurückgeben. Die Abfrage startet keine Backend-Arbeit und bleibt bei Device Loss zulässig, solange die öffentlichen XIDs gültig sind.
- `AllocateMemory`: incorrect length `BadLength`; invalid size, memory-type index, or reserved field `BadValue`; invalid or occupied create XID `BadIDChoice`; unknown or non-live Device XID `BadValue`; live resource of the wrong type or foreign Device ownership `BadMatch`; unavailable or lost Device `DEVICE_UNAVAILABLE` / `DEVICE_LOST`; backend allocation failure `ALLOCATION_FAILED`; on rejection, the target XID remains unallocated. Precedence: length, scalar fields, target XID, Device XID, type/ownership, Device state, backend allocation.
- `FreeMemory`: siehe die Lebensdauerregeln unten; bei Ablehnung bleibt die Allokation öffentlich gültig.
- `BindBufferMemory`: siehe die spezifische Zuordnung unten.

### Descriptor-Pool- und Pipeline-Requests

- `CreateDescriptorPool`: falsche Länge oder nicht zum `pool_size_count` passende Payload `BadLength`; ungültige Counts, doppelte Pool-Size-Typen, nicht unterstützte Descriptor-Typen oder nicht-null reservierte Felder `BadValue`; ungültige/belegte Pool-XID `BadIDChoice`; unbekannte/nicht-live Device-XID `BadValue`; falscher live Ressourcentyp oder fremde Device-Ownership `BadMatch`; nicht verfügbares/verlorenes Device `DEVICE_UNAVAILABLE` / `DEVICE_LOST`; Backend-Allokationsfehler `ALLOCATION_FAILED`; bei Ablehnung bleibt die Pool-XID unangelegt.
- `AllocateDescriptorSets`: Länge/Entry-Struktur `BadLength`; Count/reservierte Felder `BadValue`; Ziel-Set-XIDs in Array-Reihenfolge `BadIDChoice`; danach Eingabe-XIDs in Wire-Reihenfolge (Device, Pool, Layouts) `BadValue`; falsche live Typen/Ownership `BadMatch`; Device-Zustand `DEVICE_UNAVAILABLE` / `DEVICE_LOST`; Pool-/Layout-Inkompatibilität `BadMatch`; Kapazitäts-/Backend-Allokationsfehler `ALLOCATION_FAILED`. Präzedenz und Batch-Atomarität sind im Request-Kapitel normativ festgelegt; keine Teilmenge bleibt live.
- `FreeDescriptorSets`: falsche Länge `BadLength`; Count null oder nicht-null reservierte Felder `BadValue`; unbekannte/nicht-live Device-, Pool- oder Set-XID `BadValue`; falsche live Ressourcentypen, fremde Ownership oder Set gehört nicht zum angegebenen Pool/Device `BadMatch`; pending oder RECORDING-Referenz `INVALID_SYNCHRONIZATION_STATE`. Nach Device Loss bleibt die logische Freigabe zulässig und erfordert keine neue Vulkan-Arbeit; interne Referenzen bleiben bis zur sicheren Quieszenz erhalten. Keine Teilfreigabe bei Ablehnung.
- `DestroyDescriptorPool`: falsche Request-Länge `BadLength`; unbekannte/nicht-live Pool-XID `BadValue`; falscher live Ressourcentyp oder fremde Client-/Device-Ownership `BadMatch`; wenn ein Kind-Set pending verwendet oder von einem `RECORDING`-Command-Buffer referenziert wird, `INVALID_SYNCHRONIZATION_STATE`. Device Loss allein ist kein Ablehnungsgrund für die logische Bereinigung; die Pending-/Recording-Prüfungen bleiben bestehen. Die Ablehnung ist atomar: Pool, Sets und Referenzen bleiben unverändert.
- `CreatePipelineLayout`: Wire-Länge `BadLength`; `stage_flags` ungleich `COMPUTE`, `size = 0`, nicht vierbyte-ausgerichtete Werte, 32-Bit-Überlauf von `offset + size` oder überlappende Ranges `BadValue`; Ziel-XID `BadIDChoice`; Device-/Set-Layout-XIDs `BadValue`; falsche live Typen/Ownership/Cross-Device `BadMatch`; Device-Zustand `DEVICE_UNAVAILABLE` / `DEVICE_LOST`; ein Range-Ende oberhalb `maxPushConstantsSize` oder `set_layout_count` oberhalb `maxBoundDescriptorSets` `BadMatch`; Backend-Allokationsfehler `ALLOCATION_FAILED`. Kein Pipeline Layout bleibt bei Ablehnung live.
- `CreateComputePipeline`: Wire-Länge `BadLength`; Entry-Point-/Padding-/Reserved-Feldfehler `BadValue`; Ziel-XID `BadIDChoice`; Device-/Layout-/Shader-XIDs `BadValue`; falsche live Typen/Ownership/Cross-Device `BadMatch`; Device-Zustand `DEVICE_UNAVAILABLE` / `DEVICE_LOST`; ein nicht im SPIR-V-Modul vorhandener Entry-Point oder ein Entry-Point mit Execution Model ungleich `GLCompute` `BadMatch`; Backend-Allokationsfehler `ALLOCATION_FAILED`. Kein Pipeline-Objekt bleibt bei Ablehnung live.

### Normative descriptor-create validation precedence

The following ordered phases are normative. A later phase MUST NOT replace an error from an earlier phase, and no backend allocation or public resource publication occurs before all validation phases succeed.

- `CreateDescriptorSetLayout`: (1) validate exact `24 + 16 * binding_count` framing with checked arithmetic (`BadLength`); (2) validate flags, reserved fields, binding uniqueness, positive descriptor counts, descriptor types, and stage bits (`BadValue`); (3) validate the target layout XID (`BadIDChoice`); (4) resolve `device_xid` (`BadValue` if unknown/non-live); (5) validate live type and client ownership (`BadMatch`); (6) check Device availability (`DEVICE_UNAVAILABLE` / `DEVICE_LOST`); (7) check descriptor-count/device-limit support (`BadMatch` for a syntactically valid layout exceeding the selected Device's applicable limits); (8) perform backend allocation (`ALLOCATION_FAILED`). Thus malformed length beats invalid fields and target collisions; scalar errors beat target collisions; target-XID errors beat unknown Device XIDs; Device Loss beats device-limit checks and backend allocation. Rejection leaves the target unallocated.
- `CreateDescriptorPool`: (1) validate exact `24 + 8 * pool_size_count` framing with checked arithmetic (`BadLength`); (2) validate nonzero supported counts, unique pool-size descriptor types, supported descriptor types, and zero reserved fields (`BadValue`); (3) validate the target pool XID (`BadIDChoice`); (4) resolve `device_xid` (`BadValue`); (5) validate live type and ownership (`BadMatch`); (6) check Device availability (`DEVICE_UNAVAILABLE` / `DEVICE_LOST`); (7) backend allocation (`ALLOCATION_FAILED`). A malformed size array beats all later failures; scalar errors beat target collision; target collision beats Device lookup. Rejection leaves no pool or capacity reservation.
- `AllocateDescriptorSets`: (1) validate exact `20 + 8 * descriptor_set_count` framing with checked arithmetic (`BadLength`); (2) validate nonzero count and reserved/scalar fields (`BadValue`); (3) validate every target Set XID in array order, including duplicates within the request (`BadIDChoice`); (4) resolve input XIDs in wire order: Device, Pool, then each Layout (`BadValue` for unknown/non-live); (5) validate live resource types, client ownership, and Device association (`BadMatch`); (6) check Device availability (`DEVICE_UNAVAILABLE` / `DEVICE_LOST`); (7) validate Pool/Layout compatibility (`BadMatch`); (8) reserve pool capacity and allocate all Sets (`ALLOCATION_FAILED` on capacity/backend failure). In particular, any target-XID collision beats every unknown input XID; an unknown input XID beats Device Loss; Device Loss beats pool-capacity/backend errors. The operation is all-or-nothing: a failure at any phase publishes no Set and retains no capacity or Layout reference.
- A later target collision in an `AllocateDescriptorSets` array MUST be detected before resolving any input XID or publishing an earlier Set. An occupied target combined with an unknown Device/Pool/Layout returns `BadIDChoice`; a duplicate target in the final array position also returns `BadIDChoice` and leaves the entire batch absent.

### Normative descriptor-set release validation precedence

These requests are logical cleanup operations. Device Loss alone MUST NOT reject them and MUST NOT trigger new Vulkan work. Public invalidation and reference retirement are serialized; internal backend references remain retained until safe quiescence.

- `DestroyDescriptorPool`: (1) validate the exact 16-byte request length (`BadLength`); (2) resolve the Device XID, then Pool XID in wire order (`BadValue` for unknown/non-live XIDs); (3) validate live resource types, client ownership, and Device association (`BadMatch`); (4) inspect every child Set for a pending use or a reference from a `RECORDING` command buffer (`INVALID_SYNCHRONIZATION_STATE`); (5) atomically invalidate the Pool and all child Sets, and invalidate non-pending `EXECUTABLE` command buffers that reference those Sets. There is no Device-availability phase: Device Loss does not block this logical cleanup. A later child blocker MUST NOT cause partial invalidation.
- `FreeDescriptorSets`: (1) validate exact `20 + 4 * descriptor_set_count` framing with checked arithmetic (`BadLength`); (2) validate nonzero count, zero reserved/scalar fields, and no duplicate Set XIDs (`BadValue`); (3) resolve Device, Pool, then Set XIDs in wire order (`BadValue` for unknown/non-live XIDs); (4) validate live resource types, client ownership, and each Set's association with the specified Pool and Device (`BadMatch`); (5) inspect all selected Sets for pending use or a reference from a `RECORDING` command buffer (`INVALID_SYNCHRONIZATION_STATE`); (6) atomically invalidate all selected Sets and invalidate non-pending `EXECUTABLE` command buffers that reference them. There is no Device-availability phase: Device Loss does not block this logical cleanup. No selected Set may be freed unless every selected Set passes every phase.

For both requests, an earlier framing/scalar/XID/type/ownership error takes precedence over a later lifetime blocker. For `FreeDescriptorSets`, a later unknown Set XID or Pool-association mismatch MUST be detected before any earlier Set is invalidated. A rejected request preserves all public XIDs, Pool membership/capacity, command-buffer states, and internal reference edges. Successful logical invalidation does not permit early release of backend objects still reachable by active operations.

### Command Pool requests

- `CreateCommandPool`: normative Präzedenz: exakte 24-Byte-Länge (`BadLength`); Flags/reservierte Bits (`BadValue`); Ziel-Pool-XID (`BadIDChoice`); Device-XID (`BadValue`); Typ/Client- und Device-Ownership (`BadMatch`); Device-Zustand (`DEVICE_UNAVAILABLE` / `DEVICE_LOST`); Queue-Family-Index muss eine für dieses Device mit positiver Queue-Anzahl angeforderte Familie identifizieren (`BadValue`; kein separater Command-Buffer-Support-Check); Backend-Allokation (`ALLOCATION_FAILED`). Device Loss gewinnt damit gegen einen ungültigen Queue-Family-Index, aber nicht gegen frühere XID-/Ownership-Fehler. Bei jedem Fehler bleibt die Pool-XID unangelegt.
- `DestroyCommandPool`: normative Präzedenz: exakte 16-Byte-Länge (`BadLength`); Device-XID, dann Command-Pool-XID in Wire-Reihenfolge auflösen (`BadValue` für unbekannte/nicht-live XIDs); live Ressourcentyp, Client-Ownership und Device-Zuordnung prüfen (`BadMatch`); anschließend alle Kind-Command-Buffer auf `PENDING` prüfen (`INVALID_SYNCHRONIZATION_STATE`). Device Loss allein ist kein Ablehnungsgrund; sobald betroffene Submissions terminalisiert und ihre Command Buffer nicht mehr pending sind, bleibt die logische Pool-Bereinigung zulässig. Ablehnung ist atomar; bei Erfolg werden Pool und alle Kind-XIDs gemeinsam invalidiert.

### Synchronization requests

- `CreateSemaphore` und `CreateFence`: falsche Länge `BadLength`; ungültige Typen, Werte, Flags oder reservierte Felder `BadValue`; ungültige/belegte Create-XID `BadIDChoice`; unbekannte/nicht-live Device-XID `BadValue`; falscher live Ressourcentyp oder fremde Device-Ownership `BadMatch`; nicht verfügbares/verlorenes Device `DEVICE_UNAVAILABLE` / `DEVICE_LOST`; Backend-Allokationsfehler `ALLOCATION_FAILED`; bei Ablehnung bleibt die jeweilige Ziel-XID unangelegt.
- `GetSemaphoreCounterValue`: normative Präzedenz: exakt 16 Byte (`BadLength`); Device- und danach Semaphore-XID auflösen (`BadValue`); live Typ, Ownership und Device-Zuordnung prüfen (`BadMatch`); Device-Zustand prüfen (`DEVICE_LOST`); Timeline-Semaphor verlangen (`BadMatch`). Frühere Phasen haben Vorrang. Zustandsprüfung und Counter-Snapshot sind gegen Device Loss serialisiert.
- `SignalSemaphore`: verbindliche Präzedenz: falsche Länge `BadLength`; Device-XID, dann Semaphore-XID (`BadValue` bei unbekannt/nicht-live); Ressourcentyp/Ownership/Cross-Device (`BadMatch`); Device-Zustand (`DEVICE_UNAVAILABLE` / `DEVICE_LOST`); zuletzt Semaphore-Typ und Signalwert-/Reservierungsprüfung (Binary `BadMatch`; `signal_value` kleiner oder gleich dem beobachtbaren Counter `BadValue`; ein Wert oberhalb des Counters, der eine bestehende GPU-Signalreservierung kreuzt oder verletzt, `INVALID_SYNCHRONIZATION_STATE`). Bei synchroner Ablehnung wird kein Host-Signal teilweise ausgeführt und Counter sowie Reservierungen bleiben unverändert. Die numerische Reservierungsprüfung stellt keine Ausführungsreihenfolge her: Der Client MUSS sicherstellen, dass jede ausstehende GPU-Signaloperation nach diesem Host-Signal ausgeführt wird und sämtliche Timeline-Signaloperationen in streng aufsteigender Reihenfolge ausgeführt werden.
- `WaitSemaphores`: verbindliche Präzedenz: Länge/Überlauf `BadLength`; danach Count null, ungültiger Wait-Modus oder doppelte Semaphore-XIDs `BadValue`; dann Device-XID und Semaphore-XIDs in Array-Reihenfolge (`BadValue` bei unbekannt/nicht-live); danach Typ/Ownership/Cross-Device (`BadMatch`); danach Device-Zustand (`DEVICE_LOST`); zuletzt muss jeder Semaphore-Typ `TIMELINE` sein (`BadMatch`). Alle diese Fehler treten vor Wait-Registrierung auf und verändern keinen Zustand. Entry *i* ist erfüllt, wenn sein beobachtbarer Timeline-Counter mindestens `wait_value[i]` erreicht; `WAIT_ANY` benötigt mindestens einen erfüllten Entry, `WAIT_ALL` alle Entries. Ein teilweise erfülltes `WAIT_ALL` bleibt offen und kann weiterhin timeouten oder durch einen Lifecycle-Wechsel terminalisiert werden. Die Auswertung erfolgt anhand eines kohärenten Counter-Snapshots; kein Semaphore-Index wird zurückgegeben und kein Counter konsumiert. Device Loss eines bereits registrierten Waits ist ein terminaler Ausgang und wird als X11-Fehler `DEVICE_LOST` gemeldet; `DestroyDevice` beendet einen noch offenen Wait mit `DEVICE_DESTROYED`, sofern nicht zuvor Device Loss terminal festgestellt wurde. `TIMEOUT` ist ausschließlich ein normaler Reply-Status. Der zuerst committed vollständige Wait-Ausgang, Timeout oder Lifecycle-Ausgang gewinnt.
- `GetFenceStatus`: normative Präzedenz: exakt 16 Byte (`BadLength`); Device- und danach Fence-XID auflösen (`BadValue`); live Typen, Ownership und Device-Zuordnung prüfen (`BadMatch`); gespeicherten Fence-Zustand atomar abfragen. Device Loss ist für diese reine Zustandsabfrage kein Fehler.
- `ResetFence`: falsche Länge `BadLength`; unbekannte/nicht-live Device- oder Fence-XIDs `BadValue`; falscher live Ressourcentyp, fremde Ownership oder Cross-Device-Verwendung `BadMatch`; nach gültigen XIDs/Typ/Ownership hat `DEVICE_LOST` Vorrang vor dem Fence-Zustand; nur bei verfügbarem Device dürfen ausschließlich `SIGNALED` und `FAILED` zurückgesetzt werden, andere Zustände ergeben `INVALID_SYNCHRONIZATION_STATE`.
- `DestroyFence`: falsche Länge `BadLength`; unbekannte/nicht-live Device- oder Fence-XID `BadValue`; falscher live Typ, fremde Client-Ownership oder Cross-Device-Verwendung `BadMatch`; `INVALID_SYNCHRONIZATION_STATE`, solange die Fence `PENDING` ist oder eine offene `WaitForFence`-Registrierung genau diese interne Fence-Identität referenziert. Eine bereits terminal festgestellte Wait-Registrierung blockiert die Zerstörung nicht, auch wenn der Reply noch nicht gesendet wurde. Jede Ablehnung lässt XID und Fence-Zustand unverändert.
- `DestroySemaphore`: falsche Länge `BadLength`; unbekannte/nicht-live Device- oder Semaphore-XID `BadValue`; falscher live Typ, fremde Client-Ownership oder Cross-Device-Verwendung `BadMatch`; `INVALID_SYNCHRONIZATION_STATE`, solange ein angenommener Queue-Wait, Queue-Signal, eine offene `WaitSemaphores`-Registrierung für genau diese interne Semaphore-Identität oder eine andere laufende Host-Operation die Semaphore verwendet. Eine bereits terminal festgestellte Wait-Registrierung blockiert die Zerstörung nicht, auch wenn der Reply noch nicht gesendet wurde. Jede Ablehnung lässt XID und Synchronisationszustand unverändert. Device Loss allein invalidiert keine öffentlichen XIDs; wenn anschließend `DestroyDevice` verarbeitet wird, darf dessen Kaskadeninvalidierung diese normalen Ablehnungen umgehen.
- Die verbindliche XID-Zuordnung steht im Abschnitt „Verbindliche XID-Fehlerregel“: unbekannte/nicht-live XAverius-XIDs ergeben `BadValue`, falsche live Ressourcentypen `BadMatch`, ungültige Atoms `BadAtom`.

### Memory allocation and binding

- `GetBufferMemoryRequirements`: falsche Request-Länge `BadLength`; unbekannte/nicht-live Device- oder Buffer-XID `BadValue`; falscher live Ressourcentyp oder Buffer eines anderen Devices `BadMatch`.
- `AllocateMemory`: falsche Request-Länge `BadLength`; nicht-positive Allokationsgröße, reserviertes Feld ungleich null oder nicht existierender Memory-Type-Index `BadValue`; unbekannte/nicht-live Device-XID `BadValue`; falscher live Ressourcentyp `BadMatch`; nicht verfügbares/verlorenes Device `DEVICE_UNAVAILABLE` / `DEVICE_LOST`; Backend-Allokationsfehler `ALLOCATION_FAILED`. Bei jedem Fehler bleibt die angeforderte `memory_xid` unangelegt.
- `FreeMemory`: falsche Request-Länge `BadLength`; unbekannte/nicht-live Device- oder Memory-XID `BadValue`; falscher live Ressourcentyp, fremde Ownership oder Cross-Device-Nutzung `BadMatch`; irgendein intern noch lebender, gebundener Buffer `BadMatch` (auch bei bereits invalidierter Buffer-XID); angenommene GPU-Arbeit mit Zugriff auf die Allokation `INVALID_SYNCHRONIZATION_STATE`. Bei Ablehnung bleibt die Allokation unverändert.
- `BindBufferMemory`: falsche Request-Länge `BadLength`; unbekannte/nicht-live Device-, Buffer- oder Memory-XID `BadValue`; falscher live Ressourcentyp, fremde Ownership oder Cross-Device-Nutzung `BadMatch`; inkompatibler Memory-Type, bereits gebundener Buffer, ungültiges Alignment oder unzureichende Allokationsgrenzen `BadMatch`. Bei Ablehnung bleibt der Buffer ungebunden.

### `BindBufferMemory`

The complete XID, ownership, field-value, and Device error mapping is defined in the unified table above. Cross-Device use, an already-bound Buffer, invalid alignment, insufficient allocation size, or an incompatible memory type results in `BadMatch`.

### `UpdateDescriptorSets`

Normative precedence (all phases cover the entire request before mutation): (1) exact `20 + 36 * write_count` length, checked arithmetic, and X11 request limit (`BadLength`); (2) `write_count > 0`, zero reserved fields, valid typeless fields, assigned descriptor type, and no duplicate (Set, binding, array-element) slot (`BadValue`); (3) resolve `device_xid`, then each write's Set XID and Buffer XID in wire order (`BadValue` for unknown/non-live XIDs); (4) validate live types, client ownership, and Device association (`BadMatch`); (5) Device availability (`DEVICE_UNAVAILABLE` / `DEVICE_LOST`); (6) validate all Layout/Binding/Array-Slot/Descriptor-Type compatibility, Buffer binding/usage, alignment, range/overflow, and device limits (`BadMatch`); (7) reject if any affected Set is used by already accepted work (`INVALID_SYNCHRONIZATION_STATE`). A later phase MUST NOT override an earlier one. In particular, Device Loss precedes compatibility and pending-use errors.

Updates are all-or-nothing. The server prepares and retains every replacement Buffer reference before changing any slot. If validation or reference preparation fails, all newly prepared references are released and every old slot and reference edge remains unchanged. Once preparation succeeds, all slots and reference edges are swapped in one serialized commit; only then may old references be released. No partial slot update or transient loss of a required Buffer reference is permitted.

Jeder Request muss vor Implementierungsfreigabe eine vollständige, konkrete Fehlerzuordnung besitzen.

### Presentation requests (presentation-capable profile)

These rules apply to the presentation-capable profile only. The central request registry assigns `CreateSurface` through `QueuePresent` append-only subopcodes 41–47. This assignment does not make the presentation profile part of the compute-only v0.1 baseline; a compute-only server rejects these requests with core `BadRequest` before payload parsing or XID resolution.

- All presentation requests validate the exact fixed or formula-based request length first; a mismatch or overflow in `40 + 4 * wait_semaphore_count` is `BadLength`. Non-zero reserved fields, invalid enum/flag values, zero presentation tokens, duplicate wait semaphore XIDs, and malformed count/field combinations are `BadValue`. Reuse of a token from an already accepted presentation is a stateful acceptance check, not scalar syntax. Scalar/reserved validation applies only to fields actually present: `CreateSurface`, `DestroySurface`, and `DestroySwapchain` have no request-specific scalar or reserved fields, so they pass this phase without a `BadValue` scalar check.
- `CreateSurface`: invalid/already allocated target `surface_xid` is `BadIDChoice`; an unknown, destroyed, or non-Window core X11 `window_xid` is core X11 `BadWindow`; a live Window owned by another X11 client, or a live `InputOnly`/otherwise non-drawable Window, is `BadMatch`. Backend inability to present to an otherwise valid drawable Window is reported through capability negotiation and `CreateSwapchain`'s `UNSUPPORTED_CONFIGURATION`, not as a `CreateSurface` error. A failed create leaves the target XID unallocated and retains no window reference.
- `DestroySurface`: unknown/non-live Surface XID is `BadValue`; a live XID of another type or a Surface owned by another connection is `BadMatch`; any live Swapchain still referencing the Surface causes atomic rejection with `INVALID_SYNCHRONIZATION_STATE`. The only request-level lifetime blocker is a live Swapchain reference. Internal Window-identity tombstones and already-retained backend/notification references do not by themselves block destruction; after successful public invalidation they remain retained internally until quiescent. The checks and public invalidation are serialized atomically against Window lifecycle notifications and connection teardown: Window destruction first leaves the Surface `SURFACE_LOST`, which remains explicitly destroyable once no live Swapchain references it; successful `DestroySurface` first invalidates the public XID so later notifications cannot affect a reused XID. A rejected destroy leaves the Surface and its references unchanged.
- `GetSurfaceCapabilities`: resolve `device_xid` and then `surface_xid` in request-field order; an unknown/non-live XID is `BadValue`. A live wrong type or foreign connection ownership is `BadMatch`. A Surface is not Device-owned, so querying the same live Surface with different owned Devices is valid; the reply reports each Device/Surface pair's support independently and does not migrate resources. `SUCCESS`, `TEMPORARILY_NOT_PRESENTABLE`, `SURFACE_LOST`, and `DEVICE_LOST` are normal reply statuses, not X11 errors. Status-dependent zero fields and the reply-length formula remain mandatory.
- `CreateSwapchain`: invalid/already allocated target `swapchain_xid` is `BadIDChoice`; unknown/non-live Device or Surface XID is `BadValue`; wrong live type or foreign ownership is `BadMatch`; a valid Device/Surface pair that cannot present returns `UNSUPPORTED_CONFIGURATION` rather than `BadMatch` because a Surface is not Device-owned; zero image count or dimensions, unknown format/color-space/present-mode identifiers, unassigned usage bits, or non-zero reserved fields are `BadValue`. A syntactically valid but unsupported configuration returns `UNSUPPORTED_CONFIGURATION`; a zero-sized Surface or requested extent outside current bounds returns `OUT_OF_DATE`, except that a requested width or height of zero is rejected earlier as `BadValue` during scalar validation. `SURFACE_LOST`, `DEVICE_LOST`, and `ALLOCATION_FAILED` are normal reply statuses. On every non-success status the target XID remains unallocated. After wire-length and scalar-field validation, XID validation follows request field order: resolve `device_xid`, validate the target `swapchain_xid` as a create-XID, then resolve `surface_xid`. Capability/status checks occur only after these XID, type, ownership, and Device-state checks.
- `DestroySwapchain`: unknown/non-live Swapchain XID is `BadValue`; a live wrong type or foreign ownership is `BadMatch`; a recording command buffer, pending acquire registration, accepted queue work, accepted presentation, or possible backend access causes atomic rejection with `INVALID_SYNCHRONIZATION_STATE`; non-pending executable command buffers referencing the Swapchain are invalidated atomically on successful destruction. An acquired-but-idle image alone does not block destruction. Device Loss alone does not reject this logical cleanup request and does not bypass any pending-use/backend-access blocker; after successful `DestroyDevice`, the cascade has already invalidated the Swapchain XID and a later destroy returns `BadValue`.
- `AcquireNextImage`: unknown/non-live Device or Swapchain XID is `BadValue`; after exact 32-byte framing, resolve nonzero XIDs in request-field order (`device_xid`, `swapchain_xid`, optional `semaphore_xid`, optional `fence_xid`); unknown/non-live optional Semaphore or Fence XID is also `BadValue`. Validate live types, client ownership, and common Device association (`BadMatch`) before checking Device availability. Then `DEVICE_LOST` takes precedence over all later lifecycle and mutable-state checks; after it, `SURFACE_LOST` precedes `OUT_OF_DATE`. Live resource type, client ownership, and common Device association for every supplied Semaphore/Fence are checked in phase 4, before Device availability; a wrong type, foreign owner, or cross-Device object returns `BadMatch` even when the Device is lost. Only acquisition-signal eligibility and conflicting pending-acquire state are deferred until after the Device/Surface/Swapchain lifecycle checks; an ineligible state or conflicting pending acquire returns `INVALID_SYNCHRONIZATION_STATE`, even if no image is available or timeout is zero. A supplied Fence must be `UNSIGNALED` and unreserved; an open acquire registration reserves it as `PENDING` until success or non-success terminalization. Only then is availability/timeout evaluated: immediate image availability yields `SUCCESS`; no image with zero timeout yields `NOT_READY` without registration; finite expiry yields `TIMEOUT`; infinite timeout remains pending until another terminal outcome. `TIMEOUT`, `NOT_READY`, `OUT_OF_DATE`, `SURFACE_LOST`, `DEVICE_LOST`, and `DEVICE_DESTROYED` are normal reply statuses, not X11 errors, and signal neither optional object or change image state. Every non-success reply has `image_index = 0` and `reserved = 0`. The initial check and open-registration installation, image acquisition, signal-slot reservation/commit, timeout, lifecycle transitions, and DestroyDevice terminalization share one serialization domain. The first committed terminal outcome wins; late/duplicate callbacks cannot reply, acquire, signal, or release references twice. `DestroyDevice` returns `DEVICE_DESTROYED` only for a still-open pending registration; a previously committed result is immutable.
- `QueuePresent`: resolve `device_xid`, then `swapchain_xid`, then each wait-semaphore XID in array order; an unknown/non-live XID is `BadValue`. A live wrong type, foreign ownership, or cross-device use between the Device, Swapchain, and wait semaphores is `BadMatch`; nonexistent queue-family/index or image index outside the Swapchain is `BadValue`; a valid queue family whose capability record has `present_supported = 0` for the target Surface is `BadMatch`; an image not in `ACQUIRED`, or a wait semaphore that cannot be legally consumed because of an incompatible pending wait/state, is `INVALID_SYNCHRONIZATION_STATE`; a wait semaphore already marked `UNTRUSTED` is rejected with `DEPENDENCY_FAILED`. A zero token, duplicate wait XID, or reuse of a token reserved by an earlier accepted presentation is `BadValue`. `OUT_OF_DATE`, `SURFACE_LOST`, and `DEVICE_LOST` are normal reply statuses with the precedence defined below. Any rejected `QueuePresent` leaves the image state as it was immediately before that request, leaves wait-semaphore state unchanged, and does not reserve its presentation token. If an independent Device-loss transition has already invalidated the image, rejection does not restore it to `ACQUIRED`. Token uniqueness is checked against previously accepted presentations and recorded atomically with acceptance. The full QueuePresent status ordering and the independent terminal/release milestones are normative in `presentation.md`.
- For all seven requests, validation is atomic: no partial object, reference, image-state, synchronization-state, or token change attributable to the request may remain after a synchronous error or a non-success status. Independent asynchronous lifecycle transitions (especially Device loss) still take effect and are not rolled back by a rejected request. An accepted `QueuePresent` cannot later produce an X11 request error; its terminal result is reported through the presentation events and image/Swapchain state. Presentation terminalization and backend image release are independent milestones: terminal SUCCESS does not imply image reuse. The first committed terminal status is immutable, but a later lifecycle transition before image release may still invalidate the image and suppress `IMAGE_RELEASED`. The release callback may make an image AVAILABLE only after backend access has ended and current Device/Surface/Swapchain state still permits reuse.

### Normative validation precedence for the seven presentation requests

The following order is normative and applies before any externally visible state change. It supplements the request-specific error mapping above; a later stage MUST NOT run before an earlier stage has succeeded.

1. Validate exact/fixed or formula-derived wire length using checked wide arithmetic. A length mismatch or arithmetic overflow is `BadLength`.
2. Validate scalar syntax and reserved fields, including nonzero `presentation_token`, legal `wait_semaphore_count`, unique wait-semaphore XIDs, and create-request scalar values. Invalid scalar syntax is `BadValue`. For variable `QueuePresent`, compute `40 + 4 * wait_semaphore_count` with checked arithmetic before reading the wait array. Do not test whether a nonzero presentation token was previously accepted at this stage; that depends on mutable server state.
3. Resolve request XIDs in wire-field order. For create requests, validate the target XID at its defined create-XID position; `CreateSurface` checks `surface_xid` before resolving `window_xid`, while `CreateSwapchain` checks `device_xid`, then target `swapchain_xid`, then `surface_xid`. Unknown/non-live XAverius resource XIDs are `BadValue`; an unknown, destroyed, or non-Window core X11 `window_xid` is `BadWindow`.
4. Validate live resource types, connection ownership, Device ownership, and cross-device relationships. A live wrong type or ownership mismatch is `BadMatch`. For `CreateSurface`, a live Window belonging to another X11 client is `BadMatch`.
5. For requests with a Device, check Device availability after valid XIDs/types/ownership. If the reply has a defined `DEVICE_LOST` status (`GetSurfaceCapabilities`, `CreateSwapchain`, `AcquireNextImage`, `QueuePresent`), return that status; otherwise use the request's established Device error. Device loss takes precedence over Surface loss and all later mutable-state checks.
6. Validate request-specific indices and immutable constraints: queue-family/index existence, image-index bounds, and syntactic format/mode/usage identifiers. Failures use the request-specific X11 error mapping. A valid but unsupported configuration is not a syntax error and is handled by the normal status rules below.
7. Resolve lifecycle/capability outcomes before mutable image/semaphore eligibility: `GetSurfaceCapabilities` returns `SURFACE_LOST` for a lost Surface; `CreateSwapchain` returns `SURFACE_LOST` for a lost Surface and `OUT_OF_DATE` for a zero-sized Surface or a requested extent outside current bounds; `AcquireNextImage` returns `SURFACE_LOST` or `OUT_OF_DATE` before evaluating availability/timeout; `QueuePresent` returns `SURFACE_LOST` before `OUT_OF_DATE`. For `AcquireNextImage` and `QueuePresent`, evaluate Device, Surface, and Swapchain lifecycle state from one serialized snapshot; when multiple lifecycle conditions coexist, `DEVICE_LOST` wins over `SURFACE_LOST`, which wins over `OUT_OF_DATE`, regardless of the earlier arrival order of resize and Window-destruction notifications. This does not change validation-stage ordering: `QueuePresent` checks Device loss before queue/index validity, but on a usable Device an invalid queue/index remains `BadValue` before Surface/extent status. A valid `QueuePresent` queue-family tuple with no presentation support is `BadMatch` before token/image/wait state checks. A valid but unsupported swapchain configuration returns `UNSUPPORTED_CONFIGURATION` only after the higher-priority lifecycle statuses have been ruled out.
8. Validate mutable state and synchronization eligibility, then commit all state changes atomically. For `QueuePresent`, after higher-priority XID, Device, queue/index, lifecycle, and presentation-support checks, reject reuse of a token from an earlier accepted presentation with `BadValue`; then check image state, and if it is `ACQUIRED`, validate wait semaphores in array order. For each wait, `UNTRUSTED` yields `DEPENDENCY_FAILED`; another incompatible state or pending-wait conflict yields `INVALID_SYNCHRONIZATION_STATE`. A state failure leaves all object/image/semaphore state, references, and token reservations unchanged by that request; it does not roll back an independent asynchronous lifecycle transition. On successful `QueuePresent` acceptance, reserve the token and all semaphore wait slots and transition the image to `PRESENT_PENDING` as one indivisible commit.

For a new `AcquireNextImage` evaluation, after the preceding validation stages, `DEVICE_LOST` takes precedence over `SURFACE_LOST`, which takes precedence over `OUT_OF_DATE`; these outcomes precede mutable synchronization-state checks and timeout polling. Once lifecycle checks pass, validate every supplied semaphore/fence for acquisition-signal eligibility and absence of a conflicting pending acquire before polling or registering the wait; an ineligible object or conflicting registration returns `INVALID_SYNCHRONIZATION_STATE` even if no image is available or the timeout is zero. Only a usable swapchain with eligible synchronization objects reaches the timeout decision. A zero timeout then returns `NOT_READY` if no image is immediately available; a finite timeout returns `TIMEOUT` only when it expires. `DEVICE_DESTROYED` applies only when `DestroyDevice` terminalizes an already-pending acquire registration; the first terminal result serialized by the server wins, and `DestroyDevice` cannot overwrite an earlier terminal result. The optional Semaphore and Fence XIDs are resolved in request-field order after Device and Swapchain. The initial image/lifecycle/synchronization evaluation and either immediate-success commit, zero-timeout `NOT_READY`, or installation of a nonzero-timeout registration MUST be one atomic operation in the same serialization domain as image availability, signal-slot reservation, timeout, lifecycle transitions, and `DestroyDevice`. A pending registration reserves both supplied signal slots; on success the image transition and both signals commit atomically, while every non-success outcome releases reservations without signaling. The first terminal transition committed while the registration is open wins; later image-available, timeout, lifecycle, or duplicate callbacks cannot alter the result or perform any state/reference action twice.

For `QueuePresent`, status replies (`OUT_OF_DATE`, `SURFACE_LOST`, `DEVICE_LOST`) and synchronous X11 errors are pre-acceptance outcomes: the rejected request itself consumes no semaphore, reserves no token, and makes no image-state change. The image remains in its pre-request state; a separate lifecycle transition such as Device loss may already have invalidated it. Token reuse is a `BadValue` only if that token belongs to a previously accepted presentation; a token used only by a rejected attempt remains available. A zero token is always `BadValue`.

## Synchronous versus Asynchronous Errors

An error before acceptance is reported by an X11 error or the explicitly defined normal error reply. The request MUST NOT leave partial state.

An error after acceptance is reported through XAverius events and synchronization state. A delayed X11 error for an already accepted request is prohibited.
