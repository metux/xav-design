# XAverius Protocol Specification

**Version:** 0.1 — konsolidierter Arbeitsentwurf  
**Status:** Designentwurf; Wire-Protocol und Registries noch nicht vollständig eingefroren  
**Transport:** X11 Extension  
**Backend:** Vulkan  
**Initiale Implementierung:** Xvfb, Compute-only  
**Zielsprache der Spezifikation:** Englisch für die technische Norm; Erläuterungen können Deutsch sein.

---

## 0. Status und normative Sprache

Diese Spezifikation konsolidiert die bisher erarbeiteten XAverius-Entscheidungen.

Die Schlüsselwörter **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT** und **MAY** bezeichnen normative Anforderungen.

Es gelten drei Statusklassen:

- **Festgelegt:** Als Designentscheidung beschlossen.
- **Entwurfsregel:** Vorgeschlagene Regel, die noch gegen die vollständige Vulkan- und X11-Semantik geprüft werden muss.
- **Offen:** Muss vor einem stabilen Wire-Protocol-Release entschieden werden.

Ein offener numerischer Registry-Wert darf nicht von einer Implementierung eigenmächtig festgelegt werden, wenn er später mit einem zentral vergebenen Wert kollidieren könnte.

Diese Spezifikation ersetzt weder die X11- noch die Vulkan-Spezifikation. XAverius definiert die netzwerkseitige API und ihre zusätzlichen Garantien.

# 1. Ziel und Architektur

XAverius ist eine X11-Extension, die Vulkan-Operationen über das X11-Protokoll verfügbar macht. Vulkan-Objekte und Vulkan-Handles bleiben serverseitig. Clients adressieren Ressourcen mit XIDs.

Die erste Implementierung zielt auf Xvfb und Compute-Workloads. Grafik und Präsentation bleiben Teil der langfristigen Architektur, sind aber keine Voraussetzung für die erste funktionsfähige Implementierung.

## 1.1 Grundprinzipien

1. Vulkan-Handles werden niemals als rohe Handles über das Netzwerk übertragen.
2. Pointer, `size_t`, native C-Strukturen und compilerabhängiges Padding sind auf dem Wire verboten.
3. Alle Wire-Felder besitzen eine explizite Breite und Position.
4. Jedes logische Device besitzt seine eigenen Ressourcen.
5. Ressourcen unterschiedlicher logischer Devices dürfen nicht miteinander vermischt werden.
6. Vor Annahme eines Requests müssen alle synchron prüfbaren Bedingungen validiert werden.
7. Abgelehnte Requests dürfen keine partiellen Zustandsänderungen hinterlassen.
8. Angenommene asynchrone GPU-Arbeit kann später fehlschlagen; solche Fehler werden über XAverius-Events und Synchronisationszustände gemeldet.
9. Öffentliche XID-Gültigkeit und interne Vulkan-Objektlebensdauer sind voneinander getrennt.
10. Device-Auswahl erfolgt explizit oder durch eine definierte serverseitige Auswahlfunktion.

## 1.2 Request-Familien

Die vorgeschlagene Familienorganisation lautet:

| Familie | Inhalt |
|---:|---|
| 0 | Protocol und Version |
| 1 | Devices und Queues |
| 2 | Memory |
| 3 | Buffers und Images |
| 4 | Shaders und Pipelines |
| 5 | Commands |
| 6 | Synchronization |
| 7 | Submission und Presentation |
| 8 | Queries und optionale Features |

Diese Familiennummern sind eine Organisationsstruktur, **keine bereits zugewiesenen Subopcodes**.

# 2. X11-Framing

## 2.1 Request-Header

Jeder XAverius-Request beginnt mit dem Standard-X11-Request-Header von vier Bytes. Direkt danach folgt der XAverius-Common-Header.

```c
/* X11 header: offset 0 */
CARD8  reqType;       /* Extension major opcode */
CARD8  data;          /* X11 request framing */
CARD16 length;        /* Request length in 4-byte units */

/* XAverius header: offset 4 */
CARD8  subopcode;     /* Centrally assigned request ID */
CARD8  flags;         /* Request-specific flags */
CARD16 reserved;      /* MUST be zero in v0.1 */
```

Der Common-Header ist vier Bytes groß; der gesamte feste XAverius-Request-Header ist damit acht Bytes groß. Der Request-Payload beginnt grundsätzlich bei Offset 8, sofern ein Request nichts anderes festlegt.

Die X11-Verbindungsbyteordnung gilt für sämtliche mehrbyteigen Wire-Felder.

Der X-Server weist die Extension-Major-Opcode zu. XAverius verwendet zentral vergebene Minor- beziehungsweise Subopcode-Werte.

## 2.2 Längen, Padding und BIG-REQUESTS

- X11-Request-Längen werden in Einheiten von vier Bytes angegeben.
- Variable Bytefelder werden auf vier Bytes aufgerundet und mit Nullbytes aufgefüllt.
- Padding muss null sein.
- Ein inkonsistentes Request-Layout oder ein nicht passender Payload-Umfang ergibt `BadLength`.
- Ungültige Werte oder reservierte Bits ergeben normalerweise `BadValue`.
- BIG-REQUESTS folgt den Standard-X11-Regeln.
- Ohne BIG-REQUESTS beträgt die maximale gewöhnliche Request-Länge 262140 Bytes einschließlich Header.
- Größenberechnungen müssen vor der Verarbeitung auf Überläufe geprüft werden.

Ein Server darf variable Payloads nicht auf Grundlage ungeprüfter Counts allokieren.

## 2.3 Replies

Replies verwenden den Standard-X11-Reply-Header von 32 Bytes. `reply.length` gibt die Anzahl der Vierbyteeinheiten nach diesem Header an.

Wenn ein Reply einen variablen Payload enthält, beginnt dieser grundsätzlich bei Offset 32.

Nicht verwendete Felder müssen entsprechend der jeweiligen Reply-Definition null sein.

## 2.4 Fehler

XAverius-spezifische Fehler verwenden den standardisierten 32-Byte-X11-Error-Packet-Aufbau. XAverius definiert keine zusätzlichen Fehler-Payload-Bytes.

Der absolute Fehlercode ist:

`first_error + XAverius_error_offset`

Der Fehler muss mit der ursprünglichen Request-Sequenznummer korreliert werden.

## 2.5 XGE-Events

XAverius-Events verwenden X Generic Events (XGE). Der Standard-XGE-Header ist 32 Bytes lang. Event-spezifische Felder beginnen bei Offset 32.

Das XGE-Feld `length` zählt Vierbyteeinheiten nach dem ersten 32-Byte-Header.

# 3. Wire-Typen, XIDs und Ownership

## 3.1 Primitive Typen

| Wire-Typ | Bedeutung |
|---|---|
| `CARD8` | Unsigned 8-bit |
| `CARD16` | Unsigned 16-bit |
| `CARD32` | Unsigned 32-bit |
| `CARD64` | Unsigned 64-bit |
| `FLOAT32` | IEEE-754 binary32 |
| `BYTE[n]` | Bytefolge mit expliziter Länge |
| `XID` | 32-bit X11 Resource ID |
| `ATOM` | X11 Atom-ID |

Nullterminierung wird nur verwendet, wenn eine Felddefinition dies ausdrücklich verlangt.

## 3.2 Client-Ressourcen

Client-erzeugte XAverius-Ressourcen verwenden gültige, vom Client allokierbare XIDs.

Ein ungültiger oder bereits belegter Create-XID ergibt `BadIDChoice`, sofern der jeweilige Request keine speziellere X11-Regel vorschreibt.

Der Server muss für jede Ressource eine interne Identität verwalten, die nicht allein aus der öffentlichen XID besteht. Dadurch darf eine spätere Wiederverwendung derselben XID niemals laufende Arbeit auf eine neue Ressource umleiten.

Eine erfolgreich zerstörte öffentliche Ressource ist für neue Requests nicht mehr adressierbar.

## 3.3 Physische Devices

Physical-Device-XIDs werden serverseitig vergeben.

- Clients dürfen Physical-Device-XIDs nicht zerstören.
- Ein bestehender XID darf niemals einem anderen Physical-Device-Objekt zugewiesen werden.
- Bei Entfernung oder Ausfall bleibt die Identität erhalten; der Status ändert sich.
- Die Sichtbarkeit eines Physical Devices garantiert nicht, dass ein logisches Device darauf erstellt werden darf.
- Die konkrete Nutzungsberechtigung wird separat geprüft.

## 3.4 Device-Ownership

Jede logische Device-Ressource gehört genau einem logischen Device.

Cross-Device-Nutzung ergibt normalerweise `BadMatch`, auch wenn beide logischen Devices dasselbe physische GPU-Gerät verwenden.

Ein Ressourcen-Request muss prüfen:

1. Existenz und Typ der XID,
2. Client-Ownership,
3. Device-Zugehörigkeit,
4. Ressourcenzustand,
5. Request-spezifische Vulkan-Bedingungen.

Die exakte Reihenfolge und Zuordnung der X11-Fehler muss requestweise festgelegt werden.

# 4. Device-Discovery und logische Devices

## 4.1 Device-Auswahl

Es gibt zwei Pfade:

1. `CreateDefaultDevice`: Der Server wählt ein geeignetes Physical Device und erstellt ein logisches Device.
2. Explizite Auswahl: `EnumeratePhysicalDevices`, Eigenschaftsabfragen und `GetPhysicalDeviceQueueFamilyProperties`, danach `CreateDevice`.

Queues werden nicht über Queue-XIDs adressiert. Eine Queue wird über das Tupel

`(device_xid, queue_family_index, queue_index)`

identifiziert.

Der Queue-Family-Index entspricht der Reihenfolge der zurückgegebenen Queue-Family-Liste. Der Queue-Index adressiert eine tatsächlich für diese Familie angeforderte Queue.

## 4.2 `EnumeratePhysicalDevices`

Der Reply enthält nach dem 32-Byte-X11-Header direkt null oder mehr `PHYSICALDEVICEINFO`-Records. Es gibt kein zusätzliches Device-Count-Feld.

Fester Record-Anteil: 32 Bytes.

| Relativer Offset | Typ | Feld |
|---:|---|---|
| 0 | XID | `physical_device_xid` |
| 4 | CARD32 | `device_type` |
| 8 | CARD32 | `vendor_id` |
| 12 | CARD32 | `device_id` |
| 16 | CARD32 | `api_version` |
| 20 | CARD32 | `driver_version` |
| 24 | CARD32 | `compute_queue_family_count` |
| 28 | CARD16 | `device_name_length` |
| 30 | CARD16 | `reserved = 0` |
| 32 | BYTE[] | UTF-8-Gerätename, ohne NUL, auf 4 Bytes gepaddet |

Die Record-Länge beträgt:

`32 + ((device_name_length + 3) & ~3)`

Padding muss null sein. `compute_queue_family_count` zählt nur Queue Families mit Compute-Unterstützung.

## 4.3 `GetPhysicalDeviceProperty`

Request:

- Offset 8: Physical-Device-XID
- Offset 12: `ATOM property_atom`
- Gesamtlänge: 16 Bytes

Reply:

| Offset | Typ | Feld |
|---:|---|---|
| 8 | CARD32 | `status` |
| 12 | CARD32 | `property_type` |
| 16 | CARD32 | `value_length` in Bytes |
| 20–31 | BYTE[12] | reserviert, null |
| 32 | BYTE[] | Wert, auf 4 Bytes gepaddet |

Statuswerte:

- `SUCCESS`
- `NOT_SUPPORTED`
- `NOT_AVAILABLE`

Bei einem Status ungleich `SUCCESS` müssen `property_type` und `value_length` null sein und der Reply enthält keinen Wert-Payload.

Vorgesehene XAverius-Property-Type-IDs:

| ID | Typ |
|---:|---|
| 0 | `NONE` |
| 1 | `CARD32` |
| 2 | `CARD64` |
| 3 | `ATOM` |
| 4 | `STRING8` |
| 5 | `BYTE_ARRAY` |
| 6 | `CARD32_ARRAY` |
| 7 | `CARD64_ARRAY` |

Kandidaten für Properties sind `device.uuid`, `driver.uuid`, `compute.maxWorkGroupInvocations` und `compute.maxWorkGroupSize`. Die konkrete Property- und Atom-Registry ist offen.

## 4.4 `GetPhysicalDeviceQueueFamilyProperties`

Request: Physical-Device-XID bei Offset 8, Gesamtlänge 12 Bytes.

Reply: Standard-Reply-Header plus `QUEUEFAMILYINFO`-Records mit je 12 Bytes.

| Relativer Offset | Typ | Feld |
|---:|---|---|
| 0 | CARD32 | `queue_flags` |
| 4 | CARD32 | `queue_count` |
| 8 | CARD32 | `reserved = 0` |

Die Records folgen der Vulkan-Reihenfolge. Die Payload-Länge muss durch 12 teilbar sein.

Queue-Flag-Bits:

- Bit 0: `GRAPHICS`
- Bit 1: `COMPUTE`
- Bit 2: `TRANSFER`
- Bit 3: `SPARSE_BINDING`
- Bit 4: `PROTECTED`
- Bits 5–31: reserviert

## 4.5 `CreateDevice`

Request:

| Offset | Typ | Feld |
|---:|---|---|
| 8 | XID | `device_xid` |
| 12 | XID | `physical_device_xid` |
| 16 | CARD16 | `queue_family_request_count` |
| 18 | CARD16 | `feature_request_count` |
| 20 | CARD16 | `device_extension_count` |
| 22 | CARD16 | `reserved = 0` |
| 24 | variable | Queue-Family-, Feature- und Extension-Requests |

`QUEUEFAMILYREQUEST`:

- `CARD32 queue_family_index`
- `CARD16 queue_count`
- `CARD16 reserved = 0`
- `FLOAT32 queue_priorities[queue_count]`

Größe: `8 + 4 * queue_count`.

Die Anzahl muss positiv und unterstützt sein. Prioritäten müssen endlich und im Intervall [0,1] liegen. Doppelte Queue-Family-Einträge sind unzulässig.

`DEVICEFEATUREREQUEST`:

- `CARD32 feature_id`
- `CARD32 enabled`

Größe: 8 Bytes. In v0.1 muss `enabled = 1` sein. Nicht angegebene Features werden nicht angefordert. Doppelte Feature-IDs sind ungültig.

`DEVICEEXTENSIONREQUEST`:

- `CARD16 name_length`
- `CARD16 reserved = 0`
- ASCII-Extension-Name ohne NUL, auf vier Bytes gepaddet

Größe: `4 + ((name_length + 3) & ~3)`.

Doppelte Extensions sind unzulässig. Feature-IDs und Extensions werden über zentrale Registries definiert.

Die Erstellung ist atomar: Bei einem Fehler darf kein teilweise erstelltes logisches Device zurückbleiben.

## 4.6 `CreateDefaultDevice`

Request:

- Offset 8: `XID device_xid`
- Offset 12: `CARD16 queue_count`
- Offset 14: `CARD16 reserved = 0`
- Offset 16: `FLOAT32 priorities[queue_count]`

Gesamtlänge: `16 + 4 * queue_count`.

Die Queue-Anzahl muss mindestens 1 betragen. Der Server wählt ein geeignetes Physical Device und eine Compute-fähige Queue Family. Es werden keine optionalen Features oder Extensions implizit aktiviert.

Falls kein geeignetes Gerät existiert, wird `DEVICE_UNAVAILABLE` zurückgegeben.

## 4.7 `DestroyDevice`

Bei erfolgreichem Request werden die öffentliche Device-XID und alle öffentlichen XIDs seiner Ressourcen sofort ungültig.

Interne Vulkan-Objekte werden erst freigegeben, wenn die Vulkan-Lebensdauerregeln und alle ausstehenden Abhängigkeiten dies erlauben.

Die erfolgreiche Zerstörung bedeutet weder, dass die GPU-Arbeit abgeschlossen ist, noch dass das Device auf ein anderes Physical Device umgeleitet wurde.

# 5. Memory und Buffers

## 5.1 `CreateBuffer`

Gesamtlänge: 32 Bytes.

| Offset | Typ | Feld |
|---:|---|---|
| 8 | XID | `device_xid` |
| 12 | XID | `buffer_xid` |
| 16 | CARD64 | `size` in Bytes |
| 24 | CARD32 | `usage_flags` |
| 28 | CARD32 | `reserved = 0` |

Die Größe muss positiv sein. Buffer-Erstellung alloziert und bindet noch keinen Speicher.

Usage-Bits:

- Bit 0: `STORAGE_BUFFER`
- Bit 1: `TRANSFER_SRC`
- Bit 2: `TRANSFER_DST`
- Bit 3: `UNIFORM_BUFFER`
- Bit 4: `INDEX_BUFFER`
- Bit 5: `VERTEX_BUFFER`
- Bit 6: `INDIRECT_BUFFER`
- Bits 7–31: reserviert

Der Server darf keine Usage-Flags stillschweigend hinzufügen. Images sind in v0.1 nicht enthalten.

Für den initialen Compute-Test:

- A und B: `STORAGE_BUFFER | TRANSFER_DST`
- C: `STORAGE_BUFFER | TRANSFER_SRC`

## 5.2 `GetPhysicalDeviceMemoryProperties`

Request: Device-XID bei Offset 8, Gesamtlänge 12 Bytes.

Der Reply enthält nach dem 32-Byte-Header:

- `CARD32 memory_type_count`
- `CARD32 memory_heap_count`
- `CARD32 memory_properties_flags`
- `CARD32 reserved = 0`
- `MEMORYTYPEINFO[]`
- `MEMORYHEAPINFO[]`

`MEMORYTYPEINFO` ist 8 Bytes groß:

- `CARD32 property_flags`
- `CARD32 heap_index`

`MEMORYHEAPINFO` ist 16 Bytes groß:

- `CARD64 size`
- `CARD32 heap_flags`
- `CARD32 reserved = 0`

Memory-Type-Flags:

- Bit 0: `DEVICE_LOCAL`
- Bit 1: `HOST_VISIBLE`
- Bit 2: `HOST_COHERENT`
- Bit 3: `HOST_CACHED`
- Bit 4: `LAZILY_ALLOCATED`
- Bit 5: `PROTECTED`

Heap-Flag-Bit 0 bezeichnet `DEVICE_LOCAL`. Andere Bits sind reserviert.

Es gelten maximal 32 Memory Types und 16 Memory Heaps. Indizes beginnen bei null und bleiben während der Lebensdauer des logischen Devices stabil. Jeder Heap-Index muss gültig sein.

`memory_properties_flags` besitzt noch keine festgelegte Semantik; bis zur Zuweisung einer Registry-Definition muss das Feld null sein.

## 5.3 `GetBufferMemoryRequirements`

Request:

- Offset 8: Device-XID
- Offset 12: Buffer-XID
- Gesamtlänge: 16 Bytes

Reply:

| Offset | Typ | Feld |
|---:|---|---|
| 8 | CARD64 | `size` |
| 16 | CARD64 | `alignment` |
| 24 | CARD32 | `memory_type_bits` |
| 28 | CARD32 | `reserved = 0` |

Reply-Payload-Länge ist null. Größe und Alignment müssen positiv sein. Bits außerhalb der Anzahl unterstützter Memory Types müssen null sein.

## 5.4 `AllocateMemory`

Gesamtlänge: 32 Bytes.

- Offset 8: Device-XID
- Offset 12: Memory-XID
- Offset 16: `CARD64 allocation_size`
- Offset 24: `CARD32 memory_type_index`
- Offset 28: `CARD32 reserved = 0`

Die Allokationsgröße muss positiv sein, und der Memory-Type-Index muss existieren.

## 5.5 `BindBufferMemory`

Gesamtlänge: 28 Bytes.

- Offset 8: Device-XID
- Offset 12: Buffer-XID
- Offset 16: Memory-XID
- Offset 20: `CARD64 memory_offset`

Buffer und Memory müssen zum angegebenen Device gehören. In v0.1 darf ein Buffer nur einmal gebunden werden.

Der Memory-Type muss durch `memory_type_bits` erlaubt sein. Der Offset muss ein Vielfaches des gemeldeten Alignments sein.

Die Bounds-Prüfung muss überlaufsicher erfolgen:

- `memory_offset <= allocation_size`
- `requirements.size <= allocation_size - memory_offset`

Cross-Device-Nutzung, unpassender Memory-Type, doppeltes Binden, ungültiges Alignment oder unzureichender Speicher ergeben `BadMatch`.

## 5.6 `WriteBuffer`

Request:

- Offset 8: Device-XID
- Offset 12: Buffer-XID
- Offset 16: `CARD64 buffer_offset`
- Offset 24: `CARD32 data_length`
- Offset 28: Byte-Payload
- anschließend Null-Padding bis zur nächsten Vierbytegrenze

Gesamtlänge:

`28 + ((data_length + 3) & ~3)`

`data_length` muss positiv sein.

Der Buffer muss gebunden sein, `TRANSFER_DST` besitzen und den vollständigen Zielbereich abdecken. Bounds werden mit `buffer_offset <= buffer_size` und `data_length <= buffer_size - buffer_offset` geprüft.

Jeder `WriteBuffer`-Request ist ein eigenständiger Schreibvorgang. Es gibt weder Upload-ID noch einen mehrteiligen Upload-Transaktionszustand oder ein Final-Chunk-Flag.

Clients dürfen mehrere Requests im normalen X11-Request-Stream hintereinander senden. Jeder Request erhält seine eigene Sequenznummer und seinen eigenen Reply.

Ein erfolgreicher Reply garantiert:

1. Die Eingabedaten wurden übernommen.
2. Der Client darf seinen Eingabepuffer wiederverwenden.
3. Der Transfer ist abgeschlossen.
4. Die geschriebenen Bytes sind für nachfolgende abhängige XAverius-GPU-Arbeit sichtbar.

Der Server darf Staging-Speicher einsetzen. Er muss die korrekte Reihenfolge überlappender Writes und nachfolgender abhängiger GPU-Arbeit gewährleisten.

## 5.7 `ReadBuffer`

Request:

- Offset 8: Device-XID
- Offset 12: Buffer-XID
- Offset 16: `CARD64 buffer_offset`
- Offset 24: `CARD32 data_length`

Gesamtlänge: 28 Bytes.

Die Länge muss positiv sein. Der Buffer muss gebunden sein, `TRANSFER_SRC` besitzen und den angeforderten Bereich abdecken.

Der Reply enthält nach dem 32-Byte-Header die gelesenen Bytes ab Offset 32, mit Null-Padding auf vier Bytes. `reply.length = ceil(data_length / 4)`.

Der Reply darf erst gesendet werden, wenn die angeforderten Daten bereit sind und relevante vorherige GPU-Schreibzugriffe sowie erforderliche Host-Visibility- und Cache-Operationen abgeschlossen sind.

Eine konservative Implementierung darf für v0.1 das Device vollständig synchronisieren, wenn keine feinere Abhängigkeitsverfolgung vorhanden ist.

# 6. Shader, Descriptor-Layouts und Pipelines

## 6.1 Shader Modules

`CreateShaderModule` überträgt SPIR-V explizit. `DestroyShaderModule` zerstört die öffentliche Ressource.

`pNext`-Strukturen und Vulkan-Allocator-Callbacks werden in v0.1 nicht über das Protokoll übertragen. Die genauen Wire-Layouts und Subopcode-Zuweisungen sind noch offen.

Nach erfolgreicher Erstellung einer Compute-Pipeline darf das Shader Module öffentlich zerstört werden, soweit dies mit den Vulkan-Lebensdauerregeln vereinbar ist.

## 6.2 Descriptor Set Layout

Die Binding-Records von `CreateDescriptorSetLayout` sind jeweils 16 Bytes groß.

| Relativer Offset | Typ | Feld |
|---:|---|---|
| 0 | CARD32 | `binding` |
| 4 | CARD32 | `descriptor_type` |
| 8 | CARD32 | `descriptor_count` |
| 12 | CARD32 | `stage_flags` |

Im initialen Compute-Test werden Bindings 0, 1 und 2 jeweils als `STORAGE_BUFFER`, Anzahl 1 und `COMPUTE_SHADER` angelegt.

Binding-Nummern müssen innerhalb eines Layouts eindeutig sein. Die Descriptor-Anzahl muss positiv sein. Descriptor-Type- und Stage-Flag-IDs müssen zentral registriert werden.

Nach erfolgreicher Pipeline-Layout-Erstellung darf das Descriptor Set Layout öffentlich zerstört werden, wenn keine Vulkan-Regel eine weitere Lebensdauer verlangt.

## 6.3 Descriptor Pool

`CreateDescriptorPool` hat die Gesamtlänge:

`24 + 8 * pool_size_count`

- Offset 8: Device-XID
- Offset 12: Descriptor-Pool-XID
- Offset 16: `CARD32 max_sets`
- Offset 20: `CARD16 pool_size_count`
- Offset 22: `CARD16 reserved = 0`
- Offset 24: Array aus 8-Byte-Entries

Jeder Pool-Entry enthält `CARD32 descriptor_type` und `CARD32 descriptor_count`.

`max_sets` und alle Descriptor-Counts müssen positiv sein. Doppelte Pool-Size-Einträge sind ungültig.

## 6.4 Allocate Descriptor Sets

Fester Header: 20 Bytes.

- Offset 8: Device-XID
- Offset 12: Descriptor-Pool-XID
- Offset 16: `CARD16 descriptor_set_count`
- Offset 18: `CARD16 reserved = 0`
- Offset 20: `DESCRIPTORSETALLOCATION[]`

Jeder Allocation-Entry ist acht Bytes groß und enthält Descriptor-Set-XID sowie Descriptor-Set-Layout-XID.

Gesamtlänge: `20 + 8 * descriptor_set_count`.

Die Allokation ist atomar. Bei einem Fehler darf keine Teilmenge der Sets öffentlich angelegt bleiben.

## 6.5 Update Descriptor Sets

Fester Header: 20 Bytes.

- Offset 8: Device-XID
- Offset 12: `CARD16 write_count`
- Offset 14: `CARD16 reserved = 0`
- Offset 16: `CARD32 reserved = 0`
- Offset 20: `DESCRIPTORWRITE[]`

Jeder Write ist 36 Bytes groß.

| Relativer Offset | Typ | Feld |
|---:|---|---|
| 0 | XID | Descriptor-Set-XID |
| 4 | CARD32 | `binding` |
| 8 | CARD32 | `array_element` |
| 12 | CARD32 | `descriptor_type` |
| 16 | XID | Buffer-XID |
| 20 | CARD64 | `buffer_offset` |
| 28 | CARD64 | `range` |

Gesamtlänge: `20 + 36 * write_count`.

In v0.1 sind nur Buffer-Deskriptoren vorgesehen, für den initialen Compute-Pfad insbesondere Storage Buffer.

Der Server prüft Layout, Binding, Array-Slot, Typ, Device-Ownership, Buffer-Bindung, Alignment, Bereichsgrenzen und Geräte-Limits.

Mehrere Writes desselben Descriptor-Slots innerhalb eines Requests sind ungültig. Ein fehlgeschlagener Request darf keine Teiländerungen hinterlassen.

Ein Descriptor Set darf nicht aktualisiert werden, solange eine angenommene Submission es verwenden kann. In diesem Fall wird `INVALID_SYNCHRONIZATION_STATE` zurückgegeben.

## 6.6 Free Descriptor Sets

Fester Header: 20 Bytes.

- Offset 8: Device-XID
- Offset 12: Descriptor-Pool-XID
- Offset 16: `CARD16 descriptor_set_count`
- Offset 18: `CARD16 reserved = 0`
- Offset 20: Array aus Descriptor-Set-XIDs

Gesamtlänge: `20 + 4 * descriptor_set_count`.

Erfolgreich freigegebene Sets werden sofort öffentlich ungültig. Ein Set, das noch ausstehend verwendet wird, darf nicht freigegeben werden.

## 6.7 Pipeline Layout

`CreatePipelineLayout` enthält:

- Offset 8: Device-XID
- Offset 12: Pipeline-Layout-XID
- Offset 16: `CARD16 set_layout_count`
- Offset 18: `CARD16 push_constant_range_count`
- Offset 20: Descriptor-Set-Layout-XID-Array
- danach Push-Constant-Range-Records mit jeweils 12 Bytes

Jeder Push-Constant-Range-Record enthält:

- `CARD32 stage_flags`
- `CARD32 offset`
- `CARD32 size`

Der Server prüft Device-Ownership, Set-Layout- und Push-Constant-Limits, Stage-Masks, Offsets, Größen und Vulkan-Kompatibilitätsregeln.

Nach erfolgreicher Erstellung darf das Descriptor Set Layout öffentlich zerstört werden. Die internen Referenzen müssen den tatsächlichen Vulkan-Lebensdauerregeln entsprechen.

## 6.8 Compute Pipeline

Vorgeschlagene Gesamtlänge von `CreateComputePipeline`:

`28 + ((entry_point_length + 3) & ~3)`

- Offset 8: Device-XID
- Offset 12: Pipeline-XID
- Offset 16: Pipeline-Layout-XID
- Offset 20: Shader-Module-XID
- Offset 24: `CARD16 entry_point_length`
- Offset 26: `CARD16 reserved = 0`
- Offset 28: ASCII-Entry-Point ohne NUL, auf vier Bytes gepaddet

Der Entry-Point muss nichtleer sein. Specialization Constants werden in v0.1 nicht unterstützt. Die Erstellung ist atomar.

# 7. Command Pools, Command Buffer und Command Streams

## 7.1 Command Pools

`CreateCommandPool` und `DestroyCommandPool` verwalten die Allokation von Command Buffers. Die genauen Request-Layouts und Subopcodes müssen noch festgelegt werden.

Ein Command Pool ist Elternobjekt der daraus allozierten Command Buffer. Die Zerstörung des Pools invalidiert die öffentlichen XIDs aller zugehörigen Command Buffer.

In v0.1 wird die Pool-Zerstörung abgelehnt, solange ein Kind-Command-Buffer ausstehend ausgeführt wird.

## 7.2 Command-Buffer-Zustände

Vorgesehene Zustände:

- `INITIAL`
- `RECORDING`
- `EXECUTABLE`
- `PENDING`
- `INVALID`

Übergänge:

- Allokation → `INITIAL`
- Create-Chunk von `CommandBufferData` → `RECORDING`
- erfolgreicher FINAL-Chunk → `EXECUTABLE`
- angenommene Submission → `PENDING`
- erfolgreiche Ausführung → `EXECUTABLE`
- asynchroner Fehler oder Device Loss → terminaler Fehlerzustand
- Pool- oder Device-Zerstörung → öffentliche XID ungültig

Ob der terminale Fehlerzustand `INVALID` oder ein separater `FAILED`-Zustand ist, muss noch festgelegt werden.

Ein `PENDING`-Command-Buffer darf nicht verändert, zurückgesetzt, freigegeben oder erneut eingereicht werden. Gleichzeitige ausstehende Submissions desselben Command Buffers sind in v0.1 nicht vorgesehen.

## 7.3 `CommandBufferData`

Wire-Layout:

- Offset 0: X11-Header
- Offset 4: XAverius-Common-Header
- Offset 8: `CARD32 command_buffer_xid`
- Offset 12: `CARD32 command_pool_xid`
- Offset 16: Command-Entries

Flags im Common-Header:

| CREATE | FINAL | Bedeutung |
|---:|---:|---|
| 0 | 0 | Entries an einen bereits aufzeichnenden Buffer anhängen |
| 0 | 1 | Letzte Entries anhängen und Recording beenden |
| 1 | 0 | Command Buffer erstellen, Recording beginnen, ersten Chunk aufzeichnen |
| 1 | 1 | Command Buffer erstellen, kompletten Stream aufzeichnen und beenden |

`FINAL` entspricht dem Ende der Aufzeichnung. Ein separater `EndCommandBuffer`-Request ist nicht vorgesehen.

Chunks dürfen nur zwischen vollständigen Command-Entries geteilt werden. Kein einzelner Entry darf über mehrere Requests verteilt sein.

## 7.4 Entry-Header

Jeder Entry beginnt mit:

```c
CARD16 command_id;
CARD16 entry_length; /* 32-bit words, including header and padding */
```

Maximale Entry-Größe: 65535 Wörter beziehungsweise 262140 Bytes. Jeder Entry muss vollständig in einen X11-Request passen.

Command-IDs werden zentral registriert und entsprechen den unterstützten `vkCmd*`-Operationen.

## 7.5 Unterstützte Command-Entries

### `CMD_BIND_PIPELINE`

Gesamtlänge: 8 Bytes.

- Relativer Offset 0: `CARD16 command_id`
- Offset 2: `CARD16 entry_length = 2`
- Offset 4: Pipeline-XID

### `CMD_BIND_DESCRIPTOR_SETS`

- Relativer Offset 0: `CARD16 command_id`
- Offset 2: `CARD16 entry_length`
- Offset 4: Pipeline-Layout-XID
- Offset 8: `CARD32 first_set`
- Offset 12: `CARD16 descriptor_set_count`
- Offset 14: `CARD16 reserved = 0`
- Offset 16: Descriptor-Set-XID-Array

Gesamtlänge: `16 + 4 * descriptor_set_count`.

Entry-Länge: `4 + descriptor_set_count` Wörter.

### `CMD_DISPATCH`

Gesamtlänge: 16 Bytes.

- Relativer Offset 0: `CARD16 command_id`
- Offset 2: `CARD16 entry_length = 4`
- Offset 4: `CARD32 group_count_x`
- Offset 8: `CARD32 group_count_y`
- Offset 12: `CARD32 group_count_z`

Die Dispatch-Werte müssen innerhalb der vom Device unterstützten Limits liegen.

### `CMD_PUSH_CONSTANTS`

- Relativer Offset 0: `CARD16 command_id`
- Offset 2: `CARD16 entry_length`
- Offset 4: `CARD32 stage_flags`
- Offset 8: Pipeline-Layout-XID
- Offset 12: `CARD32 offset`
- Offset 16: `CARD32 data_length`
- Offset 20: Datenbytes, danach Null-Padding bis zur Vierbytegrenze

Entry-Länge: `5 + ceil(data_length / 4)` Wörter.

Für v0.1 muss `stage_flags` exakt dem Compute-Shader-Bit entsprechen. `offset` und `data_length` müssen Vielfache von vier sein. `data_length` muss positiv sein.

Der Bereich muss innerhalb von `maxPushConstantsSize` liegen und von einem kompatiblen Push-Constant-Range des angegebenen Pipeline Layouts abgedeckt werden.

Die Datenbytes sind opak. Wire-Padding gehört nicht zum Push-Constant-Bereich.

## 7.6 Command-Validierung

Der Server validiert Command-Buffer-Zustand, Entry-Längen, Ressourcen-Typen, Device-Ownership, reservierte Felder, Pipeline- und Layout-Kompatibilität, Descriptor-Bindings, Push-Constant-Ranges und Dispatch-Limits.

Ein ungültiger `CommandBufferData`-Request darf keine seiner Entries teilweise anhängen. Bereits durch vorherige Requests akzeptierte Chunks bleiben erhalten, falls ein späterer Chunk fehlschlägt. Das genaue Recovery-Verhalten muss noch eingefroren werden.

# 8. Queue Submission und Synchronisation

## 8.1 Queue-Adressierung

Queues werden durch Device-XID, Queue-Family-Index und Queue-Index adressiert. Der Server muss prüfen, ob die Queue für dieses logische Device tatsächlich erstellt wurde.

## 8.2 `QueueSubmit`

Request-Layout:

| Offset | Typ | Feld |
|---:|---|---|
| 8 | XID | Device-XID |
| 12 | CARD32 | Queue-Family-Index |
| 16 | CARD32 | Queue-Index |
| 20 | XID | Fence-XID, 0 bedeutet keine Fence |
| 24 | CARD16 | Command-Buffer-Count |
| 26 | CARD16 | Wait-Semaphore-Count |
| 28 | CARD16 | Signal-Semaphore-Count |
| 30 | CARD16 | `reserved = 0` |
| 32 | variable | Command-Buffer-XIDs, Wait-Entries, Signal-Entries |

Jeder Wait-Entry ist 16 Bytes groß:

- Relativer Offset 0: Semaphore-XID
- Offset 4: `CARD64 wait_value`
- Offset 12: `CARD32 wait_stage_mask`

Jeder Signal-Entry ist 12 Bytes groß:

- Relativer Offset 0: Semaphore-XID
- Offset 4: `CARD64 signal_value`

Gesamtlänge:

`32 + 4*C + 16*W + 12*S`

Vorgesehene Wait-Stage-Bits:

- Bit 0: `DRAW_INDIRECT`
- Bit 1: `COMPUTE_SHADER`
- Bit 2: `TRANSFER`
- Bit 3: `ALL_COMMANDS`
- Bits 4–31: reserviert

`ALL_COMMANDS` darf nicht mit anderen Bits kombiniert werden. Die konkrete Vulkan-Zuordnung und die zulässigen Masks für jede Queue-Art müssen vor der Implementierung final geprüft werden. Für den Compute-only-Pfad sind insbesondere Compute, Transfer und All-Commands relevant.

Vor der Annahme werden alle Command Buffer und Synchronisationsobjekte geprüft. Alle Ressourcen müssen zum angegebenen Device gehören. Jeder Command Buffer muss ausführbar sein. Eine angegebene Fence muss `UNSIGNALED` sein und darf nicht bereits pending sein.

Doppelte Wait- oder Signal-Einträge sind in v0.1 ungültig. Dieselbe Semaphore darf in einer Submission nicht gleichzeitig im Wait- und Signal-Array stehen.

**Atomaritätsgarantie:** Wird der Request abgelehnt, wird keine Submission angelegt und kein Synchronisationszustand verändert. Bei Annahme bedeutet der Request nur, dass die Arbeit eingereiht wurde; nicht, dass sie bereits abgeschlossen ist.

`QueueSubmit` ist ein Void-Request.

## 8.3 Semaphoren erstellen

`CreateSemaphore` hat 28 Bytes:

- Offset 8: Device-XID
- Offset 12: Semaphore-XID
- Offset 16: `CARD32 semaphore_type`
- Offset 20: `CARD64 initial_value`

Typen:

- `BINARY = 0`
- `TIMELINE = 1`

Für Binary-Semaphoren muss `initial_value = 0` sein. Binary-Semaphoren beginnen unsignaled.

## 8.4 Binary-Semaphoren

Binary-Semaphoren folgen den Vulkan-Signal-/Wait-Regeln.

- Ein Signal darf nicht mehrere konkurrierende Waits erfüllen.
- Host-Counter-Abfragen, Host-Waits und Host-Signals sind für Binary-Semaphoren ungültig.
- Pending Signal-/Wait-Zustände müssen atomar validiert werden.
- Ein Signal und ein Wait müssen nach den geltenden Vulkan-Regeln zusammenpassen.

Die vollständigen Regeln für noch ausstehende Signal-/Wait-Operationen sind noch zu präzisieren.

## 8.5 Timeline-Semaphoren

Timeline-Semaphoren besitzen einen monoton steigenden unsigned 64-bit Counter.

- Ein Wait ist erfüllt, sobald der Counter mindestens den angeforderten Wert erreicht.
- Ein Wait darf eingereiht werden, bevor das Signal eingereiht wurde, das ihn erfüllt.
- Signalwerte müssen größer als der aktuelle Counter und mit allen Pending-Signalen konsistent sein.
- Mehrere Signal-Entries derselben Timeline-Semaphore in einem einzelnen `QueueSubmit` sind in v0.1 nicht erlaubt.

## 8.6 `GetSemaphoreCounterValue`

Request: 16 Bytes; Device-XID bei Offset 8, Semaphore-XID bei Offset 12.

Nur für Timeline-Semaphoren.

Reply:

- Offset 8: `CARD64 counter_value`
- Offset 16–31: reserviert, null
- Reply-Payload-Länge: null

## 8.7 `WaitSemaphores`

Fester Request-Header: 28 Bytes.

- Offset 8: Device-XID
- Offset 12: `CARD32 semaphore_count`
- Offset 16: `CARD32 wait_mode`
- Offset 20: `CARD64 timeout_ns`
- Offset 28: Array aus 12-Byte-Entries

Jeder Entry enthält Semaphore-XID und `CARD64 wait_value`.

Wait-Modi:

- `WAIT_ANY = 0`
- `WAIT_ALL = 1`

Die Anzahl muss mindestens 1 sein. Alle Semaphoren müssen Timeline-Semaphoren desselben Devices sein; doppelte XIDs sind unzulässig. Der Request wird vollständig validiert, bevor irgendeine Wait-Registrierung oder interne Referenz angelegt wird. Eine synchrone Ablehnung hinterlässt keinerlei Wait-Zustand.

### Wait-Bedingung und Linearisierung

Für jeden Entry i sei C_i der beobachtbare Counter der referenzierten Timeline-Semaphore und V_i der angeforderte Wert. Ein Entry ist genau dann erfüllt, wenn C_i >= V_i.

- `WAIT_ANY` ist erfüllt, sobald mindestens ein Entry erfüllt ist.
- `WAIT_ALL` ist erfüllt, sobald alle Entries erfüllt sind.
- Der Server MUSS die Erfüllungsprüfung und den Übergang eines offenen Waits in den terminalen Zustand unter einer serialisierten Zustandsentscheidung ausführen. Ein Wait darf genau ein terminales Ergebnis erhalten.
- Counter sind monoton steigend. Ein einmal erfüllter Entry bleibt erfüllt; ein späterer Counter-Wert kann ihn nicht wieder unerfüllt machen.
- Bei `WAIT_ANY` entscheidet der erste serialisierte Zustand, in dem mindestens ein Entry erfüllt ist. Werden mehrere Entries durch dieselbe atomare Zustandsänderung erfüllt, ist die interne Auswahl unerheblich, da der Reply keinen Semaphore-Index meldet. Der Server DARF nicht auf ein bestimmtes Array-Element oder auf die Reihenfolge späterer Callback-Ausführung vertrauen.
- Bei `WAIT_ALL` dürfen die Entries zu unterschiedlichen Zeitpunkten erfüllt werden. Der Wait wird terminal erfolgreich, sobald die letzte noch unerfüllte Bedingung erfüllt ist. Es ist nicht erforderlich, dass alle Counter gleichzeitig durch dasselbe Signal oder denselben Backend-Callback geändert werden.
- Ein Signalvorgang erfüllt einen Entry erst, wenn dessen Signalwert tatsächlich im beobachtbaren Counter angekommen ist. Eine bloß angenommene oder reservierte GPU-Signaloperation erfüllt keinen Wait.
- Ein Host-Signal und ein GPU-Signal konkurrieren anhand ihrer serialisierten Counter-Übergänge. Die Regeln aus Abschnitt 8.5/8.8 für Signalreservierungen bleiben maßgeblich; ein Wait darf weder einen reservierten Wert als bereits signalisiert behandeln noch die Signalreihenfolge verändern.

### Timeout und Lifecycle

- `timeout_ns = 0` führt eine nicht blockierende Zustandsprüfung aus. Ist die Wait-Bedingung bei dieser Prüfung erfüllt, lautet das Ergebnis `SUCCESS`, andernfalls `TIMEOUT`.
- `timeout_ns = UINT64_MAX` bedeutet unbegrenztes Warten. Jeder andere Wert ist eine relative Nanosekundenfrist, die einmalig ab Übernahme des Requests durch den Server anhand einer monotonen Uhr berechnet wird.
- Die Frist wird bei Scheduler-Unterbrechungen, internen Warteabschnitten und erneuter Registrierung niemals neu gestartet. Die Antwort darf nach Fristablauf ausgeliefert werden; maßgeblich ist der serialisierte terminale Zustandsentscheid.
- Bei konkurrierender Erfüllung und Timeout gewinnt eine Erfüllung, wenn sie vor der terminalen Timeout-Entscheidung serialisiert festgestellt wird. Andernfalls gewinnt `TIMEOUT`. Ein nach dem terminalen Timeout eintreffendes Signal ändert das Wait-Ergebnis nicht.
- Device Loss und `DestroyDevice` terminalisieren jeden zu diesem Zeitpunkt noch offenen Wait ohne weiteres Warten: Device Loss ergibt den X11-Fehler `DEVICE_LOST`, `DestroyDevice` ergibt `DEVICE_DESTROYED`. Bereits zuvor serialisiert festgestellte `SUCCESS`- oder `TIMEOUT`-Ergebnisse werden nicht überschrieben. Zwischen Device Loss und `DestroyDevice` gewinnt der zuerst serialisierte Lifecycle-Übergang.
- Ein bereits erfüllter Wait bleibt auch dann erfolgreich, wenn danach Device Loss oder `DestroyDevice` eintritt; die spätere Lifecycle-Transition darf den terminalen Wait-Ausgang nicht umschreiben.

### Registrierung und Lebensdauer

- Ein blockierender Wait blockiert niemals den X11-Dispatcher. Nach Übernahme kann derselbe Client weitere Requests, insbesondere `SignalSemaphore` und `QueueSubmit`, senden, die den Wait erfüllen können.
- Ein offener Wait hält Referenzen auf die exakten internen Semaphore-Identitäten aller Entries. XID-Wiederverwendung darf diese Referenzen nicht auf neu angelegte Ressourcen umleiten.
- `DestroySemaphore` MUSS atomar mit `INVALID_SYNCHRONIZATION_STATE` abgewiesen werden, solange eine offene Wait-Registrierung dieselbe interne Semaphore-Identität referenziert. Nach serialisiert festgestelltem terminalem Wait-Ergebnis blockiert ein nur noch ausstehender Reply die Zerstörung nicht.
- Client-Disconnect entfernt offene Wait-Registrierungen ohne Reply und gibt ausschließlich deren Registrierungsreferenzen frei. Er bricht keine bereits angenommene Signal- oder Queue-Arbeit ab und verändert keine Semaphore-Counter.
- Timeout und Disconnect verändern weder Semaphore-Counter noch Signalreservierungen oder andere Waits.

Der Reply enthält bei Offset 8 den Status `SUCCESS = 0` oder `TIMEOUT = 1`. Ein Timeout ist ein normaler Reply und kein X11-Fehler. Lifecycle-Abbrüche sind dagegen die oben genannten X11-Fehler und keine Reply-Statuswerte.

## 8.8 `SignalSemaphore`

Request: 24 Bytes.

- Offset 8: Device-XID
- Offset 12: Semaphore-XID
- Offset 16: `CARD64 signal_value`

Nur Timeline-Semaphoren sind erlaubt. Der Signalwert muss größer als der aktuelle Wert und mit allen ausstehenden Signalen konsistent sein. Prüfung und Signaloperation sind atomar.

# 9. Fences

## 9.1 Zustände

Vorgesehene Zustände:

- `UNSIGNALED = 0`
- `PENDING = 1`
- `SIGNALED = 2`
- `FAILED = 3`

Übergänge:

- Erstellung → `UNSIGNALED`
- angenommene Submission mit Fence → `PENDING`
- erfolgreiche Completion → `SIGNALED`
- asynchroner Ausführungsfehler → `FAILED`
- Reset aus `SIGNALED` oder `FAILED` → `UNSIGNALED`
- abgelehnte Submission → Zustand bleibt unverändert

## 9.2 `CreateFence`

Gesamtlänge: 24 Bytes.

- Offset 8: Device-XID
- Offset 12: Fence-XID
- Offset 16: `CARD32 create_flags = 0`
- Offset 20: `CARD32 reserved = 0`

## 9.3 `GetFenceStatus`

Request: 16 Bytes; Device-XID bei Offset 8, Fence-XID bei Offset 12.

Reply: 32 Bytes.

- Byte 1: Fence-Status
- Reply-Länge: null
- Offsets 8–31: reserviert, null

## 9.4 `WaitForFence`

Request: 24 Bytes.

- Offset 8: Device-XID
- Offset 12: Fence-XID
- Offset 16: `CARD64 timeout_ns`

Reply-Status:

- `SUCCESS = 0`
- `TIMEOUT = 1`
- `EXECUTION_FAILED = 2`
- `DEVICE_LOST = 3`

Timeout und Ausführungsfehler werden als normale Reply-Statuswerte zurückgegeben.

## 9.5 `ResetFence`

Request: 16 Bytes; Device-XID bei Offset 8, Fence-XID bei Offset 12.

Nur `SIGNALED` und `FAILED` dürfen zurückgesetzt werden. Ein Reset aus `PENDING` oder `UNSIGNALED` ergibt `INVALID_SYNCHRONIZATION_STATE`. Bei verlorenem Device wird `DEVICE_LOST` zurückgegeben.

## 9.6 Fence-Zerstörung

Die öffentliche Fence-XID wird bei erfolgreicher Zerstörung ungültig. Die interne Fence bleibt erhalten, solange angenommene Arbeit sie benötigt.

Die konservative v0.1-Regel lautet: Eine pending Fence kann nicht zerstört werden. Die genaue Fehlerzuordnung und das Verhalten nach Device Loss müssen mit der allgemeinen Zerstörungsregel konsistent umgesetzt werden.

# 10. Ressourcenlebenszyklus und Zerstörung

## 10.1 Zustandsmodell

Jedes Objekt besitzt mindestens zwei getrennte Lebensdaueransichten:

**Öffentlicher Zustand**

- `LIVE`
- `INVALID`

**Interner Zustand**

- `ACTIVE`
- `DESTROY_PENDING`
- `RELEASED`

Die Implementierung sollte zusätzlich die interne Ressourcenidentität, Client- und Device-Ownership, abhängige Objekte sowie ausstehende Submission-Referenzen verfolgen.

Die öffentliche XID wird bei erfolgreicher Zerstörung sofort ungültig. Die tatsächliche Vulkan-Zerstörung darf verzögert erfolgen.

## 10.2 Ownership-Hierarchie

Explizite Eltern-Kind-Beziehungen:

- Device → alle device-eigenen öffentlichen Ressourcen
- CommandPool → zugehörige Command Buffer
- DescriptorPool → zugehörige Descriptor Sets

Andere Beziehungen sind Abhängigkeiten, keine automatischen Ownership-Beziehungen:

- Buffer ↔ Memory
- Pipeline ↔ Pipeline Layout
- Pipeline ↔ Shader Module während der Erstellung
- Pipeline Layout ↔ Descriptor Set Layout während der Erstellung
- Command Buffer ↔ Ressourcen, die in aufgezeichneten Commands verwendet werden

Die Implementierung darf nicht annehmen, dass jedes Objekt, dessen Handle beim Erstellen eines anderen Objekts verwendet wurde, dauerhaft existieren muss. Maßgeblich sind die tatsächlichen Vulkan-Lebensdauerregeln.

## 10.3 Zerstörungsmatrix

| Ressource | Öffentliche Zerstörung | Regel bei ausstehender Verwendung |
|---|---|---|
| Device | Invalidiert Device und Kinder sofort | Interne Bereinigung wird verzögert |
| CommandPool | Invalidiert Pool und Kind-Command-Buffer | Abweisen, solange ein Kind pending ist |
| CommandBuffer | XID wird ungültig | Abweisen, solange pending |
| DescriptorPool | Invalidiert Pool und Kind-Sets | Abweisen, solange ein Kind-Set pending ist |
| DescriptorSet | XID wird ungültig | Abweisen, solange pending |
| Buffer | XID wird ungültig | Buffer und gebundener Speicher bleiben intern erhalten |
| Memory | XID wird ungültig | Tatsächliche Freigabe erst, wenn abhängige Objekte und Arbeit es erlauben |
| Pipeline | XID wird ungültig | Konservative Regel: Zerstörung bei Pending-Use abweisen |
| PipelineLayout | XID wird ungültig | Konservative Regel: Zerstörung bei noch bestehender Command-/Submission-Abhängigkeit abweisen |
| ShaderModule | Nach erfolgreicher Pipeline-Erstellung unabhängig zerstörbar | Vulkan-Lebensdauerregeln bleiben maßgeblich |
| DescriptorSetLayout | Nach erfolgreicher Pipeline-Layout-Erstellung unabhängig zerstörbar | Vulkan-Lebensdauerregeln bleiben maßgeblich |
| Fence | XID wird ungültig | Konservative Regel: Pending-Zerstörung abweisen |
| Semaphore | XID wird ungültig | Konservative Regel: Zerstörung bei Pending-Use abweisen |
| Physical Device | Nicht durch Client zerstörbar | Server-Ownership; XID wird nie neu zugewiesen |

Die Regeln sind XAverius-API-Entscheidungen und keine Behauptung, dass Vulkan für alle Ressourcentypen identische Lebensdauerbeschränkungen definiert.

## 10.4 `DestroyResource`

Vorgeschlagener generischer Request:

- Offset 8: Ressourcen-XID
- Gesamtlänge: 12 Bytes

Die genaue Zulässigkeit für einzelne Ressourcentypen wird durch die jeweilige API-Regel bestimmt. Physical Devices sind ausgenommen.

Ein erfolgreicher Request invalidiert die öffentliche XID sofort. Interne Objekte dürfen erst freigegeben werden, wenn ihre Vulkan-Lebensdauerbedingungen erfüllt sind.

Ungültige XIDs, falsche Typen und fremde Ownership werden gemäß der request-spezifischen X11-Fehlerzuordnung behandelt.

## 10.5 Device-Zerstörung und Client-Disconnect

Bei `DestroyDevice` oder Client-Disconnect werden öffentliche Device-Ressourcen ungültig.

Die interne Bereinigung muss sicher und unabhängig von der öffentlichen XID-Verfügbarkeit erfolgen. Der Server darf nicht unbegrenzt auf einem hängenden oder verlorenen Device warten.

Nach Device Loss müssen betroffene Operationen als fehlgeschlagen behandelt werden. Der Server darf nicht so tun, als sei GPU-Arbeit erfolgreich abgeschlossen worden.

## 10.6 Command Buffer und Descriptor Sets

Ein pending Command Buffer darf in v0.1 nicht verändert, zurückgesetzt, freigegeben oder erneut eingereicht werden.

Ein Descriptor Set darf nicht aktualisiert oder freigegeben werden, solange eine angenommene Submission es verwenden kann.

Update-after-bind und Update-unused-while-pending werden nicht angeboten.

## 10.7 Buffer und Memory

Ein Buffer darf öffentlich invalidiert werden, obwohl eine Submission ihn noch benötigt. Das interne Buffer-Objekt und gebundener Speicher müssen erhalten bleiben, bis Vulkan ihre Freigabe erlaubt.

Memory darf nicht freigegeben werden, solange ein gebundener Buffer oder eine ausstehende Operation darauf angewiesen ist.

## 10.8 Fehler bei ungültigen Lebenszyklusoperationen

- Ungültige oder zerstörte XID: request-spezifischer Standard-X11-Fehler
- Falscher Typ oder inkompatible Ressource: normalerweise `BadMatch`
- Falsches Device: `BadMatch`
- Zerstörung eines pending Command Buffers oder Descriptor Sets: `INVALID_SYNCHRONIZATION_STATE`
- Ungültiger Fence-Reset: `INVALID_SYNCHRONIZATION_STATE`
- Verlorenes Device: `DEVICE_LOST`, sofern der Request nicht ausdrücklich noch die logische Invalidierung erlaubt

Die erfolgreiche Device-Kaskadeninvalidierung ist eine Sonderregel und wird nicht durch die normalen Pending-Use-Ablehnungen blockiert.

# 11. Zentrale XAverius-Fehler-Registry

Die folgenden Werte sind Offsets relativ zu `first_error` der Extension.

| Offset | Symbol |
|---:|---|
| 0 | `DEVICE_UNAVAILABLE` |
| 1 | `DEVICE_LOST` |
| 2 | `INVALID_SYNCHRONIZATION_STATE` |
| 3 | `EXECUTION_FAILED` |
| 4 | `TRANSFER_FAILED` |
| 5 | `ALLOCATION_FAILED` |
| 6 | `DEPENDENCY_FAILED` |
| 7 | `INTERNAL_SERVER_ERROR` |

Der tatsächliche X11-Fehlercode ist `first_error + offset`.

Das Fehlerpaket verwendet den Extension-Major-Opcode, den Request-Subopcode, die Sequenznummer des auslösenden Requests und eine betroffene Ressourcen-XID, falls sinnvoll; andernfalls null.

## 11.1 Allgemeine Fehlerklassen

| Situation | Ergebnis |
|---|---|
| Request-Länge oder Count inkonsistent | `BadLength` |
| Ungültiger Feldwert, reservierte Bits oder Flags | `BadValue` |
| Ungültige oder bereits belegte Create-XID | `BadIDChoice` |
| Falscher Ressourcentyp oder Cross-Device-Kombination | normalerweise `BadMatch` |
| Ungültige Ressource | Request-spezifischer Standard-X11-Fehler |
| Device nicht verfügbar | `DEVICE_UNAVAILABLE` |
| Device verloren | `DEVICE_LOST` |
| Ungültiger Synchronisationszustand | `INVALID_SYNCHRONIZATION_STATE` |
| Synchroner Transferfehler | `TRANSFER_FAILED` |
| Synchroner Allokationsfehler | `ALLOCATION_FAILED` |
| Ungültige Abhängigkeit verhindert Annahme | `DEPENDENCY_FAILED` |
| Unerwarteter Serverfehler | `INTERNAL_SERVER_ERROR` |

## 11.2 Request-spezifische Fehlerzuordnung

### `WriteBuffer`

- Falsche Request-Länge: `BadLength`
- Länge null oder ungültige reservierte Felder: `BadValue`
- Ungültige XID: request-spezifischer X11-Fehler
- Falscher Typ, falsches Device, ungebundener Buffer, fehlendes `TRANSFER_DST`, Bereich außerhalb des Buffers: `BadMatch`
- Nicht verfügbares/verlorenes Device: `DEVICE_UNAVAILABLE` / `DEVICE_LOST`
- Synchroner Transferfehler: `TRANSFER_FAILED`
- Fehlgeschlagene Staging-Allokation: `ALLOCATION_FAILED`

### `ReadBuffer`

- Falsche Request-Länge: `BadLength`
- Länge null oder ungültige reservierte Felder: `BadValue`
- Ungültige XID: request-spezifischer X11-Fehler
- Falscher Typ, falsches Device, ungebundener Buffer, fehlendes `TRANSFER_SRC`, ungültiger Bereich: `BadMatch`
- Nicht verfügbares/verlorenes Device: `DEVICE_UNAVAILABLE` / `DEVICE_LOST`
- Synchroner Transferfehler: `TRANSFER_FAILED`
- Fehlgeschlagene Staging-Allokation: `ALLOCATION_FAILED`

### `QueueSubmit`

- Count-/Längenfehler: `BadLength`
- Ungültige Masks, reservierte Felder oder numerische Werte: `BadValue`
- Ungültige XID: request-spezifischer X11-Fehler
- Falscher Typ oder Cross-Device-Ressource: `BadMatch`
- Nicht ausführbarer Command Buffer, ungültiger Fence- oder Semaphore-Zustand: `INVALID_SYNCHRONIZATION_STATE`
- Nicht verfügbares/verlorenes Device: `DEVICE_UNAVAILABLE` / `DEVICE_LOST`
- Ungültige Abhängigkeit, die Annahme verhindert: `DEPENDENCY_FAILED`

### Fence-Requests

- Falsche Länge: `BadLength`
- Ungültige Flags oder reservierte Felder: `BadValue`
- Ungültige Ressource: request-spezifischer X11-Fehler
- Falscher Typ oder Device: `BadMatch`
- Ungültiger Reset-/Destroy-Zustand: `INVALID_SYNCHRONIZATION_STATE`
- Timeout und asynchroner Ausführungsfehler bei `WaitForFence`: normaler Reply-Status

### `BindBufferMemory`

Cross-Device-Nutzung, bereits gebundener Buffer, ungültiges Alignment, zu kleine Allokation oder inkompatibler Memory-Type ergeben `BadMatch`.

### `UpdateDescriptorSets`

- Falsche Länge: `BadLength`
- Reservierte Felder oder ungültige Werte: `BadValue`
- Inkompatibler Descriptor, Buffer oder Device: `BadMatch`
- Update während Pending-Use: `INVALID_SYNCHRONIZATION_STATE`

Jeder Request muss vor Implementierungsfreigabe eine vollständige, konkrete Fehlerzuordnung besitzen.

## 11.3 Synchron versus asynchron

Ein Fehler vor Annahme wird durch einen X11-Fehler oder den ausdrücklich definierten normalen Fehler-Reply signalisiert. Der Request darf keinen Teilzustand hinterlassen.

Ein Fehler nach Annahme wird durch XAverius-Events und Synchronisationszustände signalisiert. Ein später X11-Fehler für einen bereits angenommenen Request ist unzulässig.

# 12. XAverius-Events

Alle folgenden Events verwenden XGE.

## 12.1 `ASYNC_ERROR`

Gesamtlänge: 60 Bytes; XGE `length = 7`.

| Offset | Typ | Feld |
|---:|---|---|
| 32 | XID | Device-XID, null falls nicht gerätebezogen |
| 36 | CARD32 | `error_code`, zentraler XAverius-Fehleroffset |
| 40 | CARD32 | `origin` |
| 44 | CARD64 | `submission_id`, null falls nicht submissionbezogen |
| 52 | XID | betroffene Ressourcen-XID, null falls keine |
| 56 | CARD32 | `reserved = 0` |

Origin-Werte:

- 0: `ORIGIN_UNSPECIFIED`
- 1: `ORIGIN_QUEUE_SUBMIT`
- 2: `ORIGIN_WRITE_BUFFER`
- 3: `ORIGIN_READ_BUFFER`
- 4: `ORIGIN_SEMAPHORE`
- 5: `ORIGIN_FENCE`
- 6: `ORIGIN_DEVICE`

## 12.2 `DEVICE_LOST`

Gesamtlänge: 48 Bytes; XGE `length = 4`.

- Offset 32: Device-XID
- Offset 36: `CARD32 reason_code`
- Offset 40: `CARD64 device_generation`

Reason-Codes:

- 0: `REASON_UNSPECIFIED`
- 1: `HOTPLUG_REMOVAL`
- 2: `DRIVER_FAILURE`
- 3: `VULKAN_DEVICE_LOST`
- 4: `SERVER_POLICY`
- 5: `SERVER_SHUTDOWN`

## 12.3 `DEVICE_STATUS_CHANGED`

Gesamtlänge: 48 Bytes; XGE `length = 4`.

- Offset 32: Physical-Device-XID
- Offset 36: `CARD32 new_status`
- Offset 40: `CARD32 reason_code`
- Offset 44: `CARD32 reserved = 0`

Status:

- 0: `AVAILABLE`
- 1: `UNAVAILABLE`
- 2: `REMOVED`

`REMOVED` ist für diesen XID endgültig. Die XID wird nie einem anderen Device zugewiesen.

## 12.4 `DEVICE_MEMORY_PRESSURE`

Gesamtlänge: 48 Bytes; XGE `length = 4`.

- Offset 32: Device-XID
- Offset 36: `CARD32 heap_index`; `UINT32_MAX` bedeutet kein bestimmter Heap
- Offset 40: `CARD32 pressure_level`
- Offset 44: `CARD32 reserved = 0`

Pressure-Level:

- 0: `NORMAL`
- 1: `LOW`
- 2: `MEDIUM`
- 3: `HIGH`

## 12.5 `DEVICE_IDLE`

Gesamtlänge: 48 Bytes; XGE `length = 4`.

- Offset 32: Device-XID
- Offset 36: `CARD32 idle_reason`
- Offset 40: `CARD64 device_generation`

Gründe:

- 0: `IDLE_REASON_UNSPECIFIED`
- 1: `NO_PENDING_WORK`
- 2: `WORK_COMPLETED`

## 12.6 `SUBMISSION_COMPLETE`

Gesamtlänge: 56 Bytes; XGE `length = 6`.

- Offset 32: Device-XID
- Offset 36: `CARD32 queue_family_index`
- Offset 40: `CARD32 queue_index`
- Offset 44: `CARD32 reserved = 0`
- Offset 48: `CARD64 submission_id`

## 12.7 `SUBMISSION_FAILED`

Gesamtlänge: 56 Bytes; XGE `length = 6`.

- Offset 32: Device-XID
- Offset 36: `CARD32 queue_family_index`
- Offset 40: `CARD32 queue_index`
- Offset 44: `CARD32 failure_class`
- Offset 48: `CARD64 submission_id`

Failure-Class-Werte:

- 0: `EXECUTION_FAILED`
- 1: `DEVICE_LOST`

## 12.8 Event-Auswahl

Event-Typen:

| Typ | Event |
|---:|---|
| 0 | `ASYNC_ERROR` |
| 1 | `DEVICE_LOST` |
| 2 | `DEVICE_STATUS_CHANGED` |
| 3 | `DEVICE_MEMORY_PRESSURE` |
| 4 | `DEVICE_IDLE` |
| 5 | `SUBMISSION_COMPLETE` |
| 6 | `SUBMISSION_FAILED` |

Vorgesehene Masks:

- Connection-Mask Bit 0: `DEVICE_STATUS_CHANGED`
- Device-Mask Bit 0: `DEVICE_MEMORY_PRESSURE`
- Device-Mask Bit 1: `DEVICE_IDLE`
- Queue-Mask Bit 0: `SUBMISSION_COMPLETE`
- Queue-Mask Bit 1: `SUBMISSION_FAILED`

Andere Bits sind reserviert.

`ASYNC_ERROR` und `DEVICE_LOST` sind nicht maskierbar. Completion- und Failure-Events werden entsprechend der Event-Auswahl ausgeliefert. Pro angenommener Submission darf niemals sowohl `SUBMISSION_COMPLETE` als auch `SUBMISSION_FAILED` ausgeliefert werden.

Event-Auswahl-Request-Layouts und die endgültigen Event-Opcode-Registrierungen sind noch offen.

# 13. Ordering- und Synchronisationsgarantien

1. Requests desselben X11-Clients werden in X11-Protokollreihenfolge verarbeitet.
2. Ein erfolgreicher `WriteBuffer`-Reply garantiert abgeschlossenen Transfer und Sichtbarkeit für spätere abhängige XAverius-GPU-Arbeit.
3. Ein angenommener `QueueSubmit` ist nicht automatisch abgeschlossen.
4. `ReadBuffer` antwortet erst, wenn die angeforderten Daten bereit sind und notwendige GPU-/Host-Visibility-Operationen erfolgt sind.
5. X11-`Sync` bestätigt die Verarbeitung vorheriger X11-Requests, nicht die GPU-Completion.
6. XAverius synchronisiert die von `WriteBuffer` und `ReadBuffer` benötigten Transfergrenzen automatisch.
7. XAverius leitet keine beliebigen Shader-zu-Shader-Abhängigkeiten aus dem Inhalt von Shadern ab.
8. Clients bleiben für explizite GPU-Abhängigkeiten zwischen beliebigen Commands verantwortlich.
9. Für die erste Implementierung ist eine konservative vollständige Device-Synchronisation akzeptabel.
10. Nach angenommener asynchroner Arbeit werden Fehler durch Events und Synchronisationszustände gemeldet.

Die genaue Queue-übergreifende Reichweite der `WriteBuffer`-Sichtbarkeitsgarantie muss noch abschließend definiert werden.

# 14. Compute-Referenzablauf

Ziel-Workload:

`C[i] = A[i] + B[i]`

Typischer Ablauf:

1. Physical Device enumerieren oder Default Device erstellen.
2. Memory-Properties abfragen und logisches Device mit Compute-Queue erstellen.
3. A-, B- und C-Buffer erstellen.
4. Memory-Anforderungen abfragen, Speicher allozieren und Buffer binden.
5. A und B mit unabhängigen `WriteBuffer`-Requests hochladen.
6. Shader Module erstellen.
7. Descriptor Set Layout, Descriptor Pool und Descriptor Set erstellen.
8. Pipeline Layout und Compute Pipeline erstellen.
9. Descriptor Set mit A, B und C aktualisieren.
10. Command Pool und Command Buffer erstellen.
11. Pipeline binden.
12. Descriptor Sets binden.
13. Bei Bedarf Push Constants setzen.
14. `Dispatch` aufzeichnen und Command Buffer finalisieren.
15. Fence/Semaphoren erstellen, sofern erforderlich.
16. `QueueSubmit` ausführen.
17. Completion mit Fence oder Semaphore abwarten.
18. C über `ReadBuffer` zurücklesen.
19. Ressourcen nach den Lebenszyklusregeln zerstören.

Der Server muss sicherstellen, dass die Descriptoren zum Shader passen, statisch verwendete Ressourcen vorhanden sind und Dispatch-Limits eingehalten werden.

# 15. Konformität und Tests

Eine Implementierung sollte mindestens folgende Fälle testen:

- Exakte Request-Längen, Counts und Padding
- Byteordnung und feste Wire-Feldbreiten
- Reservierte Felder und unbekannte Flags
- Ungültige XIDs, Ressourcentypen und Ownership
- Cross-Device-Verwendung
- Atomare Create-, Update- und Submit-Operationen
- Überlauf- und Grenzfälle bei Buffer-Bereichen
- Memory-Alignment und Memory-Type-Kompatibilität
- Command-Buffer-Zustandsübergänge
- `WaitSemaphores`-Golden-/Conformance-Vektoren für `WAIT_ANY`: kein Entry erfüllt, genau ein Entry erfüllt, mehrere Entries bereits erfüllt, konkurrierende Signale auf unterschiedlichen Semaphoren sowie mehrere Entries, die durch denselben serialisierten Zustandsübergang erfüllt werden; das Ergebnis ist genau ein `SUCCESS` und kein Semaphore-Index wird impliziert
- `WaitSemaphores`-Conformance-Vektoren für `WAIT_ALL`: Entries werden in unterschiedlicher Reihenfolge und durch unabhängige Host-/GPU-Signale erfüllt; Erfolg tritt erst nach Erfüllung des letzten Entries ein und darf durch spätere Counter-Änderungen nicht zurückgenommen werden
- Für beide Wait-Modi muss ein bloß reservierter, noch nicht erfolgreich ausgeführter GPU-Signalwert den Wait unerfüllt lassen; erst die tatsächliche Counter-Aktualisierung darf den Entry erfüllen
- Timeout-Rennen müssen Erfüllung vor der Timeout-Entscheidung, Timeout vor einem späteren Signal sowie Erfüllung und Fristablauf im selben Scheduler-Zyklus abdecken; maßgeblich ist ausschließlich die serialisierte terminale Entscheidung, und ein terminales Ergebnis darf nicht überschrieben werden
- `timeout_ns = 0` prüft den aktuellen Zustand ohne absichtliches Warten; `UINT64_MAX` bleibt bis zu Erfüllung oder Lifecycle-Abbruch offen; Scheduler-Unterbrechung und wiederholte interne Wait-Registrierung dürfen eine endliche Frist nicht verlängern
- Device-Loss- und `DestroyDevice`-Rennen mit offenen `WAIT_ANY`- und `WAIT_ALL`-Registrierungen müssen jeweils genau einen Lifecycle-Ausgang erzeugen; ein zuvor terminalisiertes `SUCCESS` oder `TIMEOUT` bleibt unverändert, andernfalls gewinnt der zuerst serialisierte Lifecycle-Übergang
- Ein offener Wait verhindert `DestroySemaphore` für jede von ihm referenzierte interne Semaphore-Identität; nach terminal festgestelltem Wait-Ergebnis darf ein noch ausstehender Reply die Zerstörung nicht blockieren
- XID-Wiederverwendung während oder nach einem Wait darf weder die referenzierten Semaphore-Identitäten noch das terminale Wait-Ergebnis auf neue Ressourcen umleiten; Client-Disconnect entfernt offene Registrierungen ohne Reply und ohne Counter-/Signalzustandsänderung
- Fence- und Semaphore-Zustände sowie Timeouts
- Descriptor-Update/Freigabe während Pending-Use
- Ressourcenzerstörung bei internen Referenzen
- XID-Wiederverwendung bei ausstehender Arbeit
- Device Removal und Device Loss
- Korrekte XGE-Längen und Event-Feldpositionen
- Keine verspäteten X11-Fehler für angenommene asynchrone Requests
- Korrekte Berechnung von `C[i] = A[i] + B[i]`

## Anhang B. Festgehaltene Designentscheidungen

- X11 ist der Transport; Vulkan-Handles bleiben serverseitig.
- Erste Implementierung: Xvfb, Compute-only.
- Kein Queue-XID; Queue-Adressierung über Device/Familie/Index.
- Physical Devices verwenden serverseitige XIDs.
- `CreateDefaultDevice` und explizites `CreateDevice` sind vorgesehen.
- Images gehören nicht zum v0.1-Compute-Pfad.
- `WriteBuffer` verwendet unabhängige Requests, keine Upload-Transaktion.
- `QueueSubmit`-Annahme und GPU-Completion sind unterschiedliche Ereignisse.
- Asynchrone Fehler werden über XAverius-Events gemeldet.
- Öffentliche Ressourcen-XIDs werden bei erfolgreicher Zerstörung sofort ungültig.
- Interne Vulkan-Objekte dürfen bis zur sicheren Freigabe weiterleben.
- Descriptor Sets dürfen während Pending-Use weder aktualisiert noch freigegeben werden.
- Wire-Layouts sind explizit und unabhängig von nativen C-Strukturen.
- Noch nicht zugewiesene Registry-Werte bleiben offen.
